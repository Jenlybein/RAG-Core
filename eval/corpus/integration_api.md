# 接口对接与鉴权说明

## 鉴权方式与签名算法

平台对外提供两类接口：管理类接口与业务类接口。两类都使用同一套鉴权机制，差别只在权限范围。鉴权采用「应用凭据 + 请求签名」的方式，不使用长期有效的静态 token，原因是静态 token 一旦泄露无法感知，签名机制至少能把泄露的影响限制在时间窗内。

凭据由两部分组成：应用 ID 与应用密钥。应用 ID 可以公开传输，应用密钥只能保存在服务端，绝不能写进客户端代码或配置文件。凭据在平台侧按环境隔离，测试环境的凭据无法调用生产接口，反之亦然。申请凭据需要提交用途说明与调用量预估，审核通过后由平台方在控制台生成，密钥仅在生成时展示一次，页面关闭后不可再次查看。

签名算法基于 HMAC-SHA256。待签字符串由五段按固定顺序拼接：请求方法、请求路径、规范化查询串、请求体摘要、时间戳。五段之间用换行符分隔，任何一段的顺序变化都会导致签名不匹配。规范化查询串要求按参数名的字典序排序，参数值做 URL 编码，同名参数按值排序后拼接——这几条细节是签名失败最常见的原因，因为不同语言的 HTTP 库对参数排序的处理不一致。

请求体摘要取请求体的 SHA256 十六进制小写值。请求体为空时摘要取空串的 SHA256。注意不要先做 JSON 格式化再算摘要，服务端是按原始字节计算的，任何空格或者字段顺序的差异都会导致摘要不一致。序列化后应当直接复用同一份字节数组，而不是序列化两次。

时间戳采用 Unix 秒级时间戳，服务端容忍 ±300 秒的偏差。超出窗口的请求直接拒绝，返回时间偏差类错误。这个窗口是刻意留宽的，因为客户侧服务器的时间同步质量参差不齐；但也不能更宽，否则重放攻击的可行窗口会变大。建议客户侧配置 NTP，把偏差控制在 5 秒以内。

签名计算完成后放进请求头的 `X-Signature` 字段，同时把应用 ID、时间戳、随机串分别放进 `X-App-Id`、`X-Timestamp`、`X-Nonce`。随机串要求每次请求唯一，服务端在时间窗内做去重，同一个随机串重复使用会被判为重放。随机串建议用 UUID 或者 16 字节随机数的十六进制表示，不要用自增数字或者时间戳代替。

密钥轮换每 6 个月一次，轮换采用双密钥并存策略：新密钥生效后旧密钥保留一个宽限期，宽限期结束前必须完成全部调用方切换。平台会在轮换前 30 天通过公告与邮件同步给所有集成方。宽限期结束后旧密钥立即失效，未完成切换的调用方会收到签名不匹配的错误——这个错误与「密钥写错」的表现完全一样，排查时要先确认密钥版本，再看签名逻辑。

## 回调通知与重试策略

平台在异步任务完成、状态变更、告警触发这三类场景下会向调用方推送回调。回调采用 HTTP POST，请求体为 JSON，签名机制与主动调用完全一致，调用方应当用同一套验签逻辑处理，不要因为是「收到的请求」就跳过验签——跳过验签等于允许任何人伪造回调。

回调地址需要在控制台登记并完成校验。校验方式是平台向登记地址发送一个带随机串的探测请求，调用方需要在规定时间内回显该随机串。这个步骤挡掉地址填写错误与回调服务不可达两类问题，登记时不要跳过。

调用方必须在 5 秒内返回 2xx 状态码，否则视为失败。返回 2xx 后业务处理可以异步进行，但要注意：平台只关心「收到并接受」这个信号，不关心业务是否处理完成。所以不要在回调处理里做耗时操作——数据库写入、外部接口调用、文件生成都应该放到队列里异步做。超时的常见原因就是在回调里同步做了重活。

失败重试采用指数退避，间隔为 10 秒、30 秒、2 分钟、10 分钟、30 分钟、2 小时、6 小时，共 7 次，累计约 9 小时。重试期间平台侧按「同一事件」去重，但调用方仍必须自己做幂等——因为网络层的重复投递无法完全避免。幂等键建议用回调体里的 `event_id`，不要用业务主键，因为同一业务对象可能产生多个不同事件。

连续 7 次失败后该回调地址会被标记为不可用，同时向登记的运维联系人发送通知。标记为不可用后新事件不再投递，需要人工在控制台恢复。恢复前必须先排查失败原因，否则恢复后会立刻再次失败，反复几次后可能被永久禁用。

回调体里的字段分为三类。固定字段包括 `event_id`、`event_type`、`occurred_at`、`signature_version`；业务字段随事件类型变化，放在 `data` 对象里；扩展字段放在 `extra` 对象里，调用方应当忽略不认识的扩展字段而不是报错——平台会在不改变大版本的前提下增加扩展字段，报错会导致兼容性问题。

回调的时序不保证严格有序。同一业务对象的多个事件可能乱序到达，调用方要按 `occurred_at` 或者业务版本号自行排序，不能假设「后收到的就是更新的」。这一点在状态机类的业务里尤其容易出错，比如「已发货」的回调早于「已支付」到达，如果直接按到达顺序写入状态，业务状态就会错乱。

## 限流规则与配额管理

限流分三个维度：按应用凭据的分钟级请求数、按接口路径的并发数、按租户的日累计调用量。三个维度独立生效，任一维度超限都会返回限流类错误，响应头里带上剩余配额与建议等待秒数。

分钟级请求数按滑动窗口计算，不是固定窗口。固定窗口的问题在于窗口边界处会出现双倍突发：前一分钟的最后 1 秒与后一分钟的前 1 秒加起来能打满两倍配额。滑动窗口消除了这个边界效应，但也意味着「这一分钟还剩多少配额」是一个动态值，不能简单用「上限减去已用」估算。

并发数限制针对同时在建的请求，不是每秒请求数。这个维度主要防止慢接口被大量并发拖垮。调用方如果发现并发超限但请求数没超，通常意味着存在连接泄漏或者请求堆积，应当先检查自己的连接池配置与超时设置，而不是申请提高配额。

日累计调用量按自然日计算，零点重置，重置时刻以平台时区为准而非调用方时区。用尽后当日不再接受新请求，需要等到次日零点。这个维度是为了防止程序缺陷导致的无限重试——重试风暴在几分钟内就能把日配额打光，而且这类问题往往在夜间无人值守时发生。

看限流错误时要注意区分两种情形。第一种是真的流量增长，配额确实不够，处置方式是评估后申请提额。第二种是重试风暴，表现为请求量突增但业务量没变，处置方式是检查退避参数。把第二种误判成第一种，会给平台扩容，但真正的缺陷被掩盖，下次还会复发。

退避参数建议采用「指数退避 + 抖动」。纯指数退避的问题是所有客户端在同一时刻重试，反而制造新的尖峰；加抖动（通常是在退避时长上乘以一个 0.5 到 1.0 的随机系数）能把重试打散。退避上限建议设为 30 到 60 秒，超过这个时长不如直接失败并告警，让问题暴露出来。

申请提额需要提供三样材料：近 30 天的调用量曲线、峰值时刻的业务背景说明、以及提额后的退避与降级方案。缺少第三项通常会被退回，因为只提额度不给降级方案，等于把风险从调用方转移到了平台。

租户之间共享资源池时，单个租户的突发流量会挤占其他租户的配额。平台提供了独立配额的选项，适合调用量稳定且对时延敏感的场景。独立配额的申请需要评估历史峰值并预留 30% 余量，预留太少会在业务增长时立刻不够用，预留太多则会浪费成本，这个平衡点建议每季度复核一次。

## 错误码分层与排查路径

错误码按四段设计：第一位表示错误大类，第二位表示子类，后两位是序号。大类分为连接与证书类、配额与限流类、回调与签名类、存储与介质类、设备状态类五组。这个分层让调用方能先按大类判断处置方向，再看子类定位细节。

签名类错误是最容易误判的一组。表现相同的「签名不匹配」可能来自五个不同原因：密钥版本不对、待签字符串拼接顺序错、请求体被二次序列化、时间戳超出窗口、随机串重复。排查顺序建议按「成本从低到高」：先确认时间偏差（读一次响应头就知道），再确认密钥版本（控制台可见），再比对签名计算过程（本地能复现），最后才怀疑随机串与网络层。

回调类错误要注意区分「我方发出失败」与「对方处理失败」。平台侧能看到的只有 HTTP 状态码与响应耗时，看不到对方的业务异常。如果对方返回 2xx 但业务没处理，平台侧会认为投递成功，不会重试。所以调用方必须保证「返回 2xx 时业务已可靠入队」，不能返回 2xx 之后才发现处理失败。

限流类错误的排查路径已经在上文讲过，这里补充一个细节：响应头里的「建议等待秒数」是按当前窗口的剩余时间算出来的，不是固定值。有些客户端会把它缓存下来反复使用，导致等待时间不足。这个值必须每次重新读取。

连接与证书类错误在接口对接场景下主要是双向认证问题。双向认证要求两侧都校验对方证书，常见失败原因是只配了单向信任。排查方法是分别用两个方向做握手测试，只看一个方向会漏掉单向认证问题——这与证书轮换时的验证要求是一致的。

存储与介质类错误在接口场景下较少见，通常出现在文件上传下载接口。表现为写入失败或者读取超时，排查时先看磁盘使用率与 inode 数量，再看单文件大小是否超过上限。上传接口的最大单文件限制是 100 MB，超过限制会直接拒绝而不是分片，这一点要在对接文档里显式说明。

错误响应体包含四个字段：错误码、错误描述、请求追踪 ID、以及可选的建议动作。请求追踪 ID 是排查的关键，向平台报障时必须提供这个 ID，否则无法定位到具体的调用记录。建议调用方把这个 ID 写进自己的日志，与业务日志关联起来。

重试策略要按错误码分类，不能一刀切。连接超时、5xx 服务端错误可以重试；4xx 里的参数错误、签名错误、权限错误重试没有意义，只会浪费配额；限流错误要按响应头等待后再重试；回调类错误的重试由平台侧负责，调用方不要自己再重试一遍，否则会造成重复处理。
