## 三、逐题对账：127/127 题 CP/CR 与基线完全相同

对账方法是**同一个尺子对同一把标尺**：基线里的每题 CP/CR 与本轮 `per_question` 的
`context_precision` / `context_recall` 逐题比较（对账脚本只读两份 `results.json`，
没有另算一份分数，也没有按 id 去对齐切片——切片 id 每次重建都会变，见下）。

- **有差异的题：0 道。** 127 道题（`q01`～`q19`、`q23`～`q61`、`q65`～`q99`、
  `q104`～`q137`，即 137 题库里进闸门的那 127 道）全部 `ΔCP=0`、`ΔCR=0`。
- **`returned_ids` 127/127 都不同**——这一条**不是行为差异**，归「环境差异 / 产物口径」：
  语料在基线归档之后被重建过一次，切片是新的 UUID（基线归档里的 id 属于上一次
  索引构建）。语料内容哈希（`1946e4e5954f`）与题集文件哈希都没变，判分尺子按
  `(document, heading_path)` 标注在**本次**切片上解析（`_resolve_labels`），所以
  「逐题 CP/CR 相同」才是可比的那一层，「切片 id 相同」跨重建本来就不可比。
- **`q05`（C6 的归零题）恢复**：C6 守分抽样 `20261114T113656Z` 里 q05 是
  `CP 0.2→0.0 / CR 1.0→0.0`；本轮是 **0.2 / 1.0**，与基线逐字一致。归因：本票修复的
  关键词索引版本化把这一路接回来了（证据见下一节），不是「检索变了」。

## 四、关键词这一路确实命中过（§②的证据）

断言实现：`eval_retrieval.keyword_probe`（137 题门禁产物里的 `keyword_hit`），
**只走 `mode=bm25`**（不向量化、不查向量库，0 次模型调用），题目是 `q05`
（`exact_code`；`W0001` 只出现在正文，同文档里 `W0002`～`W0010` 九节措辞 90% 相同，
字面之外分不开；它也是 C6 里被关键词空跑记成 0 的那道题）。判定按「命中相关片」，
不按「有返回」——别拿总数冒充命中。

本轮读数（原样在 `run-20261114T131405Z/results.json` 的 `keyword_hit`）：


`returned_count=1` 正好说明它是字面唯一命中：整个评测索引里只有 `W0001` 那一节

`bm25_rank` 为 1/3/15/19/20——hybrid 的返回确实包含关键词那一路贡献的候选，
不是「纯向量冒名的混检」。

### 版本化现状（真库实测，均为 0 次模型调用 / 0 次写）

```text
$ curl.exe -s "http://localhost:9200/_cat/aliases?v"
rag_chunks_c6   -> rag_chunks_c6__v2
rag_chunks_eval -> rag_chunks_eval__v1

$ uv run python scripts/migrate_keyword_alias.py --alias rag_chunks_eval
state=alias alias=rag_chunks_eval version=v1
名字已经是别名：迁移过了（本脚本是幂等的 no-op）

# eval_retrieval._activate_keyword_versions 在真库上跑一次（幂等，别名已指向 v1）
{"alias": "rag_chunks_eval", "activated": [{"version": "v1", "physical": "rag_chunks_eval__v1"}]}
```

`rag_chunks_eval__v1` 里 469 条文档全部带 `index_version=v1`（用
`GET /rag_chunks_eval__v1/_search?size=1` 看过任意一条的 `_source`）；五个评测库
`knowledge_bases.active_index_version` 也都是 `v1`。检索范围因此能解析出版本、
查询侧按 `(kb, 版本)` 过滤得到这批文档——本轮 `keyword_hit` 命中就是这条链跑通的
结果。`_reset_elasticsearch`（会删索引）本轮没有真跑，它的「按 `_cat` 解析物理索引、
连同旧版本一起删」由离线用例对假 ES 响应钉住。

门禁侧还把这条断言做成了**硬判**：全量跑时 `keyword_hit.passed=false` 会把
`gate.verdict` 改成 `keyword_leg_dead`（退出码红），不允许关键词空跑躲在 hybrid
总分后面通过。

## 五、冷启动：暖机把第一次检索装配开销付在计分之外

本轮 `warmup` 读数：

```json
{"question_id": "warmup", "mode": "hybrid", "duration_ms": 3563.71,
 "degraded": true, "degraded_reason": "keyword search failed", "returned_count": 5,
 "model_calls": 1}
```

第一次检索要装配可观测性客户端，实测把事件循环堵了约 3.5s，而关键词一路预算
`KEYWORD_SEARCH_TIMEOUT_S=2.0`，于是**暖机那一次**降级了；计分的 127 道题
`degraded=0`，没有一道被记上 `keyword search failed`。对照：C6 抽样里恰好是首题
`q01` 被记上 `keyword search failed`（`c6-guard-20261114T113656Z.json` 的
`degraded` 字段），那正是「冷启动记到首题头上」的旧症状；本票的暖机把这类误归因
消掉了。

## 七、没有做 / 边界

1. **没有做全量重建（非 `--reuse`）**：那会重新切块 + 469 次文档嵌入，会顶破
   450 次预算（本轮已用 130 次）。重建路径的一处真缺陷（新建评测库没写
   `active_index_version`，检索守卫会 5xxxx）已在本票修掉，并有离线用例钉住;
   但「真库全量重建」这一次没有实跑，**不能据此宣称重建路径已真库验证**。
2. **没有跑 `eval_retrieval` 的三模式全量（A1～A10）**：3 × 127 = 381 次嵌入，
   加上已有的 130 次会超预算；A10（关键词命中断言）的同一份实现已由门禁产物
   `keyword_hit` 与离线用例覆盖，三模式对照表不是本票验收项。
3. **评测索引的迁移是一次性的**：现有集群上 `rag_chunks_eval` 已是别名
   →`rag_chunks_eval__v1`；`scripts/migrate_keyword_alias.py` 对已迁移状态是
   no-op。新环境/重建时由 `eval_retrieval._activate_keyword_versions` 写完后切别名。
