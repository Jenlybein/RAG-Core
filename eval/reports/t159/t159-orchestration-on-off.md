# #159 第一组：切片编排 **开 / 关**（同题同参，只差 `orchestration`）

**结论先说**（每一条都能在产物里对到读数，见文末「产物」）：

1. **部署口径下编排等于不可用**：整步预算 `ORCHESTRATION_TIMEOUT_MS=4000`，实测**一次**
   结构化调用就要 4.5–25 s（同一端点、同一模型），而编排是**两次**调用共用这一个预算 →
   20/20 题 `TimeoutError`、**0 块**、降级率 **100%**。这不是编排逻辑的错，是预算与端点
   延迟不匹配（读数与拆解见 §二）。
2. 把整步预算按服务入参放大到 30 s（诊断臂），**13/20 题**跑完；再放大到 60 s，**20/20**
   全部跑完。**下面所有「材料量 / 要点数 / 完整度」都来自 60 s 那一档**，逐行标着预算
   （`on_diagnostic_budget_ms=60000`），**不**与部署口径混算。
3. **材料条数没有减少**（两侧都是 5 条/题，共 40 / 60 条），减少的是「被挂到要点上的材料」：
   8 题引用语料 **34/40（85%）**、12 题基线题 **46/60（77%）** 被挂上要点，其余 6 / 14 条
   （15% / 23%）**没被任何要点引用**——它们仍然返回给调用方，只是编排没给它们位置。
4. **`complete` 判得「准」但不够用**：20/20 题都判成 `complete`（没有 partial / missing）；
   人工抽检 7 题发现：**每一条被列出的要点都确实有核心片**（这一层判得准），但 `complete`
   **不保证**「题目要的要点齐」——r08 的第三个答案要点（银卡 500 元上限）根本不在材料里，
   因此没被列成要点，判定仍是 `complete`；q96 的 5 个要点只由 **1 条**材料支撑，也照样
   `complete`。抽检逐题结论见 §五。
5. **代价是延迟**：编排跑完的 p50 = 22.5 s（引用语料）/ 22.8 s（基线题），对照不编排的
   0.22 s——两个数量级；而部署口径那 4.2 s/题是**纯浪费**（跑不完还付了预算）。

## 二、部署口径：20/20 降级、0 块、每问烧 4.2 s

**根因读数**（同一端点、同一模型、warm 之后直接量单次调用，见探针记录）：

| 调用 | 实测耗时 |
| --- | --- |
| `chat_structured`（要点）冷启动第 1 次 | **10.99 s** |
| 同上，第 2 次 | **4.50 s** |
| `chat_structured`（角色） | **5.04 s** |

编排的实现是「要点 + 角色」**两次串行**结构化调用，共用一个整步预算（`orchestration.py`：
``budget_ms = settings.ORCHESTRATION_TIMEOUT_MS if timeout_ms is None else timeout_ms``）。
4000 ms 装不下「一次 4.5 s」更装不下两次——所以部署口径下这是**结构性不可用**，不是偶发。
编排失败按既有纪律降级（检索结果照常返回），每题因此白付 4.2 s 与 1～2 次调用。

> 「1～2 次」不猜：`orchestration failed` 时响应里没有编排块、也不记编排内部调用次数，
> 所以产物里 `orchestration_llm_calls=null`；记账按下限 1 记，上界另算（§六）。

多少、少了哪些」，不能给「少了更好还是更差」（见 §七）。

抽检总结：**7/7 题的 (a) 成立**（`complete` 这一层没有被伪造出来：核心片是真实切片，

r08 直接缺答案要点）。所以 `complete` 的正确读法是「**模型自列的要点都被材料接住了**」，
不是「这题答得上」。r08 与 q96 尤其说明：**要点清单是从材料归纳的，材料缺的东西不会变成
要点，也就不会让判定变差**。

**管道左侧的 Python 已经照常跑完了一整轮**，于是在「重跑一次」的判断下同一批任务并发跑了两遍

## 七、这组对照**能回答什么、不能回答什么**

**能回答**：

- 在这个部署（`ORCHESTRATION_TIMEOUT_MS=4000`、这个模型端点）上，编排**能不能用**：不能，
  20/20 降级、0 块、每题白付 4.2 s。这是一条硬读数（部署臂）。
- 编排跑完之后**材料被怎么处理**：5 条交付单元里 77%～85% 被挂到要点上，15%～23% 完全
  未被引用；证据正文占原材料的 82%～84%；要点数 3～5 个、18/20 题顶满上限。
- `complete` 三态在本语料上的**判定边界**：所列要点都有真实核心片（7/7 抽检成立），但
  「题目要的要点齐」只有 4/7 成立（r01、r05 漏事实，r08 缺关键答案）。
- 编排的**延迟代价**：跑完的 p50 22.5 s，不编排 0.22 s，差两个数量级。

**不能回答**：

- **「编排让答案变好还是变差」**：本组没有生成答案（编排块的三个键是完整度、要点清单、
  材料清单，没有 `answer`；ADR-0001），也没有人工答案评分。材料条数/覆盖率变了多少是读数，
  但它对答案质量的方向**没有读数**——要让下游生成或人工评分来回答。
- **「重排开着（质量档）时编排的表现」**：本组重排关着（与 137 题基线同一口径）。重排会
  改变折叠后的交付单元，编排的输入因此不同；那一维没有读数。
- **「换一个更快的模型 / 更高预算之后是否值得开」**：4 s 这个数是**这个部署**的配置；预算
  与端点延迟的匹配关系换了就变，「4000 ms 不够」不能外推成「编排不值得要」。
- **「要点清单是不是用户想问的要点」**：模型自定要点是**从材料归纳**的（题集没有给它
  `answer_points`）；本组用人工把 7 题的要点与题目的答案要点对了一遍，**只覆盖 7/20 题**，
  不能外推成「20 题都准」或「20 题都不准」。
- **`partial` / `missing` 的分布**：20/20 都是 `complete`，`partial`/`missing` 两档在本轮
  **没有样本**——不是「判得严」，是「没机会出现」。要说这两档准不准，需要能造出缺材料的
  场景（不在本组题集里）。
- **与「原项目」那组效果数字比**：**不可比**。本仓库的语料与题集都是自己的，原项目那组
  （+4.9% / +7.5% / −82.5% / +3.4pp）既不是同一语料、也不是同一指标，**不并排**。
