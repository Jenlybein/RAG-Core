## 四、预算账（如实记，含一次超出）

| 项 | 调用数（下限～上界） |
| --- | --- |
| 探针（单题编排 / 4 题预热 / 原始结构化调用 3 次） | 14～19 |
| 第一组首跑（off 20 + on_deploy 20～40 + on_diagnostic 30 s 33～40 + 暖机 8） | 121～148 |
| 第一组诊断臂 60 s 补跑（20 检索 + 40 编排 + 暖机 6） | 66 |

| 两次失败的重试（一次记账抛错、一次被取消）+ 探针旁路 | 20～30 |
| 第二组（v1 入库 15 + v2 构建 13 + 两版查询 16） | 44 |
| **合计** | **约 369～437** |

**上界超出 400，原因**：第一次后台启动跑批时，`Tee-Object -FilePath` 指向的目录还不存在，
PowerShell 报了错、但管道左侧的 Python **照常跑完了一整轮**；我没意识到它真的执行了，于是
又起了一次——同一批任务并发跑了两遍（第二份产物留在 `run-orchestration-135802Z/`）。
这次意外提供的重复读数是：两次跑里部署臂都 **100% 降级**、30 s 诊断臂跑完 14/20 与 13/20，
说明降级率差异来自端点延迟抖动，不是随机 bug。教训：跑批前先建好日志目录，并且
「命令返回非零」不等于「左侧没执行」。

## 五、本轮没做到 / 边界（这些不是「没时间」，是**这批语料与预算**下做不出来）

1. **编排的答案质量**：编排块没有 `answer`（ADR-0001），本轮也没有答案标注与人工评分；
   「材料变多/变少对答案好坏的方向」没有读数。
2. **`partial` / `missing` 两档完整度没有样本**：20/20 都是 `complete`——不是判得严，是没机会
   出现。要测这两档，得造「某要点确实无核心片」的场景（不在本组题集里）。
3. **重排开着（质量档）时的编排**：本组重排关着（与 137 题基线同口径），那一维没测。
4. **切分点对照只有一处、3 篇语料**：表格行级片 / small-to-big 父节粒度 / 窗口大小在这批
   纯散文语料上换不出交付单元差异，一条读数都没有；更大的语料（候选池装不下整库）也没测。
5. **137 题语料上的切分点对照**：重建 469 片 × 2 版 ≈ 938 次文档嵌入，会顶破预算，本轮没做。
6. **编排在部署预算下的「可用性」是 0**：这一条本身就是结论，不是没做到；但因此第一组的
   材料/完整度读数只能来自**诊断臂（60 s）**，报告里每一栏都标了来源。
