## 0. 为什么重做：v1 的测量失效在哪

v1 交付了完整可跑的评测（语料 / 12 题 / 脚本 / 九条验收矩阵），但它的**测量结果失效**：

| 项 | v1 实际 |
| --- | --- |
| 语料 | 2 篇 / **39 个切片** |
| 题目 | 12 道，只有「命中了某个错误码」这一层 |
| 模式 | `vector` / `hybrid`（**漏了 `bm25` 单路**） |
| 纯向量 `R@5` | **1.0000** |
| 混合 `R@5` | **1.0000** |
| `E1024` 首条名次（vector） | **第 1 名** |

两条根因，加两条测量设计缺陷：

1. **量程不够**：39 片、每路召回深度 20。两路一捞就覆盖大半个库，`top_k=5` 里必然有
   相关切片——`R@5` 到顶不是实现完美，是**尺子没有量程**。
2. **编号写进了标题**：v1 的标题是 `## 错误码 E1024：设备证书链已过期`。而检索文本 =
   文档名 + 章节路径 + 正文（票 2 的设计），编号因此直接进了嵌入输入，BM25 的字面优势
   被抹平。两路拿到的是同一份带编号的文本，自然测不出差别。
3. **没有单路对照**：缺 `bm25`，混合的收益无法归因——你只知道「混合不比向量差」，
   不知道是向量已经足够、还是两路互相抵消。
4. **指标太粗**：只有 P/R/MRR，没有「第一条是不是被问的那个编号」。
   问 `E1025` 却把 `E1024` 排第一，在 v1 的口径里仍然算「命中」。

## 9. v1 → v2 的结论差异（可直接进教程）

v1 的结论是「纯向量与混合都 `R@5 = 1.0000`，测不出差异」；v2 终版的结论是：

> **三种模式各有明确的强项与弱项，而且强弱项随题型变化。**
> 召回：hybrid 1.0000 > vector 0.9565 > bm25 0.7609；
> 名次：hybrid 0.9275 > vector 0.8841 > bm25 0.7717；
> 编号精确性：hybrid 9/9 = bm25 9/9 > vector 8/9。
> 混合不是「全面更好」：它在同义与口语题上把向量排对的答案挤后；关键词单路则在
> `exact_code` / `rare_token` 上精确率最高，代价是召回最低。

**为什么 v1 测不出来**（四条，按重要性排序）：

1. **尺子没有量程。** 39 片语料、每路召回 20，`top_k=5` 时两路几乎必然覆盖所有相关
   切片。评测的「分辨率」不是由指标决定的，是由**语料规模 / 召回深度**决定的：
   候选池比答案大一个数量级，才谈得上区分召回。
2. **把答案写进了标题。** 检索文本 = 标题 + 章节路径 + 正文。标题里写 `E1024`，
   等于把判别信号同时喂给向量和 BM25，两路的输入完全一样，测出来的当然是「一样好」。
3. **缺单路对照与分题型。** 只有 vector vs hybrid 时，「混合没赢」既可能是向量够强，
   也可能是两路互相抵消。加上 `bm25` 单路后立刻看到它召回只有 0.7609，
   同义题 0.25——**关键词一路的洞是真实存在的**。
4. **指标表达不了「排第几 / 是不是被问的那个」。** `R@5=1.0` 与 `MRR` 打平时，
   v1 没有任何指标能区分「第一条就是答案」和「第五条才是答案」。`exact_hit@1` 与
   陷阱对把这一层补上之后，hybrid 9/9 vs vector 8/9 的差别才显现。

**v2 还推翻了 v1 的一个隐含假设**：v1 认为「嵌入模型对编号是盲的，所以要靠 BM25」。
v2 的证据是：`E1024` / `E1025` 两节正文 90% 相同、标题都不含编号，向量仍然把**正确的
那一个**排在第 1（q01 与 q02 都是）。向量并不「记不住编号」。
真正让向量掉出前五的是**同模板近邻的密度**：11 节存储告警用同一套句式，`W0001`
就被挤出前五——这是「近邻结构」问题，不是「编号表示」问题。

## 10. BM25 分析器修复（本次新增）

### 改了什么

1. **查询侧分析器**：mapping 里 `title` 与 `retrieval_text` 的 `search_analyzer` 从
   `ik_smart` 换成自定义的 `ik_smart_query` = `ik_smart` + `cn_query_stop` 停用词过滤器，
   词表是**显式的 75 条中文停用词**（疑问词 / 指代 / 时间副词 / 单字虚词）。
2. **查询体**：`multi_match` 增加 `minimum_should_match="50%"`——4 个词以上必须命中
   2 个内容词，只沾上一个域内高频词的切片进不来。

两道闸互补，不能互相替代：停用词治「罕见疑问词被当成罕见特征」，百分比治「常见内容词
单独撑起一条结果」。实现与理由见 `app/providers/keyword_search/query_builder.py`
（`QUERY_STOPWORDS` / `MINIMUM_SHOULD_MATCH`）。

### 修复前 vs 修复后（同一套 24 道题；语料 240 → 245 片）

> **口径**：修复前的数字来自 `eval/runs/20261108T021930/`（240 片 / 24 题）。
> 修复后没有单独跑一次 24 题，而是从终版 `20261108T024224` 的逐题结果中**剔除后来新增的
> q25 / q26** 后重算——这两题在修复过程中才加入，且三路都排第 1。这样两列才是同一把尺子。
> 这组修复后数字与 `app/providers/keyword_search/query_builder.py` 里「240 片 / 24 题」的
> 实测表（P@5 .4135 / R@5 .7381 / MRR .7500 / R@1 .6190 / exact 7/7）一致。
> 终版 26 题的完整数字见第 4～6 节。

| 指标 | vector 前 → 后 | bm25 前 → 后 | hybrid 前 → 后 |
| --- | --- | --- | --- |
| P@5 | 0.2286 → 0.2286 | 0.2524 → **0.4135** | 0.2381 → 0.2381 |
| R@5 | 0.9524 → 0.9524 | 0.8333 → 0.7381 | **1.0000 → 1.0000** |
| MRR | 0.8730 → 0.8730 | 0.7222 → **0.7500** | 0.8405 → **0.9206** |
| R@1 | 0.7381 → 0.7381 | 0.5238 → **0.6190** | 0.6905 → **0.7619** |
| exact_hit@1 | 6/7 → 6/7 | 5/7 → **7/7** | 7/7 → 7/7 |

读法：

- **vector 四个指标逐位不变**，证明这一列不是被语料或题目变化带出来的。
- **bm25 用召回换精确**：P@5 与 exact 上升，R@5 从 0.8333 掉到 0.7381。这是
  `minimum_should_match` 收紧的代价，不是免费收益；写教程时不要把这条藏起来。
- **hybrid 名次明显改善**（MRR +0.08、R@1 +0.07），R@5 守住 1.0000：
  RRF 把关键词一路的精确性与向量一路的召回拼到了一起。

### `_chinese_` 那个坑

ES 8.17.10 的 `stop` 过滤器接受 `_chinese_` 这个预置名，但它解析到 **Lucene CJK 包里的
`stopwords.txt`**——那份文件装的是**英文**停用词（`the` / `and` / `of` …）。`_analyze` 实测：

- `"the thing"` → 只剩 `thing`（英文停用词确实被删）；
- `"的 是 什么 怎么 哪些"` → **一个都没被删**。

也就是说，`_chinese_` 在这里等于什么都没做。必须用显式中文词表，并把它注册成**索引级**
自定义分析器（`build_es_mapping()` 的 `settings.analysis`）。这条坑已由
`tests/test_keyword_query_builder.py` 与 `tests/test_keyword_search_es.py::test_query_analyzer_drops_the_question_frame_and_requires_two_terms` 守住。

### 上线运维要求（重要）

mapping 的 `search_analyzer` 变了，而 ES 的自定义分析器是**索引级设置**，既有索引不能原地升级。
上线时必须：

1. **删掉 `rag_chunks` 索引**（评测索引是 `rag_chunks_eval`）；
2. **重新入库**（让新 mapping 重新建索引、重新写入全部切片）。

`scripts/reindex_knowledge_base.py` **不会**重建 mapping：它只把库内 `SUCCESS` 文档重新投递
索引任务，既不删 ES 索引，也不改已有 mapping。只跑这个脚本，查询侧分析器仍是旧的。
评测脚本的 `--reuse` 分支会先校验目标索引里有没有 `ik_smart_query`，旧索引直接拒跑，
避免「用旧口径跑新代码还看着一切正常」。
