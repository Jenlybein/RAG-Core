# 切块改造的验收记录

这份文件记录**口径与数字**，便于复核。语料 21 篇 / 70 380 字，题目 137 道
（可回答 127 道，`false_premise` 4 道不进主平均），`k = 5`。
默认 512/50 结构化口径切出 **469 片**、均长 **153 字**（#64 多语言代码语料合入后
的数字；此前的 20 篇 / 456 片 / 145 字已作废）。

跑法：`uv run python scripts/eval_chunking.py`（不设环境变量就是生产默认口径）。
下文「参数网格」「节说明消融」两张表用的是**真实嵌入服务**（`.env` 里的
`MODEL_API_KEY`），不是离线确定性替身；重跑需要凭据，不连 PG / ES。

## 结构化切块 vs 朴素基线

| 变体 | 切片数 | 均长 | 每题相关单元 | R@5 | R@1 | hit@1 | MRR |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 朴素 800/100 | 102 | 710 | 1.22 | 0.9081 | 0.5499 | 0.6220 | 0.7589 |
| 朴素 400/200 | 331 | 377 | 2.03 | 0.8085 | 0.3365 | 0.6378 | 0.7635 |
| 结构化 512/50（生产） | 469 | 153 | 1.21 | 0.9488 | 0.7231 | 0.7953 | 0.8770 |

`R@1` 的理论上限是 `1/N`（每题相关单元数的倒数）。相关单元数从朴素组的 1.22 涨到
结构化组的 1.21——**这是按「答案单元」计数之后的结果**：表格的行级片映射回整表片这
一个单元，所以切得再细也不会把分母撑大。

## 三件必须一起看的事

1. **表格专项**：整表片 + 行级片刚落地时，表格题平均相关切片是 **6.92**（一行一片各
   算一个相关片），R@1 的分母被放大。改成按答案单元计数后降到 **2.25**，同一次结构化
   切块的 R@1 从 0.6763 升到 0.6995、R@5 从 0.8934 升到 0.9409，而 hit@1 不动
   （0.7717）——说明降的是分母，不是放宽判定。
2. **型号题退步**：`model_number` 从 0.867 掉到 0.400。根因是 `XR-2000` 是
   `XR-2000 Pro` 的子串。把型号抽成独立段之后回到 **0.600**，仍低于朴素基线——
   纯向量口径补不平，要靠关键词与重排。
3. **节说明是代理结果**：`SECTION_CONTEXT_PROXY=1` 用「本节首句」当代理（真说明由大
   模型生成，离线跑不出来）。**代理文本本来就来自正文，不能当成模型效果**。
   完整消融见下节。

## 节说明消融（#46 / #67）

同一份语料、同一批 127 道可回答题、同一套生产切块与算分口径，只切
`SECTION_CONTEXT_PROXY` 开关。取汇总表里生产组 `D-rec-token`（512/50，Recursive +
Qwen token）的 chunk 级指标。

复现命令（PowerShell；两条都要跑，第二次显式开代理）：

```powershell
$env:PYTHONIOENCODING = "utf-8"
Remove-Item Env:\SECTION_CONTEXT_PROXY -ErrorAction SilentlyContinue   # 关
uv run python -X utf8 scripts/eval_chunking.py

$env:SECTION_CONTEXT_PROXY = "1"                                        # 开
uv run python -X utf8 scripts/eval_chunking.py
```

输出摘要（`=== D-rec-token ===` 与 `=== 汇总 ===` 段，2026-11-09 实跑）：

```
关  D-rec-token   切片数 = 469  R@5 = 0.9488  R@1 = 0.7231  hit@1 = 0.7953  MRR = 0.8770
开  D-rec-token   切片数 = 469  R@5 = 0.9528  R@1 = 0.7310  hit@1 = 0.8031  MRR = 0.8760
```

| 节说明（`SECTION_CONTEXT_PROXY`） | 切片数 | hit@1 | R@5 | R@1 | MRR |
| --- | --- | --- | --- | --- | --- |
| 关（不设，生产现状） | 469 | 0.7953 | 0.9488 | 0.7231 | 0.8770 |
| 开（`=1`，本节首句代理） | 469 | 0.8031 | 0.9528 | 0.7310 | 0.8760 |
| 差值（开 − 关） | 0 | +0.0078 | +0.0040 | +0.0079 | −0.0010 |

四个结构化组全部同向：A 组开时 `R@5=0.9567 / hit@1=0.8031`，
B/C/D 组开时 `R@5=0.9528 / hit@1=0.8031`；朴素组不受开关影响（代理只加在
结构化组，保持对照干净）。按题型看，`cross_section` 从 0.588 升到 0.647、
`negative_scope` 的长章节分组从 0.667 升到 0.750，但 `table_lookup` 从 0.882
掉到 0.765 —— 首句重复放大了某些片、也挤掉了另一些片，方向并不一致。

**结论句：部分采纳。** 首句代理在同一批题上把 `R@5` 从 0.9488 抬到 0.9528、
`hit@1` 从 0.7953 抬到 0.8031（分别只有 0.4 / 0.8 个百分点，约 1 道题），
方向为正但幅度落在单题噪声内，且**代理文本直接抄自正文首句、不是大模型生成的
节级说明，这个数字不能当成模型效果，也不能外推到真实节说明**；因此只把
「离线可开关对比 R@5 与 hit@1」这一能力记入验收，生产默认值
`SECTION_CONTEXT_ENABLED=False` 保持不变，不宣称检索收益，待真说明接入后重测。

## 参数网格（#47）

在当前语料（21 篇 / 70 380 字 / 137 题，可回答 127 道）上扫 6 个 `chunk_size` 档位。
口径：生产算法 `REC_TOKEN`（Recursive + Qwen token）；`overlap = size // 8`（12.5%，
与生产 512/50 的约 10% 同量级）；`hit@1` / `R@5` 为 chunk 级、答案单元口径、k=5。
**平均上下文 token** = 送进 embedding 的检索文本用离线 `token_count()` 真算后的算术
平均（不是片长、不是估算，不额外发网络请求）。

复现命令（PowerShell；Linux/macOS 把 `$env:X=...` 换成 `X=...` 前缀）：

```powershell
$env:EVAL_GRID = "1"
$env:CHUNK_GRID = "200,300,400,512,600,800"
$env:PYTHONIOENCODING = "utf-8"
uv run python -X utf8 scripts/eval_chunking.py
```

输出摘要（脚本 `参数网格：` 开头的表头与 6 行数据，2026-11-09 实跑）：

```
参数网格：21 篇 / 70380 字；题目 137 道（可回答 127 道）；k = 5
  size/overlap     切片数   平均上下文 token   平均片长(字)    hit@1      R@5
        200/25     497              123.3         145.1   0.7953   0.9357
        300/37     485              125.5         148.7   0.8031   0.9449
        400/50     474              127.4         152.0   0.7953   0.9449
        512/64     469              128.4         153.6   0.7953   0.9488
        600/75     469              128.4         153.6   0.7953   0.9488
       800/100     469              128.4         153.6   0.8031   0.9488
```

| chunk_size / overlap | 切片数 | 平均上下文 token | 平均片长(字) | hit@1 | R@5 |
| --- | --- | --- | --- | --- | --- |
| 200 / 25 | 497 | 123.3 | 145.1 | 0.7953 | 0.9357 |
| 300 / 37 | 485 | 125.5 | 148.7 | 0.8031 | 0.9449 |
| 400 / 50 | 474 | 127.4 | 152.0 | 0.7953 | 0.9449 |
| **512 / 64（生产）** | **469** | **128.4** | **153.6** | **0.7953** | **0.9488** |
| 600 / 75 | 469 | 128.4 | 153.6 | 0.7953 | 0.9488 |
| 800 / 100 | 469 | 128.4 | 153.6 | 0.8031 | 0.9488 |

**默认结论：保持 512，不改 `config.py`。** 依据这张表本身：

1. 512 是 `R@5 = 0.9488` 的**最小档位**——400 掉到 0.9449、200 掉到 0.9357；
   512 / 600 / 800 同为 0.9488，切片数与平均上下文 token 也完全相同（469 片 /
   128.4 token），因为 h3 成为边界后节本身就短于窗口，再放大窗口没有东西可切。
2. 800 的 hit@1 是 0.8031（比 512 高 0.0078，即 1/127 道题），但没有换来任何
   R@5、片数或上下文量上的差异，属于单题波动，不是可复现的档位优势。
3. 512 的窗口上限比 800 小 288 而结果不变，且 token 才是与 embedding 模型同一把
   尺子的单位（ADR-0015 的四组交叉也显示 800/100 与 512/50 在默认窗口下四组指标
   完全打平）；旧结论「默认保持 800」是字符时代的遗留，与
   `app/core/config.py` 的 `CHUNK_SIZE=512` 冲突，此处以实跑表格为准作废。

因此 512 不是「hit@1 唯一最优」，但在「召回打平 + 上下文最省 + 单位正确」三条
同时成立的点里它是最小、最稳的一档；不需要改生产默认值。

## 评审后的修正：折叠粒度曾经错了

代码评审查出一处实质错误：`unit_key` 用 `parent_section_id` 归组，而它是**上一级**
——对 h2 级的切片（节下没有 h3），上一级是 h1，于是整篇文档被折成一个单元。
实测 `support_errors.md` 的 40 个 h2 小节折成了 1 条结果。

修正：单元按**路径前两段**（h2 级）归组，`unit_id = sha256(前两段)`。不需要新增列，
从每个切片已有的 `heading_path` 就能算，重建前后都稳定。

修正后的数字（此前以 0.8740 记的那组作废）：

| 变体 | hit@1 chunk 级 | hit@1 交付级 | R@5 交付 | R@1 交付 |
| --- | --- | --- | --- | --- |
| naive-800 | 0.6220 | 0.6220 | 0.9081 | 0.6220 |
| naive-400 | 0.6378 | 0.6378 | 0.8085 | 0.6378 |
| structured | 0.7953 | **0.8189** | 0.9488 | 0.8189 |

按题型（chunk 级 → 交付级）：`counterfactual` 0.692→0.769、`cross_section`
0.588→0.647、`noise_robust` 0.882→0.941，其余七类持平。

与上一版（03 时代）对照：0.8189 对 0.8031，**+1.6 点**（不是修正前虚高的 +7.1）。
`model_number` 与上一版持平（0.667），`counterfactual` 仍低 7.7 点（0.769 对 0.846）。

**教训**：折叠粒度必须有一条测试钉住「同一篇文档里的两个 h2 是两个单元」。
此前接线测试里的父节 id 全是 mock 的，任何粒度都能通过。


## 收尾：两个脚本用同一口径复算（`eval_baseline_03.py` 也接了 `result_collapse`）

此前只有 `eval_chunking.py` 报交付口径；`eval_baseline_03.py` 只报 chunk 级，导致
「上一版 vs 现在」无法在两个口径上同时对比。现在脚本也调同一个 `collapse`，
并且**给 03 时代也算了交付口径**（它的片本来就近似一节一片，折叠近乎恒等）。

同语料、同 127 题、同判据、k=5：

| 指标 | 03 时代 | 现在 | 差值 |
| --- | --- | --- | --- |
| chunk 级 hit@1 | 0.8031 | 0.8110 | **+0.0079** |
| 交付级 hit@1 | 0.8031 | 0.8189 | **+0.0157** |
| chunk 级 MRR | 0.8760 | 0.8822 | **+0.0062** |
| 交付级 MRR | 0.8727 | 0.8854 | **+0.0127** |

四条全部为正，幅度 0.6~1.6 个百分点。这是**纯向量**口径，不含 BM25 与重排。

## 收尾时的两个坑（写下来免得再踩）

1. **对照脚本的 `_Chunk` 没有 `table_part`**。第一版用 `merge_table_rows=False` 回避，
   结果表格题两侧口径不一致，交付级反而被算低（0.7638）。改成用「整表的起始位置」
   当表号——与生产「同一张表一个 `table_part`」同语义，数字才对上 `eval_chunking`
   的 0.8189。**两侧口径必须真的同语义，靠开关绕过去只会自欺。**
2. `UnitKey` 从裸元组改成 `NamedTuple` 后，带默认值的字段让它恒为 4 段，不再等于
   3 段普通元组。所有构造点都要显式用 `UnitKey(...)`——这一点由测试直接抓到。


## 对照变体调整：朴素基线从 800 改为 400，并加 200 一档

原来的两组朴素是 `800/100` 与 `400/200`。前者均长 710 字，是结构化（145 字）的近 5 倍——
那种对比只能得出「结构化的片更小」，说不清谁更准。改成：

| 组 | 配置 | 角色 |
| --- | --- | --- |
| 朴素 `400/100` | 均长 375 字 | **主基线**：与结构化同量级 |
| 朴素 `200/50` | 均长 193 字 | 更细一档，看收益是否还在 |
| 结构化 `800/100` | 均长 145 字 | 本实现 |

重叠统一取 25%（100/400、50/200）：比例一变就同时改了两个变量。

### 新口径下的结果（127 题，纯向量）

| 指标 | 朴素 400/100 | 朴素 200/50 | 结构化 |
| --- | --- | --- | --- |
| 切片数 / 均长 | 225 / 375 | 440 / 193 | 456 / 145 |
| 每题相关片 N | 1.39 | 1.60 | 1.21 |
| R@1 达成率 | 58.2% | 65.3% | **80.2%** |
| R@5 | 0.8983 | 0.8558 | **0.9488** |
| R@1 | 0.4816 | 0.5091 | **0.7231** |
| hit@1 | 0.6220 | 0.6850 | **0.7953** |
| MRR | 0.7540 | 0.8010 | **0.8757** |
| P@5 | 0.2394 | 0.2457 | 0.2252 |

### 结论有三处变化（都如实报）

1. **表格题的优势变大了**：800 作基线时只赢 8.3 点，400 作基线时赢 **33.3 点**。
   800 字一片时一张价格表往往整张塞得进去，切不断就看不出差别。
2. **`cross_section` 翻负**（0.647 → 0.588，−5.9 点）。这组题答案分散在多节，
   结构化把每节切得更小，前后半句更容易落在不同片里——切细的固有代价。
