## 一、最初那个问题：「构建成功，但文档状态没回写」

### 根因（两个缺陷叠加，各自单独都能造成现象）

**缺陷 1：状态回写是个空操作。**
`index_build_service.build()` 先用一次读把文档对象装进会话（`status=1`）；随后
`try_claim_for_indexing` 用一条 `UPDATE` 抢租约，并且：

```python
.execution_options(synchronize_session=False)   # 不改内存里的对象
# 会话又是 expire_on_commit=False                 # 提交后也不过期
```

于是内存里那个文档对象**仍然是 `status=1`**。Tx2 收尾时 `update_status(doc, SUCCESS)` 走「赋属性 + flush」，
ORM 认为值没变 → **一条 UPDATE 都不发**。库里那一行永远停在 3。

修法（#212）：`update_status` 改成执行显式 `UPDATE ... WHERE id AND tenant_id`，并**检查影响行数**
（`written != 1` 就记 warning）——「写成功但一行没动」这种静默失效从此会留下痕迹。

**缺陷 2：构建能「一篇都没真重建」却判定成功。**
旧循环丢掉了 `index_existing_document` 的返回值，每篇都 `indexed += 1`。抢不到租约的篇也被算作已重建
→ 四项计数在「切片 0 / 向量 0 / 关键词 0」时三方相等 → 一路 `ready` 并激活，线上静默变成
「版本正常、检索全空」。

修法（#214）：计数只数真的写进切片的篇，收尾判据改成**读真值**（`COUNT(DISTINCT document_id) FROM chunks
WHERE (index_version, doc_version)`），分母是起跑快照。

### 现在怎么保证不再发生

| 防线 | 机制 | 落在哪 |
| --- | --- | --- |
| 状态写入不会静默失效 | 显式 UPDATE + 检查 `rowcount` | `document_repository.update_status`（#212） |
| 迟到的任务写不进别人的地盘 | Tx2 开头 `SELECT ... FOR UPDATE` 核对**租约令牌**，不匹配就回滚 | `indexing_service`（#213） |
| 空版本不可能上线 | 收敛读真值，分母是起跑快照 | `index_build_service.converge`（#214） |
| 构建行自己会过期 | `converge_deadline`，清扫器按它收尾 | #214 / #225 |
| 长文档不被误判为死 | 解析后、每批嵌入前各刷一次**心跳**（独立会话，不动令牌） | `indexing_service._heartbeat`（#225） |
| 测试不许再「断言函数被调用过」 | 状态类断言一律走**真库** | `tests/test_index_sweeper.py` 等 |

## 二、八条诉求逐条落地

### 1. 文档状态加「排队中」
`SUCCESS=1 / FAILED=2 / PROCESSING=3 / QUEUED=4`（序号沿用旧值）。上传、重建、回滚三入口落 `4`，
Worker 抢到才进 `3`。迁移 `b3f7c2a91d40` 把存量「`3` 但没租约」的行改成 4。

### 2. 卡住的东西自动恢复（#225，三件全做）
`app/tasks/index_sweeper.py`：Worker 进程内的守护线程，每 60 秒 `SET NX EX` 抢锁，抢到跑一轮。

| 症状 | 判据 | 处置 |
| --- | --- | --- |
| 构建过期限仍 `building` | `converge_deadline` | 按真值收尾（`converge(final=True)`） |
| 构建未过期但缺篇 | 真值 vs 参与篇数 | 补投（`dispatch(skip_existing=True)`），重投封顶 `MAX_REDISPATCH` |
| 文档停在 `3` 且心跳过期 | `COALESCE(index_heartbeat_at, index_claimed_at)` | 清租约 + 回 `4` + 重投；超 `MAX_LEASE_REDISPATCH` 标失败 |

**心跳与租约分两列**：`index_claimed_at` 是 fencing 令牌（永不变），`index_heartbeat_at` 是活的证据（会变）。
合成一列只有两个坏结果——抢走正在跑的长文档（白烧一轮嵌入），或长文档永远不被救。

### 3. 套餐加「库数」与「每库 token 容量」
`plans.max_tokens_per_kb` + `documents.token_count`。**两种 token 口径**：容量用正文 token，
每日额度用检索文本 token。门禁两处：入口预检（库满了不收新的）+ 解析后硬拦（`incoming` 带数字）。
重建排除自己（`excluding_document_id`），否则库满后连重建都做不了。

### 4. 彻底删掉「处理中名额」
`plans.max_processing_documents` 物理删除（迁移 `b9f4d2c70e13`）。**代价**（无公平调度）写进 ADR-0034 决策八。

### 5. embedding 批大小面板可改
模型→上限表（v1/v2=25、v3/v4=10、qwen3.7=20，封顶 25）+ `RESTART_PANEL_WRITABLE_KEYS`：
这一键**面板可改但有重启提示**（其余重启级键仍只读）。

### 6. 每日切块额度（「三本账变四本」）
`plans.chunk_daily_tokens`（300K / 4M / 9M / 15M）+ `usage_events.meter_chunk` + `usage_daily.meter_chunk`。
Redis 租户日桶 `quota:chunk:daily:tenant:<tid>:<YYYYMMDD>`，TTL 26h。先判后记；超额抛 **20037**。
`endpoint='index'` 的行**排除出请求统计**（`requests` / 成功率 / 分位）但保留计量。

### 7. 前端与设计稿同步
前端：库卡片进度条 + 未入新版本明细、**库容量进度条（已用/上限 + 余量）**、文档 `token_count`、
`QuotaPanel` 第四栏「切块 · token」、套餐两个新字段可编辑、`CODE_COPY` 登记 20036/20037。
设计稿（复用 `design/rag-console-replica`）：`kb-detail`（进度条+失败明细）、`usage`（第四栏）、
`admin-plans`（三档容量/额度 chip）、`knowledge-bases`（容量条）、`usage-key`（第四栏去哪了的说明）、
`admin-tenant`（四格容量/额度 KPI）。

## 三、构建按篇化（#215 #216）

```
start_build（记下 auto_activate 与 converge_deadline）
   └─> dispatch_build_task（分页读参与文档，差集去掉已有切片的）
          └─> 每篇一条 build_document_task（task_routes -> build 队列）
                 └─> worker-build（独立进程，-Q build --concurrency=1）
                        └─> 跑完记账 → converge(final=False)
```

- **续建**：目标版本 + 稿号下已有切片的直接跳过，不重复 embedding。
- **失败不改文档状态**（ADR-0034 决策九）：失败只落构建行 `failed_documents`（JSONB），是「未入新版本」的唯一真相源。
- **重投上限** 3 次。
- **`auto_activate` 记在构建行上**（迁移 `f1a4b8d6c392`）：改切块设置那条路径收敛成 `ready` 后立刻激活。
  这是评审发现的回归——原先它作为载荷传给派活任务，改成按篇投递之后在半路丢了，
  症状是「构建跑完停在 ready 不激活、前端『需重建』提示一直挂着」。

## 五、部署变化

> **重建镜像之后必须 `--force-recreate`（本次踩到的坑）**
>
> `docker compose build` 只更新镜像 tag，**正在跑的容器不会自己换过去**——`up -d` 也会跳过
> 「配置没变」的容器。结果是一次 build 之后，四个容器分别跑在**四个不同时刻的镜像**上
> （实测：`api` 跑在旧镜像、`worker-build` 跑在更旧的、`worker` 才是最新的那个）。
>
> 症状是「改了代码，容器里却是老行为」，而且 `docker ps` 看起来一切正常。正确的收尾是：
>
> ```bash
> docker compose -f deploy/docker-compose.yml build
> docker compose -f deploy/docker-compose.yml up -d --force-recreate
> # 核对：三个应用容器必须是同一个镜像 ID
> for c in rag-api rag-worker rag-worker-build; do docker inspect $c --format "$c {{{{.Image}}}}"; done
> ```


| 服务 | 变化 |
| --- | --- |
| `worker-build` | **新增**，`-Q build --concurrency=1`，只跑构建（+15 连接） |
| `worker` | 只消费 `celery`（不再有 `maintenance`） |
| `beat` | **不引入**——清扫器是 worker 进程内线程 + Redis 单实例锁 |
| 连接预算 | `15×API + 15×常规worker + 15×构建worker + …`；清扫器是线程，不额外开池 |

## 八、有意的取舍（不是遗漏）

1. **没有公平调度**：删掉「处理中名额」之后就真的全收了（ADR-0034 决策八写明代价）。
2. **每日额度是绝对上限**：pro/max 档一天内做不了一次全量重建（这是额度该有的样子）。
3. **建版本 / 回滚不加容量门禁**：理由见第七节第 5 条（加了会把救援路径封死）。
4. **清扫器只做「逾期收尾 / 缺篇补投 / 租约重投」三件**，不做「构建心跳」——构建行的期限就是它的心跳。
5. **`documents.token_count` 的迁移回填只是下界**（按字符数）。真值由
   `scripts/backfill_document_tokens.py` 跑一遍覆盖。方向安全：下界偏小只会「多放一点」，不会「误拒」。
6. ~~端到端构建编排 helper 未落地~~ → **已补上**（见第十节）。

## 十二、现场第二轮：三个界面问题与一个语义修正

用户点完第一版「一键重建」之后报了三个问题，第二个暴露了第一版的设计错误。

### 1. 点完「一键重建」，「需重建」提示消不掉 —— 第一版做错了

第一版把按钮做成「把库里每篇文档逐个投进单篇重建队列」。文档确实都重切了，但那条提示还在，
原因在语义里：

* 单篇重建（`POST /documents/{id}/reindex`）把切片写回**当前生效版本**，而生效版本上的
  `params` 快照与版本名都不变 → 「生效版本用的是哪套参数」这件事没变，`needs_rebuild` 仍为真；
* 更糟的是生效版本里会混进**两种切法**的切片，`params` 快照从此失真。

要让新设置真正生效只有一条路：**产出新版本并激活它**。于是：

| 改动 | 位置 |
| --- | --- |
| 新增 `POST /console/knowledge-bases/{kb_id}/rebuild` | `app/api/routes/console_kbs.py` |
| 新增 `rebuild_kb` 服务（不改设置，只写一条 `kb.rebuild` 审计 + 起 `auto_activate=True` 的构建） | `app/services/console_kb_service.py` |
| 前端按钮改为调它，`rebuildingKbId` 只转被点的那张卡 | `frontend/src/views/KnowledgeManagePage.vue` |

**为什么不复用「改设置」那条接口**（`PATCH .../settings` + `{confirm: true}`）：它的审计
before/after 是**设置快照**，而这条什么都没改——会写出一条 before == after 的记录，读账的人
会以为改坏了。所以给它自己的动作名 `kb.rebuild`。

实测（`lian diao kb`，那条提示就是它）：

```
重建前：v1 active  params=NULL          → needs_rebuild=True（老版本行没留参数，判 True）
重建后：v2 active  params={chunk_size:512, split_strategy:structure, section_part_max_chars:2000}
        lian diao kb   needs_rebuild=False
        test           needs_rebuild=False
```

### 2. 「一键重建」改名为「重建」

它现在做的是整库重切（产出新版本 + 自动切换），叫「一键重建」会让人以为只是把任务重排一遍。

### 3. 去掉多余的「详情」按钮

整卡可点本来就是详情入口（`role="button"` + `@click` + Enter/Space）。按钮组里那个「详情 →」
要么是裸文字被外层 `@click.stop` 吞掉点击（点了没反应的原始 bug），要么与整卡点击完全重复。
**删掉按钮，保留整卡点击**——回归用例改成守「按钮组里不许再出现『详情』」。

### 顺带验证的一次真实自愈

演示脚本第一次跑时在 `after_commit` 那里报错（脚本没有圈 `async_transaction`），而
`start_build` 已经把 v2 的 `building` 行落库了 —— 于是留下一条**没有任何一方会推进**的构建行。
这正是清扫器该处理的情形，60 秒后它自己接上了：

## 十三、现场第三轮：进详情要按 F5 —— 读模型拆分、计数口径与刷新可见化

用户的原话是「我进到详情卡片里，还需要刷新一次状态才能看到真正的文档状态」。查下来是**三件
事叠在一起**，其中一件是真 bug（数字算错），不是缓存问题。

### 1. 三条根因（报告先行、未动代码时的结论）

| # | 现象 | 性质 |
| --- | --- | --- |
| 1 | 进详情要按 F5 | 详情**没有自己的请求**，读的是列表那棵树；而树的轮询在「全终态」时 `refetchInterval` 返回 `false` —— 彻底停，且界面上没有任何东西说明它停了 |
| 2 | 界面「分块数」偏大 | 真 bug：计数只锁「当前稿」不锁「**生效版本**」，把留存版本的切片全算进去了（实测某文档 152 片 vs 生效版本 38 片，正好 4 倍 = 4 个留存版本），每次重建涨一份且永不回落 |
| 3 | 构建期间看不出「在重建」 | 文档状态列几乎一直是「成功」（每篇只有自己那一秒是 `3 索引中`），唯一真信号 `build_progress` 只在卡片上、弹窗一开就被盖住 |

后端 `list_tree` 全程实时读库，**没有任何缓存** —— 用户看到的不是陈旧数据，是「**没有请求**」。

### 2. 按提案落地的四件（第五件 SSE 明确留到下一轮）

## 十四、现场第四轮：横幅念的台词与画面自相矛盾

用户截了图：两个库的卡片都写着 **v2 已生效 · 13:09:06** / **v7 已生效 · 15:26:37**，顶上却挂着
一条「有构建在跑或有文档在排队/索引中，正在自动刷新」。

### 状态是对的，解释是错的

查库确认：`test` 的 v7 **72 秒前**刚激活（活动窗内），所以「快刷」本身没错——收尾之后确实要
再跟几轮确认。错的是**横幅把三种理由念成一句话**：

| 真实理由 | 该说的话 | 原来念的话 |
| --- | --- | --- |
| `running`（真有在途工作） | 有构建在跑或有文档在排队/索引中 | ✅ 同一句 |
| `recent`（刚收尾，再跟几轮） | 刚有构建收尾，正在再跟几轮确认 | ❌ **也念上面那句** |
| `idle`（慢查） | 不出现 | ✅ 不出现 |

**模式只有 live/idle 两档，而文案是写死的**——于是 `recent` 那一档必然说错话。这与第七步
「构建失败 → 文档状态不变」是同一类错误的镜像：**内部抽象少了一档，表达层就会替它编一个**。

### 改法

1. `lib/refreshPolicy.ts` 增加 `RefreshReason = 'running' | 'recent' | 'idle'`，
   `kbRefreshReason` / `listRefreshReason` 是**唯一**判定处；`kbIsLive` / `listRefreshMode`
   由它派生（模式与理由不会各自漂）。`running` 优先于 `recent`：同时发生时报更强的那一件。
2. 横幅按理由分两句（`v-if="listReason === 'running'"` / `v-else`）。
3. **活动窗从 120 秒缩到 30 秒**。它唯一的职责是接住 `ready → active`（两笔事务）与失败明细
   的最终落地，实测都是秒级（10 篇的构建 18.975 秒收敛成 ready，下一秒就 active）。
   30 秒够跟十来轮，又不至于让一句与画面矛盾的话挂两分钟。

## 十五、现场第五轮：Key 丢失之后 —— 重新获取、24 小时过渡密钥与调试台手输 Key

用户提了两件事：**API Key 页加「获取 Key」**（点开先提醒「只显示一次、丢了只能重新生成、旧 Key 的业务会失效」，弹窗里「关闭 / 重新生成新 Key」），**调试台把「选 Key 与库」改成主面板手输 Key +「选择知识库」**。

### 15.0 这条需求一开始是「不可能」的

`GLOSSARY.md` 第 70 行写着：`api_keys` 里只有 `scrypt$<n>$<r>$<p>$<salt>$<hash>`，术语表把「Key 原文」列为**禁用说法**。所以「获取 Key」不可能是「把已有的那把再拿出来看一眼」——它只能是**签发一份新的密钥本体**。

于是真正的问题不是「加个按钮」，而是**「换的是什么」**。本仓当时只有一条路：删 Key + 签发新 Key。这条路有三个坏处，每一个都会在真实事故里先炸一次：

| 坏处 | 现场长什么样 |
| --- | --- |
| **配置会丢** | 密钥配置独立于 Key，删 Key 不删配置，可新 Key 得**重新配一遍**白名单/授权位/额度——而用户正处在「钥匙丢了」的当口 |
| **身份会变** | `key_id` 变了，审计里的 `target: key:<id>`、日志、对账脚本全都对不上前后两条记录 |
| **失效没有过渡** | 删除那一刻就是一次立即中断，中间没有「新旧都能用」的一段时间给线上业务换配置 |

### 15.1 定了什么（ADR-0036）

| 决策 | 结论 | 为什么 |
| --- | --- | --- |
| **换的是凭证，不是身份** | 同一把 Key 换密钥本体：`key_id` / 名字 / 配置 / 白名单**全不变** | 「丢 Key 但不想重配白名单」是这个需求唯一的真需求 |
| **旧密钥留 24 小时窗口** | `prev_key_hash` / `prev_key_tail` / `prev_key_expires_at` | 立刻失效会把所有集成当场打断；长期有效则「怀疑泄露」永远收不了口 |
| **只保留最近一把** | 窗口内再轮换一次，上一把旧址被覆盖（等于同时作废） | 留一串旧址 = 同时允许一串凭证有效，与「一把 Key 只有一份有效密钥」相反 |
| **结束只有一个判据** | `now <= prev_key_expires_at`；**提前作废 = 把截止时刻改到过去** | 加一个 `revoked_at` 就是第二个条件，宽一秒 = 作废了还能用，严一秒 = 还没到期先拒 |
| **过渡密钥不进校验缓存** | 当前密钥照常缓存；过渡密钥每请求真校验 | 见到下一个坑（15.3） |

界面据此：行内「获取 Key」（只在行内，空状态仍走签发）→ **一窗两态**（警示 → 展示，展示态隐藏「重新生成」、只留「关闭」，避免连点生成两把互相作废）→ 行内 `ⓘ` 悬停给「旧址末 5 位 + 可用至几点」（**只在窗口内出现**，窗口结束后什么都不写）→ 行内「作废旧 Key」次要链接（轻确认）。

### 15.2 调试台：从「选 Key 与库」到「手输 Key + 选择知识库」

改造前那一页的结构比想象中绕：主面板只有 chips 摘要与一个文字按钮「选 Key 与库」，而**真正粘 Key 的输入框藏在一个叫「粘贴 API Key」的弹窗里**。也就是说，用户要先开弹窗、粘 Key、关弹窗，才能去另一个弹窗选库。

改成了：Key 输入框**常驻主面板**（`show-password` + 「应用」按钮/回车）、库选择仍在弹窗但改名为「选择知识库」（Key 那半删掉）、应用后先清空已选库再拉库列表、失败时原样摊出后端原话并把选择器置灰、Key 存 `sessionStorage`（关标签页即清）。调试台**不再读** `GET /console/keys`——一个 Key 只从一个真相来（用户手里那一串）。

### 15.3 途中抓到的真问题：作废之后旧 Key 还能用 60 秒

第一版把过渡期里验过的旧串也写进了 `KeyVerifyCache`。端到端用例立刻炸了：**点了「作废旧 Key」，旧串下一次请求仍然 200**。

原因不是过期判据写错，而是缓存短路：`key_id_of(token) == key_id` 就直接返回，**根本不会再验一次「窗口还在不在」**。于是缓存把一把正在退役的凭证变成了「60 秒有效的钱包」，而 `key_verify_cache.py` 模块文档的承诺恰恰是「撤销一律立即生效」。

修法：**过渡密钥这条支路不进缓存**。代价是过渡期内旧业务每请求多烧一次 scrypt（50~100ms）——那本来就是一段要被赶快的状态，值得。

这条是这一轮最值得记的一处：**缓存省掉的是「校验」，不是「判定」**；一旦判定里含一个会过期的量，缓存就必须绕开它。

--- after revoke ---
old  -> (20010, '这把 Key 的密钥已重新生成，请使用新 Key：在 Key 管理页拿到当前 Key 后把业务里的那一份换掉')
new  -> (0, 'success')
```

界面侧核对：`KeysPage-*.js` 里有「过渡期只保留最近一把」、`RetrievePage-*.js` 里有「选择知识库」，而 `选 Key 与库` 与「粘贴 API Key」弹窗标题在产物里**各 0 处**。

### 15.5 有意没做（不是遗漏）

1. **没做「查看当前 Key」**。原文不在库里（ADR-0004），这个按钮只能是「重新生成」，界面也已经按这个说法写清（弹窗第一句就是「只会显示这一次」）。
2. **没给过渡窗口做配置项**。24 小时写死在 `api_key_service.PREV_KEY_TTL`；窗口长度被**记在每一行的截止时刻**里，所以以后调这个常量不会追溯改变已在窗口里的行。
3. **没在调试台加「用会话身份免 Key」**。调试台的价值是复现接入方看到的真实结果（白名单 / 授权位 / 额度全生效）；加了免 Key 路径，它就会开始骗人。
4. **`prev_key_expires_at` 的时区标签仍是「naive 当 UTC」**。与读模型那批时间戳同一套约定：容器里 TZ=UTC 时正确；本机（+08）跑用例时不能拿 `datetime.now(UTC)` 直接比，所以端到端用例改成「作废之后比作废之前更早」这种与机器时区无关的断言。

## 十六、现场第六轮（紧急修复）：额度是 0，却报「操作太频繁」

用户截图：调试台选「改写后检索」→ 召回结果位置报 **`操作太频繁：稍等一会儿再试（业务码 20005）`**。

### 16.1 根因不在限流，在额度

复现（容器内真栈，用该租户同一套密钥配置签一把临时 Key）：

```
policy: testt | retrieve_allowed: True | rewrite: True | decompose: True | research: True | rerank: True
limits  llm_qps: 0   llm_daily: 0
/api/v1/rag/rewrite    code 20005 | msg: llm qps of key … exceeded
/api/v1/rag/decompose  code 20005 | msg: llm qps of key … exceeded
/api/v1/rag/research   code 20005 | msg: llm qps of key … exceeded
/api/v1/rag/retrieve   code 0     | msg: success
```

也就是说：**这份密钥配置把「大模型」这本账的额度配成了 0，同时把改写 / 分解 / Research 三个能力位都开着**。而 `0` 在本仓的既有约定里是「这套集成不用这本账」（自洽校验第三段注释写的就是这句），于是 `0 used of 0` 永远成立——**每一次**调用都会被拒。

### 16.2 为什么它报的是最误导人的那一句

`quota_gate` 把「秒级超额」与「日额超额」分别报 `20005` / `20014`，判据是 `used >= limit`。上限为 0 时这个判据永远成立，于是它走进「秒级超额」那支，报出 `20005`，前端翻成「操作太频繁：稍等一会儿再试」。**这句话给了用户一个永远不会到来的下一步**：等多久都是 0。

这是本轮第二次遇到同一形状的错——**内部只准备了两档，表达层就替第三档编了一句**（§十四 的横幅文案是同一个病）。这里被压掉的那一档是「这本账压根没开」。

### 16.3 改了什么

1. **运行时说真话**（`app/services/quota_gate.py`）：`limit <= 0` 时不再走「超额」那两支，改报 **`20013`（FEATURE_NOT_ALLOWED）**，文案点明 `quota is 0 … 不是「调用太快」… 去 Key 管理页把额度填上，或把对应能力位关掉`。前端那一格本来就有 `20013` 的处置文案（「当前 Key 的密钥配置没有授权这项能力：去 Key 管理页改配置」），与这条的真相应答完全一致。
2. **界面在勾选那一屏就说清**（`KeyPolicyEditor.vue` + `utils/keyPolicy.ts` 纯函数）：
   - 勾上「改写 / 分解 / 研究」而模型额度两格仍为 0 时，**按套餐上限把额度补上**（值出现在「高级设置」的两个输入框里，用户看得见、可改小）；
   - 套餐本身给不出额度时不编数字，改为**红字警告**：「这本账没开，每次调用都会被拒（不是「调用太快」）」——那句话正是现场缺的那句。
3. **存量坏配置修数据**：把「能力位开着、对应账本为 0」的四条策略按**套餐上限**补齐（四条都是 `pro` 档，上限 5/1500 与 15/5000）：

```
6ab58b9d default        llm 5/1500  rerank 15/5000
15ecb6f1 lian diao key  llm 5/1500  rerank 15/5000
ed8af658 testt          llm 5/1500  rerank 15/5000
fbd5789f smoke-t15      llm 1/300   rerank 3/1000
```

补的是**套餐已经卖给这个租户的上限**，不是魔数；界面上随时可以调小。

### 16.4 为什么不在写入时直接拒（一度这么写过，又撤了）

第一版我给 `ensure_policy_consistent` 加了第四段：能力位开 + 账本 0 → `20015`。随即 4 条既有用例变红，其中一条的名字就叫 **`test_a_zero_processing_quota_is_a_legal_configuration`**——「0 是这套集成不用这项能力」，这是被单独写下来钉住过的决定。

撤掉它有两个理由：
1. **0 额度仍然是合法的运行状态**（运维临时把一本账关掉就靠它），把它判死等于没收一个刹车；
2. 那条决定要改，应当是一次有意识的推翻（改用例 + 改 ADR），不该混在一次紧急修复里。

于是改成「运行时说真话 + 写入时界面预警/补齐」：**配置仍然可以这样存，但它不可能再默默失败**。

### 16.5 验证

                                          与计数无关；连同既有 24 条额度用例）
前端    407 passed（47 文件）            （新增 10 条 keyPolicy 纯函数 + 3 条编辑器守卫）

## 十七、现场第七轮（紧急修复）：用量页「没数据」——两处真错

用户说：在调试台用过几次，**用量页的数据没显示出来**。

查下来是两件互不相干的事，都很像「统计坏了」，但原因完全不同。

### 17.1 三本账永远是 0：写账发生在扣账之前

`usage_events` 里那一批数据面调用行的 `meter_r / meter_rr / meter_llm` 全是 0：

```
 2026-11-27 11:08:38 | rewrite   | tenant_beta | top_k 5 | meter_r 0 meter_rr 0 meter_llm 0
 2026-11-27 11:08:35 | retrieve  | tenant_beta | top_k 5 | meter_r 0 meter_rr 0 meter_llm 0
```

设计上有一个 ``meter_tally`` 上下文：门禁在 ``record_n`` 那一刻把「这次真扣了几次」记进去，
写账方优先读它。但**顺序是反的**：

```
组合根（rag_service / decompose_gate）    门禁（retrieval_gate）
  ① 响应成形
  ② 写下 usage_events 那一行  ──┐
                               │   ③ record_success / record_n（真正扣账）
  ④ 返回 payload  ─────────────┘   ⑤ count_meter → tally 才有值
```

写账那一刻 tally 一定是 ``(0, 0, 0)``。于是这个「优先读 tally」的分支把**一个确定的错数**
写进了库：看板上「检索 / 重排 / 大模型」三栏永远是 0。

修法：**全 0 的 tally 不是事实，是「门禁还没走到那一步」**。`current_meter_counts()` 在全 0 时
返回 ``None``，写账方据此回落「这次用了哪些能力」的推断值——而那三个路径的推断值与门禁真扣
的值**本来就相等**（retrieve r=1；rewrite 再加 llm=1；重排 applied 时 rr=1；分解检索 r=N）。
有信号时才用 tally，于是以后真把扣账搬到写账之前，这份数会自动变成权威值。

真栈验证（改后）：

```
/api/v1/rag/retrieve  -> 0   meters 1 1 0     （重排真的跑了）
/api/v1/rag/rewrite   -> 0   meters 1 1 1
/api/v1/rag/decompose -> 0   meters 3 3 1     （3 条子查询各扣一次）
```

### 17.2 7d / 30d 窗口是空的：汇总表只有人工脚本会填

短窗口（1h / 1d）读 `usage_events`，长窗口（7d / 30d）读**按天汇总表** `usage_daily`。而它只
有一个**人工**脚本（`scripts/rollup_usage_daily.py`）会写——没人跑脚本，长窗口就只有上次
有人跑过的零星几天：

```
7d   requests=2  ok=1  failed=1     ← 而今天明明有 21 次调用
```

这不是「统计算错」，是**少了一个运维步骤**，而用户从界面上看不出这件事。本仓刻意**没有 beat**
（ADR-0034「兜底任务的形状」：需要周期性的东西挂在 Worker 的守护线程上），所以修法是把汇总
挂到本来就每 60 秒醒一次的清扫器上：

- 每 5 分钟（Redis `SET NX EX 300` 节流）压**今天与昨天**两天的格；更早的天不会再变，没有重算必要；
- **再加一条补射**：最近 30 天里「有明细、却没有汇总格」的日子顺手补上。只做今天与昨天有一个
  盲区——整栈停过一天以上、或上线之前的历史，洞里那些日子永远不会自己长出来，看板会永远少
  一块。实测第一次跑就补出 5 天（11-11 / 11-12 / 11-14 / 11-16 / 11-17）；
- 汇总失败只留 warning，**不许**影响清扫（否则「看板晚 5 分钟」会升级成「卡住的文档没人救」）；
  补射那一步失败也一样——今天与昨天照压；
- 清扫器的返回值多一格 `rolled`，与 `settled / redispatched / revived` 分开（排版动作不该
  污染「这一轮修了几篇文档」那个读数）。

为什么补射按天逐格探问而不是一条 SQL 算出来：`usage_events.created_at` 存的是**本地裸时间**，
`usage_daily.day` 是 **UTC 日历天**的标签，两者的换算只有 `day_bounds` 一处。在 SQL 里再算一遍
日期等于把那份换算写第二遍，而「差一天」只会在跨时区部署上偶发——最难查的那种错。

存量补齐两条都做了：`scripts/rollup_usage_daily.py --days 8`（34 格）+ 上线后第一次自动补射。

改后四个窗口：

```
 1h | source=events | requests=24 ok=15 failed=9 | 检索=5 重排=5 大模型=2 | 切块=0
 1d | source=events | requests=24 ok=15 failed=9 | 检索=5 重排=5 大模型=2 | 切块=112928
 7d | source= daily | requests=26 ok=16 failed=10 | 检索=6 重排=6 大模型=2 | 切块=112928
30d | source= daily | requests=26 ok=16 failed=10 | 检索=6 重排=6 大模型=2 | 切块=112928
```

真栈实跑（`rag-worker-build` 里那条守护线程，容器日志原文）：

```
11:27:36  usage rolled up  days=['2026-11-26', '2026-11-27']  rolled=2
11:58:41  usage rolled up  days=['2026-11-26', '2026-11-27', '2026-11-11',
                                '2026-11-12', '2026-11-14', '2026-11-16',
                                '2026-11-17']  rolled=7      ← 补射第一次就找到 5 个洞
```

补完之后：最近 30 天「有明细的日子」10 天、其中缺汇总 **0** 天；7d 读数 26 次、30d 读数 85 次。

### 17.3 验证

```
后端    新增 tests/test_usage_events_write.py 2 条（全 0 tally = 没信号；只记 0 也不算证据）
        + tests/test_usage_rollup_schedule.py 4 条（只压近两天 / 节流 / Redis 挂了跳过 / 一天坏了不拖累另一天）
前端    未改动（这一轮全是账与看板的数据问题）
真栈    meters 三行已带着真值；四个窗口读数如上；自动汇总在容器日志里可见

### 17.4 一处仍在的结构债（说清楚，不假装没有）

「写账发生在扣账之前」这个顺序没被改掉——改的是**它对读数的后果**（全 0 不再被当成事实）。
真正的根治是把 `usage_events` 那一行推迟到扣账之后写，那需要把交付物事实（片 id / 稿号 /
版本映射）从组合根交出来，是一次结构性重排。现在三本账的值来自「按能力推断」而不是「扣账
那一刻的真值」，两者在今天的四条路径上**相等**，但不是同一件事——所以这条债记在这里。

## 十八、现场第八轮：不留人工——把三件「记得敲命令」的事转成自动

用户的话很短：**不留人工，能转自动的都转自动。**

盘点之后剩下三类人工动作，全部转掉：

| 原先的人工动作 | 多久要做一次 | 忘了的后果 | 现在 |
| --- | --- | --- | --- |
| `docker exec rag-api alembic upgrade head` | **每次换代码** | 不是报错，是**新代码跑在老表结构上**（现场五就是这么撞上的） | compose 里一个一次性 `migrate` 服务，起栈先跑，其余容器等它成功退出 |
| `scripts/purge_usage_events.py` | 看心情 | 明细账无限增长（每次调用一行）；磁盘悄悄涨 | 清扫线程每天一次（90 天明细 / 395 天汇总） |
| `scripts/purge_document_versions.py` | 看心情 | 每改一稿多一套切片，检索永不命中却一直占着向量库与关键词索引 | 同上 |

加上上一轮已经把 `rollup_usage_daily.py` 转成自动并带 30 天补射，四个运维脚本现在都不需要人记得。

### 18.1 迁移：从「记得敲」到「起栈即完成」

```yaml
migrate:                     # 一次性服务，同一个镜像
  command: ["alembic", "upgrade", "head"]
  container_name: rag-migrate
  restart: "no"
  depends_on: { postgres: { condition: service_healthy } }
# api / worker / worker-build 都加了：
#   migrate: { condition: service_completed_successfully }
```

为什么是**单独的一次性服务**、而不是塞进 api 的 entrypoint：三个容器同时启动时，只有迁移服务
在跑 DDL；塞进每个容器就是三次并发迁移。链尾之后没有新迁移时它是空操作，所以每次起栈都跑它
安全且便宜。

真栈验证：`docker compose up -d` 之后 `rag-migrate` 的状态是 `Exited (0)`，
`alembic_version = e4b1d7a9c2f5`；api / worker / console 全部起来（200）。

### 18.2 保留期清理：藏在清扫线程里，每天一次

新增 `app/services/retention.py`（判定与执行）+ `index_sweeper.retention_once`（调度）：

* **明细 90 天 / 汇总 395 天**（与两个脚本的默认值同一口径）；
* **删除前按天复核**：那一天的汇总格在 → 删它的明细；不在 → **放过**并记进 `skipped_days`。
  这是「数据只有一份」的直接后果——长窗口看板只读汇总表，明细被删掉而汇总没生成，等于永久丢失；
* **版本清理**走 `document_version_service.purge_expired_versions`（与人工脚本**逐字同一条规则**），
  每篇文档一笔事务，一篇失败只记 `failed_documents`；
* 两个动作**互不拖累**（各一个 try/except），返回值分开记账
  （`events_deleted` / `daily_deleted` / `versions_purged`），不合成一个「干了活」；
* 节流键与汇总分开（`lock:retention:daily`，86400s），于是「每 5 分钟的汇总」与「每天的清理」
  互不压制。

**顺序**也定死了：`sweep → rollup（带补射）→ retention`。先补洞再删，被删的那天一定有格兜着。

真栈日志：

```
13:05:46  usage rolled up  days=['2026-11-26', '2026-11-27'] rolled=2
13:05:46  retention purged usage rows  daily_deleted=0 events_deleted=0 skipped_days=0
```

（当前库里最老的一行是 11-11，还在 90 天窗口内，所以这一晚确实没有可删的——这本身是对的。）

### 18.3 章程变更写进了 ADR

清扫器从「只修卡住的文档」变成「夜里还做汇总与清理」，这是**章程变更**，不是随手加一个调用：
写进了 `docs/adr/0034-queue-state-and-build-convergence.md` 的「决策七实现补充」，含三条约束
（先汇总后删明细 / 分工明确 / 节流键分开）与代价。

### 18.4 验证

```

        新增 tests/test_retention_schedule.py 6 条（每天一次 / 两个动作互不拖累 / Redis 挂了跳过 /
        单篇失败不拖累整晚）

### 18.5 仍然留下来的人工（只有这一类）

**产品决策类**，不是运维动作：给谁开租户、发哪把 Key、给哪个套餐（`scripts/create_tenant.py` /
`issue_api_key.py` / `change_tenant_plan.py`）。它们要的是「谁批准」，不是「谁记得跑」——把
授权也自动化就等于把审批自动化，那是另一个问题，不在这一轮的范围里。
