## 一、先回答最初那个问题：「构建成功，但文档状态没回写」

### 根因（两个缺陷叠在一起，各自单独都能让用户看到「构建好了、文档还停在索引中」）

**缺陷 1：状态回写是个空操作。**
`index_build_service.build()` 先用一次读把文档对象装进会话（`status=1`）；随后
`try_claim_for_indexing` 用一条 `UPDATE` 抢租约，并且：

```python
.execution_options(synchronize_session=False)   # 不改内存里的对象
# 会话又是 expire_on_commit=False                 # 提交后也不过期
```

于是内存里那个文档对象**仍然是 `status=1`**。Tx2 收尾时 `update_status(doc, SUCCESS)` 走的是
「赋属性 + flush」的旧路径 → ORM 认为值没变 → **一条 UPDATE 都不发**。库里那一行永远停在 3。

这条在 #212 修掉了：`update_status` 改成执行显式 `UPDATE ... WHERE id AND tenant_id`，
并**检查影响行数**（`written != 1` 就记 warning）——「写成功但一行没动」这种静默失效从此会留下痕迹。

**缺陷 2：构建能「一篇都没真重建」却判定成功。**
旧循环丢掉了 `index_existing_document` 的返回值，每篇都 `indexed += 1`。抢不到租约的篇也被
算作已重建 → 四项计数对账在「切片 0 / 向量 0 / 关键词 0」时三方相等 → 一路 `ready` 并激活，
线上静默变成「版本正常、检索全空」。这条在 #214 修掉了：计数只数真的写进切片的篇，
并且**收尾判据改成读真值**（见第二节）。

### 现在怎么保证不再发生

| 防线 | 机制 | 落在哪 |
| --- | --- | --- |
| 状态写入不会静默失效 | 显式 UPDATE + 检查 `rowcount` | `document_repository.update_status`（#212） |
| 迟到的任务写不进别人的地盘 | Tx2 开头 `SELECT ... FOR UPDATE` 核对**租约令牌**，不匹配就回滚并返回 0 | `indexing_service.py`（#213） |
| 空版本不可能上线 | 收敛读 `COUNT(DISTINCT document_id) FROM chunks WHERE (version, draft)`，分母是起跑快照 | `index_build_service.converge`（#214） |
| 构建行自己会过期 | `converge_deadline = 起跑 + 基数 + 每篇预算 × 篇数`，清扫器按它收尾 | #214 / #225 |
| 测试不许再「断言函数被调用过」 | 状态类断言一律走**真库**（`pytest.mark.integration` + `RAG_INTEGRATION_DATABASE_URL`） | `tests/test_index_build_dispatch.py` 等 |

## 二、八条诉求逐条落地

### 1. 文档状态加「排队中」
`app/utils/status.py`：`SUCCESS=1 / FAILED=2 / PROCESSING=3 / QUEUED=4`（**序号沿用旧值**，不重排）。
上传、重建、回滚三个入口一律落 `4`；Worker 抢到才进 `3`。
迁移 `b3f7c2a91d40`：存量「`status=3` 但没有租约」的行改成 4（那是改造前排队中却被记成处理中的那一批）。
前端 `utils/documentStatus.ts` + `StatusBadge.vue`；轮询条件是 `{3,4}` 而不是「等于 3」。

### 2. 卡住的东西自动恢复，而不是靠人跑脚本
- **构建**：真值收敛（#214）+ 构建行租约 + 清扫器（#225，`beat` 每 5 分钟扫一遍逾期构建，
  按真值收尾成 `ready` 或 `failed`，并把缺哪几篇写进明细）。
- **单篇**：租约令牌围栏（#213）保证迟到的任务写不进去；失败可重试的那条路径释放租约后重投。
- 运维脚本仍然在：`scripts/reconcile_build.py`（#214），人触发时按 `build_id` 跑得更准。

### 3. 套餐加「库数」与「每库 token 容量」
- `plans.max_tokens_per_kb`（迁移 `d5f9c2a7b3e8`）+ `documents.token_count`。
- **两种 token 口径，别混**：容量用**正文** token（与切块器同一把尺子）；每日额度用**检索文本**
  token（真正发给嵌入模型的那一行）。混用会让「容量没满但额度超了」解释不清。
- 门禁在两个位置：**入口预检**（库已经满了就不收新的，便宜）+ **解析后硬拦**
  （`token_count(parsed.content)` 超了就在切块与嵌入之前拒掉，准确）。
  重建时排除自己（`excluding_document_id`），否则库满之后连重建都做不了——那是自锁。
- 四档值：30K / 300K / 2M / 5M；同时把 `max_kb` 提到 3 / 10 / 50 / 100（ADR-0035 决策六）。

### 4. 彻底删掉「处理中名额」
`plans.max_processing_documents` 物理删除（迁移 `b9f4d2c70e13`），`ensure_processing_quota`、
`count_processing_for_tenant` 及其语句一起删。写入口一律接受、全部排队。
**接受的代价**（写进 ADR-0034 决策八）：没有公平调度，一个租户一次传一万篇会拖慢别人。

### 5. embedding 批大小面板可改

### 6. 每日切块额度（「三本账变四本」）

## 三、构建按篇化（#215 #216）

**改造前**：一个任务顺序跑完整个库。三个代价都不是调参能解决的——失败粒度是整个库、
进度不可见、整段时长只占一个 Worker 槽位。

**改造后**：
```
start_build ──> dispatch_build_task（派活：分页读参与文档，差集去掉已有切片的）
                    │  每篇一条 build_document_task（task_routes -> build 队列）
                    ▼
              worker-build（独立进程，-Q build --concurrency=1）
                    │ 走与用户单篇重建完全相同的流水线
                    ▼
              跑完回去记账（documents_done +1 / 失败写明细）→ converge(final=False)
```
- **续建**：目标版本 + 稿号下已有切片的直接跳过（重投不再烧一整轮 embedding）。
- **失败不改文档状态**（ADR-0034 决策九）：那篇文档本身没坏，线上旧版本照常可查；
  失败只落构建行的 `failed_documents`（JSONB），是「未入新版本」的唯一真相源，也是续建清单。
- **重投上限** 3 次（`MAX_REDISPATCH`）：救不回来也是一个必须兑现的结论。
- `build_index_version_task`（一次跑完整个库）保留，供运维一次性跑；不再是默认形状。
- `converge` 的判据：`decide_convergence(truth, planned, failed, final)`——纯函数，四种组合
  在离线用例里逐条钉死。

## 五、部署变化（要动运维清单）

`deploy/docker-compose.yml` 新增两个服务、一条队列：

| 服务 | 作用 | 连接预算 |
| --- | --- | --- |
| `worker-build` | `-Q build --concurrency=1`，只跑构建 | +15 条（一套异步池） |
| `beat` | `celery beat`，每 5 分钟投清扫任务 | **0**（不读库） |

- 常规 `worker` 显式只消费 `celery,maintenance`——**不加 `build`**，否则构建任务被它抢走，
  `worker-build` 的隔离就名存实亡。
- 清扫器走 `maintenance` 队列，理由是它必须在「构建把槽位占满」时也跑得起来。
- `docs/架构.md` 的连接预算一节按进程数重算：`15×API + 15×常规worker + 15×构建worker + …`。
- `beat` 的 `--schedule` 指到 `/tmp`（容器里 `/app` 不一定可写；踩到的症状是
  `Exited (1)` + `Permission denied: 'celerybeat-schedule'`）。

## 七、有意的取舍（不是遗漏）

1. **没有公平调度**：删掉「处理中名额」之后就真的全收了（ADR-0034 决策八写明了代价）。
2. **每日额度是绝对上限**：pro/max 档一天内做不了一次全量重建（这是额度该有的样子，
   不是 bug）。要一次性放开，运维临时调额度。
3. **清扫器只做逾期收尾**，没做「缺篇未过期就补投」与「单篇租约过期重投」：
   前者由期限兜底 + `reconcile_build.py --redispatch` 更准；后者由 lease-token 围栏兜住，
   而两者都需要一条**跨租户读**。取舍写在 `app/tasks/index_sweeper.py` 模块文档与
   ADR-0034「决策七的实现补充」。
4. **ADR-0034 决策七被翻案一次**：原方案是「清扫器住在 worker 常驻循环 + Redis 心跳、不要 beat」，
   落地改成 `beat` —— 因为 `worker_process_init` 是**每子进程**各调一次，4 核就是每 5 分钟扫 4 遍，
   想只扫一遍还得加一把锁。这条偏离与代价记在 ADR 里。
5. **`documents.token_count` 的迁移回填只是下界**（按字符数）。真值由
   `scripts/backfill_document_tokens.py` 用词表算一遍覆盖（脚本在窗口内可跑，不影响容量判据
   的正确性方向：下界偏小只会「多放一点」，不会「误拒」）。
