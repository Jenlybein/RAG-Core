# 第 11 步 S7 · 收尾压测：4 / 16 / 64 并发下的形状，与 S0、#127 三向对比

> 只读压测：不连真 Redis、不写库、不改生产代码路径。整条链路跑在进程内（ASGI + 既有注入缝），数据库与三类 Provider 都是**离线替身**。
> 这份读数是**尺子**，不是生产容量承诺：绝对延迟取决于下面「假设」表里的模拟值，可比较的是**形状**（并发升高时谁劣化、劣化多少、吞吐卡在哪）。

## 一、复现

```powershell
uv run python scripts/loadtest_baseline.py --levels 4,16,64 --requests 160 --warmup 8 `
  --db-call-ms 0.5 --embed-ms 2.0 --vector-ms 2.0 --keyword-ms 2.0 `
  --json-out eval/loadtest-baseline/results-after-134.json `
  --report-out docs/step11-loadtest-after-134.md
```

脚本自己装配离线替身（会话、嵌入、向量库、关键词引擎）并把进程级注入点全部换掉；跑完把同一份读数写成 `--json-out`（机器读，本次在 `eval/loadtest-baseline/results-after-134.json`，含提交号 / Python / 平台）与 `--report-out`（人读，就是本文件）。

**输入从哪来**：问句取自 `eval/questions.json`（137 道评测题，只取 `query` 字段，按请求序号循环使用）。选它是因为它是仓库里唯一一份固定的「真实用户问法」；替身返回的切片与这些问句无关（离线替身不检索真数据），问句在这里只负责「每次请求带一段真实长度的文本」。

## 二、口径

- **P50 / P95**：逐请求墙钟耗时，升序第 `⌈p/100 × N⌉` 个，**不插值**（最近秩法）。与 `scripts/eval_gate.py` 的延迟口径同一把尺子。
- **吞吐**：该档完成的请求数 ÷ 该档墙钟（req/s）。
- **错误率**：HTTP 非 200 或业务码非 0 的占比。**降级单列**：混合模式降级是成功响应（`code=0` + `degraded_reason`），算进错误率会让「并发下悄悄只剩一路」看不见。
- **阻塞事件循环的 DB 占比**：见第四节。**第 11 步票 #127 起这个刻度换了**（账本从「按线程分主循环 / 执行池」改成「按调用形态分阻塞 / 被 await」），所以它只能读「现在是 0」，**不能**与 S0 那一列的数字做严格对比（S0 是同步会话，分子天然不为 0）。

## 三、三档并发读数

| 并发 | 请求数 | P50 (ms) | P95 (ms) | 吞吐 (req/s) | 错误率 | 降级率 |
| --- | --- | --- | --- | --- | --- | --- |
| 4 | 160 | 23.61 | 36.56 | 161.3 | 0.00%（0/160） | 0.00% |
| 16 | 160 | 65.52 | 235.52 | 190.8 | 0.00%（0/160） | 0.00% |
| 64 | 160 | 296.99 | 584.15 | 154.4 | 0.00%（0/160） | 0.00% |

从 4 并发到 64 并发（并发 ×16）：P95 从 36.56 ms 涨到 584.15 ms（×16.0），吞吐从 161.3 涨到 154.4 req/s（**×0.96**）。

**这就是结论**：并发涨了 16 倍，吞吐只涨了 0.96 倍，而 P95 涨了 16 倍。这条链路的上限不在并发数上，而在主循环的**串行工作**上——多出来的并发只是排队，不是吞吐。第四节把那段串行工作里「同步数据库」的那一份量出来：它是 0，所以剩下那部分是框架本身（JSON 解析、pydantic 校验、两个中间件）。

三档一共 480 个请求：**错误 0、降级 0**。所以上面的劣化全部来自「同样的活，排队方式不同」，不是失败或降级掩盖出来的。

## 四、数据库调用：阻塞事件循环的那一半

这是**近似**：分子是**同步**会话调用的耗时之和（插桩在会话替身上，按调用计时），分母是同一批请求的墙钟耗时之和。第 11 步之后检索链路上的数据库访问全部是 ``await`` 的，所以分子是 0；被 await 的等待单独记一列，它**不占**事件循环。

| 并发 | 每请求阻塞主循环的 DB 次数 | 每请求阻塞耗时 (ms) | 占请求时间 | 占整档墙钟（主循环被占住） | 被 await 的 DB 等待 (次) |
| --- | --- | --- | --- | --- | --- |
| 4 | 0.00 | 0.00 | 0.00% | 0.00% | 1280 |
| 16 | 0.00 | 0.00 | 0.00% | 0.00% | 1280 |
| 64 | 0.00 | 0.00 | 0.00% | 0.00% | 1280 |

按最高一档推一下每请求的主循环份额：实测吞吐 154.4 req/s 的倒数是 **6.5 ms/请求**——主循环被占满时，这就是一条请求摊到的串行时间。**这是推断，不是读数**：串行工作的构成（JSON 解析、pydantic 校验、中间件、折叠）从来没有被单独计时过，压测账本只插桩数据库。其中 **0.0 ms 是同步数据库调用**，剩下约 6.5 ms 是框架本身。

次数那一列包含会话上的**全部**方法：`add` 与 `close` 不产生往返（方法分解里它们的耗时约等于 0），真正花时间的是 `execute` / `flush` / `commit` 这几次往返。它们现在都是 `await` 的，因此记在最后一列。

两个占比是**两件事**，都要看：

- **占请求时间** = 阻塞耗时 ÷ 这次请求的墙钟。它回答「这次请求里有多少时间被同步数据库调用**卡住**了事件循环」。异步栈上它是 0：每次访问都让出循环，别的请求照跑。
- **占整档墙钟** = 阻塞耗时 ÷ 这一档的墙钟。它回答「事件循环有多少比例被这些调用**占住**」。第 11 步票 #127 之前这个数随并发升高而上升（主循环被同步查询占满）；之后它一直是 0。

读法：两列都是 **0**。如果它们不是 0，说明检索路径上又出现了一次**同步**数据库调用——那正是第 10 步用执行池掩盖、第 11 步要根除的东西。**这条守卫现在有了更硬的版本**：同步的请求级依赖（`get_db` / `get_transaction`）在票 #134 已经被删掉，控制面的依赖树里只允许出现 `get_async_db`（`tests/test_console_async_reads.py` / `test_console_async_writes.py`），所以「在请求路径上再写一个同步查询」不再是一件顺手就能做到的事。

## 七、局限（读之前先看这一节）

- **延迟是模拟的**：单次 DB 调用、嵌入、向量召回、关键词召回都是固定睡眠，不是实测的网络与数据库延迟。绝对数不能当容量规划，只能当形状与占比的尺子。
- **进程内单进程**：没有 uvicorn、没有多 worker、没有真实连接池上限。执行池在 #127 之后已经删除，所以并发上限是数据库连接池与模型端点。
- **替身只实现检索路径真正用到的那几种语句形状**：遇到新的形状会**当场报错**，不会静默返回空结果。
- **默认离线套件不受影响**：脚本不进 `tests/` 的默认路径，跑全量仍然不需要真库 / 真 Redis。
- **同机重复跑有抖动**：这台机器上吞吐的抖动约 ±10%、P95 约 ±15%（受同机其他负载影响）。第九节把「参数的差别」与「机器的差别」分开列了。

### 8.1 「阻塞事件循环的 DB 占比」：这一列不跨报告比

刻度在 #127 就换过了（账本从「按线程分主循环 / 执行池」改成「按调用形态分阻塞 / 被 await」）：

| 读数 | 每请求阻塞主循环的 DB 次数 | 占整档墙钟（2 并发 / 4 并发 / 64 并发） |
| --- | --- | --- |
| S0 基线（同步会话） | 7 次 | 24.44% / 32.79% / 未测 |
| #127（异步会话） | 0 | 0% / 0% / 0% |
| **#134（本报告）** | **0** | **0% / 0% / 0%** |

能说的只有一句：**现在是 0，而且再想让它不是 0 需要绕过整层依赖**（同步的请求级依赖已经不存在）。**不能**说「从 24% 降到 0 是这次改的」——那是 #127 的账。

### 8.2 参数之外的差别：这一台机器比 #127 那次慢

为了让「参数的差别」与「机器的差别」分开，本票用 **#127 的原参数**（2 / 4 / 64，每档 64 请求，预热 8）复跑了一次同一条命令：

| 并发 | #127 读数（P95 / 吞吐） | #134 同参数复跑（P95 / 吞吐） | 差 |
| --- | --- | --- | --- |
| 2 | 16.20 ms / 195.5 | 15.54 ms / 162.5 | P95 −4%，吞吐 −17% |
| 4 | 17.49 ms / 258.1 | 24.27 ms / 193.7 | P95 +39%，吞吐 −25% |
| 64 | 348.74 ms / 178.9 | 412.57 ms / 151.8 | P95 +18%，吞吐 −15% |

**这一张表里没有任何一行该归因于代码**：本票（#134）删掉的是同步引擎的两个请求级依赖、按循环的客户端注册表与一个线程锁——三件事都不在检索的每请求路径上，其中两件是**纯删除**（没有任何请求会因此多做事）。同参数、同机器、不同时刻，差异落在「同机抖动」这一档甚至更差，说明**这台机器这一次整体更慢**（跑批时它同时在跑其他负载）。

读数该这么用：**跨报告只能看方向与倍数，不能看两位小数**；要拿它当回归尺子，必须在同一台机器上空载重复跑。

## 九、验收结论（三条，逐条说清楚）

票面与父 spec 的 S7 判据是三条，逐条给结论：

1. **64 并发吞吐 ≥ 2×** —— **没达到，如实写**。本报告 4 → 64 的吞吐倍数是 **×0.96**（161.3 → 154.4）；#127 同口径是 ×0.92（258.1 → 178.9）；S0 基线 2 → 4 是 ×1.43（64.3 → 92.2）。也就是说**第 11 步从头到尾都没有把这条链路的吞吐随并发放大**，一次也没有。
    原因在第四、五节里：这条链路的并发上限落在**一个事件循环的串行工作**上——数据库那一段已经不是瓶颈（阻塞占比 0，第八节 8.1）。**注意**：先前这里写过的「约 6.5 ms/请求 = 主循环串行上限」是用吞吐倒数倒推出来的，**框架本身（JSON 解析、pydantic 校验、中间件）的占用从未被单独测量**，所以那是一个推断而不是读数；同机复跑差 −4% ~ +39% 也说明这个量级不可靠。
   所以**第 11 步的收益不是吞吐**：它是「并发下不再排队降级」「取消能传导到数据库驱动」「请求路径上只有一套会话写法」「少一层（执行池 + 注册表）」。父 spec 早就写了这句话，这里只是把它兑现成读数。
2. **单请求 P95 不劣化（±5%）** —— **没有定论**。三份读数（#127 −50% ~ −61%、本票同机复跑 −4% ~ +39%、#137 −17% / +3% / −18%）的参数与机器状态都不同，任何一格的差都同时包含「改动」与「抖动」，因此既不足以证明、也不足以证伪 ±5%。能说的只有一句：**没有观察到把延迟系统性推高的改动**。
3. **阻塞事件循环的 DB 占比 = 0** —— **达成**（三档全 0），而且比 #127 更硬：同步的请求级依赖已经不存在（第八节 8.1）。

**一句话**：这一步把「形状」改完了（一套栈、一个循环、没有线程、取消可传导），**没有**把吞吐改上去；两者都写在纸上了。
