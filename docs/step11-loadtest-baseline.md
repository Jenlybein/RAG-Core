# 第 11 步 S0 · 并发基线：这条链路在 4 / 16 / 64 并发下的形状

> 只读压测：不连真 Redis、不写库、不改生产代码路径。整条链路跑在进程内（ASGI + 既有注入缝），数据库与三类 Provider 都是**离线替身**。
> 这份读数是**尺子**，不是生产容量承诺：绝对延迟取决于下面「假设」表里的模拟值，可比较的是**形状**（并发升高时谁劣化、劣化多少、吞吐卡在哪）。

## 一、复现

```powershell
uv run python scripts/loadtest_baseline.py --levels 2,4 --requests 8 --warmup 2 --db-call-ms 0.5 --embed-ms 2.0 --vector-ms 2.0 --keyword-ms 2.0
```

脚本自己装配离线替身（会话、嵌入、向量库、关键词引擎）并把进程级注入点全部换掉；跑完把同一份读数写成 `--json-out`（机器读，本次在 `eval/loadtest-baseline/results.json`，含提交号 / Python / 平台）与 `--report-out`（人读，就是本文件）。

**输入从哪来**：问句取自 `eval/questions.json`（137 道评测题，只取 `query` 字段，按请求序号循环使用）。选它是因为它是仓库里唯一一份固定的「真实用户问法」；替身返回的切片与这些问句无关（离线替身不检索真数据），问句在这里只负责「每次请求带一段真实长度的文本」。

## 二、口径

- **P50 / P95**：逐请求墙钟耗时，升序第 `⌈p/100 × N⌉` 个，**不插值**（最近秩法）。与 `scripts/eval_gate.py` 的延迟口径同一把尺子。
- **吞吐**：该档完成的请求数 ÷ 该档墙钟（req/s）。
- **错误率**：HTTP 非 200 或业务码非 0 的占比。**降级单列**：混合模式降级是成功响应（`code=0` + `degraded_reason`），算进错误率会让「并发下悄悄只剩一路」看不见。
- **主循环同步 DB 占比**：见第四节。它有两个口径（占请求时间 / 占整档墙钟），**都是近似**，分子分母在那一节写清。

## 三、三档并发读数

| 并发 | 请求数 | P50 (ms) | P95 (ms) | 吞吐 (req/s) | 错误率 | 降级率 |
| --- | --- | --- | --- | --- | --- | --- |
| 2 | 8 | 30.63 | 32.28 | 64.3 | 0.00%（0/8） | 0.00% |
| 4 | 8 | 42.71 | 44.41 | 92.2 | 0.00%（0/8） | 0.00% |

从 2 并发到 4 并发（并发 ×2）：P95 从 32.28 ms 涨到 44.41 ms（×1.4），吞吐从 64.3 涨到 92.2 req/s（×1.43）。

**在这组模拟延迟下，这就是结论**：并发涨了 2 倍，吞吐只涨了 1.43 倍，而 P95 涨了 1.4 倍。这条链路的上限不在并发数上，而在主循环的**串行工作**上——多出来的并发只是排队，不是吞吐。第四节把那段串行工作里「同步数据库」的那一份量出来；敏感性表说明这个倍数会随「单次 DB 调用多慢」变化，但**方向不变**。

三档一共 16 个请求：**错误 0、降级 0**。所以下面的劣化全部来自「同样的活，排队方式不同」，不是失败或降级掩盖出来的。

## 四、主循环同步 DB：占比与口径

这是**近似**：分子是主循环线程上同步会话调用的耗时之和（插桩在会话替身上，按调用计时），分母是同一批请求的墙钟耗时之和。执行池线程上的调用不进分子。

| 并发 | 每请求主循环同步 DB 次数 | 每请求主循环同步 DB 耗时 (ms) | 占请求时间 | 占整档墙钟（主循环被占住） | 执行池线程上的同步 DB 调用 (次) |
| --- | --- | --- | --- | --- | --- |
| 2 | 7.00 | 3.80 | 12.28% | 24.44% | 16 |
| 4 | 7.00 | 3.56 | 8.29% | 32.79% | 16 |

最高一档（4 并发）按方法分解（主循环线程，ms）：

| 方法 | 耗时 (ms) |
| --- | --- |
| `execute` | 14.15 |
| `commit` | 8.62 |
| `flush` | 5.69 |
| `add` | 0.00 |
| `close` | 0.00 |

按最高一档推一下每请求的主循环份额：实测吞吐 92.2 req/s 的倒数是 **10.9 ms/请求**——主循环被占满时，这就是一条请求摊到的串行时间，也就是这条链路的上限。其中 **3.6 ms（32.79%）是同步数据库调用**，剩下约 7.3 ms 是框架本身（JSON 解析、pydantic 校验、两个中间件）。后面那一半不在本报告的分子里，所以「占整档墙钟」是**下限**而不是全部。

次数那一列包含会话上的**全部**方法：`add` 与 `close` 不产生往返（方法分解里它们的耗时约等于 0），真正花时间的是 `execute` / `flush` / `commit` 这几次往返。

两个占比是**两件事**，都要看：

- **占请求时间** = 同步 DB 耗时 ÷ 这次请求的墙钟。它回答票面上的问题「其中多少时间花在主循环上的同步数据库调用」。**并发越高它越小**——不是因为它变快了，而是因为请求越来越多的时间花在**排队**上（排在别人那次同步调用后面），分母被排队撑大。
- **占整档墙钟** = 同步 DB 耗时 ÷ 这一档的墙钟。它回答「事件循环有多少比例正卡在这些调用里」。这个数不随并发稀释：它是吞吐被封顶的**直接原因**——主循环被占住的时候，第 2、第 64 个请求一步都推不动。

读法：如果两列都在涨/都贴住高位，说明「并发上限不是数据库，是主循环」；如果「占整档墙钟」在 64 并发时明显低于「占请求时间」的推断，说明瓶颈在别处（框架 CPU、模型调用）。注意主循环上的串行时间不止这一段：JSON 解析、pydantic 校验、中间件也都在主循环上，本报告只量了**同步 DB 那一半**——「占整档墙钟」因此是同步 DB 的**下限**贡献，不是主循环占用率的全部。

## 七、局限（读之前先看这一节）

- **延迟是模拟的**：单次同步 DB 调用、嵌入、向量召回、关键词召回都是固定睡眠，不是实测的网络与数据库延迟。绝对数不能当容量规划，只能当形状与占比的尺子。
- **进程内单进程**：没有 uvicorn、没有多 worker、没有真实连接池上限。「并发上限是池」这件事在这里体现为执行池（4 条线程）的排队，而不是数据库连接数。
- **替身只实现检索路径真正用到的那几种语句形状**：遇到新的形状会**当场报错**，不会静默返回空结果——后续票往主循环上新增查询时，这个入口会先红一次，逼人先想清楚那条查询该不该在主循环上。
- **默认离线套件不受影响**：脚本不进 `tests/` 的默认路径，跑全量仍然不需要真库 / 真 Redis。
- **同机重复跑有抖动**：这台机器上吞吐的抖动约 ±10%、P95 约 ±15%（受同机其他负载影响）。所以对比时看**倍数与形状**，不要拿两位小数当结论；要更稳就加大 `--requests`。

## 八、后面每一张票怎么用它

同一条命令、同一组参数，改完再跑一次，对比三件事：（1）64 并发吞吐是否 ≥ 2×；（2）单请求 P95 是否 ±5% 以内；（3）「主循环同步 DB 占比」是否趋近 0。三条都是 S7 的验收数字。
