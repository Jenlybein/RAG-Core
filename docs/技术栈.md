# RAG-Core 技术栈

技术栈按**一次请求流经哪些层**组织，而不是按「语言 / 框架 / 工具」分类。分层表不是目录，是排障地图：线上出问题时只要能定位「卡在哪一层」，就知道该看哪个日志、哪个指标。

## 请求视角的整体结构

```
请求进来
  ↓ Web 框架（FastAPI + Pydantic）        ← 收参数、校验、序列化
  ↓ 平台层（自研 套餐/档位 + Redis）       ← 鉴权、限流、配额
  ↓ 业务编排（纯 Python + asyncio）        ← 串起下面这些
  ↓ 数据访问（SQLAlchemy → PostgreSQL）    ← 业务数据
  ↓ 外部能力（Provider 层，六类）
      ├ Embedding 服务（HTTP）
      ├ 向量库（pgvector，就在 PostgreSQL 里）
      ├ 关键词检索（Elasticsearch + IK）
      ├ 大模型（HTTP）
      ├ 重排服务（HTTP）
      └ 文档解析（本地库：mammoth / markdownify / pdf-inspector）
  ↓ 异步侧（Celery + Redis）              ← 索引链路
  ↓ 观测（Langfuse；离线评测 RAGAS）       ← 旁路
```

三处结构特征值得记住：

1. **平台层在业务之前** —— 鉴权、限流、配额是横切关注点，放在业务编排之前，业务代码里就不会散落 `if not check_quota(): return`。
2. **向量库不是独立一档，而是外部能力里的一个分支** —— 因为它物理上就在 PostgreSQL 里，走同一个连接池。这和「向量库是一个独立中间件」的常见架构不同，是本项目最关键的架构选择。
3. **异步侧和观测都是旁路** —— 主链路不依赖 Celery 完成，也不依赖 Langfuse 在线；这两者挂了，检索仍要能返回结果。

## 八个分层

| 层 | 技术 | 职责 |
| --- | --- | --- |
| 1 · Web 框架 | FastAPI · Pydantic v2 · Uvicorn | 收参数 → 校验 / 序列化 → 交业务层；统一响应体 `{code, msg, data}`；异常转错误码 |
| 2 · 平台层 | 自研 套餐 / 档位 · Redis | 鉴权（谁在调）→ 数据范围白名单（能查哪些库）→ 套餐 / 档位判定（能调多好）→ 限流（QPS）→ 日配额 |
| 3 · 业务编排 | 纯 Python · asyncio · httpx | 串起下面几层：查询改写（`services/query/`）→ 双路召回 → 融合 → 重排 → 组装检索结果；控并发、超时、降级 |
| 4 · 数据访问 | SQLAlchemy 2.x · Alembic · psycopg 3 · PostgreSQL 16 | 业务数据持久化与迁移；请求路径**一套**会话（`AsyncSession`），见下方第 4 层 |
| 5 · 外部能力 | 六类 Provider | embedding / 向量库 / 关键词 / 大模型 / 重排 / 解析 |
| 6 · 异步侧 | Celery + Redis | 异步文档索引：解析 → 切块 → 向量化 → 双写（第 3 步只写 pgvector，ES 双写是第 4 步目标形态） |
| 7 · 观测 | 归属索引 · 六段 span · ragas | `metadata.trace_id` + 六段耗时（去向可切）+ 本地反馈；门禁零 LLM、旁证只提示。旁路 |
| 8 · 前端调试台 | Vue 3 · Vite · Element Plus | 把整条链路的中间态暴露出来：召回几条、融合后剩几条、重排后分数怎么变 |

### 为什么这样分

- **按变化频率分，不按技术类型分。** Web 框架、组件库换得频繁，业务编排很稳定；稳定的放中间、易变的放两头，改动影响面最小。
- **按失败域分。** 外部能力会挂、Redis 会挂、Langfuse 会挂，它们必须在不同层，才能各有独立降级策略；全塞进一个 Service，降级就只能一刀切。
- **按同步 / 异步分。** 看到 `async def` 就知道在跟外部服务说话，看到 `self.db.` 就知道是本地库——读代码时靠这个快速定位耗时来源。

### 各层的关键约束

**第 1 层是唯一允许知道 HTTP 存在的地方。** 业务层不出现 `Request` / `HTTPException`，否则加一个入口（比如 MCP）就要改业务。请求模型用 `extra="forbid"`——这是防越权的第一道闸：攻击者往 JSON 里塞一个 `tenant_id` 或质量参数会整单参数校验失败（`20002`），而不是被静默丢掉。静默忽略会让调用方以为自己的参数生效了。

**第 2 层的技术含量不在 Redis，在顺序。** 顺序固定为：鉴权 → 数据范围白名单 → 套餐 / 档位门禁 → 限流 → 日配额；后一关依赖前一关的产出。顺序反了会出现「未鉴权的请求也在消耗限流配额」或「越权请求先扣掉客户当天的额度」，被刷时正常用户被误伤。一个 Redis 实例承担四个角色：Celery broker（0/1 号库）、两级 QPS 计数、按天配额计数（`quota:` 前缀）与套餐缓存（2 号库、`plan:` 前缀）。鉴权解出来的是「租户 + **这套密钥配置** + 当前套餐」，后面的能力门禁与限额都基于它们算——改这套配置，只影响引用它的那些 Key；改套餐，下一次调用就按新套餐判。

**第 3 层是唯一知道完整流程长什么样地方。** 编排逻辑是这个项目真正的业务价值，用纯 Python 写，才既能被 HTTP 调用、也能被 Celery 任务调用、还能被测试直接调用。

**第 4 层在请求路径上是异步的，与上面全异步的世界同构。** 数据库操作是 `await db.execute(...)`（`AsyncSession`），驱动仍是 psycopg 3（同步与异步共用同一个 dialect，见 ADR-0024）。因此「不要在多个线程间共享 Session」这条约束在请求路径上不再需要——异步会话不绑线程，一个请求一条会话，由依赖的 `finally` / 事务入口负责关。**只剩一处仍是同步的**：Provider 装配期的角色指针（`get_llm_provider` 是同步工厂）、运行时配置热刷新（跑在线程池里）与运维脚本；它们都不在请求路径上，逐个写在 ADR-0024 里。

**第 5 层收口的是「慢、会挂、会换供应商」的能力。** 收进同一层才能统一做超时、重试、降级；否则降级策略会散成几份不一致的实现。这三个特征也正是「算不算一类」的判据，且按**最终生产形态**看：Rerank 二期已落地——生产装的是 `Qwen3RerankProvider`，打的是自己的 Cross-Encoder 端点，不再借道大模型 Provider，所以计入六类；而查询改写 + 同义词（`services/query/`）自己不出网，归业务编排层。

**第 6 层里有个不显然的写法**：每个 worker 子进程一个**常驻事件循环**（`app/db/worker_loop.py`，ADR-0023），任务把协程的**工厂**投进去执行——因为 worker 是同步进程模型，而 Provider 与数据库访问都是 `async def`。不用「每任务 `asyncio.run` 一次」，是因为异步引擎的连接池绑在创建它的循环上（每任务一个循环 = 每任务一套池，且任务路径里没有活着的循环能 `dispose()`）。

**第 8 层不是「好看」，是可观测性前端。** 它和 Langfuse 是同一件事的两种视图：一个给人调参，一个给运维追查。它承载**用户面板**（账号操作本租户资源）与**管理员面板**（账号 / 套餐 / 审计，需 `admin` 角色）。

## 依赖管理与装环境

### 依赖声明

教程原项目没有 `requirements.txt`、`uv.lock`、`poetry.lock`，全部走 `pyproject.toml` 的可选组；**本仓库现状已改为 `uv` + 提交 `uv.lock` 锁定版本**，下面的可选组是原项目口径的对照，不是本仓库的最终清单（以根目录 `pyproject.toml` 为准）。

```toml
[project]
name = "rag-core"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = [
    "fastapi>=0.115", "uvicorn[standard]",
    "sqlalchemy>=2.0", "alembic", "pydantic>=2.0", "pydantic-settings",
    "psycopg[binary]", "pgvector", "httpx",
]

[project.optional-dependencies]
parsers = ["mammoth==1.8.0", "markdownify==1.2.3", "pdf-inspector==1.25.2"]
eval    = ["ragas>=0.2.0", "datasets>=2.0.0"]
async   = ["celery[redis]>=5.4.0", "redis>=5.0.0"]
observe = ["langfuse==5.2.0"]

# 这一段必须写，否则 pip install -e . 直接报错
[tool.setuptools.packages.find]
include = ["app*"]
exclude = ["migrations*", "tests*", "eval*", "scripts*"]

[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"
```

不写 `packages.find` 的报错是：

```
error: Multiple top-level packages discovered in a flat-layout: ['app', 'migrations'].
```

setuptools 在根目录发现两个 Python 包，不知道哪个是主包。这是装环境撞上的第一个坑。

**可选组的意义在于顺序**：解析库和评测库体积大、带 C 扩展，早装会拖慢第一次 `pip install`；建骨架时只需要基础依赖，等到真要用解析库再装，编译失败也挡不住前面的进度。

```bash
.venv/bin/pip install -e .                # 基础依赖
.venv/bin/pip install -e ".[parsers]"     # 解析 docx / pdf 时才需要
.venv/bin/pip install -e ".[eval]"        # 跑 RAGAS 时才需要
```

没有 lock 文件的代价是「不同时间装出来的版本会不一样」，所以上面矩阵才要把硬约束单独标出来。

> 建议始终用显式路径调用（`.venv/bin/pip`、`.venv/bin/python`），不要依赖「激活了没有」——踩过 `command not found: pip` 的坑，就是 shell 里 venv 没真正生效。

```yaml
services:

  pg_data:
```

```bash
docker compose up -d
docker exec -it pg16-pgvector psql -U postgres -d rag_db \
  -c "CREATE EXTENSION IF NOT EXISTS vector;"
```

最后那条建扩展的命令别忘：pgvector 镜像虽然预装了扩展文件，但**每个数据库仍要显式 `CREATE EXTENSION`** 才会启用类型。漏了它，建向量列时会报 `type "vector" does not exist`。

## 六个版本陷阱

这六个里有五个有明确报错原文，且**报错信息与真实原因常常毫无关系**；第三个（Python 版本）是约束型的，没有单一报错，但同样容易踩。

### 一、向量维度 1536 是硬约束

```python
# app/models/chunk.py
embedding: Mapped[list[float]] = mapped_column(Vector(1536))
```

列定义写死 1536 维，所以换 Embedding 模型不能随性。就算模型支持多维度（`text-embedding-v4` 支持 1024 / 1536 等），调用时也必须显式传参，否则服务端默认可能是 1024：

```python
resp = await client.post("/embeddings", json={
    "model": settings.EMBEDDING_MODEL,
    "input": texts,
    "dimensions": 1536,      # ← 不写这个，服务端默认可能给 1024
})
```

报错长这样：`expected 1536 dimensions, not 1024`。

**换模型的正确流程**：改 `.env` 模型名 → 改 `Vector(新维度)` → 写新迁移 → **全量重建索引**（旧向量全部作废）。

### 二、IK 分词器版本必须等于 ES 版本

`8.17.10` 的 ES 必须配 `8.17.10` 的 IK，**差一个补丁号都装不上**：

```
Exception: plugin [analysis-ik] was designed for elasticsearch version 8.16.0,
but is installed on 8.17.10
```

报错说的是「插件是给 8.16.0 设计的」，第一反应会去怀疑下载链接、镜像源、网络——真实原因只是版本号差最后一位。

装完必须验证分词真的生效：

```bash
curl -X POST "http://127.0.0.1:9200/_analyze" \
  -H "Content-Type: application/json" \
  -d '{"analyzer":"ik_max_word","text":"退款申请流程"}'
```

能切出 `退款` / `申请` / `流程` 才算成功。**返回把整句当一个 token，说明走了默认分词器**——插件装了但没生效，或根本没装。

### 三、Python 版本：教程写 3.11，本项目按 3.12（cp312）落地

教程早期钉 3.11，但 `pyproject.toml` 的 `requires-python >=3.12` 已经把 3.11 排除；本机实际是 3.12.14。3.11 与 3.12 同为 cp312 ABI，依赖 wheel 等价；真正要避开的是 3.13——那里仍有部分依赖缺预编译 wheel，会退化成源码编译再因缺工具链失败。**不要把解释器降回 3.11 去对齐教程**，也不要在 3.13 上做验收。

### 四、Embedding 单批上限按模型不同

百炼的 embedding 接口单批上限**不是固定数字**，它跟模型绑定：`text-embedding-v3/v4` = 10 条、`text-embedding-v1/v2` = 25 条、`qwen3.7-text-embedding` = 20 条。一次传 200 个切片会报（以 v3/v4 为例）：

```
400 Bad Request: batch size is invalid, it should not be larger than 10
```

这个坑的特殊之处：它不是版本问题，但**症状像版本问题**——刚换了模型、刚升了 SDK，一跑就 400，很容易怀疑 SDK 或模型。正确做法是在 Provider 里按配置分批（`EMBEDDING_BATCH_SIZE`，默认取最保守的 10），不要写死一个数字；换模型时改 `.env` 即可，且分批粒度与重试粒度一致（一批失败只重试这一批，不要整篇重跑）。

### 五、`celery` / `kombu` / `redis-py` 三方约束可能互不相容

这三者是**传递约束**：celery 限定 kombu 的版本窗口，kombu 再限定 redis-py 的版本窗口。三个包装得上、彼此"满足对方"，整体却不可用。实际踩到的组合：

```
celery[redis]==5.4.0    →  kombu <6.0,>=5.3.4   →  解析到 kombu 5.7.0
celery[redis]==5.4.0    →  redis !=4.5.5,<6.0.0,>=4.5.2   （自己封顶 6.0）
kombu 5.7.0             →  redis >=6.4.0
```

三者不可能同时满足。症状不在 `pip install`/`uv sync`（那时没报错），而是在**第一次投递任务时**：

```
kombu.exceptions.VersionMismatch: Redis transport requires redis-py versions 6.1.0 or later. You have 5.2.0
```

本项目采用的自洽组合：`celery[redis]==5.5.3` + `kombu 5.5.x` + `redis==5.2.0`（celery 5.5 把 kombu 封在 `<5.6`，而 kombu 5.5 允许 `redis<=5.2.1`）。

之所以值得单列一条陷阱：**离线测试碰不到 broker，CI 全绿，而真实上传 100% 失败**。守卫在 `tests/test_dependency_compat.py`——它只读 `importlib.metadata` 的 `Requires-Dist`，把"上游声明的可选依赖窗口"与"实际装到的版本"对齐，不发网络请求。

### 六、`langchain-community` 必须钉 `0.4.1`，否则 `import ragas` 直接失败

`ragas==0.4.3` 的 `ragas/llms/base.py` 在**模块顶层**写着：

```python
from langchain_community.chat_models.vertexai import ChatVertexAI
```

而 `langchain_community.chat_models.vertexai` 这个模块在 `langchain-community==0.4.2` 被删除了。于是升级到 0.4.2+ 之后：

```
ModuleNotFoundError: No module named 'langchain_community.chat_models.vertexai'
```

它特殊在：**我们自己的代码从不直接 import 这个模块**，所以没有任何调用点会提示你；它是 ragas 的传递依赖，`uv sync` 顺手升上去看起来毫无异常，直到某次导入评测库才炸。症状与真实原因（上游删模块）也没有直接关系。

守卫同样在 `tests/test_dependency_compat.py`：它直接断言 `langchain_community.chat_models.vertexai` 这个模块**仍然存在**（而不是只守版本号）——因为 `import ragas` 要等到评测代码才发生，中间没有任何调用点会提醒你。改依赖时别只看直接依赖。

## 换掉某项技术要连带改什么

| 想换的东西 | 可替代方案 | 必须连带改 | 建议 |
| --- | --- | --- | --- |
| pgvector | Milvus / Qdrant / Weaviate | 只改 `VectorStore` 实现；SQL 里的余弦距离算子要改写；**不再是同一事务**，删文档要做补偿 | 千万级向量以上再换，早期换是纯亏 |
| Elasticsearch + IK | OpenSearch + IK / Meilisearch / PG 全文检索 | `KeywordSearch` 实现；中文分词词典；`_analyze` 验证方式；IK 与引擎完全同版这条约束仍在 | 已经在用 ES 的团队别动；想省运维可先试 PG 全文检索 |
| PostgreSQL 16 | PG 15 / PG 17 | pgvector 版本要跟着对；`vector` 扩展要重新 `CREATE EXTENSION` | 16 是当前最稳的版本，别为了新而新 |
| Celery | RQ / Dramatiq / arq / BackgroundTasks | 任务定义、重试装饰器、监控全要重写；`asyncio.run()` 那层可能不需要 | 需要重试 + 并发控制就留 Celery；只要「发个任务别阻塞」，BackgroundTasks 够用 |
| Redis | KeyDB / Valkey / Memcached | Memcached 不能当 Celery broker，只能当缓存 | 单机小流量，Redis 就是最优解 |
| Embedding 模型 | `text-embedding-3-small` / BGE-M3 / 其他 1536 维模型 | `EMBEDDING_MODEL` + `base_url` + `api_key`；**维度必须仍是 1536**，否则改列 + 迁移 + 全量重建 | 换模型 = 全量重建索引，成本要提前算 |
| 大模型 | Qwen / GLM / 任何 OpenAI 兼容端点 | `LLM_BASE_URL` + `LLM_MODEL` + `api_key` | 一期只有一个模型，换成本最低 |
| qwen3.7-text-rerank | Cohere Rerank / BGE-reranker / LLM 重排 | `RerankProvider` 实现 + `RERANK_BASE_URL` / `RERANK_MODEL`（端点路径段随供应商变，别照抄 embedding 的 `compatible-mode`） | 换重排模型要重跑评测集，否则不知道变好还是变坏 |
| mammoth / markdownify / pdf-inspector | unstructured / pdfplumber / docx2txt | `DocumentParser` 实现；**输出必须仍是带结构的 Markdown**，否则切块策略全废 | 该项目已换成 `pdf-inspector==1.25.2`，OCR 走它自带管线，需要 PDFium + ONNX Runtime + PP-OCRv6 三个运行时资产 |
| Langfuse | LangSmith / Phoenix / 自建 OpenTelemetry | SDK 初始化 + span 埋点名 + UI 端口 | 要私有化就别选 SaaS |
| Vue 3 | Svelte / Solid / 原生 TypeScript | 只改视图层；接口路径、响应体、错误码全部不变 | 选团队熟的 |
| Element Plus | Naive UI / Ant Design Vue / PrimeVue | 组件标签名、表单校验接入方式 | 只影响视图层 |

换任何一项前先问三个问题：**① 有没有抽象接口挡着**（有就只改实现）；**② 有没有数据要迁移**（向量、索引、迁移历史）；**③ 有没有评测基线**（没有就是在盲改）。

## 环境变量

按能力分组，不是按章节。

```dotenv
# 基础
APP_ENV / DATABASE_URL / VECTOR_STORE
CHUNK_SIZE=512 / CHUNK_OVERLAP=50 / TOP_K=5（单位是 Qwen token）
QWEN_TOKENIZER_PATH（词表路径；先跑 scripts/fetch_qwen_vocab.py，缺失即拒绝启动）
MODEL_BASE_URL / MODEL_API_KEY / EMBEDDING_MODEL / EMBEDDING_DIMENSIONS=1536

# 身份、配额与控制面（第 7 步）
AUTH_ENABLED=false                # 关 = 内置开发身份（仍需带 DEV_API_KEY）；生产必须 true
DEV_API_KEY=dev-key / DEV_TENANT_ID=tenant_demo
RATE_LIMIT_ENABLED=false          # 关 = 限流与日配额整段 no-op；生产必须 true
REDIS_URL=redis://localhost:6379/2 / PLAN_CACHE_TTL_SECONDS=60
CONSOLE_SESSION_TTL_SECONDS=28800

# 索引
CELERY_BROKER_URL / CELERY_RESULT_BACKEND
DOCUMENT_STORAGE_PATH / DOCUMENT_MAX_SIZE_MB / TABLE_MAX_ROWS_PER_CHUNK
EMBEDDING_BATCH_SIZE=10

# OCR（第 3 步；容器里由镜像默认值接管，本机 Windows 只跑文字版 PDF）
OCR_MODE=auto / OCR_OFFLINE / OCR_MODEL_DIRECTORY
PDFIUM_LIB_PATH / ORT_DYLIB_PATH

# 检索（RRF k=60 写死，没有 HYBRID_FUSION / HYBRID_RRF_K 这类开关）
KEYWORD_SEARCH_PROVIDER / ELASTICSEARCH_URL / ELASTICSEARCH_INDEX
RETRIEVAL_MODE=hybrid / HYBRID_RECALL_TOP_K=20
LLM_PROVIDER / LLM_BASE_URL / LLM_MODEL=deepseek-flash / LLM_STRONG_MODEL=deepseek-v4-pro / LLM_TIMEOUT_SECONDS
DEEPSEEK_API_KEY / QWEN_API_KEY / ARK_API_KEY / OPENAI_API_KEY / ANTHROPIC_API_KEY / GEMINI_API_KEY（按厂商各填一个）
QUERY_REWRITE_ENABLED / QUERY_REWRITE_TIMEOUT_MS / SYNONYM_EXPANSION_ENABLED
RERANK_ENABLED（其余重排配置见下面「专用重排端点」一组）
# 结果形状偏好不是环境变量：折叠 / 表格展开由密钥配置提供（`key_policies.include_parent` /
# `expand_table_rows`），请求体里没有这两个字段，见 ADR-0010「第三次修订」

# 检索文本（第 3 步增补；默认关闭）
SECTION_CONTEXT_ENABLED / SECTION_CONTEXT_TIMEOUT_MS / SECTION_CONTEXT_MAX_INPUT_CHARS

# 观测（第 9 步）
# 六段耗时的去向：jsonl（默认，一次检索一行）/ langfuse / none；切它不改链路代码
TRACE_SINK=jsonl / TRACE_JSONL_DIR=logs/traces / TRACE_JSONL_RETENTION_DAYS=7
# 只有 TRACE_SINK=langfuse 时才用这三个；没有 LANGFUSE_ENABLED 这种开关
LANGFUSE_HOST / LANGFUSE_PUBLIC_KEY / LANGFUSE_SECRET_KEY

# 专用重排端点（第 10 步票 3 起；路径段与 embedding 不同）
# RERANK_ENABLED=true = 用专用端点重排；端点没配齐就是「明确不可用」（回空实现），不回落大模型
RERANK_BASE_URL=…/compatible-api/v1 / RERANK_MODEL=qwen3.7-text-rerank
RERANK_API_KEY（留空回落 MODEL_API_KEY） / RERANK_TIMEOUT_SECONDS=15
RERANK_MAX_CANDIDATES=20 / RERANK_CHUNK_MAX_CHARS=1024（候选另有一层硬上限 50）

# 受控 Research
QUERY_MAX_LENGTH=2000
```

三个关键开关：

| 变量 | `false` 时 | 用在哪 |
| --- | --- | --- |
| `AUTH_ENABLED`（第 7 步） | 落进内置开发身份（身份、配置、套餐由服务端配置合成），但仍要求带 `DEV_API_KEY` 那把占位 token | 本地开发很省事，**生产必须 true** |
| `RATE_LIMIT_ENABLED`（第 7 步） | 秒级限流与日配额整段是 no-op——所有租户无限额度 | 默认离线套件不需要 Redis；**生产必须 true** |
| `TRACE_SINK`（第 9 步） | `none`：六段耗时照样算，只是丢弃（不落文件、不发网络） | 唯一决定观测去向的开关；`trace_id` 与它无关，任何取值下都非空（由 `log_id` 确定性派生） |
