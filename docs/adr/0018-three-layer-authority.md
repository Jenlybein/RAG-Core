# 0018. 三层授权：请求管范围与问题、密钥配置管这套集成、套餐管这个租户

- 状态：已采纳
- 日期：2026-11-10
- 相关：父 spec #72「第 7 步」、ADR-0010「检索契约（含第三次修订）」、ADR-0017「套餐定义进库」、ADR-0003「API Key 即应用身份」、[`../../GLOSSARY.md`](../../GLOSSARY.md)「密钥配置」「档位」「自洽校验」「配额两级」

## 一句话

一次检索要回答三个互不重叠的问题，各有各的归属：

| 层 | 回答什么 | 归属 |
| --- | --- | --- |
| **请求** | 问什么、查哪些知识库 | 调用方，每次请求当场给出（`kb_ids` + `query`） |
| **密钥配置** | 这套集成能用多好、能用多少 | 租户管理员签发 Key 时定，随 Key 生效，调用方改不了 |
| **套餐** | 这个租户买得起多少 | 平台管理员授权给租户，进库、可改、可预览、可追责（ADR-0017） |

三层的关系是**包含**而非并列：配置只允许在套餐划出的范围内分配，请求只允许在配置圈定的范围内收窄。

## 决策

### 1. 请求不进质量参数，也不进授权参数

请求只有 `kb_ids` + `query`（ADR-0010「第三次修订」）。质量参数、结果形状、`tenant_id`、档位一律不在请求体里：请求体里出现它们就是 `20002`，不是「被忽略」。

理由与档位锁在 Key 上同源：请求里每多一个可以表达授权或质量的字段，服务端就要在热路径上多判一次「你填的这个算不算越权」；而**签名里有什么，模型就能填什么**，MCP 入口会把这条风险直接放大。

### 2. 配置时做自洽校验

一套密钥配置被创建时，校验三条**逐级包含**的关系：

```text
档位展开所需的能力  ⊆  配置自己的能力开关  ⊆  套餐允许的能力
```

- 第一段：选了 `quality` 档，就得开混合检索、重排、查询改写；`quality` 要重排而配置关了重排，这套配置从落地那一刻就是自相矛盾的。
- 第二段：配置开了重排而套餐不给重排，同样不成立——配置只能在套餐上限内分配，不能凭空造能力。
- 数值同理：配置的 QPS 与日配额不得超过套餐上限，授权知识库不得超过套餐的库数上限。

**不自洽的配置根本不允许被创建**，错误码用「参数 / 配置非法」那一档（`20015`）。这里刻意选在**创建时**失败：那是一瞬间的动作，有人盯着，改一下就行；换成运行时失败，就是客户的生产调用在半夜开始报错。

### 3. 运行时只复核套餐

请求进来的热路径上，**只重新判套餐这一层**：

- 命名档位是否仍在套餐的档位白名单内；
- 配置的能力开关是否仍被套餐允许；
- 单次检索的库数是否超过套餐上限。

配置层的自洽在创建时已经验过，运行时不重复验；请求层的范围（`kb_ids` 是否在白名单内）在六道关卡的第二道单独校验，不属于本节的复核。

这样分的收益很具体：**管理员把套餐调低，下一次调用就按新套餐判**，不必等缓存过期、不必重启、也不必让客户重新签发 Key。代价是热路径上多一次套餐读取，用按套餐 id 的短期缓存兜住（改完删缓存，不写缓存）。

### 4. 六道关卡，顺序不可换

```text
鉴权（解析 Key 与租户） → 白名单校验 → 套餐解析 → 档位展开与门禁 → 限流 → 日配额 → 业务执行 → 成功后才计数
```

后一关依赖前一关的产出，反过来就会出具体问题：先扣额度再判越权，攻击者拿一个不存在的 `kb_id` 连打就能把客户当天的额度打光——越权请求不该先花掉配额。计数只在成功后发生，所以被拒绝与失败的请求不扣额度；一次跨多库检索只计一次。

**同一份白名单也用于列库，这是本步补充的决定**：spec 只要求检索锁住范围，但白名单表达的是「这把 Key 能**看见**哪些库」。列库若把租户的全部库都列出来，调用方不必越权就能数清这个租户有几个库——那是把别人的清单当成公开信息。所以列库与检索判同一份范围，只是反应不同：检索撞到范围外拒绝（`20008`），列库把范围外的直接去掉。

### 5. 两种超限反应刻意不同

| 情形 | 反应 | 为什么 |
| --- | --- | --- |
| 命名档位越权（套餐不再允许这个档） | **拒绝**（`20013` 功能超出套餐） | 档位名是产品契约，降级沿用同名等于欺骗：客户以为还在跑 `quality`，实际少了重排 |
| `custom` 档的手动参数超套餐上限 | **裁剪 + 回显** | 上限要兜住，使用权不必剥夺；但裁剪**必须回显**——响应里说清实际生效了什么、裁掉了哪些字段，否则与欺骗无异 |

`custom` 的裁剪有**两个来源**：套餐上限（`mode` / `rerank` / `rewrite`）与平台红线（`top_k` 夹到 `MAX_TOP_K=50`）。后者刻意不来自套餐：套餐里没有「返回条数」这一列（条数不是成本旋钮，召回深度才是），但平台红线必须始终成立——否则一个 `custom` 档就能一次把整个库拖回来。来源不同，回显不分家：被裁的字段都进同一份 `clipped`。

## 被否决的两种做法

| 做法 | 为何不选 |
| --- | --- |
| 每请求把三层都重新判一遍 | 表面上「更安全」，实际是把配置层的矛盾推到运行时爆发：某天管理员调了套餐，一把挂着 `quality` 的 Key 就会在无人改动它的情况下**悄悄丢掉重排**，而档位名还叫 `quality`——名字成了谎。要么当场拒绝（客户的生产调用突然失败，且失败原因藏在别人的一次改动里），要么静默降级（更坏）。把矛盾关在创建时，才不会在运行时变成事故。 |
| 能力开关只对 `custom` 档生效，命名档位直接信预设 | 那就有了两套规则：命名档位看套餐、`custom` 看配置开关，每个判据都要问一句「这个档位算哪种」。两套规则最终会长出两套代码路径和两套测试，而它们的差异没有业务含义——档位只是「一次填好的一组参数」，不是另一种授权模型。 |

## 后果

- **配置是授权的载体，不是请求的备忘录**：同一套配置可以被多把 Key 引用（本期先按一对一用），改一次配置，所有引用它的 Key 同时变；删配置则引用它的 Key 级联失效。
- **建 Key 时的校验变重、运行时的校验变轻**：这是有意的换算——把复杂度放在低频动作上，把热路径留给限流与配额。
- **档位只能通过改配置来换**：想从 `balanced` 换到 `quality`，改这把 Key 的密钥配置即可，不必重新签发 Key，改完立刻生效。
- **套餐降级会在下一次调用生效**，不再有「缓存还没过期所以暂时还能用」的窗口；这也是「改完删缓存」这条规则必须封在写入口里的原因。
- 三层各自的术语与边界见 [`../../GLOSSARY.md`](../../GLOSSARY.md)：请求侧的「数据范围组」、配置侧的「密钥配置」「结果形状组」「档位」、校验侧的「自洽校验」、计量的「配额两级」。
