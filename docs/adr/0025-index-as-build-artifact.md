# 0025. 索引即构建产物：一次构建 = 一个不可变版本，检索 pin 生效版本

## 背景

这一章要补的地基，是四条互不相干的现象指向同一件事。

### 1. 重建没有知识库级的一致快照

现在的重建是「先删后写」，原子性只到**单篇文档**：一篇文档的切片在一次事务里删旧写新，一篇之内不会出现半新半旧。但整个知识库没有快照——500 篇文档重建到第 300 篇时，索引里同时躺着「前 300 篇的新切法」与「后 200 篇的旧切法」，而检索毫无察觉地照常返回。这个中间态可能持续几十分钟：长于一次评测，长于一次客户演示。

### 2. 事后答不出「那次检索查的是哪次构建」

归属索引（ADR-0021）记了谁、查了哪些库、命中哪些片、多慢、为什么空。唯独没记版本。`index_version` 这个字段其实一直存在（默认 `v1`），只是它从来没变过，所以没人需要在日志里记它。一旦版本会变，同一个 `kb_ids + query` 两次调用的结果差异就无从归因：切法变了？文档变了？还是召回抖了？

### 3. 引入「关系」之后，这件事从「结果不一致」变成「硬故障」

图谱的边指向具体的节（ADR-0027）。边若与切片不在同一个版本里，重建期间旧边会指向已经被删掉的目标节——不报错，只是静默地少一条命中；更糟的是指向一个**同 id、不同内容**的新节（`section_id = stable_hash(文档 id : 标题路径)`，重建后同名节会得到同一个 id，但正文可能已经变了）。断边不报错，是这类系统最难查的故障。

### 4. 评测要求「同一套题跑 v1 与 v2」

切法改动的真实影响只能靠同题对照。没有并列存在的两个版本，这件事做不了，只能靠「重建前后各跑一次」这种机器对不上的比较。

四条同一个根因：**索引不是「当前状态」，它是一次次构建的产物，而我们把产物当成了状态。**

## 决策一：一次构建 = 一个不可变版本

新增一张表，一行 = 一次构建：

| 字段 | 含义 |
| --- | --- |
| `id` | 版本行身份 |
| `tenant_id` / `kb_id` | 作用域（一个库一条版本序列） |
| `version` | 版本名（`v1`、`v2`…），同一库内唯一 |
| `status` | `building` / `ready` / `active` / `archived` / `failed` |
| `document_count` / `chunk_count` | 构建完成时的计数快照，用于校验 |
| `error_message` | `failed` 时的原因 |
| `created_at` / `activated_at` / `archived_at` | 生命周期时间点 |

```text
building ──▶ ready ──(单事务切换)──▶ active ──▶ archived
    │
    └──▶ failed（线上仍查旧的 active，error_message 记原因）
```

两条约束写死：

- **同一库同一时刻最多一个 `active`、最多一个 `building`**；
- **`ready` 的前置条件是四项计数相等**（知识库、切片、向量、关键词文档）。不相等不允许标记可用——构建中途失败的版本可能三项对得上、一项差几篇，那种版本一旦上线，表现是「有些文档搜不到」，而且不报错。

**「不可变」的意思是 `ready` 之后内容不再改动**：要改就再构建一次。这一条让版本可以当**引用目标**——边、归属索引、评测 run 都指向它，而不是指向「某个大概的时候」。

**知识库增加一列「当前生效索引版本」**：激活时和状态一起改（决策三），检索范围的构造从「常量 `v1`」改为读这一列（决策四）。**配对关系仍是映射形状**，绝不写成两个独立的集合条件。

## 决策二：构建期间线上照旧查旧版本

构建由后台任务逐文档执行，全程写入**目标版本**；active 仍是旧版本，检索完全不受影响。这要求切片、向量、关键词索引、关系边全部带 `index_version`。

**关键词索引按版本物理隔离，用一个别名指向 active**，不在同一个物理索引里双写两个版本。理由是可回滚：同一索引里双写，回滚只能删文档（ES 的删除是标记，不会立刻省空间）；而且任何一条漏带版本条件的查询都会同时捞到两个版本的行——那正是决策四要防的那种「不报错但配对错了」。

## 决策三：激活是单事务

激活要同时改三处：旧版本置 `archived`、新版本置 `active`、知识库的「当前生效版本」列更新。**三者同成同败**，在一个事务里。

分开做会留下「一半新一半旧」的中间态：知识库指向新版本、但新版本还没 `active` 时，检索拿到一个不存在的生效版本，结果是空——诚实空（`no_chunks_matched`）会把它包装成「本次没命中」，于是故障看起来像查询问题。

**失败只落 `failed`**，不触碰 active：`error_message` 记原因，线上完全不受影响。

## 决策四：检索 pin 生效版本，配对映射的形状不变

ADR-0010 §5 的映射形状一个字不改：`kb_id → version`，SQL 仍是 `(kb AND version) OR (kb AND version)`，仍不许写成两个独立 `IN`（那会拼出「A 库配 B 库版本」这种不存在的组合，且不报错）。

**改的是取值来源**：从「所有库都配 `v1` 这个常量」变成「每个库配它自己的生效版本」。唯一构造点仍是那个函数，`index_versions` 仍是一份构造出来的映射——这也是这条改动便宜的原因：范围形状早就按多版本写好了。

补一条边界：**版本不是请求参数**（ADR-0010 / ADR-0018）。调用方不能指定，也没有任何请求字段能影响它。能指定版本，就是能让检索回到旧切法——那等于绕过重建，还会让「不同调用方看到不同的事实」。

## 决策五：节的身份证不含版本

```text
section_id = stable_hash(文档 id : 标题路径)
```

- **必须带文档 id**：不带的话，两份文档都有「退款 > 流程」会算出同一个 id，跨文档一对就串。
- **必须不含版本**：重建后同一个节应得到同一个 id，否则「新旧构建逐节对比」做不了（而那正是这套东西最想要的能力之一）。
- **版本由引用方的数据范围表达**：边的键是 `(租户, 库, 版本, 文档 id, 节 id)`——版本在那一层，不在 id 里。

## 决策六（契约变更声明）：归属索引新增一列 `index_versions`

**这是一次契约变更，明写在这里，不是悄悄改表。**

ADR-0021 决策 2 把归属索引的列**一列列枚举**出来（身份、范围与规模、结果指针、结局、时间；实现那句注释写的是「留下的十列」）。要回答「这次检索查的是哪次构建」，这张表必须再加一列：

| 新增列 | 形状 | 为什么必须是这个形状 |
| --- | --- | --- |
| `index_versions` | JSONB，`{kb_id: version}` | 与检索范围同一个形状。**不能存成两个并列数组**（`kb_ids` 一个、`versions` 一个）：那正是 ADR-0010 §5 明令禁止的「两个独立集合」——`['kb-a','kb-b']` 配 `['v1','v2']` 拼得出「A 库配 B 库版本」这种不存在的组合，而且不报错 |

变更的边界只有这一条，ADR-0021 其余三条决定一条不动：

- **仍只存结构、不存原文**：版本名是结构（`v1`），不是「用户说了什么」。ADR-0021 决策 1 的红线不受影响。
- **仍是独立短事务、写失败只记 warning**：不因为多一列就把归属索引从旁路变成主链路。
- **仍是一次检索一行**，`trace_id` 仍是 `log_id` 的确定性派生。

**随之要改的两处，都是这一列的必然结果，一并记在这儿**：实现里 `app/models/retrieval_trace.py` 的模块注释与 `docs/step9-acceptance.md` 验收表里的「十列」，要改成十一列。**本文的票（#139）只落决策**——这两处与建表迁移一起随 D 票（#140）改，不在本文范围里动代码。

**为什么不把版本塞进 `trace_id` 或文件名**：`trace_id` 是 `log_id` 的确定性派生，动它就是动「一次检索一行」的身份规则（ADR-0021 决策 2 第三条性质）；塞进观测栈则答不了「按库统计某次构建的命中率」——观测栈是旁路，可以丢，归属索引不是。

## 决策七：迁移分两步，中间必须回填

```text
① 加列（切片版本、知识库生效版本、关系边版本）
② 回填：把历史数据写进一个 v1 版本行，切片按库回填版本
③ 核对四项计数相等
④ 才允许启用版本过滤
```

**顺序颠倒等于历史数据静默变空**：先启用过滤、后回填的话，历史切片的版本列是空值，`(kb AND version)` 一条都匹配不上——不报错，只是搜不到，而且看起来像「这个库没内容」。回填脚本必须能识别「尚未回填」的状态（守卫用例），否则运维没有任何信号知道自己漏了一步。

## 被否掉的方案

| 方案 | 为何不选 |
| --- | --- |
| **不做版本生命周期**，继续单版本、重建期间接受混排 | 三件事同时失去：不能回滚（切法出问题只能再建一次，而新一次同样有中间态）、不能同题对照 v1/v2、事后答不出出处。图谱一进来还多一件：**跨版本断边不报错**——那时这个方案不是「少一个功能」，是「多一类静默故障」，而且是最难查的那类。 |
| **改成「边随切片同事务重建」**（每篇文档重建时把它相关的边一起重建） | 原子性只到单篇，而关系是**跨文档**的：整库重建到第 300 篇时，A 文档的新边指向 B 文档的旧节 id（B 还没重建），跨文档边必然断；等 B 重建完，它又会改写指向 A 的边。一篇篇重建的中间态不是「部分正确」，是「每条边都可能是错的」。让「边与切片在同一版本内配对」成为唯一解——那需要版本，不需要更细的事务。 |
| **只加一个 active 版本列**（库上加 `active_version`，不建版本表） | 这一列只能指向「某个存在的东西」，而那个东西就是版本表。省掉表，就同时省掉了：`building` / `failed` / `archived` 三个状态（无法回答「上次重建为什么失败」）、计数快照（无法做 `ready` 的前置校验）、激活时间（无法回答「这版什么时候上的」）、历史版本清单（无法做 v1/v2 对照，也列不出「还能回到哪一版」）。剩下一个只能前进、不能回滚的指针。 |

## 影响范围

- **`/rag/retrieve` 的请求与响应逐字节不变**：版本不进响应。要查「这次用的是哪一版」，读归属索引的 `index_versions`（按 `log_id` / `trace_id`）；要看细节，去观测栈按 `trace_id` 查。评测者要的「这次用的哪次构建」由此可答，不必扩响应契约。
- **新表 + 迁移 + 回填脚本**：本章最危险的地方是顺序（决策七）。测试按「迁移双向干净」「回填未做时能识别」「四项计数不等不允许 ready」写。
- **一次构建的产物变多**：切片、向量、关键词索引、关系边都要带版本；存储按版本增长，保留几个版本是运维问题（见翻案条件）。
- **构建变慢是有意的**：不再原地覆盖，而是整库重建到新版本。代价是存储与时间，收益是零抖动与可回滚。
- **评测多一种跑法**：同一套题 pin 不同版本，得到逐节可比的两次结果——这是这一轮唯一能证明「切法改动值不值」的手段。
- **`ready` 的判定变成运维可见的一步**：四项计数相等才允许上线，这是「不把半成品推上线」的唯一硬闸门。

## 翻案条件

- **版本数增长到存储不可控**（例如每库保留 10 个版本后磁盘告警）：出归档清理策略（保留最近 N 个 + 最近一次被引用的），但**不取消版本**——清理是删除 `archived` 的旧版本，不是回到原地覆盖。
- **出现「必须原地小改一批文档、不重建整库」的强需求**：先讨论「增量构建产出一个新版本」，不要退回原地覆盖；原地覆盖会把决策二、三、四三处问题一起重新打开。
- **`ready` 的四项计数在某种存储上无法一致**（例如关键词索引只有最终一致）：改成「计数在容差内 + 显式确认」并在这里登记，不允许静默放宽成「不校验」。

## 自检

1. **为什么不能只加一个 active 版本列？** —— 状态、计数快照、失败原因、历史清单全在版本表里；没有它，只剩一个不能回滚的指针。
2. **归属索引改了什么、没改什么？** —— 多一列 `index_versions`（映射形状）；仍只存结构、仍一次检索一行、仍独立短事务。
3. **为什么 `section_id` 里不能有版本？** —— 重建后同名节必须同 id，否则逐节对比做不了。
4. **迁移的坑在哪？** —— 顺序：加列 → 回填 → 核对 → 才启用过滤。颠倒是静默变空。
