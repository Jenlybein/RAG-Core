# 0035. 容量上限与第四本账：两种 token 口径、四本账与错误码分码

- 状态：已采纳（票 #211；**本文只落决策**，实现随 #219–#223 落地）
- 日期：2026-11-26
- 相关：父 spec #209「排队状态、构建按篇化与套餐容量上限改造」、票 #211（本文）、票 #210（[ADR-0034](0034-queue-state-and-build-convergence.md)「排队状态、构建收敛与自愈」）、[ADR-0033](0033-usage-ledger-and-windows.md)（三本账、日界口径与「先判后记账」）、[ADR-0025](0025-index-as-build-artifact.md)（构建即产物）、[ADR-0031](0031-document-version-management.md)（正文的真值在版本行）、[ADR-0017](0017-plans-in-database.md)（套餐定义进库、改前可预览）、`GLOSSARY.md`「单库容量上限」「每日切块额度」「账（meter）」「检索文本」

## 背景

改造前，套餐只回答「数量」，不回答「体量」与「成本」：

- **体量**：限制的是「能建几个库」「每库几篇文档」。一篇五万 token 的文档和一篇两百字的文档都算一篇。于是「库里装得下多少」这件事，套餐从来说不清，用户也从来算不出。
- **成本**：没有任何「一天能烧多少切块」的额度。一次误操作的重建、一次恶意重放，可以把 embedding 余额一次烧光，而套餐在这一维上完全沉默。
- **口径**：仓库里一个 token 数字都没有（明细表明确写着「不存 token / 成本」），所以「体量」和「成本」都无从计量——不先定口径，加多少列都是猜。

本文只做三件事：**定两个 token 口径**、**定四本账与三道容量门禁**、**定报什么码**。具体的落地切片分在 #219（分码）、#220（单库容量）、#222（日额度）、#223（账可见）、#221（容量可见）。

## 决策一：两种 token 口径，不许混用

| 口径 | 量什么 | 服务谁 | 什么时候算 | 谁看得见 |
| --- | --- | --- | --- | --- |
| **正文 token** | 整篇文档解析后的正文（与版本行正文同源） | **单库容量**（`max_tokens_per_kb`） | 索引那一笔事务里，与切片、状态一起写进文档行 | 文档列表上「这篇占多少」、库上「已用 / 上限」 |
| **检索文本 token** | 真正发给嵌入模型的那份文本（文档名 + 标题路径 + 正文 + 可选的节说明 / 型号前缀） | **每日切块额度**（`chunk_daily_tokens`） | 每次实际调用嵌入模型时累加 | 用量页第四栏、管理员下钻 |

**为什么是两个口径，而不是一个**：

- **检索文本比正文多 10–20%**。它多出的是标题路径与节说明、型号这些前缀——每片一份，片越多前缀越多。用正文 token 去算额度，会**系统性低估**，而这个低估恰好出现在「花钱最多的那次操作」（整库重建）上。账单认的是检索文本，所以额度必须也认检索文本。
- **两者语义不同**。容量回答「这个库能装多少东西」，它应当**与切块参数无关**：管理员把切块调细，库的容量不该跟着变。额度回答「今天能烧多少」，它必须随切块参数变（切得越细，前缀越多，烧得越多）。一个口径背不动两件事。
- **混用会让用户的数字互相打架**。用户看到「已用 2.3 万 / 3 万」（正文口径），又看到「今日已用 2.7 万」（检索文本口径），两个数都叫「已用」却对不上——这不是四舍五入，是分母不同。**同名的两个数必须同源**，否则用户永远算不出还能装多少。
- **混用还会让一次拼装改动引发全库「已用」跳变**。改检索文本的拼装方式（加一个前缀）会让检索文本口径的数整体上浮，但库里装的东西一个字没变。分开之后，前者只影响额度，后者不受影响。

**一处刻意的近似**：单库容量的判据里，「这一篇的正文 token」在解析之前不知道，所以入口预检只能判「库已经满了」这一种情况；真正的「这一篇装不装得下」在解析之后判（决策四）。额度同理（决策五）。两处都是**有意的两阶段**，不是漏判。

## 决策二：两个数字都是本地词表口径，不是 provider 账单口径

两个数都用**项目自带的本地词表**数出来（与切块窗口同一套口径，[ADR-0015](0015-token-window-and-vocab.md)）。它们服务**判定**（拦不拦、让不让），不服务**对账**（这一单到底付了多少钱）。

**为什么不冒充账单**：本地词表与 provider 的分词器不是同一个东西，同一个字符串在两边可能差几个 token；provider 还可能按别的方式计费（按请求、按图、按缓存命中打折）。本地数出来的数**是确定的、可复现的、不依赖任何外部服务的**——这是它作为门禁判据的全部价值；一旦把它写进账单，那份确定性就变成了「一个看起来像事实的估算」。

**翻案条件（提前写死）**：provider 开始回报真实计量之后，**加列，不改口径**——用专门的一组列存 provider 的读数，本地口径继续服务判定。这与 [ADR-0033](0033-usage-ledger-and-windows.md) 翻案条件里那条「加列而不是改口径」是同一条纪律：**判据与账单是两件事，可以并列，不能互相顶替**。

## 决策三：四本账并列，第四本只有租户级

| 本 | 单位 | 计量对象 | 层级 | 被拒时 |
| --- | --- | --- | --- | --- |
| 检索账 | 次数 | 内核调用（分解检索一次算 N） | Key 级 + 租户级 | 不记账 |
| 重排账 | 次数 | 重排实际发生的次数 | Key 级 + 租户级 | 不记账 |
| 大模型账 | 次数 | 真实的模型调用次数 | Key 级 + 租户级 | 不记账 |
| **切块账（新增）** | **token** | 实际发给嵌入模型的检索文本 token | **只有租户级** | **不记账** |

**第四本账为什么只有租户级**：前三本的两级结构都假定「一次调用总有一个发起的 Key」（「Key 级卡住单个外部应用，租户级聚合不超过套餐上限」，`GLOSSARY.md`「配额两级」）。**索引任务里没有这个主语**——它是租户级的后台工作，由上传、重建、构建派活触发，不经过任何一把 Key 的凭证判定，Worker 里根本没有密钥身份的概念。给它硬造一个 Key 级，只能是「记在随便哪把 Key 上」（错的归属）或「记在一把虚拟的 Key 上」（一个新的真相）。

所以第四本账在数据结构上就是**租户级**：Key 级恒不参与判定，也不出现在响应里。这不是简化，是**这一本账本来就只有一层主语**。

**记账口径沿用既有硬约束**（[ADR-0018](0018-three-layer-authority.md) / [ADR-0033](0033-usage-ledger-and-windows.md)）：**先判后记账，被拒不记账**；记账发生在那一笔事务**提交成功之后**（另起短事务）。理由不变——记账先于执行，会在执行失败时留下一次没发生的消耗；记账在事务里，会把旁路的账变成主链路的成败条件。

**第四本账不进「调用次数 / 成功率 / 耗时」**：那三个读数的分母是「进了门的请求」，而切块是**后台作业**，没有请求、没有业务码、没有延迟分位。它进用量页的**独立一栏**（一张卡），并用一个专门的端点标记与前三本的行区分开——**混进去会让成功率凭空掉一截**，而且掉得毫无道理。用量事件的 token 列单位就是 token，不写别的。

## 决策四：单库容量判据排除本篇，两处检查，存量只禁新增

判据一条：

> **其他文档的正文 token 之和 + 本篇的正文 token ≤ 单库容量上限。**

**排除本篇**是为了让**重建不自锁**：一篇已经顶到上限的文档去重建，如果把自己也算进「已用」，它会因为「库已满」被拒——而它其实一点空间都不多占。

两处检查，各自解决一类：

| 检查点 | 时机 | 判什么 | 结果 |
| --- | --- | --- | --- |
| **入口预检** | 落行之前 | 库是否**已经**满了（不看本篇，因为还不知道） | 当场拒绝，回「单库 token 超上限」，带已用 / 上限 / 套餐 |
| **解析后硬拦** | 解析完、调嵌入之前 | 其他文档 + 本篇是否超限 | 这一篇置**失败**，固定中文文案带「本篇 X / 已用 Y / 上限 Z」与处置建议；**不写切片、不花嵌入** |

**为什么必须两处**：只做入口预检，用户要为「装不下」等上两分钟才知道（而且是在花掉嵌入之后）；只做解析后硬拦，用户会觉得「明明满了为什么还让我传」。入口预检是体验，解析后硬拦是保证——**两个都要，且文案不同**（一个是「库满了」，一个是「这一篇太大了」）。

**存量超限只禁新增**：已经超限的库**照常检索**，只是不能再往里加东西，也不能把它撑得更大（重建一篇已经在库里的文档不算新增，见「排除本篇」）。理由：容量上限是**准入**规则，不是**清算**规则。让存量库停止检索，等于用一次配置改动烧掉客户已经在用的数据；而「只禁新增」让超限变成一件**可见、可处置、不破坏**的事（界面上置红、提示「删掉旧文档就能继续」）。

**文档行新增一列正文 token 数**，在索引那一笔事务里与切片、状态一起写（与「一篇文档一次事务」的既有形状一致，不引入第二处提交点）。存量回填走一次性脚本：优先读版本行正文、文档行兜底，**默认 dry-run 先出报表**——上线前把「已经超过新上限的租户名单」报出来，这是回填唯一的实际用途。

## 决策五：日额度是绝对上限，不是容量倍数

**日额度以检索文本 token 计**，量的是真正发给嵌入模型的那份文本，门禁复用现有的日桶实现（同一个窗口、同一个口径、同一次重置）。

四条口径：

- **绝对上限**：它与单库容量**没有倍数关系**，也不由容量推出来。两个数字各自独立可调：管理员完全可以给一个大档套餐很大的库、很小的日额度。
- **入口预检不预扣**：解析前不知道会花多少 token，所以预检只判「今天是不是已经用尽」。**这个近似是刻意的**——预扣一个猜出来的数会在「猜高了」时误拒，而日均消耗的账面误差比误拒便宜。
- **解析后硬拦**：本次会超限时，这一篇置失败，文案写明重置时间（**UTC 零点 / 本地 08:00**，与日界口径同一个事实，[ADR-0033](0033-usage-ledger-and-windows.md) 决策 2）。
- **先把话说开**：日额度是上限而不是保险丝。**大档套餐单日做不完一次整租户的全量重建**——一个 pro 档租户的库容量合计是千万级 token，而日额度是百万级；重建整租户需要好几天或提额。**这是接受的产品取舍**：一个「能把整租户一天重建完」的额度，等于没有额度，因为它恰好等于「一次误操作就能烧光余额」的那个量。

| 口径 | 谁重置 | 在哪判 |
| --- | --- | --- |
| 日额度 | UTC 零点（本地 08:00） | 入口预检 + 解析后硬拦 |

**为什么不能靠「额度不足就整库不跑」**：一次整库重建里，前几百篇成功、后面因为额度耗尽失败——这正是本决策要的样子（已建的算数、剩下的明天或提额后继续，见 [ADR-0034](0034-queue-state-and-build-convergence.md) 的续建）。若做成「额度不足就整库不跑」，结果既没省下多少钱，也一件事没做成。

## 决策六：四档默认值

套餐新增两列。四档的**种子值**如下（`plans` 表里的行才是真相，代码里的常量只是**首次播种**用的种子——只在列为空时写，绝不覆盖运营改过的值）：

| 档 | 库数 `max_kb` | 单库容量上限 `max_tokens_per_kb` | 每日切块额度 `chunk_daily_tokens` |
| --- | --- | --- | --- |
| free 免费版 | 3 | 30,000 | 300,000 |
| plus 进阶版 | 10 | 300,000 | 4,000,000 |
| pro 专业版 | 50 | 2,000,000 | 9,000,000 |
| max 旗舰版 | 100 | 5,000,000 | 15,000,000 |

四条读法（为什么是这些数）：

- **容量按「一篇一千 token 量级」推**：free 的 3 万约等于 30 篇千 token 文档，正好与它的 `max_documents_per_kb=30` 对齐（两条上限同时卡住，谁先到算谁）；plus 的 30 万约 300 篇；pro 的 200 万约 2,000 篇、max 的 500 万约 5,000 篇。**pro / max 的 token 上限会比文档数上限更早生效**——这是刻意的成本封顶，不是算错。
- **日额度与整租户「全量容量」的倍数逐档下降**：free ≈ 3.3 次全量重建、plus ≈ 1.3 次、pro ≈ 0.09 次、max ≈ 0.03 次。换成「单个装满的库能全量重建几次」则分别是 10 / 13 / 4.5 / 3 次。**这正是决策五那条取舍的量化形状**：档位越大，越不能靠一天重建完整个租户。
- **两个数字是两条独立的旋钮**，所以表里不成整齐的倍数关系。**不要把它们理解成一条公式的两个参数**。
- **成本量级要一并看**：按国内主流嵌入模型约 ¥0.5 / 百万 token 估，日额度打满的成本约为 free ¥0.15、plus ¥2、pro ¥4.5、max ¥7.5 一天。若定价与这个量级不符，调表即可，其余段落无需动。
- **这些是业务参数，不是技术参数**。改它们不需要改代码、不需要发版，也不需要迁移（[ADR-0017](0017-plans-in-database.md)：套餐可改、改前可预览、每次改动留档）。

## 决策七：错误码分码

新增四个业务码，与既有「配额用尽」分开：

| 码 | 枚举名 | 含义 | 典型触发 | 调用方该做什么 |
| --- | --- | --- | --- | --- |
| `20034` | KB_COUNT_QUOTA_EXCEEDED | 库数超套餐 | 建库时该租户已有库数已达 `max_kb` | **删库**或提额（删是立刻可行的，提额要找运营） |
| `20035` | KB_DOCUMENT_QUOTA_EXCEEDED | 单库文档数超套餐 | 往已满的一库上传（已达 `max_documents_per_kb`） | **删该库里的旧文档**或提额 |
| `20036` | KB_TOKEN_QUOTA_EXCEEDED | 单库 token 超上限 | 入口预检发现库已满；解析后发现「其他文档 + 本篇」超限 | **删旧文档**或提额；手上这篇太大就拆开 |
| `20037` | CHUNK_DAILY_QUOTA_EXCEEDED | 每日切块额度用尽 | 今日已消耗的检索文本 token 达 `chunk_daily_tokens` | **等重置**（UTC 零点 / 本地 08:00）或提额 |

**`20014` 的语义收窄**：它从「库数 / 文档数 / 并发数 / 日额度」收窄为**只管「按天调用额度（检索 / 重排 / 大模型）」**。这是**有意的破坏性变更**：老客户端如果按 `20014` 判「库满了」，从此会漏判——它需要改判 `20034` / `20035`。这条变更同时写进错误码全表与变更说明，不许悄悄改。

**每一码都要带三种东西**：机器可读的原因、`已用 / 上限 / 套餐` 三个数字、以及一句**人话**（不是英文片段）。`20034` / `20035` / `20036` 的处置是「删东西或提额」，`20037` 的处置是「等重置或提额」——**这两种处置完全不同，文案不许共用**。旧实现那句「等额度重置，或去套餐 / 密钥配置里调整上限」在这两种情形下都是错话：它把「删旧文档就能继续」说成「等重置」，又把「要运营改套餐」说成「密钥配置里调整」。

**前端必须登记**：错误码文案表里没有登记的码会退化成「业务码 N」，等于把「库满了」这句话换成了一串数字。

## 备选方案

| 方案 | 为何不选 |
| --- | --- |
| **只用一个 token 口径（正文）** | 会系统性低估 embedding 消耗 10–20%，而且低估发生在最贵的一次操作上；同时把「改切块参数」变成「改容量」，两个旋钮被焊在一起。 |
| **用 provider 账单口径当门禁** | 它不是本地可复现的：门禁要能离线判、要能在没有网络时判，也要能在 provider 抖的时候照常判。门禁依赖外部服务，等于给写路径加一个外部失败源。 |
| **切块额度做成 Key 级 + 租户级两级** | 索引任务里没有 Key 这个主语（决策三）。硬造一层等于制造一个假的归属，还会让「同一租户多把 Key 分摊」变成一个没人能解释的数。 |
| **容量算上本篇（不排除自己）** | 一篇顶到上限的文档永远重建不了——「库满了」会把「它自己」也拒掉，而这正是用户最需要重建的时候。 |
| **只做解析后硬拦** | 用户为「装不下」白等两分钟并烧掉嵌入；体验与成本双输。 |
| **只做入口预检** | 预检时还不知道这一篇多大，于是「一篇五万 token 的文档塞进剩余两万 token 的库」会一路跑到失败点才发现，而且失败时可能已经写了一半。 |
| **让日额度 ≈ 容量倍数**（比如「一天能重建一次整租户」） | 那个额度等于「一次误操作烧光余额」的量级，即没有额度。取舍见决策五。 |
| **把切块账也混进「调用次数 / 成功率」** | 后台作业没有请求、没有业务码、没有延迟分位；混进去会让成功率凭空掉一截，而且掉得没有原因可解释。 |

## 被这条决策翻案的既有结论

**三处既有结论被本改造翻案**，都在这里登记边界，不留给读者自己猜：

1. **用量账 ADR 里「为什么不存 token / 成本」的结论需要修订**。原文说的是「仓库里没有任何 provider 侧的计量，硬算只能靠估算，而估算出来的成本会被人当成事实去汇报。等有了真实计量再加列」。
   **修订**：现在**有了**一个确定性的本地词表口径，所以「存 token」这件事本身不再是估算。但它**只用于容量与额度**（拦不拦、让不让），**不冒充账单**（不写进成本、不做对外结算）。原文那句「等有了真实计量再加列」仍然成立且继续有效：真实计量来了就**加列**（决策二），本地口径不动。**翻案的边界就在这一句：可以存数，不可以把这个数叫成本。**
2. **静态配额模块里「并发处理数是唯一一条『不超自己的上限也会伤害别人』的配额，因此必须存在」的论证作废**。这条配额已被删除（[ADR-0034](0034-queue-state-and-build-convergence.md) 决策八：它量的东西本身是假的，且入口拒绝不是对「拖慢别人」的处置）。取代它的是一组**容量型**上限——库数、单库文档数、单库 token——它们都只防「这个租户自己装得太多」，**不控制并发、不保护别人**。保护别人的手段是构建专用队列；公平调度明确没做，代价记在 ADR-0034 里。
3. **技术栈文档里「分批粒度与重试粒度一致（一批失败只重试这一批）」的声称不存在**。分批是真的（嵌入接口有单批上限），**批级重试不是**：一次批调用失败会让整篇文档的索引失败，失败粒度是**整篇文档**。本文只要求**把措辞改成事实**并把「批级重试」列为未实现项——**不承诺实现它**，也不借这条措辞去描述任何新行为。改为按篇重试、还是按批重试，是后续独立决策。

## 影响范围

- **套餐**：加两列并按四档种子播种（只在空值上写）；两列都进套餐编辑页与影响面预览；删「并发处理名额」列（取值已留档在 [ADR-0034](0034-queue-state-and-build-convergence.md)）。
- **文档**：加「正文 token 数」列，在索引那一笔事务里写；附一次性回填脚本（默认 dry-run，先出报表）。
- **用量**：用量事件表与日汇总各加一列（单位 token）；第四本账进用量页一栏与一个计数端点；「调用次数 / 成功率 / 耗时分位」三处必须把它排除。
- **门禁**：三道容量门禁（库数 / 单库文档数 / 单库 token）各有自己的码；日额度两道（入口预检 + 解析后硬拦）。
- **错误码**：`20034`–`20037` 新增，`20014` 收窄（破坏性变更，需在变更说明里明写）；前端文案表同步登记五个码（含 `20014` 的新说法）。
- **一处口径不写进响应契约之外的地方**：这两个 token 数**不参与检索**，不改变 `/rag/retrieve` 的任何请求或响应字段——它们只服务写入侧的门禁与展示。
- **实现时以票面为准**：本文与代码现状若有出入（例如某个写入口当前并未经过容量门禁），按父 spec #209 与各票的描述实现，并在实现该票时回来登记。

## 翻案条件

- **provider 回报真实 token 计量**：加一组列存 provider 读数（不改本地口径），并在账单/成本语境里改用那一组；本地口径继续服务门禁——因为它在断网、provider 抖动、离线测试时都要能判。
- **本地词表与 provider 分词器的偏差被证实大到会影响判定**（例如某类文档系统性差三成以上，导致额度判定失真）：先量化，再考虑换词表或按文档类型加系数；**不要直接改成 provider 口径**，那会把门禁绑到外部服务上。
- **单库容量上限在实践中总是被文档数上限先撞到**（读数：绝大多数租户从未接近 token 上限就到文档数上限）：那时要考虑的是**抬高文档数上限，或重构这两条上限的关系**，而不是删掉 token 上限——它存在的理由正是「一篇五万 token 的文档不该和两百字的一样算一篇」，那个理由不会因为撞得少就消失。
- **日额度的两阶段检查出现「预检放过、硬拦全拒」的常态化**（读数：硬拦率显著高于成功率）：说明预检的粒度不够，那时才考虑「按篇大小预扣」或「按库平均大小预估预扣」，并同步改写决策五里的那条「刻意的近似」。
- **切块账需要 Key 级**：只有当索引任务有一天真的带上「哪把 Key 发起」这个身份时才可能；那是一个身份模型变更（不是加一层配额），必须先改 ADR 再改账。

## 自检

1. **为什么不能只留一个 token 口径？** —— 检索文本比正文多 10–20%（账单认它），而且容量应当与切块参数无关、额度必须随切块参数变。一个口径背不动两件事。
2. **这两个数是账单吗？** —— 不是。本地词表口径，只判让不让；provider 回真实计量后**加列**，不改口径。
3. **第四本账为什么没有 Key 级？** —— 索引任务里没有密钥身份这个主语，硬造一层只会得到一个没人能解释的归属。
4. **重建一篇已经顶到上限的文档会被拒吗？** —— 不会。判据排除本篇，为的就是「重建不自锁」。
5. **日额度为什么故意做成「大档一天做不完一次全量重建」？** —— 能一天重建完整租户的额度等于没有额度；这是接受的取舍，已写进决策五。
6. **`20014` 改了什么？** —— 从「库数 / 文档数 / 并发数 / 日额度」收窄为「按天调用额度」。这是有意的破坏性变更，老客户端按旧码判「库满」会漏判。

## 实现补充（第 17 步 #222 落地时）：索引行的四条「不成立」列

第四本账的明细行落在 `usage_events` 上，而那张表是按**检索请求**的形状设计的：`top_k`（这次
要了几条）、`latency_ms`（这次花了多少毫秒）、`kb_ids` / `chunk_ids`（参与了哪些库与切片）
都是 NOT NULL。索引不是一次请求，这四个量对它**都不成立**。

落地时踩到的是「离线套件看不见 NOT NULL」：`tests/fake_db.py` 不模拟约束，测试全绿；第一次
真跑索引就炸 `NotNullViolation: null value in column "top_k"`，修完又炸 `latency_ms`。

约定：**这四个列在索引行上一律填「零值」，而不是编一个像样的数**——`top_k=0`、
`latency_ms=0`、两个 jsonb 是 `[]`。零值在这里的含义是「这个量在这一行上不存在」，而编一个
`top_k=5` 会被后来的读者当成「索引按 top_k=5 召回了 5 条」。真正该关心耗时的地方是构建行的
`converge_deadline`，不是这里。

代价写清：`usage_events` 的 `latency_ms` 分位统计只要排除掉 `endpoint='index'` 的行就仍然
成立（`console_usage._denies_index` 两表共用同一份判据，见其注释）。
