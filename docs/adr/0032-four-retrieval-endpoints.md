# 0032. 检索拆成四条端点：加工方式由端点表达，授权与计量分离，后端不再有档位

- 状态：已接受（2026-11-16，第 13 步 · spec #184）
- 修订：[ADR-0010](0010-retrieval-contract.md)（请求体/回显）、[ADR-0018](0018-three-layer-authority.md)（三层授权）、[ADR-0026](0026-research-citation-blocks.md) 与 [ADR-0029](0029-scope-down-to-controlled-research.md)（Research 的词表）——这四份的相关段落自本文起失效，见各自文末「第 13 步修订」
- 相关：父 spec #184、票 #185–#195、`GLOSSARY.md`「检索」「授权位」「计量账」「档位」「模型角色」「降级原因」「停止原因」

## 背景

`/rag/retrieve` 这一条端点同时承担了三种互不相干的语义：原句直查、改写后查、以及（通过 Research 端点）分解后查。前两种藏在调用方看不见的密钥配置里——同一个 `query`、同一个库，两把 Key 跑出两种行为，调用方既无法按次选择，也看不出这次会花几次模型调用。

档位系统（`speed/balanced/quality/custom`）同时充当三个角色：质量预设、能力上限的载体、授权口径。`hybrid/rerank` 是质量维度，`query_rewrite/research` 是加工方式，它们被塞进同一组能力开关；想关掉改写要同时理解档位字段、套餐列、配置列三处。

配额只有「检索」和「Research」两本账，回答不了「一次改写、一次分解、一次重排各自花了什么」。语义评测是平台自检工具，却挂在租户面板里。

## 决策

### 1. 四条数据面端点

`POST /rag/retrieve`（原句直查，零模型调用）、`/rag/rewrite`（一次改写，原句与改写句并池取优）、`/rag/decompose`（一次分解 + N 次内核 + 合并）、`/rag/research`（受控 Research）。请求体一律 `kb_ids + query`（ADR-0010 第三修不变）；MCP 四把同形工具。

四条端点共用同一份检索内核（ADR-0028），组合根 `rag_service.retrieve` 收一个 `query_variant` 参数分叉 direct/rewrite；decompose 走独立组合根，复用同份内核装配。**加工方式由端点表达**——这是否决「请求里加 `decompose: true` 开关」的核心理由：那会凿开「请求体只有两字段」的墙。

### 2. 授权与计量分离

授权回答「能不能用」：五个布尔位 `retrieve/rewrite/decompose/research/rerank`，套餐与密钥配置两层都给才放行，否则 `20013`。计量回答「用了多少」：三本账 `retrieve`（内核调用次数，decompose 记 N）/ `rerank`（重排次数）/ `llm`（实际大模型调用次数），每本 Key + 租户两级 × QPS + 日额三格。位为假 → `20013`；额度用尽 → `20014`。新账四格全 0 = 未配额度 → no-op（旧 Key 升级上来不会被误拒）。

否决「按能力开户」（一次 decompose 扣一份虚构单位）：成本表里没有「一次 decompose」这种真实动作。

### 3. 后端取消档位

`profile_chain_of` 直读配置里三项参数 `mode/top_k/rerank`——物理上已落为 `key_policies` 的三列（迁移 `b4f6c1d90e27` 从 `custom_options` 搬迁而来），缺键逐键回落部署缺省；`rerank` 缺键 = 不要。`profile_presets` 表、`profile` / `allowed_profiles` / `custom_options` 列与全部档位模块已物理删除；旧缓存里的 `profile` 名不参与任何判定。所有超限一视同仁：裁剪 + 回显，没有「命名档位越权就拒绝」这一档。档位名退化成前端预设按钮与文档评测里的参数组合别名。

四档套餐（`free / plus / pro / max`，`standard` 改名 `plus`、新增 `max`，各带 `max_top_k` 5/10/15/20）由迁移 `d7e3b8a1f642` 播种，仍是**可编辑的授权数据**。

### 4. 分解检索的合并口径

复用 Research 的 Planner 收敛规则（要点 ≤5、首轮查询 ≤3，分解独立于材料——ADR-0029 决策三），子查询不二次改写。合并按交付单元身份去重，**每条子问题保底 1 条**，剩余名额按子问题顺序轮转填满 `top_k`。每条结果带 `matched_queries`；跨子问题的 `score` 不可比，不许当阈值。

否决「并池取优」（改写用的口径）：改写是同一问题的两种说法，分解是几个不同问题——一个池会让 A 子问题的高分命中挤掉 B 子问题的唯一命中，而「别漏」正是分解存在的理由。

### 5. 单一模型角色与失败即失败

平台不再分 `fast/strong`，只有一个 `default`（`LLM_MODEL`）。改写、分解、Research 四阶段的模型调用失败一律整单 `50003`（客户重试），不再「失败即降级」。Research 的 `stop_reason` 从七条收敛到六条（退役 `degraded`），强模型兜底字段与两条固定串删除，`coverage.unknown` 只剩「补证捞到材料但不回头复判」一种含义。

### 6. 降级与回显词表

降级原因四条：`vector search failed` / `keyword search failed` / `rerank failed` / `rerank quota exhausted`。`query rewrite failed` 退役（词条留作解释历史归属索引行）。`tenant_policy` 回显改报参数本身（plan/mode/top_k/rerank/kb_count/clipped），删 `requested_profile` 与 `rewrite`。黄金哈希据此重采——这是有意的契约变更，检索内容那条红线一条没放宽。

### 7. 语义评测搬进管理员后台

它是平台自检工具（跑固定语料、LLM 裁判），挂在 `/admin/evaluation`，守卫从租户改管理员，跑批身份固定为语料所属租户，归属过滤去掉（管理员看全部）。

## 被否掉的方案

| 方案 | 为何不选 |
| --- | --- |
| 请求里加 `decompose`/`rewrite` 布尔开关 | 凿开「请求体只有 kb_ids + query」的墙；调用方从此能表达「用多好」，那正是 ADR-0010 拿掉的东西 |
| 同一端点按密钥配置切换加工方式 | 调用方无法按次选择，改配置会连累这把 Key 的其它调用 |
| 分解复用改写的并池取优 | 见决策 4：会把一条子问题的唯一命中挤掉 |
| 三本账按端点开户 | 「一次 decompose」不是真实资源动作，成本无法归因 |
| 保留 fast/strong 双角色 + 失败降级 | 与「模型失败即失败」的契约冲突；兜底让调用方误以为拆分真的发生了 |
| 语义评测留在租户面板 | 它跑的是平台固定语料，租户看不到「本租户」这回事（守卫本来就拒管理员） |

## 影响范围

- 四端点 + MCP 四工具 + 前端相应入口；五授权位、三本账、max_top_k 进种子与门禁；档位系统在判定链上消失。
- 一批 ADR 的相关段落失效；GLOSSARY 的相关词条重写；教程对应章节反向修订。
- 归属索引仍「一次调用一行」、trace 仍一份、分列分数契约不变。
- 存储层：`custom_options`（JSONB）是三项参数的**等价载体**，`profile`/`allowed_profiles`/旧能力列与 `profile_presets` 表物理上仍在库里，但**不参与任何判定**（保留只是为了旧缓存/存量数据可读）。物理拆列、删表是后续纯存储改动，不改变本文任何行为语义——本 ADR 的决策落在**行为边界**上，不绑死存储形态。

## 翻案条件

- 出现第五种加工方式且高频组合：再加一条端点，而不是给请求加开关（决策 1 的纪律不变）。
- 计量要跨进程聚合（多副本部署）：三本账的 Redis 桶要换成集中账本——这是实现变化，不是边界变化。
- 需要「一次调用内混用改写与分解」：那要把两条端点合成一条带编排的新能力，需先回答「谁决定组合顺序」，不是简单加参数。

## 自检

1. 加工方式由什么表达？——端点；请求体永远只有 kb_ids + query。
2. 授权位与计量账各答什么？——能不能用 / 用了多少；位假 20013，额度尽 20014。
3. 后端还有档位吗？——没有；三项参数直存，改档位名不改变行为。
4. 分解为什么不能并池取优？——见决策 4。
5. 模型调用失败怎么收场？——整单 50003，客户重试。
