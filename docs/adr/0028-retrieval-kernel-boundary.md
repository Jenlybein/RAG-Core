# 0028. 检索内核只抽检索内核本身

- 状态：已采纳（第 11 步 · C 票的边界决定；本文只落决策，实现随 #142 落地）
- 日期：2026-11-13
- 相关：父 spec #138、票 #139（本文）、ADR-0010（检索契约）、ADR-0013（折叠与交付单元）、ADR-0021（观测旁路：一次调用一份 trace）、ADR-0024（端到端异步：请求路径的形状）、ADR-0025（索引版本）、**ADR-0027「图谱只建节级边」**（注入位在内核里）、ADR-0026（Research：本文给它的检索粒度定边界）、ADR-0018（三层授权：范围与配额在外层）、`GLOSSARY.md`「检索链路」「检索内核」「切片编排」「受控 Research」「归属索引」「观测旁路」、`app/services/rag_service.py`、`app/services/retrieval/`

## 背景

受控 Research 的一条查询要跑若干次「检索」：首轮 1~3 条查询各一次，补证 ≤2 条再各一次。

最省事的做法是**让它调 `/rag/retrieve` 背后的那条完整服务**：一条子查询 = 一次普通检索。这在功能上「能跑」，但会在四个地方同时出错，而且四处都不报错：

1. **每条子查询再改写一次。** Planner 已经把问题分解成互不重叠的子查询；改写会把「已经分好的」再揉一遍——不是重复劳动那么简单，是**改坏**（把子查询改回原问题的语义，分解白做）。成本上还多 N 次模型调用，而这一轮的硬上限是 3 次。
2. **每条子查询写一行归属索引。** 一次 Research 应该只有一行：它的 `log_id` / `trace_id` 是这次调用的身份。写 N 行会让「一次 Research」在统计里消失，变成「N 次互不相关的检索」。
3. **每条子查询发一次观测。** 成本账本碎掉：「这次 Research 花了多久、几次模型调用」要跨 N 份 trace 拼；而阶段预算（90 秒，阶段间检查）本该按整次调用算。
4. **每条子查询重判一次可见性、扣一次配额。** 范围校验在请求开头做一次就够，重复做只是把热路径上的判断乘以 N；配额更糟——一次 Research 扣 N 次，额度凭空少 N 倍。

四条同一个根因：**把「一次调用」的东西塞进了「一次检索」的粒度里。**

## 决策

### 1. 内核 = 六步，边界写死

```text
召回 → 融合 →（图谱注入位）→ 重排 → TopK → 折叠
```

- **图谱注入位在内核里**：它是候选阶段的事（候选池成形之后、截断 TopK 之前），三种检索方式与 Research 都要吃（ADR-0027）。
- **内核吃「已解析好的上下文」，不吃请求**：库与版本范围（已解析成 `kb_id → version` 映射）、档位展开后的参数、注入的 Provider 与工厂。它不读请求体、不解析 Key、不碰配额。

### 2. 留在外层的是这五件

| 留外层的 | 谁做 | 为什么不能进内核 |
| --- | --- | --- |
| 查询改写 | 外层（进入内核之前）；Research 里由 Planner 代替 | 内核被调用 N 次，改写就是 N 次；Research 里「再改写一遍」会把已分解的子查询揉回原问题 |
| 可见性校验 | 入口一次（六道关卡里的白名单与套餐解析） | 范围是**这次调用**的属性，不是每次子检索的属性；重复校验只是把判断乘以 N，不增加安全 |
| 配额记账 | 外层一次（「被拒的请求不扣额度」，成功后记一次） | 内核不知道自己被谁调用；记账要按调用粒度，按子检索记就是扣 N 次 |
| 归属索引写入 | 外层一次（一次调用一行，`chunk_ids` 存最终证据的节） | 同上；归属索引是「这次调用发生过什么」，不是「这条子查询发生过什么」 |
| 观测提交 | 外层一次（一份 trace，子检索在里面以阶段出现） | 阶段预算按整次调用算；N 份 trace 让成本与延迟无从归因 |

### 3. 判据（可机械核验，不用吵）

> 这一步是「每条子查询都要各做一次」，还是「每次调用只应做一次」？

- 各做一次是对的 → **内核**；
- 每次调用只应做一次 → **外层**。

按这条判据，`召回` 与 `重排` 显然在内核（每条子查询各查一次、各排一次）；`改写`、`校验`、`记账`、`写索引`、`提交观测` 显然在外层。以后有人想往内核里加一步，先答这一句。

### 4. 形态：一个内核，两个调用方

- `/rag/retrieve` 与 Research 共用**同一份内核实现**：retrieve 在外层做完那五件事，然后调内核。
- HTTP 与 MCP 两个入口只递参数，不各长一套（ADR-0008 的同一形状）。
- 内核是**可注入的**：Research 吃「注入的检索内核 + 模型工厂」，于是状态机可以脱开真实检索测（五步的每条降级出口、硬上限、七种停止原因）。

## 被否掉的方案

| 方案 | 为何不选 |
| --- | --- |
| **Research 直接复用完整的 retrieve 服务** | 见背景四条：每条子查询再改写一次（把已分解的查询改坏 + 破 3 次模型调用上限）、写 N 行归属索引（一次 Research 在统计里消失）、发 N 次观测（成本账本碎掉、阶段预算失准）、重判可见性与扣 N 次配额（额度凭空少 N 倍）。四条都不报错，只在月度账单与「这条 Research 为什么慢得离谱」里体现。 |
| 把改写 / 校验 / 记账都放进内核，用参数开关逐个关掉 | 一个内核带五个开关，就是五条没人测的分支；而且「关掉改写」与「改写没配」在代码里会长成同一条路径——下一处误用是沉默的。这与 ADR-0024 删同步栈是同一条理由：宁可删掉，不留半套。 |
| 给 Research 另写一条精简链路（复制召回 + 融合 + 重排） | 立刻出现两套融合公式、两套折叠逻辑、两套降级判定，而且它们会各自演进。本项目已经付过一次这类学费：评测复刻生产逻辑、复刻错了，三次数字全错（ADR-0013「备选方案」最后一条）。 |
| 让内核返回「裸切片」，由调用方自己折叠 | 折叠是交付口径的一部分（ADR-0013：小片算分、大块交付）。挪出去，两个调用方各折一次，形状立刻不一致；而归组键（`unit_path_of` 取前两段，不是 `parent_section_id`）踩过坑，复制一次就多一次踩坑机会。 |

## 影响范围

- **retrieve 也被重构到内核上**：一次抽出，两个调用方。要求 `/rag/retrieve` 在编排与图谱关闭时响应**逐字节不变**（黄金哈希用例）。
- **一次 Research 的检索次数 = 1 + 补证轮次**（每条首轮查询一次、每条补证查询一次）；阶段预算按整次调用算，且是**阶段间检查，不是硬超时**——不强制中断已经发出的单次外部请求。
- **一次调用一份 trace、一行归属索引**：子检索在 trace 里以阶段出现，不单独成行。
- **测试接缝多一处**：内核可替身，于是 Research 可以只测状态机；反过来内核本身用既有的检索用例守（响应形状靠黄金哈希）。
- **改写只剩一处**：`/rag/retrieve` 的改写路径不变；Research 里没有改写，只有 Planner 分解（分解出的查询不再二次优化）。

## 翻案条件

- **Research 需要每条子查询各自的可见性范围**（例如按要点限定在某几个库）：那内核就要吃「范围参数」而不是「已解析的上下文」，边界要重画——但**仍然不要回到「复用完整 retrieve」**，因为另外三条（改写 / 记账 / 观测）的错法一个字没变。
- **出现第三个调用方**（例如批量检索接口）：先看它要的是内核还是完整链路；只有它也要「一次调用五件事只做一次」时，才有理由把外层也再抽一层。
- **内核需要跨进程复用**（例如 Worker 里跑检索）：那时内核要变成不依赖请求上下文的纯函数——这是形态变化，不是边界变化。

## 自检

1. **内核有哪六步？** —— 召回 → 融合 → 图谱注入 → 重排 → TopK → 折叠。
2. **为什么改写在外层？** —— 内核被调用 N 次；Research 里改写会把已分解的子查询改坏，还多花模型调用。
3. **一次 Research 写几行归属索引、发几份 trace？** —— 各一份。
4. **判断一个步骤在内核还是外层，问什么？** —— 「每条子查询各做一次，还是每次调用只做一次」。
