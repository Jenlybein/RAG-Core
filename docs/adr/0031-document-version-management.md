## 背景

[ADR-0005](0005-doc-version-in-scope.md) 早就把「文档版本与索引版本正交、默认只查当前稿、每条结果带稿号」定成了决策，但它只写到**契约层**：库里有几个字段、检索带什么谓词。真正把稿次落成库里的**一等事实**时，冒出来八个必须当场表态的问题——每一个都有看起来更省事的另一种做法，而且**选错的后果全都是静默的**（不报错、不告警，只是答案错或查空）。

这一轮把八个问题一次答完，写在这里的理由与 ADR-0005 不同：ADR-0005 回答「要不要做」，本文回答「**做的时候为什么是这一个形状**」——它是未来读者翻到某段代码（一次 JOIN、一个布尔、一条迁移里的 Python 循环）时会问「为什么不能更简单」的那份答案。

三条前提，先摆在这儿，八个决策都从它们推出来：

- **仓库零外键**（`git grep ForeignKey -- app migrations` 为空）：级联一律由应用层显式删，顺序因此成为契约（决策六）。
- **写路径纪律**：一个请求一笔事务，提交点只有一处（`app/db/transaction.py`）；投递重建与翻转关键词标记登记在**提交之后**（`after_commit`），不靠「先 commit 再……」（决策七）。
- **两条版本轴正交**（ADR-0005 决策，本文不动）：稿号回答「这篇文档改过几次」，索引版本回答「这批文档算了几遍」。本文所有决策只碰稿号这一轴。

## 决策一：历史稿的切片保留，每稿各留一套

**选 B：每稿的切片都留在库里**，切片带稿号，检索靠谓词只取当前稿（决策二、三），保留策略给窗口封顶（决策四）。

否决的方案 A「只留当前稿切片」看起来便宜得多：检索不必过滤、关键词索引不必 `is_current`、清理几乎不用做。**它省掉的恰恰是这一整套东西存在的理由**：

1. **它把「事故复盘能分开归因」从根上取消。** 线上答错一条，结论可能是「稿子写错了」也可能是「稿子对、检索没召回」。只有当前稿的切片时，旧稿那一边**没有任何可查的检索事实**——只剩正文比对，而正文比对恰好回答不了「当时检索召回了什么」。
2. **「按版本只读检索」这个排查工具将不存在**（`POST /documents/{id}/versions/{v}/search`）。它是「旧版明明写了、新版为什么召回不到」唯一能直接验证的手段；没有旧稿切片，想查旧稿得**先把指针回滚过去**——那是为了排查而改线上状态，排查动作本身成了风险。
3. **B 的代价是有界的，A 的损失是无界的。** B 多出来的存储被保留窗口卡住（默认 3 稿，决策四）；而 A 丢掉的是整条时间轴上的可观测性，没有任何窗口能把它补回来。

**代价照实记**：B 引入了一类「只有靠过滤才不出现」的故障——**旧稿切片被召回**。它不报错，症状是同一段内容出现两次、或答案引用了已经改掉的条款。这是本步最主要的风险面，所以 ADR-0005 那条「约束必须落在 SQL / filter 里，不是应用层记得加」这一轮被当成硬要求执行（决策二、三）。

## 决策二：三重命名，各说各的事

同一个「版本」在库里出现三次，**三个名字必须互不复用**：

| 概念 | 库里的名字 | 一句话 |
| --- | --- | --- |
| 当前稿指针 | `documents.current_version` | 这篇文档**现在生效**的是第几稿，一个整数 |
| 稿号本体 | `document_versions.version` | 这一行是第几稿，一稿一行 |
| 这一片属于第几稿 | `chunks.doc_version` | 切片的属性，真实列，建 `(document_id, doc_version)` 索引 |

**为什么把 `documents.doc_version` 改名成 `current_version`**（#171）：改名之前，同一个词在两张表里指两件事——文档行上的 `doc_version` 是**指针**，切片上的 `doc_version` 是**归属**。这两个含义在代码里长得一模一样（都是 `doc_version`），而最容易写错的那一句恰好是最常见的一句：

```python
# 想「只看当前稿」，写成了按文档行上的指针值过滤切片
Chunk.doc_version == doc.doc_version      # 语义错位，但类型完全正确
```

写错的后果不是报错，是**静默查空**：指针与切片归属在多数时刻数值相同，一旦某篇文档回滚过或刚建完新稿，这一句就筛出一批不存在的行——检索返回「没命中」，看起来像「这个库没内容」。**同名不同义必然写错一次**，所以宁可付一次改名的代价（一次迁移、一次全树替换），也不留一个「大多数时候碰巧对」的写法。

**为什么 `chunks.doc_version` 是真列而不是 JSONB 里的一个键**（#173）：JSONB 副本删掉了，稿号只有一个来源。检索条件要能落在 SQL 与关键词 mapping 的 filter 里（ADR-0005 的硬要求），而 JSONB 键在不同数据库上的过滤能力与索引友好度都不一致——一条「在 PG 上能过滤、在 SQLite 替身上悄悄不过滤」的条件是最坏的一种，因为默认套件全绿。

**外部契约不动**：响应字段仍叫 `doc_version`（它是**切片的属性**，与库里的列同名同义）。改名只发生在「文档行上那个指针」，不进任何请求 / 响应。

## 决策三：关键词索引用一个 `is_current` 布尔，不枚举文档

关键词索引（ES）的 mapping 里加两个字段：`doc_version`（`keyword`，这一片属于第几稿）与 `is_current`（`boolean`，这一片是不是当前稿）。**召回只过滤 `is_current`**。

否决的方案：**把当前稿的 `(document_id, doc_version)` 成对枚举进查询体**（`should` + `terms`，每篇文档一对）。它在语义上等价，但在形状上错得离谱：

- **查询体随文档数增长。** 索引范围那对映射（`kb_id → index_version`）之所以敢用「配对枚举」，是因为一对 = 一个库，**一次调用涉及的库是个位到十位**；而「当前稿配对」的一对 = 一篇文档，同一个库里可以有几千上万篇。同一种写法，一个的规模由**请求**决定，另一个的规模由**语料**决定——后者迟早把查询体撑到 ES 拒绝或慢查询。
- 它还需要调用方先读出「这次涉及哪些文档」，而那正是**过滤本该解决的问题**；先查一遍文档表再拼查询体，等于把一次过滤变成两次往返。

**代价：与库最终一致。** `is_current` 是索引期写下的、**提交之后**才翻转的标记（`flip_current_draft_after_commit`）。所以在「指针已切、标记未翻」的那一小段里，关键词索引仍认为上一稿是当前稿。这条不一致**不是靠加事务解决的**（ES 不在数据库事务里），而是靠三件事收口：

1. 翻转登记在 `after_commit`，正常路径上窗口只有一次投递的延迟（量级未实测，**本步不产性能读数**）；
2. 对账脚本的第 4 条判据数「`is_current=true` 的切片稿号 ≠ 文档指针」的分歧（「在途窗口」另算一条信息项，见决策七）；
3. `is_current` 缺失（存量索引补 mapping 之前的老文档）是**信息项**，不判失败——「数据缺失」与「能力不存在」必须分开（见 `scripts/verify_document_versions.py` 里的 `undecidable`）。

补一条**mapping 的落地方式**：存量物理索引用 `put_mapping` 做 **additive** 补字段，不强制重建索引版本。ES 对**未映射**字段的 `term` 查询不报错，只是命中 0 条——所以不补映射的话，`is_current` 的 term 会让关键词路**静默全空**，而症状与「库里没内容」一模一样。

## 决策四：清理走运维脚本，不引入调度基础设施

保留窗口：留最近 3 稿（`RETAIN_VERSIONS`，业务参数不是技术参数），窗口外的**归档**稿连切片带版本行一起清。**执行者是 `scripts/purge_document_versions.py`，不是定时任务**：

- **默认 dry-run**，`--apply` 才动手，`--retain` 可覆盖窗口。运维先看「将删哪几篇的哪几稿」再决定；
- **仓库没有调度基础设施**：现在没有 Celery beat，也不为这一件事引入。引入 beat 意味着多一个常驻进程、多一份部署配置、多一条「两个实例同时跑」的并发问题，换来的只是「不用写 cron」；
- **它是脚本，所以它的失败是可读的**：退出码、逐篇统计、失败原因都在 stdout 里，与既有运维脚本（`backfill_document_content.py`、`requeue_stuck_documents.py`）同一套口径；定时是运维的事（cron / Windows 任务计划）。

三条口径写死在脚本里：只删**归档**稿（当前稿永不删，哪怕它是 v1 而指针在 v9）；窗口按**稿数**算（`current_version - retain`），不按时间——一天改十稿的文档不会保留几十个工作日的切片；**每篇文档一笔事务，先删切片再删版本行**（顺序的理由见决策六的反向情形）。

保留窗口的**可靠性边界**照实记：向量切片与版本行在同一个数据库事务里，失败一起复原；关键词索引不在事务里，最坏情况下多删一次那几稿的关键词文档——它们属于窗口外的归档稿，检索永远查不到（pin 在生效版本 + 当前稿上），下一次重建会补回来。

## 决策五：迁移里的校验和用 Python 逐行算，代价是不支持离线渲染

`document_versions` 的存量回填要给每篇文档的正文算 `sha256`。**用 `app.utils.checksum.checksum_of` 逐行在 Python 里算**，不在迁移里调数据库的 `digest()` / `pgcrypto`。

理由是**判重口径必须唯一**：规范化磨三样东西（换行统一、Unicode NFC、去首尾空白）。如果迁移用数据库算、新写入用 Python 算，就有了两套规范化——它们在某次改动里必然分叉，而症状是「同一份正文算出两个校验和」：要么判重永远判不出来（同一份内容被一遍遍灌成新稿次），要么一次真改动被判成「内容没变」（静默丢一次改稿）。两者都不报错。

**代价写在这里**：这条迁移**不能 `alembic upgrade --sql` 离线渲染**（渲染时没有库可读，Python 逐行算无从谈起）。迁移里为此留了一个显式的拒绝分支：检测到离线渲染就 `raise RuntimeError` 并给出可操作提示（「逐行算校验和需要真库，请在线执行」），而不是让它在 `op.get_bind()` 上崩一个看不懂的 no attribute。上线流程因此限死一条：**`downgrade` 必须对称，且这条迁移必须在真库上在线跑**，异地渲染 SQL 再执行的玩法对它不适用。

## 决策六：删除文档的顺序契约

删一篇文档现在是四步，**顺序即契约**：

```text
① 清除切片（向量 + 关键词两个存储）
② 删原文件（文档级 + 每一稿各自的源文件）
③ 删版本行
④ 删文档行
```

**为什么必须先清切片、后删行**：每一步的输入都来自**后面才被删的那一行**。清除切片要知道这篇文档有哪些稿（版本行），删源文件要知道每一稿的路径（版本行的 `source_file_path`）——先删版本行，这两步就都变成了无参可传的瞎猜。

**为什么版本行要单独删一次**：仓库**零外键**（这是仓库级的一贯选择，不是本表的疏漏），库不会替我们级联。版本行不显式删就是一批孤儿行；更糟的是每一稿都有自己的源文件（`<doc_id>.v<N><ext>`，按稿号落盘），文档行上只记着**当前稿**那一份路径——不按版本行清，那些文件会变成永远无人认领的垃圾（文档行与版本行都没了，没有任何地方还记着这些路径）。

**为什么不开 `ON DELETE CASCADE` 这一个口子**：那会让「哪张表走库、哪张表走代码」说不清，而说不清的那一处迟早漏删。宁可把级联写进代码、写在同一个函数里、用用例钉住顺序与提交次数（`tests/test_document_version_delete.py` 钉仓储那一步与「不提交」；两个删文档入口「这一步真的发生了、顺序与提交次数没变」在各自的 ASGI 用例里），也不引入两种引用风格。

四条都在**同一笔事务**里（含文档行删除），提交点仍是请求那一处。

## 决策七：指针先切、切片后建，接受一个可观测的在途窗口

建版本与回滚都在**一笔事务**里完成「写版本行 + 归档旧稿 + 前移指针 + 置文档为处理中」，然后**在提交之后**才投递重建。因此存在一个窗口：指针已经指向新稿，而新稿的切片还没建好，这段时间该文档检索不到。

**接受它**，并把它变成信号：

- 文档状态是「处理中」，前端按既有轮询解释，调用方看到的是「在处理」而不是「没内容」；
- 对账脚本把「**指针指向的那一稿没有切片**」列成一条**独立的信息项**（父 spec D5），与「稿号缺版本行」「快照与真值不一致」这些**真分歧**分开计数。运维一眼能分辨「重建还没跑完」与「真的丢了」。

**否决「两阶段切换」**（重建成功之后才切指针）：它要让「哪个指针生效」有第二个来源——要么加第三个状态，要么加一个「待生效指针」列。状态来源从 1 个变 2 个，而收益只是把几秒到几十秒的空窗**挪个位置**（从「指针新、切片旧」挪成「指针旧、切片新」，后者同样是错的）。这类「用一个新状态换一个短窗口」的交易，代价是长期的（每个读指针的地方都要判两次），收益是一次性的。

## 决策八：重解析写回同一稿的版本行，且读这一稿自己的源文件

换解析器重读同一份文件时：**不新增稿次**，改写**这一稿自己的版本行**（正文 + 校验和一起换）。

- **「这篇文档改过几次」不该被技术升级污染**（父 spec 用户故事第 15 条）。换解析器是同一份内容的另一种读法，把它记成一稿新稿次，会让稿次链里一半是「内容真的变了」、一半是「解析器换了」——时间轴从此不能用来回答「改过几次」。
- 判重口径仍然唯一（决策五），所以「重解析之后正文其实变了」也不会被漏掉：校验和换掉之后，下一次真改稿照样能判出差异。

**为什么重解析必须读「这一稿自己的源文件」**：`documents.source_file_path` 是**当前稿**的源文件（按稿号落盘，`<doc_id>.v<N><ext>`）。回滚之后，文档行上那一份来自被回滚到的那一稿，而重建任务载荷里带着的是**目标稿号**——照着文档行去读源文件，就会拿 A 稿的文件解析、再贴上 B 稿的标签，写出「标着第 N 稿、装着别的稿正文」的切片。所以重解析走版本行上的 `source_file_path`：有版本行的稿读不到源文件就报 `DOCUMENT_PARSE_FAILED`，**不**退回文档行那一份（宁可失败，也不要「成了但内容是别人的」）；只有在**这一稿还没有版本行**时（#172 之前的存量数据、刚上传还没索引过）才回落读文档行——那时没有别的字节可读，也就不存在「读错稿」的风险。

顺带一条同源的纪律：**重建任务载荷显式携带稿号**，不接受「Worker 自己读当前指针」。回滚刚切完指针时，一个迟到的任务会照着新指针写错稿。

## 后果

### 正面

- 审计与复盘能答「当时引用的是哪一稿」，且能**对旧稿做只读检索**（ADR-0005 的用户故事这一轮才真正可执行）。
- 回滚只重建那一篇、不动其它文档（全量重建的对照成本未实测；本步不产性能读数）。
- 三类静默故障各有一条可查的出口：静默查空（稿号谓词落到 SQL / filter）、静默错归因（归属索引的 `doc_versions` 映射）、静默漂移（对账脚本四条判据非 0 退出）。
- 清理与对账是**脚本**，运维面与既有命令同形，没有新增常驻进程。

### 代价

- **存储与写入路径变长**：每稿一套切片 + 一套关键词文档；写成一次提交变成「写版本行 + 归档 + 前移指针 + 投递重建 + 翻标记」。
- **一类只有靠过滤才不出现的故障**（旧稿切片被召回）成为长期风险面（决策一）。
- **关键词索引与库最终一致**（决策三），窗口内存在「标记还指向上一稿」的瞬间。
- **一条迁移不能离线渲染**（决策五），上线流程少了一种「先渲染 SQL 再评审」的做法。
- **四步删除顺序**是应用层契约，写错顺序不报错、只留孤儿（决策六），所以有一条用例专门钉它。
- **在途窗口**（决策七）是设计里明写接受的一段不可检索时间，只能靠文档状态与对账信息项解释，不能消除。

## 备选方案（汇总）

| 方案 | 为何不选 |
| --- | --- |
| **只留当前稿切片**（决策一方案 A） | 省掉过滤与清理，代价是取消「事故复盘分开归因」与「按版本只读检索」；B 的代价被 3 稿窗口卡住，A 的损失补不回来 |
| **`documents.doc_version` 不改名**（决策二） | 同名不同义（指针 vs 归属），最常见的那一句写错就是静默查空 |
| **稿号只存 JSONB、不加真实列**（决策二） | 过滤能力全靠数据库实现，替身与生产分叉；「默认套件全绿、线上查空」是最坏的组合 |
| **关键词索引按文档成对枚举稿号**（决策三） | 查询体随语料规模增长；且要先查一遍文档表才知道要枚举谁 |
| **引入 Celery beat 做定时清理**（决策四） | 多一个常驻进程、一套部署配置、一类并发问题，收益只是不用写 cron |
| **迁移里用 `digest()` / `pgcrypto` 算校验和**（决策五） | 两套规范化必然分叉，症状是判重失灵或静默丢改稿；换掉的是「离线渲染」这一种方便 |
| **开 `ON DELETE CASCADE`**（决策六） | 两种引用风格并存，「哪张表走库、哪张表走代码」说不清，说不清的那处迟早漏删 |
| **两阶段切换指针**（决策七） | 多一个状态来源换一个短窗口的位移，长期成本、一次性收益 |
| **重解析新增一个稿次**（决策八） | 稿次链混进「解析器换了」，时间轴答不了「改过几次」 |
| **重解析照着文档行读源文件**（决策八） | 回滚后文档行指向别一稿的文件，会写出「标签错、内容错」的切片，且不报错 |

## 翻案条件

- **存储压不住**（保留 3 稿仍磁盘告警）：先缩小窗口或把归档稿的切片迁到冷存储，**不要退回「只留当前稿切片」**——那会取消决策一里那两件能力。真要退，先出 ADR 承认丢失的能力。
- **关键词索引的一致性窗口造成真实误答**（不是「可能」而是有复盘的案例）：改成「翻转前先置文档为处理中、检索侧对处理中文档降级」，或换一个支持事务性写入的关键词后端；**不要**改成按文档枚举稿号（那会把查询体规模问题换回来）。
- **`is_current` 的过滤成本成为瓶颈**（基数、缓存、oracle 类后端）：可评估「每文档一个当前稿别名」，但那要重新算一次「查询体规模 vs 索引数量」的交易。
- **仓库引入调度基础设施**（真的有了 beat）：清理可以搬进定时任务，但**必须先保留 dry-run 入口**，否则运维失去「先看要删什么」的能力。
- **迁移不再需要兼容存量数据**（新部署从零开始）：校验和的 Python 逐行算可换成 SQL 表达式，但那之前不能换——两套规范化并存的风险比省一次离线渲染大得多。
- **「这篇文档改过几次」不再需要精确**：决策八的重解析不新增稿次可以放宽成「记一条 `reparsed_at`」。这一条目前没有需求支撑。

## 自检

1. **为什么每稿都留切片？** —— 否则「事故复盘分开归因」与「按版本只读检索」都不存在；代价被 3 稿窗口卡住。
2. **三个名字分别是谁？** —— 指针 `documents.current_version`、稿号 `document_versions.version`、切片归属 `chunks.doc_version`。改名是为了不写错「按指针值过滤切片」那一句。
3. **为什么关键词索引不用配对枚举？** —— 一对 = 一篇文档，查询体随语料增长；这个布尔换来的代价是与库最终一致。
4. **清理为什么是脚本？** —— 仓库没有调度基础设施；脚本默认 dry-run，定时交给运维。
5. **迁移为什么不能离线渲染？** —— 校验和必须走唯一的 Python 入口；离线渲染没有库可读，迁移显式拒绝并给出提示。
6. **删文档的四步为什么是这个顺序？** —— 每一步的输入都来自后面才删的那一行；零外键，级联由代码显式做。
7. **在途窗口错在哪、为什么不消掉？** —— 指针新、切片旧；消掉它要引入第二个状态来源，收益只是把窗口挪个位置。
8. **重解析为什么不新增稿次、为什么读版本行的源文件？** —— 技术升级不该污染「改过几次」；文档行那一份属于当前稿，照着读会写出标签与内容错位的切片。
