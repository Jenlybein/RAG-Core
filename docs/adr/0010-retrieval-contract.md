## 一句话决定

一次检索请求只有一条路径：**查询优化 → 两条通道各一次全局召回 → 一次 RRF 融合（`k=60` 写死）→ 可选重排**；结果落入**拒绝 / 降级 / 诚实空**三种结局之一。每条结果同时带五个通道分列字段（重排发生时再加 `rerank_score`），而 `score` 表示**本次最终排序分**。

这条契约由 `app/services/retrieval/` 与 `app/services/rag_service.py` 实现，`app/schemas/rag.py` 负责把它固定成响应形状；三者任何一处改动都要回来看本 ADR。

## 1. 融合

### 公式

```text
score(d) = 1 / (k + rank_vector(d)) + 1 / (k + rank_keyword(d))
```

- `rank_*` 是**该路召回列表里的位置**（从 1 开始），不是按分数重新排序后的位置。
- 某一路没有召回该文档时，该项**不累加**（不是补 0 分再参与平均）。
- 两路分数量纲不同（向量分 0~1、BM25 分无上界），所以**不做加权平均，也不做带权重的 RRF**。权重一开，「同一份输入两次返回同一顺序」就不再成立，评测也无法复现。

### `k=60` 写死，不进请求体

`k` 固定为 `60`：

- 没有对应的环境变量，也没有请求字段；`fuse_by_rrf(..., rrf_k=...)` 的参数只给单测用，生产路径永远不传。
- **第 4 步时**请求体只接受 `kb_ids` / `query` / `mode` / `top_k`（`RetrieveRequest`，`extra="forbid"`）。**第 3 步增补（ADR-0012/0013）之后**又增加两个默认开启的开关 `include_parent` / `expand_table_rows`，见文末「后续修订」。`hybrid_fusion` / `rrf_k` 一类的字段仍然一概被参数校验拒绝——**放开的是结果形状，不是融合参数**。
- 理由：`k` 一旦可调，同一个「质量档位」在不同调用方那里就是不同的检索链路，历史评测与线上结果再也对不上。

### 唯一键是 `(kb_id, chunk_id)`

融合时按这个二元组去重，**不是只按 `chunk_id`**：

- 跨库结果必须能各自成为一条结果；
- 将来若出现同名切片 ID，也不会被误合并；
- 每一条结果的 `kb_id` 因此必须非空（`similarity_search_scope` 每行自带 `kb_id`）。

### 同分顺序（tie-breaker）

排序键按顺序比较，**顺序即契约**：

1. 融合分降序；
2. 两路都命中的优先（`len(ranks)` 大者在前）；
3. 两路中的最佳名次升序；
4. `kb_id` 升序；
5. `chunk_id` 升序。

没有它，同分顺序就取决于哪一路先返回——那取决于网络抖动，评测不可复现。由于固定 `k` 下 `1/(k+rank)` 是严格凸的，真正同分的两条必然名次多重集相同，第 2、3 条只在浮点碰撞时发力；即便如此，顺序也必须写死。

## 2. 三种结局

| 结局 | 触发条件 | HTTP / 业务码 | 关键字段 | 调用方应做什么 |
| --- | --- | --- | --- | --- |
| **拒绝** | 混合模式两路都失败；`mode=bm25` 时关键词引擎不可用或失败；任一知识库不可见 | HTTP 200 + 非零 `code`（`RETRIEVAL_FAILED=50002`；不可见为 `20008`）；`mode=vector` 的嵌入异常例外，为 HTTP 500 / `50000` | `code` / `msg` | 按业务码处理（重试、修配置或放弃），**不要**从空结果里猜 |
| **降级** | 混合模式仅一路失败；查询改写失败；重排失败 | HTTP 200 + `code: 0` | `metadata.retrieval.degraded: true`、`degraded_reason` | 结果可用但打了折；按原因决定是否提示用户 |
| **诚实空** | 检索成功但确实没有结果 | HTTP 200 + `code: 0` | `metadata.retrieval.empty_reason` | 按原因引导：去传文档，或换个问法；**不是故障，不要整单重试** |

几点容易读错的边界：

- **降级与诚实空可以同时出现。** 一路失败、另一路也没命中时，响应会同时是 `degraded: true` 和 `empty_reason: no_chunks_matched`。三种结局是三种「判断」，不是三个互斥的枚举值。
- **拒绝先于召回。** 知识库可见性在进入任何分支之前逐个校验；被拒的请求连嵌入都不会算（`offline_embedding.queries == []`）。
- **单模式不降级。** `mode=bm25` 时引擎不可用就是 `50002`，绝不偷偷退回向量——调用方选 `bm25` 往往就是在评测单路效果。
- **`mode=vector` 的嵌入失败不在降级矩阵里。** 它没有另一路可兜，也不该谎报空结果，按未捕获异常走 `50000`（HTTP 500）；`test_single_vector_mode_still_fails_loudly_when_embedding_breaks` 钉住这条。`50002` 用于通道层面的失败（关键词引擎不可用/失败、混合模式两路都失败）。
- **为什么嵌入失败不是 `50002`（这不是遗漏，是刻意区分）：** `50002` 是**业务拒绝**——请求合法、库里有东西、但这一路检不出来，按 ADR-0007 走 HTTP 200 + 业务码；而嵌入服务不可用是**基础设施故障**，必须让网关、重试与告警看得见。两者合并的后果很具体：嵌入服务整体宕机时，监控面板上会显示「检索命中率下降」，而不是「依赖故障」，排查方向直接跑偏。
- **空结果不是错误。** 把它当故障会让监控满地假警报，也让调用方误以为该重试。

## 3. 降级原因是一组固定英文串

`degraded_reason` 只允许四个值，**不拼异常文本**（第 11 步 #147 起是五个：多一条 `orchestration failed`，见文末「第七次修订」）：

| 原因 | 产生位置 | 含义 |
| --- | --- | --- |
| `query rewrite failed` | `app/services/query/rewrite.py` | 改写失败（含超时、空返回、结构不合法），已回退原句 |
| `vector search failed` | `app/services/retrieval/pipeline.py` | 向量通道失败（含嵌入失败），已用关键词结果继续 |
| `keyword search failed` | `app/services/retrieval/pipeline.py` | 关键词通道失败，已用向量结果继续 |
| `rerank failed` | `app/services/retrieval/rerank.py` | 重排失败（含超时、空返回），已保留融合顺序 |

规则：

- **一因一码。** 调用方按码做判断；异常文案变了不该影响判断。日志里也只记异常**类型**，不记原文（原文可能夹带提示词或切片内容）。
- **先到的原因是根因，后到的不覆盖。** 实际顺序是：改写（召回之前）→ 通道（召回时）→ 重排（融合之后）。所以改写在先失败时，通道故障与重排失败都不覆盖它；通道已降级时，重排失败也不覆盖通道原因。
- **拒绝不是降级。** `20008`（不可见）/ `20002`（参数）这类拒绝不参与降级判定，也不会被降级吞掉。
- **「没配引擎」是能力缺失，不是「查过了没命中」。** 空实现 `available=False` 在混合模式记为该路失败（降级），在 `mode=bm25` 记 `50002`。

## 4. `score` 语义变更（破坏性）

`score` 从「余弦相似度」变成「**本次最终排序分**」（第 4 步）：

| 场景 | `score` 在第 4 步是 | 具体分数该读 |
| --- | --- | --- |
| `mode=vector` | 向量分（`1 - 余弦距离`） | `vector_score` |
| `mode=bm25` | BM25 分（ES `_score`，无上界） | `bm25_score` |
| `mode=hybrid`，未开重排 | 融合分（约 `0.016`~`0.033` 量级） | `rrf_score` |
| `mode=hybrid`，重排发生 | 重排分（0~1） | `rerank_score` |

**第 3 步增补（ADR-0013 决策 4）再次改变它**：折叠开启时 `score` 变成「**单元内命中片的最高分**」，不再恒等于 `rrf_score`。这是第二次破坏性变更，迁移说明见文末「后续修订」。

**这是破坏性变更。** 旧调用方如果把 `score` 当余弦相似度做阈值判断（例如 `score >= 0.8` 才采用），升级后会得到完全不同的行为：混合模式下 `score` 只有 `0.03` 左右。请求体本身没变，变的是响应里这个字段的含义。

### 迁移方式

1. **路由 / 下一跳判定**改读分列字段，不要读 `score`：
   - 这一条是不是向量命中的：`vector_rank is not None`；
   - 这一条是不是关键词命中的：`bm25_rank is not None`；
   - 语义相似度阈值：`vector_score`；
   - 融合排序的依据：`rrf_score`；
   - 重排置信度：`rerank_score`。
2. **未命中的那一路是 `null`，不是 `0`。** 「没命中」与「命中但分数为 0」必须可区分；把 `null` 读成 `0` 会制造假的「命中但极不相关」。
3. 不要跨模式比较 `score`（向量分、BM25 分、融合分、重排分四种量纲），也不要把不同量纲的分数字段相加。
4. `score` 仍可用于「按返回顺序展示」和兼容旧的展示代码；它不再是一个可解释的相似度。

## 5. 索引范围：`index_versions` 是配对映射

检索范围由 `kb_id → index_version` 的**映射**表示，唯一构造点是 `app/models/chunk.py::default_index_versions`。本步的构造点返回常量 `v1`，请求体里没有 `index_version` 字段。**这两件事的后续**：版本生命周期在第 11 步接上（[ADR-0025](0025-index-as-build-artifact.md)）——取值来源从常量改成「每个库自己的生效版本」，而**映射形状与「绝不能写成两个独立 `IN`」这条一字不改**；`index_version` 仍永远不是请求参数。

### SQL / 查询条件必须是配对

向量侧：

```python
or_(*[
    and_(Chunk.kb_id == kb_id, Chunk.index_version == version)
    for kb_id, version in index_versions.items()
])
```

关键词侧：每一对是一个 `bool.filter`（`term kb_id` + `term index_version`），对与对之间是 `should` + `minimum_should_match=1`。

**绝不能写成两个独立的 `IN`：**

```text
kb_id IN ('kb-a', 'kb-b') AND index_version IN ('v1', 'v2')
```

单版本时两种写法等价；多版本并存时会匹配出「`kb-a` 配 `v2`」这种根本不存在的组合——那是越权或脏数据，而且不会报错。

### 空映射编译成恒假

- 向量侧：`build_scope_filter({})` 返回 `false()`，SQL 渲染成恒假条件，**不是**「不过滤」。
- 关键词侧：`should: []` + `minimum_should_match: 1`，按构造匹配不到任何文档。
- 原因：拿不到范围却不过滤，等于把整个租户的库都召回——比空结果严重得多。

## 6. 多库：一次全局召回 + 一次融合

- 两条通道各查**一次**，各自的查询覆盖全部「库 + 索引版本」配对；嵌入只算一次，不随库数量增加。
- `top_k` 是**全局**返回条数；`HYBRID_RECALL_TOP_K` 是每路召回深度。**没有「每库各占名额」**——分库各召回一批再合并是假均衡，不相关的库也会占名额，把真正该进来的切片挤掉。
- **「某库没有切片进入结果」不是失败。** 不记 `failed_kb_ids`，也不按结果条数推断某个库出了事；结果只按实际命中呈现，每条结果自带 `kb_id`。
- 可见性校验在进入任何分支之前统一做一遍（N 个库 = N 次查询），拒绝（`20008`）先于召回，且不参与降级。

## 8. 代价

- **`score` 是破坏性变更。** 旧调用方的阈值逻辑必须迁移，且没有「两个语义并存」的过渡期字段。
- **`k=60` 写死**意味着不能按业务调融合的平滑度；要改就得改代码并重跑评测。
- **降级与诚实空可同时出现**，调用方必须同时读 `degraded` 和 `empty_reason`，不能只读一个。
- **不按库记失败**让「某个库是不是坏了」不能只从响应判断，需要看日志或监控；这是用「不误报」换来的。

## 9. 翻案条件

- **要调 `k` 或引入加权融合**：先出新 ADR，再用同一份语料/题目重跑 `eval/ACCEPTANCE.md` 的矩阵；没有新数字不改。
- **产品需要「每库保底名额」**：那会推翻「一次全局召回」，等于换一种检索语义；应作为独立需求评估，不要在现有 RRF 上加隐式配额。
- **调用方普遍需要「相似度阈值」**：优先引导读 `vector_score` / `rerank_score`；只有在两种分列字段都无法满足时，才考虑新增专门的阈值字段。

真实链路与评测数字：`eval/ACCEPTANCE.md`（**第 4 步时**语料 245 片 / 26 题，基线 `418 passed, 11 skipped`；后续已扩容，以该文件当前内容为准）。

## 后续修订（第 3 步增补，2026-11-09）

本 ADR 写于第 4 步。之后 ADR-0012 / 0013 为「切块粒度变细」做的改造，**改了本 ADR 的三处契约，但融合、三种结局、`k=60`、配对映射一律未动**。下表是唯一权威口径：

| 契约 | 第 4 步（本 ADR 初版） | 现在 | 依据 |
| --- | --- | --- | --- |
| 请求体 | `kb_ids` / `query` / `mode` / `top_k` | 再加 `include_parent`（默认 `True`）/ `expand_table_rows`（默认 `True`） | ADR-0012、`app/schemas/rag.py` |
| 一条结果代表 | 一个**切片** | 一个**节**（折叠）；身份是 `section_id`，`chunk_id` 是代表片 | ADR-0013 决策 1–3 |
| `score`（折叠开启时） | 本次最终排序分（混合 = `rrf_score`） | **单元内命中片的最高分** | ADR-0013 决策 4、`app/services/rag_service.py` |

**§1 与 §4 的表格只描述第 4 步的历史状态**，不要拿它们当现状；`fuse_by_rrf`、`k=60`、五种 tie-breaker、三种结局、四个降级原因、配对映射与空映射恒假全部仍然成立。

**#31 修订（2026-11-09）**：`QUERY_REWRITE_ENABLED=true` 现在是「**原句 + 改写句都搜**」，不再是「用改写句替换原句」——向量一路逐句各做一次嵌入与一次范围召回，按 `(kb_id, chunk_id)` 去重、同名次取更好的一次、分数取更高者，合成**一个池**后直接交给既有的 `fuse_by_rrf`（不新增内层 RRF）。关键词一路仍用 `search_query`，重排仍用 `effective_query`，改写失败仍只剩原句并标 `query rewrite failed`；关闭时响应逐字节不变。落地在 `app/services/query/optimizer.py`、`app/services/retrieval/vector_recall.py`。

同一修订还补上一个**观测缺口**：改写真的发生时，响应 `metadata.retrieval` 多一栏 `query_optimization`（`effective_query` / `vector_queries` / `rewrite_degraded`），评测把它逐题落盘，这样「名次变了」能归因到检索还是改写，而不是只能猜（q16 当年就卡在这里）。**改写未发生时这一栏不出现**，恒等变换不新增字段，以免破坏「关闭改写时响应逐字节不变」这条红线。

### 第二次破坏性变更的迁移方式

`score` 不再恒等于 `rrf_score`：

1. **要融合排序依据 → 读 `rrf_score`**（它仍是代表片那条命中结果的融合分，原样保留）。
2. **要判断「这一节整体有多相关」 → 读 `score`**（取组内最高分，不是平均——平均会惩罚「一节里多片都命中」这种好情况）。
3. **阈值判断请显式选字段**：`vector_score` / `rerank_score` / `rrf_score` 各有量纲，别把 `score` 当相似度。
4. 想要第 4 步那种「一条结果 = 一片」的响应，把 `include_parent` 显式传 `false`：此时**连按节归组都不做**，响应形状与折叠之前一致，召回深度也从 `top_k × OVERFETCH_FACTOR` 降回 `top_k`。

> 命名遗留：`include_parent` 这个名字来自 ADR-0012（当时准备附加 `parent` 字段）。ADR-0013 已删除 `parent` 字段，开关实际控制的是**是否折叠**。为不破坏已发布的请求契约，名字保留，语义以本表为准。（第 7 步之后这条保留理由已经消失：开关搬进了密钥配置，不再是已发布的请求字段，见下节。）

## 第三次修订（第 7 步，#73，2026-11-10）：请求只剩两个字段

**本节取代四处旧口径**：§1「`k=60` 写死，不进请求体」里那句「请求体只接受 `kb_ids` / `query` / `mode` / `top_k`」、§1 中「第 3 步增补又增加 `include_parent` / `expand_table_rows`」、上面「后续修订」表格的「请求体」一行，以及「第二次破坏性变更的迁移方式」第 4 条（想让响应回到「一条结果 = 一片」就显式传 `include_parent=false`）。那几处现在**只描述第 4 步与第 3 步的历史状态**，不要再照它们实现。

### 1. 契约

一次检索请求只有两个字段，`extra="forbid"` 照旧：

| 字段 | 表达什么 |
| --- | --- |
| `kb_ids` | 查哪些知识库（必填） |
| `query` | 问什么（必填） |

- 检索方式、返回条数、是否重排、是否查询改写、是否折叠成整节、是否把表格行折回整表——**全部来自密钥配置**，请求里一个都没有。同义词扩展**不在其中**：它是部署级开关（`SYNONYM_EXPANSION_ENABLED`），不按 Key 分配。两篇结果装饰 ADR 里的两个开关因此换了归属，见 ADR-0012 / ADR-0013 文末的第 7 步修订。
- 旧调用方继续传 `mode` / `top_k` / `include_parent` / `expand_table_rows`，拿到的是参数校验失败（`20002`），**不是被忽略**。静默忽略比报错更糟：调用方会以为自己的参数生效了，直到某天发现 `quality` 档根本没照它想的跑。
- HTTP 与 MCP 两条入口字面一致：工具签名里有什么，模型就能填什么（见 ADR-0018）。
- 唯一的例外是**链路常数**：召回深度与融合池仍由服务端配置决定（`HYBRID_RECALL_TOP_K` / `RERANK_MAX_CANDIDATES`），既不进请求，也不按 Key 分配。它们决定「池子里有多少料」，不是「这次用多好」；做成可调项会让同一个档位名在不同租户那里变成不同链路。

§6 的「`top_k` 是全局返回条数」仍然成立，变的是这个数的**来源**：它来自密钥配置（命名档位，或 `custom` 档下的那批手动参数），不再来自请求。

### 2. 为什么：档位名必须处处是同一条链路

命名档位（`speed` / `balanced` / `quality`）承诺的是一整条链路，例如 `quality` = 混合检索 + 重排 + 查询改写（三个档位的返回条数都是 5，档位之间差的是链路，不是返回多少个字）。这个承诺要成立，前提是「同一个档位名在任何一把 Key、任何一条入口、任何一次调用上都是同一条链路」。

只要请求还能带质量参数，这个前提立刻就碎：同一把 Key 上的 `quality`，在 A 应用那里是混合 + 重排 + 改写，在 B 应用那里被它自己传的 `mode=bm25` 削成单通道。于是评测量到的 `quality` 与线上跑着的 `quality` 不再是同一个东西，历史数字与线上现象再也对不上——本项目已经在 `score` 语义上付过一次这种代价（§4），不该在档位上再付一次。

档位锁在 Key 上另有一个好副作用：调用方拿不到旋钮，也就不必理解 embedding、重排、融合这些底层细节，只需要回答「问什么、查哪些库」。

### 3. 被否决的三种做法

| 做法 | 为何不选 |
| --- | --- |
| 请求里带 `profile`（档位名） | 档位一旦能按次指定，它就从「这套集成的配置」退化成「这次调用的建议值」：同一把 Key 的两次调用可能跑不同链路，服务端无法预测、评测无法复现；而且「这个档位是否在套餐白名单内」这条门禁要在每次请求上重复判，判定点从建 Key 时前移到热路径上。 |
| 请求保留 `mode` / `top_k` | 这两个正是命名档位要承诺的内容。留着它们等于允许调用方半途改写档位：`quality` 配 `mode=bm25` 既不是 `quality` 也不是 `custom`，成了第三种没人定义过的东西；`top_k` 留着则「返回条数」这半条承诺也守不住。 |
| 只删其中一个（只删 `mode` 或只删 `top_k`） | 这两个参数是同一件事的两半，删一半等于留一个后门：只删 `top_k` 时调用方仍能翻转 `mode`，「单模式不降级」的语义可以被请求改写；只删 `mode` 时返回条数仍由调用方定，档位承诺的链路被削掉一半，召回成本也不再可控。何况「一半参数在请求、一半在配置」的契约还得在文档里额外解释哪一半算哪一半——这本身就是不可复现的迹象。 |

### 4. 后果

- **破坏性变更**：`mode` / `top_k` / `include_parent` / `expand_table_rows` 从请求体删除，旧调用方会拿到 `20002` 而不是结果。迁移方式是「把这次调用想要的行为写进这把 Key 的密钥配置」，不是把字段加回来。
- **档位判定从参数校验挪到配置解析**：档位展开与门禁发生在鉴权之后、限流之前，六道关卡的顺序不变（见 ADR-0018）。
- **`include_parent` 这个命名遗留一并了结**：它搬进密钥配置后不再是已发布的请求契约，那一层不必再沿用这个与语义相反的名字。
- **`tenant_policy` 回显更有必要**：请求里已经看不出这次跑了什么，它是唯一能解释「为什么这次慢了」「为什么没重排」的地方。

## 第四次修订（第 7 步收尾，2026-11-10）：`requested_tier` 改名为 `requested_profile`

**这是一次已发布响应字段的破坏性改名**：`metadata.tenant_policy.requested_tier` 现在叫 `requested_profile`。没有两个名字并存的过渡期——回显里同时出现两个键就等于有了第二个真相，而这正是本 ADR 反复拒绝的那类设计。读旧字段的调用方只需改读新键；值、位置与语义都不变（仍是 `speed` / `balanced` / `quality` / `custom`）。

为什么必须改：

- **`tier` 是术语表的禁用词。** `GLOSSARY.md` 的规范名是**档位（Profile）**，而 `tier` 同时被列为「档位」「套餐」「模型角色」三个概念的 `_Avoid_`。拿它命名档位是一处双重违规：名字既不是规范名，又让读者无法判断它指的是「这次用多好」还是「这个租户买得起多少」——这两件事在 ADR-0018 里是两层互不重叠的授权。
- **改名之后词根一致。** 回显字段与 `TenantPolicy.requested_profile`、密钥配置的 `profile` 列、套餐的 `allowed_profiles` 白名单同词，读代码不必再翻译一次。
- **同一轮只动名字、不动语义。** 平台层的模块与类型同理改名：`app/services/profile_policy.py`、`ProfileChain`、`PROFILE_CHAINS`（原 `tier_policy` / `TierBundle` / `TIER_PRESETS`）。它们不进响应契约，改名不影响调用方。

迁移方式：把读 `metadata.tenant_policy.requested_tier` 的地方改成 `metadata.tenant_policy.requested_profile`；这段回显只在经套餐门禁解析的调用上出现，不经门禁的内部调用本来就没有这一栏（见第三次修订第 4 条）。

## 第五次修订（第 9 步，#99，2026-11-11）：响应 `metadata` 多一个 `trace_id`，六段耗时留在观测里

**这次只动响应的一处**：`metadata` 增加 `trace_id`，**永远非空**。除此之外检索响应逐字节不变（有测试钉住）——同一步里对归属索引的整改（只存结构、不存原文）动的是一张从未进过响应的表。

### 1. 契约

| 位置 | 字段 | 取值 |
| --- | --- | --- |
| `metadata.trace_id` | 这一次调用在观测里的那根线 | 32 位十六进制串；**任何情况下都不为空串、不为 `null`** |

- **由中台派生，不由观测后端分配。** `trace_id` 以本次调用的 `log_id` 为种子派生：同一个 `log_id` 永远得到同一个 `trace_id`。推给观测栈时**沿用我们生成的这个值**（`trace_context`），不让 SDK 另生成一个——于是响应里那根线与观测栈里那条 trace 是同一个值，中间不需要第二张对照表。
- **先派生，再尝试写入。** 归属索引的写入是旁路：那次写入失败只记一条 `warning`，检索照常返回，`trace_id` **仍然有值**。反过来「写入成功才拿到 id」就等于把契约挂在旁路的健康度上——观测抖一下，响应就少一个字段。
- **六段耗时**不进响应。本次**不新增任何耗时字段**；`metadata.retrieval.rerank` 里那条耗时是第 4 步就有的重排事实，原样保留，也不被拿来承载六段 span 的耗时。
- `metadata` 其余层次（`mode` / `top_k` / `vector_store` / `retrieval{...}` / `tenant_policy?`）一字未动，加字段的位置在**顶层**，不在 `retrieval` 里面：它是「这一次调用的身份」，不是「这一次检索的细节」。

### 2. 为什么：可追溯是契约，性能数字不是

- 调用方要的是一个**能写进自己日志、报障时能交给运维对账**的 id。它必须稳定、不依赖外部服务、每次都有——这三条正好是「自己派生」而不是「向观测服务要」的理由。
- 「这次慢在哪一步」是运维问题，不是调用方问题。把它放进响应，等于让每个调用方都解析一份不属于契约的性能数字；更糟的是：耗时有就得有观测开关，而观测开关是部署级配置，于是同一个接口在不同部署下响应形状不同。
- ADR-0020 已经把这个判断写死过一遍：调试台只回答「这次结果为什么是这个结果」，观测回答「这次调用把时间花在哪」。「为什么慢」的答案属于后者，不该反过来漏进契约。
- 加字段本身向后兼容，但它**改掉了一条旧红线**。新的红线逐字是：**除 `metadata.trace_id` 外，响应逐字节不变**。

### 3. 被否决的两种做法

| 做法 | 为何不选 |
| --- | --- |
| `trace_id` 由观测 SDK 生成后回填响应 | 观测是旁路。去向切到 `jsonl` / `null`、或观测服务连不上时就没有 id 可回填，响应形状随观测健康度变化——同一个接口在两种部署下有两种形状，评测与回归都钉不住。 |
| 六段耗时一并进 `metadata` | 契约只承诺「返回了什么」，不承诺「时间花在哪」。耗时一旦进响应就得跟观测开关联动，而开关是部署级配置；需要归因的场合（评测对不上名次、线上慢查询）去观测栈读同一根 `trace_id` 即可。 |

### 4. 后果

- 调用方可以把 `trace_id` 写进自己的日志，报障时只给这一个值。**代价是它不能再假设响应字节稳定**：做快照比对、签名、缓存键的调用方要把这个字段排除掉。
- **对外只有 `trace_id` 一个 id。** 归属索引的对外身份仍是 `log_id`，但它不出现在响应里。两个 id 在同一行上、由确定性派生绑定：要按 `log_id` 查就用 `id`，要按 `trace_id` 查它也在同一行，不必额外维护一张对照表（派生是纯函数，给定种子结果唯一）。
- 六段耗时只能从观测栈读：观测栈没起（或去向是 `jsonl` / `null`）的部署，就没有「哪一步慢」的答案。这是旁路的代价，不是遗漏。
- 响应变长几个字节，但不引入「可能缺席」的字段：`trace_id` 是**必填**，调用方不必写 `if trace_id is not None` 这种分支——那种分支会掩盖「这次没记上」的事实。

### 5. 翻案条件

- **要跟上游系统串成一条链**（调用方自己已有 `traceparent`）：那时再评估是否接受请求头透传。眼下没有多系统链路，先加请求头只会给「trace 由谁生成」制造第二个答案。
- **调用方普遍需要六段耗时**（不只运维要）：先证明观测栈这条路真的读不到，再出一次新修订重新设计形状与时序；注意那会再破一次「逐字节不变」。
- **换观测后端**：「32 位十六进制」与「同一 `log_id` 恒等派生」这两条不跟着换——换后端改的是注入方式，不是契约。若某个后端要求别的 id 形状，那就让适配层去转，不改响应。

## 第六次修订（第 10 步，2026-11-12）：`metadata.retrieval.rerank` 多两个身份字段

**改了什么**：`metadata.retrieval.rerank` 增加 `provider`（`qwen3` / `llm` / `none`）与 `model`（如 `qwen3.7-text-rerank`）。`applied` / `candidates` / `returned` / `duration_ms` 不变；没有重排时（`applied=false`）两个新字段是 `null`，不缺席。

**为什么**：换件之后，「这次到底是哪种重排、哪个模型」不再是实现细节——同一台机器上并存两种实现（生产走专用端点、评测可显式装旧的大模型重排做对照），而调用方与排障者只看响应。不给这两个字段，「为什么这次慢」只能靠人去翻日志；而日志与响应读同一份事实，是本契约从第 4 步起就有的要求。

**代价**：hybrid 响应又长了几十个字节，`test_multi_query_union.py` 的逐字节黄金哈希必须把这两段摘掉再比（与 `trace_id` 同一种做法，基线常量一个都没重采）。**这是第三次因为「多一个可解释的字段」而破逐字节不变**——不是失守，是那条红线本来只该覆盖「不该变的字段」。

**没有改**：六段耗时仍不进响应（第五次修订的结论不变）；`vector` / `bm25` 两个单模式没有重排段，响应逐字节不变。

**翻案条件**：若调用方开始依赖这两个字段做路由（例如按 provider 计费），它们就得升级成稳定的枚举并写进 OpenAPI；那时要再出一次修订，而不是在响应里悄悄加第三个名字。

## 第七次修订（第 11 步，#147，2026-11-13）：`data` 顶层多一块可选的 `orchestration`，回显多一个 `orchestration`，降级原因多一条

**改了什么**（三处，都在响应侧；请求体仍是 `kb_ids` + `query`）：

| 位置 | 形态 | 什么时候出现 |
| --- | --- | --- |
| `data.orchestration` | 对象：`completeness`（`complete` / `partial` / `missing`）+ `points[]` + `evidence[]` | **只有开启编排、且有候选**时才出现；关闭时这个键**连存在都不存在**（不是 `null`） |
| `metadata.tenant_policy.orchestration` | 布尔 | 与 `rerank` / `rewrite` 同一列、同一来源（`RetrievalOptions`），在 `rewrite` 之后 |
| `metadata.retrieval.degraded_reason` | 第五个固定串 `orchestration failed` | 模型装不上 / 超时 / 输出不合法时；检索结果照常返回 |

`points[]` 每项是 `point_id`（`A1…An`）+ `text`（模型给的要点）+ `has_primary`；`evidence[]` 每项是
`evidence_id`（`E1…En`）+ `point_id` + `role`（`primary` / `supporting`）+ `chunk_id` / `kb_id` /
`document_id` / `title` / `heading_path` / `content`。**没有 `answer`**：ADR-0001 说 `/rag/retrieve`
永不生成答案，这里一个字的模型正文都不留。

三条硬规则决定了这个形状：

- **模型只点序号。** 两次结构化调用（先要点、再每个要点下的核心 / 辅助），模型的输出里只有要点文本与
  候选序号，拿不到切片 id、也不会被要求写正文。正文因此**只能**由后端按序号回查候选重建——提示词注入
  最多让它点错序号，点错的结果是一条真实切片站错位置，而不是一段凭空生成的内容。
- **越界序号整条拒掉。** 序号不在 `1..len(候选)` 就不产生材料，不猜、不截、不用模型给过的文本补位。
- **完整度由核心片数出来。** 模型的结构化输出里**没有**「齐了 / 没齐」这一栏，三态完全由「每个要点有没有
  核心片」数出来；「模型说齐了但没有核心片 → 仍判 `partial`」在结构上无法被推翻。

**为什么**：检索结果已经升级成「一份材料」，但调用方仍然得自己判断「这个问题有几个要点、哪个是核心、
缺哪一块」。这一块是**组织**而不是检索（不重新召回、不改排名），所以它属于响应契约的一层新增，而不是
一条新的检索路径。开关仍按 ADR-0018 三层（套餐允许 / 配置启用 / 档位想要），**请求里一个参数都没有**——
ADR-0010 第三次修订的结论不变。

**为什么回显在 #147 才出现**（#146 的收口判断在此到期）：`tenant_policy` 只放「本次真实生效**且改变了
结果**」的项。编排在 #146 时没有消费者，把它放进回显等于宣告一个不存在的生效值；#147 接上链路之后它
和 `rerank` / `rewrite` 一样是生效值，于是从同一个 `options` 上读出来（同源，不可能「回显说开了、实际
没跑」）。

**被否决的三种做法**：

| 做法 | 为何不选 |
| --- | --- |
| 关闭时也放 `orchestration: null` | `null` 也是字节。「关闭时响应逐字节不变」是红线，而这一块的意义正是「不开它的人完全不受影响」。Pydantic 默认会把它序列化成 `null`，所以 `RetrieveData` 显式在序列化时摘掉这个键。 |
| 把块塞进 `metadata.retrieval` | `retrieval` 回答「这次检索遇到了什么」（模式、降级、空结果原因）；编排块是「这次编排出了什么」，与 `retrieved_chunks` 同级。混在一起之后，读 `retrieval` 的人会以为自己拿到了一份元数据。 |
| 让模型直接返回要点 + 正文 | 那是把「正文来自库」这条可追溯性交给模型自己保证。序号 + 回查是**结构性**保证，不是提示词里的请求——后者在注入面前一文不值。 |

**代价**：

- 开了编排的档位多两次小模型调用（约 4 秒硬上限，超时即降级），延迟可预期但确实更长；代价只付在开了它
  的那几把 Key 上——关闭时**一次模型都不调**（有用例钉住）。
- `tenant_policy` 多一个键，所以 `test_multi_query_union.py` 的逐字节黄金哈希必须把它摘掉再比（与
  `trace_id`、`rerank` 身份键同一种做法，基线常量一个都没重采）。**这是第四次因为「多一个可解释的字段」
  而破逐字节不变**；摘掉之后仍与旧基线逐字节相同，这正是「只多了这一个键」的证据。
- 编排本身**不进六段耗时**（那是观测的事，第五次修订的结论不变），所以「编排花了多久」只在日志的
  `evidence orchestration failed` 那条 warning 里能看到一次。

**没有改**：请求体只有 `kb_ids` + `query`；`retrieved_chunks` 一条都不动（编排是组织材料，不是重新检索）；
`empty_reason` 语义不变；`metadata` 内部一个字节都没动（`trace_id` 仍是 `metadata` 的最后一个键），编排块整段
排在 `data` 的最末——位置与第五次修订给 `trace_id` 的那条理由同构：把新东西放最后，「摘掉它之后与原响应
逐字节相同」在字节层面直接成立。

**翻案条件**：若调用方要求「按次选择是否编排」，那要先推翻第三次修订（请求里不许有质量参数）——要么
证明它不在「质量参数」这一类，要么承认档位承诺破了。若调用方普遍需要「编排耗时」，先证明观测栈这条路
读不到（第五次修订的翻案条件同款），再考虑加第六段之外的计时字段。
