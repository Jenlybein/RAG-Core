# 0027. 图谱只建节级边、只做候选不做裁决

- 状态：已采纳（第 11 步 · A 票；本文只落决策，实现随 #141 落地）
- 日期：2026-11-13
- 相关：父 spec #138、票 #139（本文）、**ADR-0013「一条检索结果代表一节」**（折叠与交付单元）、**ADR-0025「索引即构建产物」**（边的版本作用域来自它）、ADR-0010（检索契约：结果字段）、ADR-0018（三层授权：范围过滤在这里判）、ADR-0021（观测旁路：关系查询失败也只降级）、**ADR-0028「检索内核只抽检索内核本身」**（注入位在内核里）、`GLOSSARY.md`「关系边」「引用指针」「候选注入」「上下文恢复」「降级原因」、`app/services/retrieval/`、`app/services/section_context.py`

## 背景

三条具体缺口，都是「调用方拿到一堆命中，却拿不到一份能读懂的材料」的不同侧面：

1. **折叠跨不过节的边界。** 交付单元按标题路径前两段归组，同一个二级标题之内会拼回整节，但两个不同的二级标题之间永不合并。真实文档里一个答案常常横跨两节：2.3 写「超期需人工审核」，2.4 才写「3 个工作日内到账」。只命中 2.3 的调用方拿到的是半份事实。
2. **跨文档的路标完全不被使用。** 文档里写着「详见《促销活动与优惠券使用规则》2.4 节」。那句话今天只是一段文本：它可能被当成一个微弱的命中，也可能根本不为召回所动，但**它从不指路**。
3. **关掉折叠时，小片读不懂。** 「只要精确到那一行」的调用方拿到 `table_row` 或细片，缺父节上下文，读起来像断章。

而「关系」这个能力最容易长成两件坏事，本文的两条边界就是防它们的：

- **自己裁决相关性**：图说相关就相关，重排被架空；
- **变成越权通道**：A 库的边指向 B 库，甚至指向另一个租户的节，于是「关系」本身就是一条绕开白名单的路。

## 决策

### 1. 节点是「节」，不是切片

节的键 = `(租户, 库, 版本, 文档 id, 节 id)`。

- **两端都带文档 id**：不带的话，两份文档都叫「退款 > 流程」会撞同一个 `section_id`，跨文档一对就串（ADR-0025 决策五）。
- **带版本**：边必须与切片在同一版本里才配对；旧边指向新版本里同 id 的节，是一个不会报错的错答案（ADR-0025 决策一）。

### 2. 只有三种边型

| 边型 | 含义 | 例子 |
| --- | --- | --- |
| `reference` | 显式引用：这一节指向另一节 | 「参见《X》第 2.4 节」「本文件第三节」、Markdown 链接、同文档锚点 |
| `sibling` | 兄弟节：同一父节下相邻的两节 | 2.3 与 2.4 |
| `parent` | 父节：这一节与它所属的上一级节 | 2.x 与 2 |

一条有向边一行，字段：作用域（`tenant_id` / `kb_id` / `index_version`）、两端（文档 id + 节 id）、`relation_type`、`metadata`（抽取时命中的原文片段与章节号，供排障）。

**边型只有三种，不加第四种**：每加一种都要回答「它该不该参与注入、优先级排第几、抽取规则怎么验」，而三种已经覆盖文档里真实存在的结构关系。语义关系（「这两节讲同一件事」）不是结构关系，见决策 3。

### 3. 只认文档显式表达，不按相似度猜边

- 只识别文档中**真实存在的显式表达**：「参见《X》第 N 节」「本文件第三节」、Markdown 链接、同文档锚点。
  **Markdown 链接按文件名对目标**（登记时那份 `documents.source_filename`，去扩展名、大小写不敏感），标题只在没有文件名时兜底——`eval/corpus-refs` 里的三条链接写的是 `./points_policy.md`，而文档标题是《积分规则》，按标题对文件名一条边都建不出来；链接后面紧跟的「第 N 节」属于这条链接。
- **目标存在歧义时不建边**（《X》可能是两篇文档，或「第三节」在两篇里都成立）——宁可少一条，不可错一条。
- **不按语义相似度推断**引用关系。
- 纯路标切片标为 `reference_pointer`：**只用于建边，不参与召回**。它没有信息量，进候选池只是占名额，还会把「命中一句『参见别处』」变成一次成功的召回。
  **落法（#152 实现时定型）**：它照样作为切片落库、照样进向量与关键词索引，**召回侧按 `chunk_type` 过滤**（向量 SQL 与关键词查询各一处）。没有选「干脆不写进存储」是因为 ADR-0025 的 `ready` 闸门要求「切片数 == 向量数 == 关键词文档数」——少写一处就少一份计数，闸门要么报错、要么被迫放宽，两者都比一条过滤条件更糟。过滤条件是显式的、可测的，而且对历史数据也是同一句话（缺这个键的切片不是路标，必须留在召回里）。

### 4. 只做候选，不做裁决

注入点在**候选池成形之后、截断 TopK 之前**，三种检索方式（向量 / 关键词 / 混合）都生效：

| 项 | 取值 | 为什么 |
| --- | --- | --- |
| 种子 | 融合结果前 N 条（≤10） | 只从头部往外扩；尾部整体是弱命中，扩出来的是噪声 |
| 每个种子的邻居 | ≤2 条，优先级 `reference` > `sibling` > `parent` | 引用是「文档作者亲自指的」，兄弟节是「上下文连续」，父节是「够读」 |
| 候选池上限 | ≤30 | 重排有成本，池子不能无限扩 |
| 注入项分数 | `score = 0` | **相关性交给重排裁决** |
| 注入项标记 | `retrieval_source = graph_injection` | 调用方要能分开「直接命中」与「按关系补进来」 |
| 注入内容 | 目标节的**一个代表片**，不是整节 | 整节由折叠展开；先注入整节会让候选池体积失控 |

上限是**常量，不走环境变量**：可调旋钮在样本量不足时必然被调成过拟合值（与折叠的 over-fetch ×3 同一条理由，ADR-0013 决策 6）。

**为什么是 0 分，而不是给高分或按边型给基线分**：图谱只知道「这两节有关系」，不知道「这一节回不回答这个问题」。给它分数，等于让「有引用关系」冒充「相关」，重排就从裁决退化成微调——而重排是整条链路上唯一同时看到 query 与正文的环节。0 分表达的是「它进了池，名次完全由重排决定」，这是唯一诚实的写法。它与「未命中的那一路是 `null` 而不是 0」是同一条纪律的两面：**0 是一个明确的值，不是一个空缺**。

### 5. 跨库边允许存在，注入时按请求范围过滤

- 跨**库**的边允许建：《促销规则》在另一个库，这是真实情况。
- 跨**租户**的边不允许：关系本身不能成为越权通道。
- **注入时按本次请求的 `kb_ids` 与版本范围过滤**：边界由查询过滤堵死，而不是靠建边时禁止跨库。

为什么把边界放在查询而不是放在建边：建边时禁止跨库，等于让「跨库引用」这种最常见的真实关系永远进不来；而查询过滤是一处、可测、覆盖所有注入路径。过滤失败的表现必须是「少注入几条」，不是「多注入一条别的库的」。

### 6. 关系查询失败 = 降级，不是失败

跳过注入，主链路照跑，`degraded_reason` 记一条专码（一因一码，不拼异常文本）。图谱是旁路能力：它的失败不许影响检索结果，也不许把一次成功的检索变成降级失败。

### 7. TopK 之后：只在单元小于「节」时补父节

折叠关掉、或无标题文档时，交付单元小于节，读不懂。此时补父节内容，**不改分数、不改排名，只附加内容**（与「上下文恢复」同一条纪律）。折叠开着时不重复补——折叠已经把整节给了，再补就是材料量翻倍、token 白花。

## 被否掉的方案

| 方案 | 为何不选 |
| --- | --- |
| **边建在切片上**（chunk → chunk） | 切片在一次重建里会变（切法改动、表格行级片增删、h3 边界调整），边跟着碎；而且交付单元是节（ADR-0013），边落在切片上，注入时还得再折一次——等于把折叠逻辑复制进图谱，两份实现迟早分叉（归组键取章节路径前两段这个坑，复制一次就多踩一次）。 |
| **按语义相似度补边** | 三件事同时坏：①与向量召回做同一件事（重复劳动，还多一份存储与一次计算）；②「猜出来的引用」会在回答里长成**假引用**——可回溯性反而下降，而这一轮的全部押注就在可回溯；③无法验收：人工判「这两节语义相近」没有稳定口径，评测也就无法证明它有用。宁缺毋滥。 |
| **建图数据库**（Neo4j 一类） | 只查一跳邻居、边数在十万级以内，PG 一张表加两个索引就够。多一套有状态服务、一套备份、一套连接预算、一套迁移，换来的只是一跳遍历——而这个查询用两个 `WHERE` 就写完了。等真需要多跳再说（见翻案条件）。 |
| **注入时给高分**（或按边型给不同的基线分） | 见决策 4：那是让图谱裁决相关性，而偏见来自「有引用关系」这条与 query 无关的事实。给了分数，重排的输入就带着偏见，评测也无法区分「图谱有用」与「图谱把排序带偏了」。 |
| **建边时禁止跨库** | 跨库引用是最常见的真实关系（政策文档指向另一份规则），禁掉等于把图谱砍成「同库邻居」，而它最有价值的用法恰恰是跨文档指路。越权该在查询侧堵（决策 5），不该在知识侧删。 |

## 影响范围

- **三种检索方式都吃到图谱**：单路评测也能验证它，不必为了测图谱先开混合。
- **响应多一个可选标记**（`retrieval_source`），只在图谱开启且确有注入时出现；**图谱关闭时响应逐字节不变**（黄金哈希用例守着）。具体字段名与位置由 A 票定型，本文只定边界：关闭时不变、开启时「直接命中」与「关系注入」必须可区分。
- **多一条 `degraded_reason` 专码**（关系查询失败），已有的四个码不变，仍是一因一码、不拼异常文本。
- **索引链路多一步抽取**：在切块之后、与切片写进**同一个版本**（ADR-0025）。
- **评测必须新语料**：本仓库现有语料**显式引用 0 条**（「参见」「详见《X》」一条都没有）。图谱的价值用现有语料证明不了，必须另建 3 篇带显式引用的文档 + 8 道定向题，且**不动现有基线语料**（往里加文档等于基线当场失效）。
- **上下文恢复多一个触发条件**：交付单元小于节时补父节；折叠开着时不补。

## 翻案条件

- **新语料里仍抽不出足够的边**（例如 3 篇只抽出 2 条）：问题在抽取规则的覆盖，不在决策。先补抽取（`reference_pointer` 的识别、章节号匹配、跨库文档名消歧），**不要**放宽成「相似度补边」。
- **需要多跳**（补进来的节还要继续往外扩）：那是另一个决定——一跳 → 多跳会把候选池与成本放大一个量级，并且那时才值得讨论图数据库；本文的三种边型仍是它的输入。
- **注入的采纳率极低**（重排后几乎没有注入项留在 TopK）：先看种子是不是选错了（前 N 条里塞了大量弱命中），再考虑降上限；**不要靠给分数救它**。
- **跨库注入被滥用成越权**（哪怕只出现一次越权用例）：收紧到「只有显式 `reference` 才允许跨库注入」，而不是取消跨库。

## 自检

1. **边建在什么上？** —— 节（带文档 id 与版本），不是切片。
2. **图谱决定名次吗？** —— 不。它不是候选来源，注入项 `score = 0`，名次由重排给。
3. **跨库引用怎么办？** —— 允许建边，注入时按本次请求的库与版本过滤。
4. **关系抽取的最大风险是什么？** —— 抽错边（假引用）。所以有歧义就不建，且不按相似度猜。

## 落法（#144 实现时定型）

本文只定边界，具体形状由 A 票落地时定死；这一节记录的就是那一份，改动它等于改契约。

**装配与开关**：组合根 `rag_service.retrieve` 收一个 `graph_factory`（协程工厂，与
`rerank_factory` 同形），缺省 `None` = 这一步不存在。一个开关覆盖三种检索方式——注入位
在「候选池成形之后」这个位置，三种方式都经过它：混合模式在 `hybrid_retrieve` 内部
（`fuse_by_rrf` 之后、`rerank_stage` 之前），单模式（`vector` / `bm25`）在内核里召回
之后、折叠之前。`None` 时不装配、不查询、不加任何字段。

**上限**（常量，不走环境变量）：种子 ≤10、每个种子 ≤2、注入项 ≤30（`app/services/graph_injection.py`）。

**响应**（都在既有形状上追加，摘掉 `null` 后关闭时逐字节不变）：

| 位置 | 字段 | 何时出现 |
| --- | --- | --- |
| 每条结果 | `retrieval_source` = `graph_injection` | **只有**注入项；直接命中项连这个键都没有 |
| `metadata.retrieval` | `graph` = `{injected, seeds, by_relation}` | 开了图谱就出现（与 `rerank` 同一栏口径） |
| 每条结果 | `parent_content` | 折叠关闭且父节有正文时（`content` 仍是切片原文） |
| `metadata.retrieval` | `degraded_reason` = `graph injection failed` | 关系查询失败时（一因一码，不拼异常文本） |

**范围过滤两处独立成立**：边按 `kb_id → 版本` 的配对映射查（与写入侧同一份三列作用域），
服务层再用同一份映射核一遍（`kb_id` 与 `index_version` 都要对上）。查询写错时不报错的那
类故障，只有两道条件都独立成立才挡得住。

**父节恢复的位置**：`collapse_results` 的**不折叠分支**。折叠开着时不补——那交付单元
本来就是节，再补就是材料量翻倍。

## 开关归属（#144 收口时定型）

**图谱不设套餐 / 密钥配置 / 档位三层开关，它跟着重排走。** 条件是「重排生效 ∧ 图谱实现存在」。

理由是这一步的物理性质决定的：注入项 `score = 0` 且追加在候选池末尾，**只有重排会重新给它打分**。重排关着的档位（speed / balanced）里，注入项必然被 `top_k` 截掉——那次关系查询一次也帮不上忙，纯粹是延迟与数据库负担。

三条边界因此写死：

- **不注入时一次关系查询都不发**（不是"查了但丢掉"）；
- **不注入时响应里没有 `graph` 那一栏**（"没有这一步"与"有这一步但没注入"必须可区分）；
- **生产入口的缺省就是生产实现**（`DbSectionGraph`）。曾有一版把缺省设成 `None`，让生产入口"忘了传"，结果整整一票变成死代码：所有用例都绿，没有一条生产调用会走进来。

## 翻案条件（开关归属）

出现「重排关着的档位也要吃图谱」的真实需求时，**先讨论要不要给注入项一个非零基线分**，而不是先加一个开关——加开关不改物理事实（0 分 + 池尾 = 被截掉）。这是与决策二（`score = 0`，相关性交给重排）直接冲突的一步，必须同时改两条。
