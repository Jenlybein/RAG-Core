## 背景

三条具体缺口，都是「调用方拿到一堆命中，却拿不到一份能读懂的材料」的不同侧面：

1. **折叠跨不过节的边界。** 交付单元按标题路径前两段归组，同一个二级标题之内会拼回整节，但两个不同的二级标题之间永不合并。真实文档里一个答案常常横跨两节：2.3 写「超期需人工审核」，2.4 才写「3 个工作日内到账」。只命中 2.3 的调用方拿到的是半份事实。
2. **跨文档的路标完全不被使用。** 文档里写着「详见《促销活动与优惠券使用规则》2.4 节」。那句话今天只是一段文本：它可能被当成一个微弱的命中，也可能根本不为召回所动，但**它从不指路**。
3. **关掉折叠时，小片读不懂。** 「只要精确到那一行」的调用方拿到 `table_row` 或细片，缺父节上下文，读起来像断章。

而「关系」这个能力最容易长成两件坏事，本文的两条边界就是防它们的：

- **自己裁决相关性**：图说相关就相关，重排被架空；
- **变成越权通道**：A 库的边指向 B 库，甚至指向另一个租户的节，于是「关系」本身就是一条绕开白名单的路。

## 决策

### 1. 节点是「节」，不是切片

节的键 = `(租户, 库, 版本, 文档 id, 节 id)`。

- **两端都带文档 id**：不带的话，两份文档都叫「退款 > 流程」会撞同一个 `section_id`，跨文档一对就串（ADR-0025 决策五）。
- **带版本**：边必须与切片在同一版本里才配对；旧边指向新版本里同 id 的节，是一个不会报错的错答案（ADR-0025 决策一）。

### 2. 只有三种边型

| 边型 | 含义 | 例子 |
| --- | --- | --- |
| `reference` | 显式引用：这一节指向另一节 | 「参见《X》第 2.4 节」「本文件第三节」、Markdown 链接、同文档锚点 |
| `sibling` | 兄弟节：同一父节下相邻的两节 | 2.3 与 2.4 |
| `parent` | 父节：这一节与它所属的上一级节 | 2.x 与 2 |

一条有向边一行，字段：作用域（`tenant_id` / `kb_id` / `index_version`）、两端（文档 id + 节 id）、`relation_type`、`metadata`（抽取时命中的原文片段与章节号，供排障）。（历史：`index_version` 该列已在迁移 `e8b2c47d91f5` 删除；这张图谱本身也已被 ADR-0029 否决，正文按当时的论证保留。）

**边型只有三种，不加第四种**：每加一种都要回答「它该不该参与注入、优先级排第几、抽取规则怎么验」，而三种已经覆盖文档里真实存在的结构关系。语义关系（「这两节讲同一件事」）不是结构关系，见决策 3。

### 3. 只认文档显式表达，不按相似度猜边

- 只识别文档中**真实存在的显式表达**：「参见《X》第 N 节」「本文件第三节」、Markdown 链接、同文档锚点。
  **Markdown 链接按文件名对目标**（登记时那份 `documents.source_filename`，去扩展名、大小写不敏感），标题只在没有文件名时兜底——`eval/corpus-refs` 里的三条链接写的是 `./points_policy.md`，而文档标题是《积分规则》，按标题对文件名一条边都建不出来；链接后面紧跟的「第 N 节」属于这条链接。
- **目标存在歧义时不建边**（《X》可能是两篇文档，或「第三节」在两篇里都成立）——宁可少一条，不可错一条。
- **不按语义相似度推断**引用关系。
- 纯路标切片标为 `reference_pointer`：**只用于建边，不参与召回**。它没有信息量，进候选池只是占名额，还会把「命中一句『参见别处』」变成一次成功的召回。
  **落法（#152 实现时定型）**：它照样作为切片落库、照样进向量与关键词索引，**召回侧按 `chunk_type` 过滤**（向量 SQL 与关键词查询各一处）。没有选「干脆不写进存储」是因为 ADR-0025 的 `ready` 闸门要求「切片数 == 向量数 == 关键词文档数」——少写一处就少一份计数，闸门要么报错、要么被迫放宽，两者都比一条过滤条件更糟。过滤条件是显式的、可测的，而且对历史数据也是同一句话（缺这个键的切片不是路标，必须留在召回里）。

### 4. 只做候选，不做裁决

注入点在**候选池成形之后、截断 TopK 之前**，三种检索方式（向量 / 关键词 / 混合）都生效：

| 项 | 取值 | 为什么 |
| --- | --- | --- |
| 种子 | 融合结果前 N 条（≤10） | 只从头部往外扩；尾部整体是弱命中，扩出来的是噪声 |
| 每个种子的邻居 | ≤2 条，优先级 `reference` > `sibling` > `parent` | 引用是「文档作者亲自指的」，兄弟节是「上下文连续」，父节是「够读」 |
| 候选池上限 | ≤30 | 重排有成本，池子不能无限扩 |
| 注入项分数 | `score = 0` | **相关性交给重排裁决** |
| 注入项标记 | `retrieval_source = graph_injection` | 调用方要能分开「直接命中」与「按关系补进来」 |
| 注入内容 | 目标节的**一个代表片**，不是整节 | 整节由折叠展开；先注入整节会让候选池体积失控 |

上限是**常量，不走环境变量**：可调旋钮在样本量不足时必然被调成过拟合值（与折叠的 over-fetch ×3 同一条理由，ADR-0013 决策 6）。

**为什么是 0 分，而不是给高分或按边型给基线分**：图谱只知道「这两节有关系」，不知道「这一节回不回答这个问题」。给它分数，等于让「有引用关系」冒充「相关」，重排就从裁决退化成微调——而重排是整条链路上唯一同时看到 query 与正文的环节。0 分表达的是「它进了池，名次完全由重排决定」，这是唯一诚实的写法。它与「未命中的那一路是 `null` 而不是 0」是同一条纪律的两面：**0 是一个明确的值，不是一个空缺**。

### 5. 跨库边允许存在，注入时按请求范围过滤

- 跨**库**的边允许建：《促销规则》在另一个库，这是真实情况。
- 跨**租户**的边不允许：关系本身不能成为越权通道。
- **注入时按本次请求的 `kb_ids` 与版本范围过滤**：边界由查询过滤堵死，而不是靠建边时禁止跨库。

为什么把边界放在查询而不是放在建边：建边时禁止跨库，等于让「跨库引用」这种最常见的真实关系永远进不来；而查询过滤是一处、可测、覆盖所有注入路径。过滤失败的表现必须是「少注入几条」，不是「多注入一条别的库的」。

**口径澄清（#156 复核时写下，本条不新增决定，只把「允许」与「这一轮建了什么」分开）**：

| 问题 | 答案 |
| --- | --- |
| 表结构允许跨库边吗？ | **允许**。边的键是 `(租户, 库, 版本, 文档 id, 节 id)`，目标那三列可以指向另一个库——约束里没有「同库」这一条 |
| 越权由谁堵？ | **注入侧的查询过滤**（本次请求的 `kb_ids` + 版本配对映射），不是建边时禁止 |
| 本轮抽取实际建了什么？ | **只建同库边**。目标解析用的是**库级目录**：`catalog_from_rows` / `load_catalog` 的 `EdgeScope` 就是「租户 + 一个库 + 一个版本」，跨库文档根本不在目录里。所以「详见《另一个库的规则》2.4 节」在本轮**解析不到目标，一条边都不建**（按决策 3「目标歧义 / 不存在就不建边」处理，不是按越权处理） |
| 这算不算与「允许跨库」矛盾？ | 不算。**允许**说的是结构与该不该禁，**这一轮建了什么**说的是抽取的输入边界（目录是库级的）。要建跨库边，需要先把目录扩到「本租户这次可能查到的多个库」，那是另一次决定（见翻案条件），而不是把表约束收紧 |

- 评测语料里的三条 Markdown 链接与「详见《X》第 N 节」都在**同一个库**（`eval/corpus-refs`）里，所以「跨文档引用」这一组题验的是同库跨文档，**不是**跨库——报告与结论里不许把两者说成同一件事。
- 注入侧的范围过滤是**一处**（查询里，按请求的 `kb_ids` 与版本配对映射），所以「跨库能不能注入」这个问题的答案恒为「取决于本次请求的库范围」，与建边时扩大了什么无关。

### 6. 关系查询失败 = 降级，不是失败

跳过注入，主链路照跑，`degraded_reason` 记一条专码（一因一码，不拼异常文本）。图谱是旁路能力：它的失败不许影响检索结果，也不许把一次成功的检索变成降级失败。

### 7. TopK 之后：只在单元小于「节」时补父节

折叠关掉、或无标题文档时，交付单元小于节，读不懂。此时补父节内容，**不改分数、不改排名，只附加内容**（与「上下文恢复」同一条纪律）。折叠开着时不重复补——折叠已经把整节给了，再补就是材料量翻倍、token 白花。

## 被否掉的方案

| 方案 | 为何不选 |
| --- | --- |
| **边建在切片上**（chunk → chunk） | 切片在一次重建里会变（切法改动、表格行级片增删、h3 边界调整），边跟着碎；而且交付单元是节（ADR-0013），边落在切片上，注入时还得再折一次——等于把折叠逻辑复制进图谱，两份实现迟早分叉（归组键取章节路径前两段这个坑，复制一次就多踩一次）。 |
| **按语义相似度补边** | 三件事同时坏：①与向量召回做同一件事（重复劳动，还多一份存储与一次计算）；②「猜出来的引用」会在回答里长成**假引用**——可回溯性反而下降，而这一轮的全部押注就在可回溯；③无法验收：人工判「这两节语义相近」没有稳定口径，评测也就无法证明它有用。宁缺毋滥。 |
| **建图数据库**（Neo4j 一类） | 只查一跳邻居、边数在十万级以内，PG 一张表加两个索引就够。多一套有状态服务、一套备份、一套连接预算、一套迁移，换来的只是一跳遍历——而这个查询用两个 `WHERE` 就写完了。等真需要多跳再说（见翻案条件）。 |
| **注入时给高分**（或按边型给不同的基线分） | 见决策 4：那是让图谱裁决相关性，而偏见来自「有引用关系」这条与 query 无关的事实。给了分数，重排的输入就带着偏见，评测也无法区分「图谱有用」与「图谱把排序带偏了」。 |
| **建边时禁止跨库** | 跨库引用是最常见的真实关系（政策文档指向另一份规则），禁掉等于把图谱砍成「同库邻居」，而它最有价值的用法恰恰是跨文档指路。越权该在查询侧堵（决策 5），不该在知识侧删。 |

## 影响范围

- **三种检索方式都吃到图谱**：单路评测也能验证它，不必为了测图谱先开混合。
- **响应多一个可选标记**（`retrieval_source`），只在图谱开启且确有注入时出现；**图谱关闭时响应逐字节不变**（黄金哈希用例守着）。具体字段名与位置由 A 票定型，本文只定边界：关闭时不变、开启时「直接命中」与「关系注入」必须可区分。
- **多一条 `degraded_reason` 专码**（关系查询失败），已有的四个码不变，仍是一因一码、不拼异常文本。
- **索引链路多一步抽取**：在切块之后、与切片写进**同一个版本**（ADR-0025）。
- **评测必须新语料**：本仓库现有语料**显式引用 0 条**（「参见」「详见《X》」一条都没有）。图谱的价值用现有语料证明不了，必须另建 3 篇带显式引用的文档 + 8 道定向题，且**不动现有基线语料**（往里加文档等于基线当场失效）。
- **上下文恢复多一个触发条件**：交付单元小于节时补父节；折叠开着时不补。

## 翻案条件

- **新语料里仍抽不出足够的边**（例如 3 篇只抽出 2 条）：问题在抽取规则的覆盖，不在决策。先补抽取（`reference_pointer` 的识别、章节号匹配、跨库文档名消歧），**不要**放宽成「相似度补边」。
- **需要多跳**（补进来的节还要继续往外扩）：那是另一个决定——一跳 → 多跳会把候选池与成本放大一个量级，并且那时才值得讨论图数据库；本文的三种边型仍是它的输入。
- **注入的采纳率极低**（重排后几乎没有注入项留在 TopK）：先看种子是不是选错了（前 N 条里塞了大量弱命中），再考虑降上限；**不要靠给分数救它**。
- **跨库注入被滥用成越权**（哪怕只出现一次越权用例）：收紧到「只有显式 `reference` 才允许跨库注入」，而不是取消跨库。

## 自检

1. **边建在什么上？** —— 节（带文档 id 与版本），不是切片。
2. **图谱决定名次吗？** —— 不。它不是候选来源，注入项 `score = 0`，名次由重排给。
3. **跨库引用怎么办？** —— 允许建边，注入时按本次请求的库与版本过滤。
4. **关系抽取的最大风险是什么？** —— 抽错边（假引用）。所以有歧义就不建，且不按相似度猜。

## 落法（#144 实现时定型）

本文只定边界，具体形状由 A 票落地时定死；这一节记录的就是那一份，改动它等于改契约。

**装配与开关**：组合根 `rag_service.retrieve` 收一个 `graph_factory`（协程工厂，与
`rerank_factory` 同形），缺省 `None` = 这一步不存在。一个开关覆盖三种检索方式——注入位
在「候选池成形之后」这个位置，三种方式都经过它：混合模式在 `hybrid_retrieve` 内部
（`fuse_by_rrf` 之后、`rerank_stage` 之前），单模式（`vector` / `bm25`）在内核里召回
之后、折叠之前。`None` 时不装配、不查询、不加任何字段。

**上限**（常量，不走环境变量）：种子 ≤10、每个种子 ≤2、注入项 ≤30（`app/services/graph_injection.py`）。

**响应**（都在既有形状上追加，摘掉 `null` 后关闭时逐字节不变）：

| 位置 | 字段 | 何时出现 |
| --- | --- | --- |
| 每条结果 | `retrieval_source` = `graph_injection` | **只有**注入项；直接命中项连这个键都没有 |
| `metadata.retrieval` | `graph` = `{injected, seeds, by_relation}` | 开了图谱就出现（与 `rerank` 同一栏口径） |
| 每条结果 | `parent_content` | 折叠关闭且父节有正文时（`content` 仍是切片原文） |
| `metadata.retrieval` | `degraded_reason` = `graph injection failed` | 关系查询失败时（一因一码，不拼异常文本） |

**范围过滤两处独立成立**：边按 `kb_id → 版本` 的配对映射查（与写入侧同一份三列作用域），
服务层再用同一份映射核一遍（`kb_id` 与 `index_version` 都要对上）。查询写错时不报错的那
类故障，只有两道条件都独立成立才挡得住。（历史：`index_version` 已在迁移 `e8b2c47d91f5` 删除，
范围现在只有 `kb_ids`；这张图也被 ADR-0029 撤销，正文按当时的论证保留。）

**父节恢复的位置**：`collapse_results` 的**不折叠分支**。折叠开着时不补——那交付单元
本来就是节，再补就是材料量翻倍。

## 开关归属（#144 收口时定型）

**图谱不设套餐 / 密钥配置 / 档位三层开关，它跟着重排走。** 条件是「重排生效 ∧ 图谱实现存在」。

理由是这一步的物理性质决定的：注入项 `score = 0` 且追加在候选池末尾，**只有重排会重新给它打分**。重排关着的档位（speed / balanced）里，注入项必然被 `top_k` 截掉——那次关系查询一次也帮不上忙，纯粹是延迟与数据库负担。

三条边界因此写死：

- **不注入时一次关系查询都不发**（不是"查了但丢掉"）；
- **不注入时响应里没有 `graph` 那一栏**（"没有这一步"与"有这一步但没注入"必须可区分）；
- **生产入口的缺省就是生产实现**（`DbSectionGraph`）。曾有一版把缺省设成 `None`，让生产入口"忘了传"，结果整整一票变成死代码：所有用例都绿，没有一条生产调用会走进来。

## 翻案条件（开关归属）

出现「重排关着的档位也要吃图谱」的真实需求时，**先讨论要不要给注入项一个非零基线分**，而不是先加一个开关——加开关不改物理事实（0 分 + 池尾 = 被截掉）。这是与决策二（`score = 0`，相关性交给重排）直接冲突的一步，必须同时改两条。

> 📌 **关于「注入总数 ≤30」这条上限**：种子上限 10、每种子 2 条，所以实际可达的最大注入数是 20，30 这个闸门**当前不可达**。它留着是纵深防御——一旦有人调整种子数或每种子邻居数，这条闸门仍然成立，而不是靠「反正够不到」来保证。它不是死代码，是**第二条独立约束**：三条上限里任何一条被改，另外两条仍然各自兜底。

## 决策 8（#158，测量后定型）：补两条「定位符」规则，**不引入 LLM**

### 先测：正则的语法对不上真实文档的语法

#152 的抽取规则是照着三种表达写的，而 `eval/corpus-refs` 那三篇语料**出自同一份设计文档**——9/9 全绿只证明「我们自己写的写法被认出来了」，不证明真实文档里的写法被认出来。所以先做一份不属于本轮自造语料的标注集（`eval/graph-labels/`，87 条、四类、三档语料），再量两个数：

| 档 | 可外推性 | explicit | 建出边 | TP / FP / FN | precision | recall |
| --- | --- | --- | --- | --- | --- | --- |
| 工程文档（真，本仓库 3 篇 ADR） | **可**外推到带链接与编号的技术文档 | 18 | 3 | 1 / 2 / 17 | 0.3333 | **0.0556** |
| 政策散文（合成 5 篇） | 不可外推 | 18 | 1 | 1 / 0 / 16 | 1.0000 | 0.0588 |
| 会议纪要（合成 2 篇） | 不可外推 | 2 | 2 | 1 / 1 / 1 | 0.5000 | 0.5000 |
| **总体** | — | 37 | 6 | 3 / 3 / 34 | 0.5000 | **0.0811** |

票面的阈值是「recall ≥ 0.7 且 precision ≥ 0.95 才不上 LLM」。按这个阈值，第一版报告得出「引入 LLM 当候选提出者」。**那个结论是错的**——详见下一节。

### 低于阈值 ≠ 需要语义：先问缺的是「语法」还是「语义」

阈值只回答「够不够好」，不回答「为什么不好」。补一步测量：对每一条 `explicit` 标注，不经过抽取器，直接问

> 给定 evidence 原文与目标节标题，**有没有一种确定性匹配能唯一定位到那个节？**

（脚本口径见 `scripts/eval_graph_ceiling.py`：只做归一化与编号比较，不含任何模型。）

| 档 | explicit | 可确定性定位 | 需语义 | 上限 recall |
| --- | --- | --- | --- | --- |
| 工程文档（真） | 18 | **17** | 1 | **0.944** |
| 政策散文（合成） | 18 | 18 | 0 | 1.000 |
| 会议纪要（合成） | 2 | 2 | 0 | 1.000 |
| **总体** | 38 | **37** | 1 | **0.974** |

按规则分解：**编号定位（R2）27 条**、引号标题名（R1）7 条、裸标题名（R1）3 条。

只剩 **1 条**需要语义：`见背景四条` 指向一个两字标题「背景」——两字标题在正文里到处都是，出于精度考虑被短名保护挡住。换句话说，**可外推档的缺口几乎全是语法，不是语义。**

工程档那 15 条漏项的共同形状，**不是「意思没读懂」，而是「定位符的写法没覆盖」**：

```text
（ADR-0025 决策五）              → 目标节标题「决策五：节的身份证不含版本」
见决策 3                        → 目标节标题「3. 只认文档显式表达，不按相似度猜边」
见文末「后续修订（第 7 步）」     → 目标节标题「后续修订（第 7 步，#73，2026-11-10）：…」
本文「后果」一节                 → 目标节标题「后果」
```

作者在这些地方写的是**节的名字或编号**，不是「第 N 节」。这不是语义问题：标题名就在目录里，编号就在标题开头，两者都能机械比对。

### 决策

补两条**确定性**规则，**不引入 LLM**：

| 规则 | 识别什么 | 怎么解析 |
| --- | --- | --- |
| **R1 标题名引用** | 引号括住的短语（`「后果」`）或紧跟引用动词的裸标题名（`见翻案条件`） | 归一（去标点 / 全角→半角 / 中文数字→阿拉伯）后，**等于或前缀于**目标文档里唯一的一条节标题 |
| **R2 编号定位** | `决策 N` / `第 N 条` / `第 N 款` / `第 N 项` / `Section N` / `第 M 章第 N 节` | 取编号，与目标文档里**标题开头编号恰为 N 的那唯一一条**比对（`2` 不匹配 `2.1`） |

三条守卫（少一条都会让精度塌掉）：

- **唯一性**：命中 0 条或 >1 条一律弃权，与决策 3 同口径；
- **短名保护**：裸标题名只在 ≥4 字时才试（`背景`、`自检` 这种两字标题在正文里到处都是，撞上的概率不是「可能」而是「必然」）；
- **仍然不建语义边**：两条规则都只比对「作者写下的定位符」，不引入任何相似度计算。

### 为什么不是 LLM

| 维度 | 补规则 | LLM 提候选 |
| --- | --- | --- |
| 能救回的（工程档） | **15 / 18** | 最多 18 / 18（但那 3 条是裸标题名，R1 也能覆盖） |
| 可复现 | 同一文档重建两次 → 同一批边 | 每次构建可能不同边 |
| 成本 | 零 | 每文档每次构建一次调用 |
| 失败形态 | 认不出 → 少一条边（安全） | 提错目标 → 由代码守门拦下（也安全，但要为它加 confidence 字段、归属索引多一档、GLOSSARY 多两个词条） |

决策 1 那句话在这里仍然成立：**宁可关系少，不可关系错**。既然缺的是语法而不是语义，用 LLM 换回的 0 条真实增量（R1 已覆盖那 3 条）不值得让「边的可复现性」这条性质作废。

### 翻案条件

1. **按 R1 + R2 重测之后**，工程档 recall 仍 < 0.7 或 precision < 0.95 → 那时才考虑 LLM 提候选（分工仍是「LLM 只提三元组、代码守门」）；
2. 出现「散文式指代」成为主流引用形态的语料（`见上文` / `另见后文关于退款的说明` / `按上次说的`）→ 那是语义问题，规则确实做不好；
3. 语料里出现**第四种编号体系**（例如 `§2.4`、`Art. 5(2)`），先加规则，不要直接跳到模型。

### 与「路标切片」的关系

路标切片（`is_reference_pointer`）判定的是「这一片除了引用没有别的内容」，与本节无关；但 R1 / R2 扩大了「什么算引用表达」，所以路标判定的 `reference_spans` 也要同步认识这两种形态——否则会出现「这一片确实是纯路标，但没被识别成路标」的漏网。

### 重测结果（#158 收口，2026-11-14）

同一份标注集、同一个测量脚本，按 R1 + R2 重测（`scripts/eval_graph_labels.py --write` → `eval/graph-labels/report.md`）：

| 档 | explicit | 建出边（前→后） | TP / FP / FN（前→后） | precision（前→后） | recall（前→后） |
| --- | --- | --- | --- | --- | --- |
| 工程文档（真） | 19 | 3 → **14** | 1 / 2 / 17 → **14 / 0 / 5** | 0.3333 → **1.0000** | 0.0556 → **0.7368** |
| 政策散文（合成） | 18 | 1 → **16** | 1 / 0 / 16 → **16 / 0 / 1** | 1.0000 → **1.0000** | 0.0588 → **0.9412** |

票面阈值（recall ≥ 0.7 且 precision ≥ 0.95）**每一档都成立 → 不引入 LLM**。

### 补了一条标注，以及为什么这不算「按结果调尺子」

首次重测时工程档 precision 是 0.9286、总体 0.9688（合并档过阈值、工程档差 0.0214），差的都是同一条 FP：ADR-0013 的「后续修订」那一节正文里的一句

```text
归组键取章节路径前两段、over-fetch ×3 仍是写死的常数〔原文此处括注了那条决策的编号〕，不随这次归属变更挪进配置。
```

独立核对原文与标题清单就能判它是**真引用**：ADR-0013 的标题里有一条编号 6 的决策节，作者在指向自己写的**那一条关于 over-fetch 的决策**（编号 6 那一节），抽取器建出的边方向与粒度都对。**所以错在标注集漏了这条 `explicit`，不在抽取器。**

补的依据是原文，不是抽取器输出——这两者的区别决定了它是不是调尺子：

- 若依据是「抽取器建了它，所以它算对」→ 那是把尺子拟合到被测物，结论作废；
- 若依据是「原文里的定位符确实指向那个节」→ 那是修正标注遗漏，属正常测量迭代。

补完之后每一档 precision 都是 1.0000，不再需要「合并档过阈值、工程档差一点」这种带解释的表述。

**仍漏的 6 条全部不是语义问题**：四条是「同名两节」（本节新增了一个与本文既有小节同名的三级标题，目录里变成两条）→ 唯一性守卫弃权；一条指向两字标题（短名保护）；一条指向另一份文档（不在本目录里，解析不到）。原样表达式见 `eval/graph-labels/report.md` 的漏项表。

**R1 / R2 落在哪几处**

| 规则 | 识别 | 解析 |
| --- | --- | --- |
| **R1 标题名** | 引号短语（要有「本文 / 文末 / 文档编号 / 链接」或「一节 / 一条」后缀给出上下文）；裸标题名（紧跟 `见 / 按 / 依据…` 引用动词） | 归一后等于或前缀于目标文档里**唯一**一条节标题；裸名 **≥4 字**才试 |
| **R2 编号** | `决策 N`（要引用框架：`见 / 按 / （` 或 `说 / 里 / 中`；范围引用 `决策 M–N` 不算）；`第 N 节/条/款/项`（同文档必须有限定语，跨文档必须《标题》）；`第 M 章第 N 节`；`Section N`（`of the X` 指别的文档不算） | 标题开头编号归一后**恰为 N 的唯一一条**（`2` 不匹配 `2.1`）；`决策 N` 先按「决策 N：…」惯例找，再落回「3. …」惯例 |

**三条守卫怎么落**：①唯一性 = 标题名 / 编号解析命中 0 或 >1 直接 `None`（与决策 3 同口径）；②短名保护 = 裸标题名归一后 <4 字不试（`背景` / `自检` 直接不进入候选）；③不建语义边 = 两条规则只比对作者写下的定位符，没有引入任何相似度。

**收口时补的四条精度守卫**（都是「哪些形态不算引用表达」，不是放宽判据）：

- 引号短语没有文档上下文的不算（光在引号里只说明在引用原文，不说明指向哪一节）；
- 同一行出现 `→` 的「写法 → 目标」对照行不算（决策 8 自己那张例子表就长这样，切块后围栏消失、箭头还在）；
- 围栏代码块里的内容不算引用（格式示例）；
- 否定词清单（`已作废 / 已废止 / 已关闭 / 不再追踪 / 已取代 / 仅供参考`）在**产生候选之后、解析之前**挡掉「提到但不依赖」。

**仍然漏掉的 6 条**（没有一条是「意思没读懂」）：

| 标注 | 为何仍漏 |
| --- | --- |
| eng-0027-11 / eng-0027-14 `（见翻案条件）` | 这个标题在本文有两节（顶层一节 + 决策 8 下一节），唯一性守卫弃权 |
| eng-0013-06 / eng-0013-07 `本文「后果」一节` | 这个标题在 ADR-0013 有两节同名（顶层与第 7 步修订下），同上 |
| eng-0028-03 `见背景四条` | 目标标题只有两个字，短名保护不试（见下） |
| pol-p05-05 `Section 1 of the SLA terms` | `Section N` 后面写了**另一份文档**（SLA terms），本目录解析不到——R2 只认「标题编号」，不认英文文档名 |

**「见背景四条」为什么仍不做**：要救它，得先做「四条 = 第四节」的口语换算（真写「第 4 条」时 R2 已经覆盖），再把**两字标题**放进来。两字标题在正文里到处都是（`背景` / `自检` / `决策` / `后果`），放开的不是「可能撞」而是「必然撞」；而它在唯一要外推的工程档里只出现 1 次（18 条里 1 条）。用系统性误报换 1 条召回，与决策 1「宁可关系少，不可关系错」冲突。

**与「路标切片」同步**：`reference_spans` / `is_reference_pointer` 已认识 R1 / R2 的形态（决策号无目录也能认；裸标题名在给了本文标题清单时认），`indexing_service` 在切块后把本文标题清单传进去——否则「纯路标片」会漏成普通切片。

**与「可定位上限」的差**：`scripts/eval_graph_ceiling.py` 的上限（工程档 0.944 / 总体 0.974）只判「给定目标标题有没有一种确定性匹配能定位到它」，**不含唯一性**；因此它把两个同名标题的那 4 条算成了「可定位」。真实规则在唯一性守卫下会弃权，工程档实测 recall 0.7222 就是这两类（4 条）+ 短名（1 条）的差。这个差是规则的确定性代价，不是实现漏了。

> 📌 **本节自己也在被测的语料里。** 上表是在**本节加入之前**的文档状态下测的；此后只重跑报告不重测，数字不保证不变。所以本节文字刻意不写可解析的定位符——否则它会成为被测量的一部分，改变自己引用的那些数字。

> 📌 **写这份文档时要遵守这份文档自己的规则。** ADR-0027 是被测量的源文档之一，所以本节第一次补写时在正文里内联写的那两处定位符（一个「文档编号 + 引号标题名」的组合、一个同文档决策号）被抽取器当成引用，建出两条**假边**，总体 precision 从 1.0000 掉到 0.9412、判定直接翻成「引入 LLM」。
>
> 结论有两条：①**被测量的文档里不能内联写定位符**，示例一律放进围栏代码块（围栏内容不参战）；②`tests/test_graph_labels.py::test_report_matches_the_current_state` 是这条的守卫——报告与当前标注集/抽取器不一致就红，所以下次改这段文字必须重跑 `--write`。
