# 0004. API Key 本期明文存储，生产再改「哈希 + 密文」

- 状态：已采纳（**本期口径**，生产前必须复审）
- 日期：2026-11-03
- 相关：`GLOSSARY.md`「API Key」、「docs/架构.md」②平台管控

## 背景

Key 的正确存储方式是「只存哈希」：数据库里放 `sha256(key_value)`，校验时把请求里的 Key 哈希后比对。这样即使库被拖走、备份泄露、DBA 看库、日志打点，也拿不到可用的 Key。

但这个项目的控制台里有一个必须看原文的界面——**调试台**。它要拿你自己那把 Key 去打真实检索接口（走完整六道关：鉴权、套餐、档位、限流、配额、隔离）。如果只存哈希，Key 生成后一次没抄下来，面板上就再也取不出来，调试台等于废掉一半。

## 决策

**本期明文存储**：`api_keys.key_value` 直接存 `rc_live_` + 32 位随机十六进制的原文；备注名为独立列 `label`。

这是**明确标注的取舍**，不是疏忽：

- 面板可直接展示 Key，调试台能用它打真实接口；
- 风险由「本期是内部/演示环境」这个前提承担；
- 生产前必须改成「哈希 + 密文」双列：哈希列用于查找（唯一索引），密文列用于面板展示，明文只在创建时返回一次。

## 后果

### 正面

- 调试台可以「选一把 Key → 打真实接口」，开发者看到的就是线上真实链路，而不是模拟。
- 校验路径最简单：`api_key_repo.get_by_value(db, raw)` 一次索引查询。
- 运营自查方便：面板上直接能看出「这把 Key 是谁的」。

### 代价

- **任何能读库的人都能拿到可用 Key**（备份、只读从库、DBA、误打的日志）。这是必须写进风险清单的一条。
- 未来改「哈希 + 密文」要做一次数据迁移：补哈希列、回填、切换查找路径，并接受「老 Key 面板不可见」这个体验降级（或提供「重新生成」）。
- 与「最小权限」原则冲突，得靠环境边界（内网、访问控制、审计）来补。

## 备选方案

| 方案 | 为何不选（本期） |
| --- | --- |
| 只存哈希 | 调试台拿不到原文，功能废掉一半；若要保留调试台就得另建一套「演示 Key」机制，反而更复杂 |
| 哈希 + 密文双列 | 这是**生产**的正确解，本期不做是因为多一层密钥管理（加密密钥放哪、怎么轮换），会把本期的重点（多租户与配额）冲淡 |
| 明文 + 只展示一次 | 与「只存哈希」等价，面板刷新即失效，调试台同样受影响 |
| 不存 Key，用 OAuth | 单机 + 服务间调用的场景下 OAuth 过重，且 MCP 入口要的是 `Authorization: Bearer` |

## 后续修订（第 7 步收尾，2026-11-10）：Key 前缀从 `rk_live_` 改为 `rc_live_`

**改了什么**：`API_KEY_PREFIX` 由 `rk_live_` 改为 `rc_live_`，本文与其它文档里出现的前缀一并更新。**存储方式不变**——仍是明文（本文的主决策一字未动）。

**为什么改**：`rk_live_` 与 **Stripe 的 restricted key 前缀完全相同**。这不是措辞问题，它有一个具体的、已经发生过的事故面：推送代码时 GitHub 的 push protection 把测试里的假 Key 判成「Stripe Live API Restricted Key」并**拒绝推送**；同一套规则也会作用在租户身上——任何人把一把真实的 RAG Key 贴进 issue、日志或群里，都会被判成支付平台密钥泄露，久而久之是报警疲劳。

**为什么不是「只改测试里的假值」**：假值只是症状。只要生产 Key 仍以 Stripe 的前缀开头，同一个误报就会在每一个新文件、每一次真实泄露告警里重演。前缀本身是产品契约的一部分，改契约比改测试彻底。

**代价**：已发出的 `rk_live_` Key 不再匹配（本步刚完成，库里只有演示与测试数据，因此不做双前缀兼容）；历史提交里的字符串一并改写，因此**改写前后所有提交的 sha 都变了**——若有人已经克隆过旧历史，需要重新克隆而不是拉取。

**判据**：前缀应当属于自家命名空间，且不与任何已知第三方前缀冲突。`rc_` 取自 RAG Core，符合这一条。
