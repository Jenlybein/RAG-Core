# 0019. 调试台的 Key 由用户自己粘贴，页面永不从服务端取原文

- 状态：已采纳（现行口径）
- 日期：2026-11-10；修订：2026-11-23
- 相关：`docs/adr/0004-api-key-hashed-storage.md`、`GLOSSARY.md`「API Key」「调试台」

## 背景

调试台要拿**真实生效的那把 Key** 去打数据面接口，走完整六道关（鉴权、白名单、套餐、档位、限流、配额）——开发者看到的是线上真实链路，而不是模拟；超配额、被限流时调试失败是**真实结论**。

ADR-0004 之后，服务端已经拿不出原文：`api_keys` 里只有 `key_hash` 与 `key_tail`，`GET /console/keys` 只有 `key_masked`。于是问题变成：**那把 Key 从哪来？**

## 决策

**由用户自己粘贴。**

1. 检索页（调试台）不再是「选一把 Key」，而是一个粘贴框：用户把签发时拿到的那一整条
   `rc_live_<key_id>.<32 位密钥>` 粘进去；
2. 前端从串里**本地**解出 `key_id`（`lib/apiKey.ts`），再到已经拉取的 Key 列表里找到那一行
   ——「这把 Key 的密钥配置」因此照旧显示得出来，白名单预筛、改配置深链也照旧成立，
   而密钥本体只出现在 `Authorization` 头里；
3. **原文只进内存**：不写 `localStorage` / `sessionStorage`、不进 URL、不进页面标题。
   刷新即失效，重新粘一次；
4. 签发成功的那次弹窗给两个出口：`复制` 与`去调试台试用`（后者把刚签发的串直接交给请求层，
   跳过去）。这是唯一一次「不用再粘」的例外，因为它就发生在同一屏里。

## 后果

### 正面

- 浏览器里**没有任何路径**能把某把 Key 的原文再取回来一次：XSS、恶意扩展、被污染的依赖
  都拿不到「一次拿到该租户全部 Key」那个捷径。
- 服务端一条新入口都不加：鉴权仍然走真实的 `Authorization: Bearer`，六道关一道不少，
  「被配额打断」这件事照样学得到。
- 一套身份、一条路径：调试台打的就是任何外部集成会打的那个接口。

### 代价

- **体验变差**：每次刷新页面都要重新粘一次。这是「原文不落地」的直接价格，不是遗漏。
- **粘贴本身是新的失手面**：粘一半、粘成打码形态（`rc_live_…4f3a2`）、粘成上一套环境的 Key。
  所以后端把「格式不对」单列成一条消息（`MSG_KEY_MALFORMED`），前端在本地先解一次串
  ——两层都只回答「这串像不像我们的 Key」，不替后端判断它对不对。
- 「这把 Key 能查哪些库」要靠本地解出的 `key_id` 去列表里对一行；对不上就提示「不在本租户
  的列表里」，而不是发一次注定 20010 的请求。

## 备选方案

| 方案 | 为什么不选 |
| --- | --- |
| 服务端中继：`POST /console/debug/{retrieve,…}` 收 `key_id`，服务端用这一行构造身份再进 `retrieval_gate` | 六道关能保住，但它**不再是真实 HTTP 路径**——`Bearer` 解析、`Authorization` 头的形状、客户端错误处理这一整层都学不到。多一条入口、多一套错误契约，换来的只是省一次粘贴。 |
| 只有「刚签发、还在本页内存里」的那把能试，刷新即失效 | 与「粘一次」等价，但把可用范围缩到签发那一屏：隔天回来复现一个问题就做不到了。 |
| `GET /console/keys` 继续发明文，靠前端纪律兜住 | 那正是要拆掉的东西：原文一旦过网，XSS / 扩展 / 依赖污染就一次拿到全部租户 Key。纪律不是边界，数据流才是。 |
| 用户粘贴后存 `sessionStorage`，刷新不丢 | 刷新不丢的代价是 XSS 也拿得到；「只进内存」这条纪律比省一次粘贴重要。 |

## 与「只此一次」的对齐

签发响应里的 `key_plaintext` 是原文唯一一次露面（ADR-0004）。调试台的粘贴框是它的**消费者**，不是第二个来源：两件事合起来才是完整的闭环——**签发时看一次 → 自己保存 → 要用时粘回来**。想再要一次，只能重签一把。
