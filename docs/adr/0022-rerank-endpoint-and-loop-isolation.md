# 0022. 重排端点的配置来源，与连接复用按事件循环隔离

- 日期：2026-11-12（修订：2026-11-13）
- 相关：父 spec #113「第 10 步」、票 #116 / #117 / #118 / #119、ADR-0002「六类 Provider」、**ADR-0009「异步索引用 Celery + `asyncio.run`」**（它的前提句已由 #117 修订，本文只引用）、ADR-0011「LangChain 边界」、`GLOSSARY.md`「重排端点」「模型配置」「模型角色」「Worker 常驻循环」、`.env.example`、`app/core/config.py`、`app/providers/rerank/`、`app/core/http_clients.py`、`app/core/loop_pool.py`（**已删除**，见文末修订）

## 背景

第 10 步把两件原本「能跑就行」的事各自逼成了一个决定：

1. **重排从「借大模型逐条打分」换成「专用 Cross-Encoder 端点」**（`Qwen3RerankProvider`，`qwen3.7-text-rerank`，OpenAI 兼容 `POST {base}/reranks`）。新端点要配地址、模型、密钥、超时——这些值放哪儿？本仓库已经有一套「管理员可增删的模型接入 + 两个角色指针」（`model_configs` + `runtime_settings` 的 `model.role.fast` / `model.role.strong`），看起来正合适。
2. **模型类流量的连接从「每请求新建」改成「复用 + 确定性收尾」**。改造前一次检索要建 3~4 个 `httpx.AsyncClient`，每一题重做一次 TLS 握手，收尾还刷一串 `Event loop is closed`。要复用，就得决定客户端活多久、归谁管、跨不跨事件循环。

两条决定同属一句话：**配置跟着语义走，连接跟着事件循环走。** 它们都留下了会长期约束后来者的边界，所以单独立案。

## 决策

### 决策一：重排端点的配置来源是 `.env` + 配置目录，不进 `model_configs`

`RERANK_BASE_URL` / `RERANK_MODEL` / `RERANK_TIMEOUT_SECONDS` 写在 `.env`；端点密钥是 `RERANK_API_KEY`，**留空回落 `MODEL_API_KEY`**（重排与嵌入同属百炼，通常共用一把）。地址与模型两个键登记进 `runtime_settings` 白名单、属 `hot` 档，可以在配置页热改；密钥是 `locked` 档且只显示打码值——换一把凭证本来就是「换一条接入」，该由部署方改 `.env` 并重启。`model_configs` 表**一个字段都不加**，也不加 `rerank` 用途位或第三个指针键。

**考虑过的替代方案**：

| 方案 | 为什么不选 |
| --- | --- |
| 在 `model_configs` 加一个 `rerank` 用途位（或第三个指针键） | 那张表是**可增删的 chat 供应商接入**：`provider` 只能取 `llm_vendors` 注册表里的六个 chat 供应商，其余字段也是按 chat 形状定的。重排是另一个产品面——同一台百炼上路径段都不同（`compatible-mode/v1` vs `compatible-api/v1`）。硬塞进去以后，「这条配置能不能用于重排」得靠第二个字段表达，而那个字段只对一个用途为真。 |
| 让重排继续跟随 `fast` 角色（一期形态） | 会把「换查询改写的模型」与「换重排模型」绑成同一个动作。前者是延迟敏感的通用小模型，后者是 Cross-Encoder，选型理由、预算（15s vs 60s）、计费口径都不同；而且它让「本机有没有重排能力」变成「某条 chat 配置恰好可用」，与开关 `RERANK_ENABLED` 的真假混在一起。 |
| 单独建一张 `rerank_configs` 表 | 目前只有一台端点、一个模型，多一张表就多一套 CRUD、审计、面板与缓存失效路径。等「多家重排供应商可切换」成为真实需求再建。 |
| 把地址写死在代码里（像 `MAX_DOCUMENTS` 那样） | 端点地址含业务空间 ID，是**部署期信息**；写死等于每换一个空间就发一版。 |

**选择的理由**：

- `model_configs` 的模块文档本来就写着「不要加 rerank 用途位」——理由是「加了也没有调用点会读它，而面板上会多出一个改了也不生效的配置项」。换件之后这条判断依然成立：生产工厂只认 `RERANK_*`。
- 重排端点是**部署事实**（这台机器配没配端点），不是**可增删的接入清单**。它决定「有没有这个能力」，与 `KEYWORD_SEARCH_PROVIDER` 同级；这类开关一直住在 `.env`。
- 密钥形状也对不上：重排通常直接复用 `MODEL_API_KEY`，默认回落比逼运维再存一把更接近事实。
- 「端点没配」必须能被表达成**明确不可用**：`RERANK_ENABLED=true` 但地址或密钥缺一，工厂返回空实现（回显 `applied=false`），**不回落**大模型重排。两种实现的延迟差一个数量级（P95 20.65s vs 1.18s，见 `docs/架构.md`「评测」），读数不可比，回显却都写着「重排开了」——那比不可用更难查。

**代价**：

- 面板的「模型接入」页**看不到重排**：要改重排得去配置页（两个热改键）或 `.env`（重启档）。这是刻意的，但确实是「两个地方管模型」。
- 端点地址是部署期信息，换机器要改 `.env`，不能像 `model_configs` 那样「加一条、点一下」就切。
- 回落链是两级（`RERANK_API_KEY` → `MODEL_API_KEY`），排障时多读一行。
- 路径段与嵌入不同，照抄 embedding 那一行会打到另一个路径段上（`compatible-mode/v1/reranks` 未验证过），症状是「端点像是没配」而不是「配置错了」——这一条必须写在 `.env.example` 里，否则照抄者会以为开关没生效。

**翻案条件**：

- 真的出现「多家重排供应商要按租户或按档位切换」：那时该建的是**重排自己的配置表与角色**，并同时给出面板、审计与缓存失效路径；仍然不是塞进 chat 表。
- 端点需要按**租户**分配（不同租户走不同业务空间）：`model_configs` 是平台级资源、不属任何租户，这条需求同样不能靠它满足，要走新的租户级接入表。
- 上游把 `/reranks` 收进 chat 供应商的同一套端点与计费语义：那时「同一张表」才第一次说得通。

### 决策二：连接复用的形状是「按事件循环的注册表 + 固定规模执行池」

`app/core/http_clients.py` 按**当前正在运行的 loop** 注册客户端（弱引用键，loop 回收即消失）；`app/core/loop_pool.py` 提供 **N=4 条常驻线程**（各持一个常驻 loop、**排队预算 2 秒**）承接**混合检索的向量分支**；两者的收尾都是确定性的（关当前 loop 的客户端 / 停止接收 → 逐个 loop 关客户端 → 停循环 → join），关不掉只记 warning。

**考虑过的替代方案**：

| 方案 | 为什么不选 |
| --- | --- |
| 进程级 lifespan 单例（一个 `httpx.AsyncClient` 全局共享） | 异步客户端的连接池绑在**创建它的** loop 上。本仓库已经为这条付过两次学费：Celery 每任务 `asyncio.run` 一次，进程级客户端在第二个任务里直接 `RuntimeError: Event loop is closed`；执行池里的 worker 各有各的 loop，同样不能共用。跨 loop 复用不是「性能差一点」，是当场炸。 |
| 每个请求新建客户端（改造前形态） | 一次检索建 3~4 个客户端，每题重做 TLS 握手，收尾刷噪音。实测：同一份题集上「重排调用自身」均值 10866.3 ms、P95 20263.7 ms（`eval/baseline-rerank`），换成专用端点 + 复用连接后是 389.0 / 615.9 ms（`eval/runs/20261112T135017Z`）。 |
| 所有请求共用一个常驻 loop（不做池） | 向量分支里有一次**同步** pgvector 查询，会把唯一的循环卡住，并发直接退化成 1。 |
| 每请求 `asyncio.to_thread` + `asyncio.run`（改造前形态） | 每个请求一个新 loop，客户端永远复用不了——「并行」只是字面上的，客户端数 = 请求数。 |
| 让单模式（纯向量）也进池 | 单模式用的是**请求的 Session**，而 SQLAlchemy 的 `Session` 不是线程安全的；进池等于跨线程共享会话，这是最难查的一类故障。 |
| 池按需扩缩容 | 扩缩容本身要一套策略与观测；固定 4 条 + 排队预算已经能把「慢」变成可预期的降级，先别加旋钮。 |

**选择的理由**：

- 「按 loop 注册」把正确性做成了**结构**，而不是纪律：跨 loop 复用这件事在形状上就不可能发生，不需要每个调用点记得「别缓存客户端」。
- 池让「复用」与「不阻塞主循环」同时成立：worker 有常驻 loop，客户端因此在请求之间活着；同步查询被关在自己的 worker 里，主循环照常推进（既有用例断言关键词协程在向量分支阻塞期间仍在推进）。
- 排队预算是**排队**的预算，不是干活的预算：干活的超时仍由各 Provider 自己兜（嵌入 60s、重排按配置），两件事不混在一个数字里。
- 投递的是**工厂函数**而不是协程对象：协程一创建就绑在当前 loop 上，在另一个 loop 里 `await` 会炸；工厂在 worker 的 loop 里被调用，协程从一开始就属于它。
- 可观察证据：10 题冒烟里 `http_client_created` 共 **5** 个（主循环 1 + 池里 4 个），修复前是每题 1 个。

**代价**：

- **向量分支的并发上限是 4**，超过就排队，排队超 2 秒按这一路失败降级。调大要连着上游配额一起算，它不是纯性能旋钮。
- 多了一层需要收尾的东西：池的关停是四步（停止接收 → 逐个 loop 关客户端 → 停循环 → join），worker 卡在同步查询里时关不掉，只能交给进程退出；评测脚本没有 lifespan，靠 `atexit` 兜底。
- **客户端不再是「全局资源」**：任何「拿一个客户端存起来跨请求用」的新代码都会在第二个 loop 里炸；这条约束要一直传下去（写进了 `app/core/http_clients.py` 的模块文档）。
- 同步客户端仍是进程级单例：LangChain / OpenAI SDK 的包装对象在构造时**即使拿到异步客户端也会顺手建一个同步 `httpx.Client`**（本机实测约 43 ms/次）。它是唯一一个不按 loop 隔离的例外，因为它不承载异步流量。
- 「单模式留在主循环」意味着主循环仍可能被那条同步查询短暂卡住——这是「会话归属正确」换来的，不是遗漏。

**翻案条件**：

- **端到端异步是终态**：把同步 SQLAlchemy `Session` 换成 asyncpg（或异步 SQLAlchemy + 异步向量查询）之后，向量分支不再需要「为了绕开阻塞而进线程」，执行池可以整个删掉，客户端回到「一个进程一个客户端」的简单形状。这不是优化，是**换整层数据访问**，属于另一个阶段；在那之前，池是**正确的临时形状**，不是技术债。
- 上游 SDK 支持「连接池与 loop 解耦」（可跨 loop 复用的传输层）：注册表可以退化成进程级单例；但「降级归编排层」这条不变。
- 生产并发长期低于 4、排队从不触发：可以缩到 2，省两套 loop 与客户端；先要有读数（`retrieval_pool_job` 的 `queue_wait_ms`），不靠感觉。
- 若出现「同一请求内需要并发打多个重排端点」：池的简单轮转调度要重新评估（当前不做优先级）。

## 备选方案

两条决定合起来还有两种「更省事」的整包方案，都不选：

| 整包方案 | 为何不选 |
| --- | --- |
| 进程级 lifespan 单例客户端 + 重排进 `model_configs`（最像「标准做法」的一揽子） | 两处都错在语义：客户端按进程管会跨 loop 复用，Celery 与执行池都会当场炸；重排进 chat 表会让「改了不生效」的配置项出现在面板上。省下来的复杂度会以「最难查的两类故障」形式还回来。 |
| 维持现状（每请求新建客户端 + 重排跟随 `fast`） | 不需要任何新概念，但延迟差一个数量级，且在 15 秒生产预算下大模型重排那一轮有 **16/127** 题的**重排调用本身**超过 15 秒、会降级回融合顺序——「连接不复用」不只慢，还会让高质量档位悄悄退回融合顺序。 |

## 翻案条件

- **端到端异步落地**（asyncpg + 异步向量查询）：决策二的池整段作废，注册表可退化为进程级单例；决策一不受影响。这一步要换整层同步 Session，属于另一个阶段，不在第 10 步。
- **重排供应商出现真实的多家 / 多租户需求**：决策一要重做（建重排自己的配置表与角色），决策二不受影响。
- **上游端点语义变化**（`/reranks` 并入 chat 供应商同一套计费与端点）：决策一的「不进 `model_configs`」可以重新讨论，但「端点没配 = 明确不可用、不回落另一种实现」这条要保留——它守的是读数的可比性，不是配置的位置。
- **可观测性给出反证**（例如某台机器的 `queue_wait_ms` 长期贴着 2 秒预算）：先调池的规模与预算，再评估是否提前做端到端异步；**不要**因为排队就退回「每请求新建客户端」。

## 修订（2026-11-13，第 11 步票 #127）：决策二里的执行池已删除

**触发的正是本文写下的第一条翻案条件**：「端到端异步落地（异步向量查询）之后，决策二的池整段作废」。

### 变了什么

- `app/core/loop_pool.py` **整段删除**（连同 `tests/test_loop_pool.py`、`RETRIEVAL_POOL_SIZE` / `RETRIEVAL_QUEUE_BUDGET_MS` 两个配置键与它们的 `runtime_settings` 登记）。
- 向量分支回到**普通 `await`**：`PgVectorStore.similarity_search_scope` 收 `AsyncSession`、`await db.execute(...)`，与关键词一路一样跑在主循环上。
- 向量分支不再另开 `SessionLocal()`：一个请求一条会话（异步会话不绑线程，「会话不能跨线程」这条约束随之消失）。
- 按事件循环注册的客户端（`app/core/http_clients.py`，决策二的前半段）**保留**：Celery 每个任务自带循环，仍需要它。

### 为什么现在做

- **前提消失**：池存在的唯一理由是「同步 pgvector 查询会卡住事件循环」。查询改成 `await` 之后，这条前提不再成立，留着池就是留着一条没人需要绕的路。
- **它还带来了新的失败形态**：「排队超预算 → 这一路失败」会把一次本可以成功的检索降级成「仅关键词」，而并发越高越容易触发——这是第 10 步为了换掉同步查询而付的临时代价，不该在前提消失后继续收。
- **取消不再能传导**：任务被丢进 worker 线程之后，取消只取消「等结果」，活照样跑完。客户端断开后仍在烧嵌入与召回，是这张票要消掉的东西。

### 代价

- 检索链路的并发上限从「4 条常驻线程」回到「数据库连接池 + 模型端点配额」。压测读数（`docs/step11-loadtest-after-127.md`）显示这是**净收益**：同一组参数下 P95 不劣化，64 并发下不再出现「排队超预算」降级，且「阻塞事件循环的 DB 占比」恒为 0。
- 池曾经顺手兜住的「向量分支自己开会话、失败不影响请求会话」不再存在：现在两路共用请求会话。这是**想要的**——异步会话本来就不需要隔离，失败也由 `gather(return_exceptions=True)` 与既有降级矩阵兜住。
- `app/core/http_clients.py` 的「按 loop 注册」这条约束继续有效，只是理由从「池里每个 worker 一个 loop」变成「Celery 每个任务一个 loop」。

### 没变的东西

- 决策一（重排端点的配置来源）**一个字没动**。
- 「降级归编排层、一因一码」不变：通道故障仍只有 `vector search failed` / `keyword search failed` 两个码，重排失败仍是 `rerank failed`；只是 `vector search failed` 不再可能由「排队超预算」引起。
- 术语表里「检索执行池」这一条**删除**（连同 `_Avoid_: 事件循环池` 的指代改写）：它已经不是一个存在的概念，留在术语表里会让人去找一个不存在的模块。

### 现在的翻案条件

- 如果压测显示 psycopg 的**异步驱动本身**成为瓶颈（而不是数据库或模型端点）：翻案的方向是换 `asyncpg`（改 dialect 与 URL，业务代码零改动），**不是**把执行池装回来。
- 如果某台机器上出现「一次检索的并发高到把连接池打满、`pool_timeout` 把请求拖成超时」：先按 `docs/架构.md`「双栈期的数据库连接预算」调池与 `max_connections`；只有在证明「瓶颈是事件循环上的 CPU 工作」时，才需要重新讨论「把某一段挪出主循环」——那与本文的执行池不是同一件事。
