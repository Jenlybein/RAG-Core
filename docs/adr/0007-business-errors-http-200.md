# 0007. 业务错误统一返回 HTTP 200 + 分段错误码

- 状态：已采纳（**唯一例外见文末「后续修订」**）
- 日期：2026-11-03
- 相关：`GLOSSARY.md`「错误码」、「docs/架构.md」②平台管控、**ADR-0014「切块策略即语料准入」**

## 背景

早期错误处理是散落的：`raise HTTPException(404, "not found")`、`raise ValueError("kb not exist")`、`return {"error": "quota exceeded"}`。三种形状，调用方没法统一处理，日志里也分辨不出「是哪类问题」。

直觉的修法是「按 HTTP 语义来」：参数错 400，没权限 403，资源不存在 404，超限 429。但这套语义有一个根本问题：**它假设失败的来源是「这个 HTTP 请求本身有问题」**。而在这个中台里，绝大多数失败是「请求完全合法，只是业务上不能给」——Key 过了但配额没了、库存在但不归你、档位存在但套餐不够。

## 决策

**HTTP 状态码只回答「服务在不在」，业务结果由 body 里的 `code` 回答。**

- 业务可预期的失败（参数错 / 鉴权失败 / 套餐不足 / 配额超限 / 资源不存在）→ **HTTP 200**，`code` 非 0；
- 服务真的坏了（数据库连不上、未捕获异常）→ **HTTP 5xx**，同时 `code = 50000`；
- 错误码**按责任方分段**：`2xxxx` 请求 / 鉴权 / 套餐 / 资源，`3xxxx` 存储，`4xxxx` 模型调用，`5xxxx` 系统与服务。

统一响应结构：

```json
{ "code": 20008, "msg": "knowledge base not found", "data": null }
```

全局异常处理器分三类翻译：`AppError`（业务）与 `RequestValidationError`（参数）走 200，其余走 500。

## 后果

### 正面

- 调用方判断逻辑变成两层且互不污染：先看 HTTP 状态判断「服务还在不在」，再看 `code` 判断「业务上发生了什么」。
- 分段让排障有方向：看到 `40xxx` 直接找供应商，看到 `20008` 直接查传入的 `kb_id`。
- 业务失败不会被网关 / 重试中间件误判：HTTP 200 不会被当成「可重试的服务故障」，避免配额被无意义地打满。
- 空结果也有原因（`empty_reason`）：`no_indexed_chunks`（该传文档）与 `no_chunks_matched`（该换问法）能区分开。

### 代价

- **只看 HTTP 状态码的工具会「看不见」业务失败**——网关、APM、监控大盘默认统计 4xx/5xx，业务失败在它们眼里全是成功。必须额外埋点（按 `code` 聚合、`degraded` 计数），否则线上「一片绿」而实际大量失败。
- 团队新人第一反应会是「失败怎么不是 4xx」，需要这份 ADR 来解释。
- 与分析工具 / 浏览器网络面板的直觉不符：调试时得点开响应体看 `code`。

## 备选方案

| 方案 | 为何不选 |
| --- | --- |
| 严格按 HTTP 语义（4xx/429 等） | 业务失败被摊成十几种状态码，调用方要为每种写分支；且「配额没了」用 429、「档位不够」用 403，语义边界模糊 |
| HTTP 200 + 一维递增错误码 | 看到 `1043` 不知道是哪类问题，排障无方向 |
| 只用 HTTP 状态 + `msg` 文本 | 调用方无法程序化处理，只能匹配字符串 |

## 后续修订（ADR-0014，2026-11-09）

**唯一例外**：上传的文件格式不在目标知识库白名单里时，返回 **HTTP 422 + `code = 20028`**。

理由：那不是「请求完全合法、只是业务上不能给」，而是**请求体本身就不满足协议约束**——格式不对的文件根本不该进索引队列，用 200 会让客户端把它当成「已收下、稍后处理」。判定发生在上传入口，早于任何业务链路。

其余业务失败（Key 无效、配额耗尽、库不可见、档位不够……）仍一律 HTTP 200 + 业务码。改动落点集中在 `app/api/error_handlers.py` 的 `_STATUS_BY_CODE` 一处，见 [ADR-0014](0014-split-strategy-is-admission.md) 与 `docs/设计决策.md` 决策四。
