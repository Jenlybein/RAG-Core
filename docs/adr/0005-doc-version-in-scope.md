# 0005. 文档版本（`doc_version`）纳入实现范围，与 `index_version` 正交

- 状态：已采纳
- 日期：2026-11-03
- 相关：`GLOSSARY.md`「文档版本」「索引版本」、「docs/架构.md」③知识与文档

## 背景

项目里已经有一个版本概念：**索引版本（`index_version`）**，用来让「重建索引」可以不停机——建一套新版本，重建期间线上继续查旧版本，切指针后旧版本再回收。

在讨论「要不要做文档版本」时，很容易把它当成索引版本的同义词，理由是「反正都是版本号，合并成一个字段更简单」。但两者回答的问题完全不同：

- 索引版本回答**「这是第几次重建算出来的」**——同一份内容、同一套切块算法，重建一次就是新版本；
- 文档版本回答**「这是第几稿」**——稿子本身改了（《退款政策》从 7 天改成 15 天），内容变了。

合并成一个字段会出现两类事故：

1. **重建导致引用错位**：审计要求「当时引用的是哪一稿」，重建一次版本号就变了，历史引用全部指向错误的内容。
2. **改稿导致重建语义丢失**：只改了一个字也要新建「索引版本」，版本号会被内容变更淹没，无法判断「这次是重建还是改稿」。

## 决策

**文档版本纳入实现范围**，与索引版本**正交并存**：

- `doc_versions` 表记录每一稿（`doc_version`、`checksum`、状态、创建时间）；
- `chunks` 与 ES mapping 都带 `doc_version`，也带 `index_version`，两个字段同时存在；
- **默认只查当前稿**，这个约束必须落在 SQL / ES filter 里（不是「应用层记得加」）；
- 检索结果每条带 `doc_version`，引用因此成为可回溯的三元组：**文档 + 稿次 + 切片**。

## 后果

### 正面

- 审计可答：「这条引用当时用的是哪一稿」。
- 事故可归因：错在稿子（内容变了）还是错在检索（召回漂移），可以分开验证。
- A/B 可做：同一 query 在两稿上跑，把「内容变量」隔离出来。
- 回滚有据：回滚是「把当前指针拨回某一稿」，不是改一个字段——**指针变了，切片必须重建**。

### 代价

- 存储与清理变复杂：每稿都留切片，需要保留策略（默认留最近 3 版，超出窗口的连切片带版本行一起删）。
- 写入路径变长：提交新稿 → 写版本行 → 投递重建 → 切片带 `doc_version` 落库。
- **最大的坑**：`chunks.doc_version` 不回填就启用过滤 = **静默查空**。迁移必须回填并核对「库数 / 切片数 / 向量数 / ES 文档数」四项一致。
- `purge` 的删除键必须扩一位（`document_id + doc_version`），只清一边存储或漏扩这一位，都会删掉历史版本切片。

## 备选方案

| 方案 | 为何不选 |
| --- | --- |
| 不做文档版本，只留索引版本 | 审计与事故归因直接做不到；而且 `content` 是原地覆盖的，改了稿就再也回不到「当时引用的原文」 |
| 与 `index_version` 合并成一个号 | 两类语义被压成一个数，重建与改稿无法区分（见背景） |
| 只存版本行不留切片 | 回滚时切片已不存在，必须全量重建才能查——回滚从秒级退化成分钟级 |
