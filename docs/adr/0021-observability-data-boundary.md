# 0021. 观测是旁路：原文只进内网观测栈，归属索引只存结构

- 状态：已采纳；**决策 2 的「十列」已由 [ADR-0025](0025-index-as-build-artifact.md) 决策六声明修订**（归属索引新增一列 `index_versions`，回答「这次检索查的是哪次构建」，十列 → 十一列；其余三条决定不动，仍只存结构、仍一次检索一行、仍独立短事务）
- 日期：2026-11-11
- 相关：父 spec #98「第 9 步」、**ADR-0010「第五次修订」**（响应 `metadata.trace_id`）、ADR-0020「调试台不做流式」（把「哪一步慢」判给观测）、`GLOSSARY.md`「观测旁路」「trace」「span 阶段」「门禁指标」「旁证指标」「归属索引」、`.env.example`（`LANGFUSE_*` 一组）、`app/services/rag_service.py`（`_metadata_of`）

## 背景

第 8 步的调试台回答了「这次结果为什么是这个结果」，答不了「这次调用把时间花在哪」——ADR-0020 当时就把后半个问题判给了第 9 步。要答它，得把检索链路拆成带耗时的 trace，并有一个能查 trace 的地方。

一起要结的还有两笔旧账：

1. **归属索引里存着问句原文。** 早期表设计把问句、改写句、切片正文一并写进业务库——那是把「用户问了什么」复制了一份到租户数据的边界外面。备份、只读副本、`pg_dump` 都会把它带走，而检索本身从来不需要回读这些原文。
2. **反馈的写入曾经依赖观测服务。** 「反馈存不下」与「观测服务不可用」曾经被写成同一个错误码，于是一个纯旁路的依赖能造成业务失败：运维重启一下观测栈，用户就点不了「没用」。

四条决定要一起看才有意义：它们同属一句话——**观测能看得更细，但业务库只留结构，反馈不靠观测**。

## 决策

### 1. 原文只进内网自托管观测栈

问句、改写句、检索文本、切片正文这些**原文**，只允许进内网自托管的观测栈，不允许进公网 SaaS，也不允许落业务库。

- 判据只有一条：**这段文字会不会离开机房**。会离开的，就不放。公网观测 SaaS 因此从一开始出局，与价格无关。
- 观测栈里留原文是为了回答「这次为什么这么排」：只看结构与耗时，改写得对不对劲、召回偏没偏，都无从归因。
- 栈自己的保留期与采样由栈的配置管：**留多久是观测的事**，业务库不跟着一起留。
- 原文进栈是**旁路写**：栈挂了、桶满了、worker 卡住，检索照常返回，只是这一次查不到 trace（见决策 3 与「代价」）。

### 2. 归属索引只存结构、不存原文

中台在业务库里留一张**结构索引**，记「这一次调用发生过什么」，不记「这一次说了什么」：

| 留下 | 具体是什么 |
| --- | --- |
| 身份 | 行 `id`（对外即 `log_id`）、`tenant_id`、`trace_id`（**NOT NULL**，派生先于写入） |
| 范围与规模 | `kb_ids`、`top_k` |
| 结果指针 | `chunk_ids`：交付单元的代表片 + 溯源片，**只存 id** |
| 结局 | `latency_ms`、`degraded_reason`、`empty_reason` |
| 时间 | `created_at` |

**不存**：问句、改写句、检索用句、切片正文、任何分数明细，也不存 `user_id` 与档位。

- 这张表跟业务库同生共死（备份、只读副本、迁移脚本都会带上它），所以它上面的每一个字都是**长期承诺**。原文放进来，等于把「租户问过什么」承诺给所有拿到备份的地方；观测需求该由观测栈满足。
- 留下的这一列列**全部可枚举**：谁、查了哪些库、命中哪些片（可回指）、多慢、是不是降级、为什么为空。要回答「上周哪类查询变慢」这类问题，它够用；要回答「那次到底问了什么」，去观测栈按 `trace_id` 查。
- `chunk_ids` 只存 id、不存正文与分数：正文在切片表里有一份，分数明细属于评测与 trace，重复存只会多一份会过期的副本。
- **写入走独立短事务**：请求会话是只读语义、从不 `commit`，在它上面顺手 `INSERT` 会被 `db.close()` 丢掉。写入失败只记 `warning`，不影响返回。
- `trace_id` 是 `NOT NULL` 且**先于写入产生**：这样「写库失败」不会导致「响应里没有 `trace_id`」（ADR-0010 第五次修订）。

### 3. 反馈权威在本地

「这条结果有没有用」的**判定权与写入权都在本地库**：

- 两步校验全在本地完成：这条记录存不存在、它是否属于当前租户。不查观测服务，也不靠它鉴权。
- 把反馈分数推给观测栈是**旁路**：推失败只记 `warning`，接口照常返回成功。
- 错误码语义随之改写：「反馈写入失败」现在只指**本地写入失败**。观测服务不可用**不产生任何业务失败**。
- 理由：反馈是业务数据——要统计、要进评测、要给排序实验看。它的可用性不该与一根探针绑在一起；一个观测组件挂掉就让用户点不了赞，是把旁路的失败升级成了产品的失败。

### 4. 观测栈自托管：v4 全家桶的代价与收益

选定**自托管的一整套**（上游 v4 全家桶：web / worker 两个应用进程，外加 ClickHouse / MinIO / Redis 三套依赖），而不是 SaaS，也不是「只写文件」。

**收益**：

- 原文不出内网，决策 1 才成立；SaaS 方案这一条直接做不到。
- **一根线串起线上与评测**：线上 trace 与评测 run 用同一套数据形状与同一个 `trace_id` 概念，评测里名次变了可以直接对着 trace 看，不用在两种工具之间翻译。
- 无按量计费，保留期由自己定；想留 90 天就留 90 天，不必因为账单改口径。
- 反馈打分挂在同一条 trace 上，能跟耗时、召回、重排对照着看。
- 离线可起：测试与 CI 用轻去向（见「代价」最后两条），不需要栈在线。

**代价（这部分不能只写好处）**：

- **要运维五样东西**。原来 PG + Elasticsearch 已经是有状态服务，现在再多 ClickHouse 与 MinIO 两套有状态、Redis 一套中间态：备份策略、磁盘水位、保留期、桶的清理，全部要有人管。磁盘涨起来最快的是 ClickHouse。
- **版本要成对**：web 与 worker 必须同版本，worker 落后时写入形状会错；跨大版本升级要按上游的迁移说明逐版走，不能跳。
- **认证与网络自己管**：public / secret key 自己发、自己轮换；TLS 与访问控制自己配。栈内网可达即可，但「可达」这件事以前是 SaaS 帮我们做的。
- **单机开发机吃资源**：PG + ES + ClickHouse + MinIO + Redis + 应用进程同机，内存很容易见底。所以有两个**轻去向**：`jsonl`（单行 ≤ 2 KB、按天轮转、只读最近若干天）与 `null`（测试与 CI）。它们是**降级去向，不是替代品**——JSONL 没有查询与聚合，「上周哪类查询变慢」只能 grep。
- **原文只有一份**：既然业务库不存原文（决策 2），观测栈的保留期一到，那批问句就永久没有。这是「业务库不承担观测数据」的必然结果，接受它，别在事后想把原文搬回去。
- **旁路的边界要一直守住**：五个容器里任何一个挂掉，检索都必须照常返回。这条最容易在「顺手加一次读取」时被破坏——读 trace 的东西（控制台、评测脚本）可以失败，检索主链路不许。

## 后续登记（第 11 步 · #156）

两件事在这里登记，都不改上面四条决定：

### 1. 归属索引从「十列」变「十一列」，由 ADR-0025 决策六声明

决策 2 那张表列的是「留下的十列」（实现里 `app/models/retrieval_trace.py` 的模块注释也这么写）。第 11 步为了回答「这次检索查的是哪次构建」，加了第十一列：

| 新增列 | 形状 | 为什么必须是这个形状 |
| --- | --- | --- |
| `index_versions` | JSONB，`{kb_id: version}` | 与检索范围同一个形状，不能写成两个并列数组 |

**这次加列是契约变更，明写在 [ADR-0025](0025-index-as-build-artifact.md) 决策六里**，本文只做指向与承认：十列 → 十一列，其余三条性质一条不动——**仍只存结构、不存原文**（版本名是结构），**仍是独立短事务、写失败只记 warning**，**仍是一次检索一行**、`trace_id` 仍是 `log_id` 的确定性派生。所以「观测是旁路」的判据不变：观测栈全挂时，响应仍与栈健康时逐字节相同。

### 2. 编排耗时**暂不**进六段 span（加第七段属于观测契约变更，本轮不做）

六段（`query_optimization` / `vector_recall` / `keyword_recall` / `fusion` / `rerank` / `collapse`，见 `app/observability/stage_timing.py` 与 `GLOSSARY.md`「span 阶段」）是**既有契约**：观测栈按段名聚合、控制台瀑布按段名成列、历史行也是这六个名字。

切片编排发生在折叠**之后**，还会额外调两次小模型，因此「六段之和 ≠ 总耗时」在开了编排的档位上本来就不成立。本轮的处理是**不新增第七段**：

- 它的成本今天可以从两处读到——归属索引的 `latency_ms`（总耗时），以及失败时那条 `evidence orchestration failed` 日志里的 `duration_ms`；
- 六段回答的是「检索链路各步花了多久」，编排不是检索链路的一步（它改的是交付材料的组织方式，ADR-0025 之外的 B 票口径）；
- 往段名表里加一个字符串**看着只改一行**，实际要连带改：按名字聚合的观测存储、控制台瀑布的列、既有行的形状、以及「六段」这条写在术语表里的承诺——那是观测契约变更，不是一次顺手补字段。

**翻案条件**：出现连续多起「这次为什么慢了 N 秒」无法用六段 + `latency_ms` + 那条失败日志归因的问题时，再加 `orchestration` 段；届时**一次性**改四处（`stage_timing.py`、术语表「span 阶段」、控制台瀑布、观测聚合口径），不要只在一处加字符串。同理，图谱注入的耗时也不单独成段：它发生在融合与重排之间，已包含在那两段里。

## 备选方案

| 方案 | 为何不选 |
| --- | --- |
| 用公网观测 SaaS | 原文要出内网，与决策 1 直接冲突；再多一个外部依赖坐在链路旁边，为它买来的便利抵不过合规上的硬约束。 |
| 自己在 ClickHouse 上裸写 trace 表 | trace 模型、查询面板、反馈打分、保留期都要自己造，工作量主体不在检索而在观测产品；这笔钱应该花在检索质量上。 |
| 只写 JSONL，不起栈 | 没有查询与聚合，追问「哪一类查询变慢了」只能人工 grep；保留为降级去向，不作为唯一去向。 |
| 归属索引照旧存原文，只把耗时交给观测栈 | 业务库成了原文副本，备份、只读副本、`pg_dump` 都带出去；观测需求不该由业务库承担。这正是本次要拆掉的那笔旧账。 |
| 反馈仍然写观测栈，只是把失败改成 warning | 反馈是业务数据，落在观测栈里会跟着保留期一起消失，统计还要跨库拼；而且它仍然是「观测挂了反馈就危险」的结构，只是把报错换成了静默丢数据。 |

## 翻案条件

- **合规收紧到「原文不得离开应用进程」**（连内网栈也不行）：决策 1 要跟着收紧成「栈里只记结构与耗时」，同时必须承认「为什么这么排」的归因能力下降——那要重新评估还要不要留原文以外的取舍。
- **五个容器的运维成本压过收益**（例如连续两个季度没有任何人按 `trace_id` 查过 trace）：改用 `jsonl` + 轻量查询，另出 ADR；但决策 2 与 3 不跟着改。
- **上游 SDK 与自托管版本出现不可跨越的错位**：换观测后端（只要支持注入外部 trace id 即可），三条硬决定（原文只进内网、归属索引只存结构、反馈权威在本地）一律不变。
- **审计要求「必须能查问句」而观测栈保留期不够**：先延长观测栈的保留期或做归档，**不要把原文搬回业务库**——那会同时破坏决策 2 与 ADR-0010 的红线。
- **门禁指标与旁证指标的分工被质疑**（见 `GLOSSARY.md` 两词条）：那是评测侧的决定，与本文的观测数据边界正交；要改也改评测侧的 ADR，不要借这次观测改造顺手调整判据。
