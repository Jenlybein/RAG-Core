# 14. 切块策略即语料准入

日期：2026-11-09

## 状态

已接受

## 背景

第 3 步引入了两种切块策略（`structure` 按 Markdown 标题切、`size` 按固定字符窗口切），
并把它做成知识库级配置。但策略只管**切法**，不管**入口**：

- 选了 `structure` 的库照样能上传 `.pdf` / `.docx` / `.txt`；
- 这些文件经解析器转出来的文本没有 Markdown 标题，结构化切块器只能退化成窗口硬切；
- 于是切片既没有 `heading_path` 也没有 `section_id`，折叠、页码、章节溯源**全部静默失效**。

用户看到的现象是「我明明选了按结构切，pdf 出来的结果和按 size 切没区别」，而且没有
任何提示。反方向同样成立：`size` 库能收 `.md`，标题结构被白白丢掉。

还有一处不一致：JSON 上传入口的来源类型是 `text`，导致用户手写的规范 markdown
也进不了 `structure` 库——而那本来是这个库唯一想要的输入。

## 决策

### 1. 策略同时决定准入，且只在建库时定一次

| 库类型 | 白名单 | 收什么 | 切法 |
| --- | --- | --- | --- |
| `structure` | 固定 `[markdown]` | 只收 markdown | 结构化（标题 / 表格 / 代码 / 折叠 / 页码） |
| `size` | 默认五种全开 | 任意已支持格式（含 md） | 固定字符窗口，不产 `heading_path` |

`split_strategy` 建库必填、无默认值；`allowed_formats` 是独立列（不放进 `settings`
JSONB：它是准入边界而不是调参项，需要回显与查询）。

一致性校验放在**应用层的纯函数**：`structure` 的白名单必须恰好是 `[markdown]`，
传别的直接拒绝建库，而不是建出一个之后必然出错的知识库。数据库**不加** CHECK
约束——JSONB 的包含判断写成约束后报错不友好，也表达不出「恰好是」这种形状。

### 2. 格式不被接受时当场拒绝，HTTP 422

上传时判定「本次解析出的 `source_type` 在不在该库的白名单里」，不在就抛
`UNSUPPORTED_DOCUMENT_FORMAT`（20028），错误信息带该库允许的格式列表。

这是 ADR-0007「业务失败一律 HTTP 200」的**唯一例外**。理由：参数错误是「改字段重发」，
准入拒绝是「换文件或换库」——请求本身不被接受。用 422 让网关、APM 与调用方的
「客户端错误」探针能直接看见它。响应体仍是同一个三段式，变的只是状态行。

判定只有一处实现，JSON 与文件两个入口共用；且发生在**分配 ID 与落盘之前**，
被拒的请求不留存储文件、不建文档行、不投递任务。

### 3. JSON 入口视为 markdown

JSON 模式的 `source_type` 由 `text` 改为 `markdown`；`text` 从此只由 `.txt` 产生。
这样用户手写的规范 markdown 才能进入 `structure` 库。

### 4. HTML 用 bs4 + markdownify，不用 MarkItDown；docx 与 pdf 都不换

| 格式 | 选择 | 理由 |
| --- | --- | --- |
| `.html` | `beautifulsoup4` + `markdownify(heading_style="ATX")` | MarkItDown 的 html 路线本来就是这两个库；而它的基座安装会拖进 magika + onnxruntime（几百 MB 原生运行时），那套只用于文件类型嗅探 |
| `.docx` | **保持** `mammoth` + `markdownify(ATX)` | MarkItDown 的 docx 内部同样是 mammoth → HTML → markdownify(ATX)，实测同一份 docx 输出**逐字节相同**；换它只多出一条预处理（公式 LaTeX、坏 styles 修复） |
| `.pdf` | **保持** `pdf-inspector` | MarkItDown 的 pdf 是 pdfminer + pdfplumber，**完全没有标题层级识别**，表格靠词坐标聚类；实测标题退化、表格散架，比现有实现差 |

### 5. 不留「docx 转 md 升格」通道

不做「入库时把 docx 转 md 并把 `source_type` 记为 `markdown`」这种升格。白名单是
唯一闸门，简单可校验；留一条旁路会让「上传格式」与「能否结构化」脱钩，白名单就不再
是唯一答案。

### 6. 非 markdown 格式不做结构还原

PDF 的标题层级靠版式识别，是**猜的**：本轮实测确认两处误判（每页第一个标题都变成
h1、一句正文被当成 `##` 标题）。在评测语料 100% 是 markdown、收益一次未被量化的
前提下，不投入修复（需要一组长度/标点/字号比的启发式阈值，每一条都可能在新语料上
翻车）。`size` 库没有章节溯源，这作为**承诺边界**写进文档，而不是让用户自己发现。

## 后果

- **破坏性变更**：建库请求的 `split_strategy` 从「有默认值」变成「必填」。合入后所有
  创建知识库的调用方（评测脚本、调试台前端、MCP、CLI）都会拿到 422。评测脚本本轮
  已同步；前端待第 8 步做调试台时补表单。
- `structure` 库从此收不到 pdf/docx/txt/html——这是**预期**，不是功能缺失。
- `size` 库里的 markdown 也会丢掉标题结构（不弹提示，只在文档里写明）。这是「一个库
  一视同仁」的必然代价。
- 已入库的存量数据按策略回填白名单（`structure → [markdown]`、`size → 全开`）；
  本轮的开发库直接删数据卷重建，不做存量兼容。
- 三个 `known limitation`（PDF 页内标题跨页不延续、正文被误判成标题、表格靠坐标
  聚类）用测试钉住现状，修好时会变红，提示把断言改对。

## 备选方案

- **运行时按文件类型自动降级**（库选 `structure` 但收到 pdf 就悄悄用 `size`）：
  否决。配置项一旦能被内容覆盖，排障就会变成「我明明设了却没用」；同一个库还会出现
  两种粒度混在同一个 `top_k` 里。
- **给 `size` 补一层轻量 section 抽取**（用标题算 `heading_path` 但不做边界）：
  否决。与 `size`「不认结构」的定位自相矛盾，也把复杂度又请回来了。
- **把 `allowed_formats` 放进 `settings` JSONB**：否决。边界需要回显与查询，藏在
  数值旋钮的 JSON 里既不显眼也不好建约束。
- **数据库 CHECK 约束表达一致性**：否决。JSONB 包含判断写进约束后报错不友好，
  且应用层已经有一个纯函数可以做全分支测试。
- **换 MarkItDown 统一三种格式**：否决。docx 逐字节相同（无收益），pdf 明显退化。
