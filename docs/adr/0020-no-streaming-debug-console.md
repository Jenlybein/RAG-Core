# 0020. 调试台不做流式：一份事后完整的 `metadata`，而不是逐段推送

- 状态：已采纳
- 日期：2026-11-10
- 相关：`docs/adr/0001-retrieve-not-chat.md`、`docs/adr/0010-retrieval-contract.md`、`app/core/request_context.py`

## 背景

第 8 步的痛点是「检索是黑盒」：用户看不到「为什么搜到这些」「哪一步慢」「哪一步被降级」。

直觉解法是让调试台**逐段看着链路跑**：召回开始时推一条、融合完成推一条、重排完成推一条、组装完成推最后一条。为此需要 SSE 或 WebSocket，以及一套「中间事件」契约。

这个项目**从头到尾没有流式**，而且是把「没有流式」写成声明的：`app/core/request_context.py` 明说所有响应一次性返回，MCP 入口 `json_response=True`，ADR-0001 把「只检索不生成」定为边界。数据面同样是「发一次、拿一份完整结果」——没有 token 可推，因为不生成答案。

## 决策

**调试台不做流式**。它展示的是一次请求**事后**的全部真相：

- `metadata.mode` / `top_k` / `vector_store` —— 这次实际用了什么；
- `metadata.retrieval.degraded` + `degraded_reason`（四个固定英文码）—— 哪一步降级、根因是什么；
- `metadata.retrieval.empty_reason`（两态）—— 空结果到底是「库里没有可检索内容」还是「有内容但没命中」；
- `metadata.retrieval.rerank` —— 重排是否真的发生、候选数与耗时；
- `metadata.tenant_policy` —— 套餐、要求的档位、实际重排/改写、本次库数、被套餐裁掉的字段。

「哪一步慢」**不在调试台回答**，它在第 9 步（观测与评测）由 trace 回答。调试台的职责是「这次结果为什么是这个结果」，观测的职责是「这次调用把时间花在哪」。

## 后果

### 正面

- 契约不新增事件类型：HTTP 与 MCP 两条入口继续「字面一致、结果一致」，不会出现「调试台看得到中间态、外部调用方看不到」的第三种真相。
- 调试台展示的一切都来自同一个响应对象，因此**回显与生效值不可能分叉**（这正是 `tenant_policy` 那条规矩的延伸）。
- 没有「流断了怎么办」「事件顺序怎么保证」「错误在流中间怎么表达」这三类新故障。

### 代价

- 用户在等待期间只看到一个 loading，没有任何进度感；一次慢检索（重排 + 改写都开）可能等十几秒。
- 链路内部的中间数值（每路召回的原始候选、融合前后的名次变化）看不到——这些属于评测与运行日志。
- 想回答「为什么慢」必须去第 9 步，调试台自己也答不了。

## 备选方案

| 方案 | 为何不选 |
| --- | --- |
| SSE 逐段推送中间事件 | 要新增一套事件契约（事件名、顺序、错误表达），而 HTTP 与 MCP 必须对等，否则调试台看到的链路与外部调用方不同。工作量的主体不在前端，在契约。 |
| WebSocket | 比 SSE 更重，且要为「连接生命周期」再设计一套状态；检索是一次同步调用，没有需要长连接的东西。 |
| 轮询一个「进度接口」 | 检索是同步的，服务端没有可轮询的中间状态；为它造状态机等于把一次调用拆成两份真相。 |

## 翻案条件

要改成流式，必须先满足三条，缺一条就会造出「调试台专用链路」：

1. **事件契约先于实现**：事件名、顺序、每个事件的字段，以及「失败发生在第 3 个事件之后」如何表达。
2. **双入口对等**：MCP 也要能拿到同一份事件序列（MCP 的 `json_response=True` 要跟着改），否则调试台看到的东西外部调用方看不到。
3. **回显仍然唯一**：流里推的「实际生效值」不得与最终响应里的 `metadata` 分叉。

第 9 步的观测闭环如果证明「看不到中间态」确实是瓶颈，再按上面三条重新评估。
