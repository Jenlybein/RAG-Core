# 0003. API Key 即应用身份，删除 `app_id`

- 状态：已采纳；**请求体字段与「一把 Key 携带一套配置」的表述已由第 7 步修订，见文末「后续修订（第 7 步）」**
- 日期：2026-11-03
- 相关：`GLOSSARY.md`「身份与权限」「API Key」「密钥配置」、「docs/架构.md」②平台管控、**ADR-0010「第三次修订」、ADR-0018「三层授权」**

## 背景

早期模型里，`app_id` 与 API Key 是两样东西：`app_id` 标识「哪个第三方应用」，Key 只是它的一把凭证。于是出现一种结构：

```
租户 → 应用（app_id）→ 密钥配置 → 多把 Key
```

问题有三：

1. **身份有两份**：`app_id` 说「你是谁的应用」，Key 说「你持有什么凭证」。两者必须保持一致，但没有任何机制保证——传错 `app_id` 时，服务端拿到的「应用身份」和实际用的 Key 对不上。
2. **一个应用只该有一套配置**：既然配置挂在应用上，那同一应用的几把 Key 天然共享配置，多一层 `app_id` 并没有带来表达力，只带来一张空表和一次 join。
3. **入参污染**：`app_id` 被写进请求体，等于让调用方自报身份——这正是 MCP 场景里最危险的做法（Agent 会试图自己编一个）。

## 决策

**删除 `app_id`。API Key 就是应用身份。**

```
租户（套餐定上限）
  └─ 账号（登录控制台）
       └─ 密钥配置（归租户、租户内共享、1:N 结构先按 1:1 用）
            └─ API Key（policy_id 引用配置，带 label 备注名）
                 ├─ HTTP 入口
                 └─ MCP 入口（同一把 Key）
```

由此：

- 请求体里**不再有任何身份字段**，`tenant_id` 由 Key 解出、绝不来自参数；
- `label`（备注名）承接原来 `app_id` 的唯一用途——「这把 Key 是给谁的」，只用于面板展示与日志可读性，不参与鉴权；
- 一把 Key 引用一套配置（第 7 步落成独立的 `key_policies` 表 + `policy_id`，见文末「后续修订」）；要给同一集成换配置，改这套密钥配置即可，不必换 Key。

## 后果

### 正面

- 身份只有一份，不存在「`app_id` 与 Key 不一致」这种状态。
- 请求体收敛到只剩 `query`，MCP 工具的 schema 也只剩 `query`——两个入口同构。（**第 7 步起是 `kb_ids` + `query` 两个字段**，见文末「后续修订（第 7 步）」；本文此句只描述第 1 步时的状态。）
- 作用域被物理锁定：持有 finance 配置的 Key，查不到 support 的库，不是校验拦的，是它没有那个能力。

### 代价

- 「哪个应用在调」只能靠 `label` 约定，不能强校验（同名 `label` 允许存在）。若将来真需要「一个租户下多个集成各自独立配额」，得重新引入一层实体——那时它是**配置**的粒度，不是身份。
- 迁移要清理旧数据（历史 `app_id` 列与请求体字段）。

## 备选方案

| 方案 | 为何不选 |
| --- | --- |
| 保留 `app_id`，Key 挂在其下 | 多一层无表达力的实体，且制造两份身份 |
| 用 `label` 当强身份（唯一约束 + 鉴权比对） | `label` 是给人看的备注名，一旦参与鉴权，改名就等于换身份 |
| 让调用方传 `tenant_id`（早期做法） | 等于谁都能冒充，是最严重的一类漏洞 |

## 后续修订（第 7 步，#73，2026-11-10）：请求两个字段，配置独立成表

**本文「后果·正面」里那句「请求体收敛到只剩 `query`，MCP 工具的 schema 也只剩 `query`」被推翻**：第 7 步起请求与工具签名都是 **`kb_ids` + `query`** 两个字段——`kb_ids` 表达「查哪些库」（数据范围），`query` 表达「问什么」，两者都不是身份字段，但请求确实不止 `query` 一个。完整契约见 [ADR-0010](0010-retrieval-contract.md)「第三次修订」。

**本文「决策」第 3 条原先写的是「一把 Key 对应一套配置；要给同一集成换配置，改 `config` 即可」**：第 7 步把它落成实表——配置是**独立的密钥配置实体**（`key_policies` 表），Key 通过 `policy_id` 引用它。多这一层不是为了好看，而是为了让「删配置 → 引用它的 Key 一起失效」有地方写，也让租户内复用配置成为可能（本期仍按一对一用）。要换档位或结果形状，改的是这套配置，改完即时生效，不必重新签发 Key；要删的是配置，不是 Key。

由此，本文的**核心结论不变**：`app_id` 仍然被删除，身份仍只有一份——Key 本身就是应用身份，`tenant_id` 由服务端从 Key 解出、绝不来自参数，`label` 只是给人看的备注名。变的只是「Key 携带配置」的存储形状与请求的两个字段。

| 契约 | 本文（第 1 步） | 第 7 步起 |
| --- | --- | --- |
| 数据面请求体 | `query` | `kb_ids` + `query` |
| MCP `rag_retrieve` 工具签名 | `query` | `kb_ids` + `query` |
| 配置的归属 | Key 上的一个字段 | 独立表 `key_policies`，Key 通过 `policy_id` 引用 |
| 换配置 | 改 Key 的 `config` | 改那套密钥配置（改完即时生效，不必重签 Key） |
