# 0004. API Key 只存 scrypt 哈希

- 状态：已采纳（现行口径）
- 日期：2026-11-03；修订：2026-11-23（存储方式定为「只存哈希 + 末 5 位」）
- 相关：`docs/adr/0019-debug-console-pasted-key.md`、`GLOSSARY.md`「API Key」「Key 哈希」

## 背景

API Key 是数据面**唯一**的凭证：请求里只靠它认人，没有第二个参数。这意味着**任何能读到 `api_keys` 那张表的人，都拿到了全部租户的可用凭证**——备份、只读从库、DBA、误打的日志、一次没删干净的临时导出，全都算。与最小权限原则直接冲突，而环境边界（内网、访问控制、审计）只是补丁。

正确的存储方式与口令同一个道理：**只存不可逆的哈希，原文只在签发那一刻存在**。

## 决策

### 1. Key 串自带行身份证

```
rc_live_<api_keys.id>.<32 位十六进制密钥>
```

哈希**不能当索引用**：同一个密钥每次哈希都不同（盐不同），按值查一行只能全表逐行比对。所以「这是哪一行」必须由 Key 自己携带——鉴权先拿串里的 `api_keys.id` 一次主键命中，再对密钥本体做一次 `scrypt` 校验。

前缀是 `rc_live_`（`rc` 取自 RAG Core）。不用 `rk_live_` 的理由见本文末「前缀」一节。

### 2. 库里两列，原文一列都没有

| 列 | 内容 | 用途 |
| --- | --- | --- |
| `key_hash` | `scrypt$<n>$<r>$<p>$<salt>$<hash>` | 校验 |
| `key_tail` | 密钥本体末 5 位 | 面板展示 `rc_live_…4f3a2` |

哈希规则**复用控制面口令那一套**（`app/core/passwords.py`）：`hashlib.scrypt`、每行 16 字节随机盐、参数随哈希一起存进字符串、比对走 `hmac.compare_digest`。理由不是「两个都叫密码」而是这条：**为一个函数加一个新依赖要连带锁文件、镜像与供应链评审**，而标准库的 scrypt 与 argon2/bcrypt 属同一类算法（内存硬，抗 GPU 批量猜测）。

`key_hash` **不建唯一索引**：它不参与查找，加了只是给一个没人查的列付索引维护成本。

### 3. 原文只出现一次

- `POST /console/keys` 的响应带 `key_plaintext`——**唯一**一次；
- `GET /console/keys` 只有 `key_masked`（由 `key_tail` 拼出）；
- 审计快照只记 `key_masked`（管理员跨租户可见，不能成为泄露源）；
- 丢了只能重签一把。没有「再显示一次」，也没有「找回」。

### 4. 校验缓存只省算力，不管权限

数据面的**每一次调用**都要过鉴权，而一次 scrypt 在这台机器上约 200ms。于是加一层短 TTL 缓存（`app/core/key_verify_cache.py`）：`sha256(原文) → key_id`，60 秒。

它是**性能设施，不是授权设施**：行、`status`、租户、密钥配置仍然每次读库，所以删 Key / 停用 Key / 改配置一律立即生效，缓存最多让一个已经不在库里的 token 白省一次哈希。

代价也要写清楚：Redis 里出现了一个 token 的 `sha256`，等价于把「离线验证这个猜测对不对」的 oracle 搬出了数据库。可接受的理由只有一条——密钥本体是 128 位机器随机值，反推与穷举都不成立。由此得到一条硬纪律：**这个摘要不许出现在第三个地方**（日志、浏览器、队列）。

### 5. 迁移是不可逆操作

`key_value` 一列在同一支迁移里回填完就删掉。迁移**要求显式确认**：

```bash
alembic -x confirm_drop=1 upgrade head                          # 只回填
alembic -x confirm_drop=1 -x emit_keys=keys.json upgrade head   # 回填 + 导出新串
```

`emit_keys` 写出的文件里是明文新 Key（新的串形状，密钥本体不变），用完必须删除。`downgrade()` 直接抛错：重建一列空的 `key_value` 比报错更坑——它会让人以为回滚成功了，而每一把 Key 都突然不可用。

## 后果

### 正面

- **拖库拿不到可用 Key**：泄漏的是哈希与 20 bit 尾巴，不是凭证。
- 与口令同一条规则、同一份实现：`app/core/passwords.py` 一个文件就是全部密码学决策，没有第二套参数要维护。
- 列表接口不再携带可用凭证：前端不可能把它写进 storage、URL、日志或错误上报。
- 审计、日志、错误消息里都不可能出现原文（它们读不到原文）。

### 代价

- **每次冷校验 +约 200ms**（`n=16384`、16 MiB）。缓存把稳态摊平，但每个 Key 每 60 秒仍付一次；多 worker 共享 Redis 所以不会放大。
- **Key 串从 40 字符变成 77 字符**（含 UUID），存量 Key 必须换串（迁移时一次性导出）。
- **丢失即重签**：没有「查一下原文」。这是这个决策的全部意义，也是它最容易被抱怨的地方。
- 停用窗口：手改库把 `status` 改成非 active 是立即生效的，但校验缓存里那条记录会白留到 TTL 到期（它不影响判定，只影响「省不省那一次哈希」）。
- 删 `key_value` 之后 `api_keys` 不可按原文检索：运维查「这把 Key 是谁的」只能靠 `label` / `key_id` / 末 5 位。

## 备选方案

| 方案 | 为什么不够 |
| --- | --- |
| 纯 `sha256(原文)` + 唯一索引 | 实现更简单、鉴权微秒级；但它对**低熵 Key**（手写进库的 `rc_live_000…`）无防护——拿到库的人能离线验证任意猜测。项目想要的是「密码式」，不是「摘要式」。 |
| `HMAC-SHA256(原文, pepper)` | 比纯 sha256 多一层（pepper 只在 `.env`），但仍是确定性摘要：只要 pepper 与库一起泄漏就退化。且它省不掉「每次请求算一次」以外的任何东西，而真正贵的是慢哈希。 |
| 只存哈希、串里不带行身份证 | 不可行：带盐哈希无法建索引，按值查一行要全表逐行比对，鉴权成本随 Key 数量线性增长。 |
| 换 argon2id（新依赖） | 安全性同档，代价是新依赖 + 锁文件 + 镜像 + 推翻「口令哈希只用标准库」这条既有纪律。 |
| 哈希 + 可逆密文双列（面板可回读） | 放弃了「拖库无用」这个收益，还多一套主密钥管理（放哪、怎么轮换）。而面板回读原文的唯一用途是调试台，那件事已经改由用户自己粘贴解决（ADR-0019）。 |

## 前缀为什么是 `rc_live_`

`rk_live_` 与 **Stripe 的 restricted key 前缀完全相同**，这有一个已经发生过的事故面：推送代码时 GitHub 的 push protection 把测试里的假 Key 判成「Stripe Live API Restricted Key」并拒绝推送；同一套规则也会作用在租户身上——任何人把一把真实的 RAG Key 贴进 issue、日志或群里，都会被判成支付平台密钥泄露，久了是报警疲劳。前缀属于产品契约，改契约比改测试彻底。判据：前缀应当属于自家命名空间，且不与任何已知第三方前缀冲突；`rc_` 取自 RAG Core。
