# 0024. 端到端异步：一套会话、一个循环、没有第二套数据库写法

- 日期：2026-11-13

## 一句话决定

请求路径上**只有一种数据库写法**：`AsyncSession` 一路 `await` 到驱动。同步的请求级依赖（`get_db` / `get_transaction`）连同它们的调用点一起删除；HTTP 客户端不再按事件循环分家，改成**一个进程一个**；阶段计时的线程锁一并删掉（已经没有第二个线程写它）。驱动**不换**（仍是 psycopg 3），Celery 用**一个进程一个常驻循环**（ADR-0023）。

**这句话里没有任何一条是性能承诺**：压测读数（`docs/step11-loadtest-after-134.md`）显示 64 并发吞吐相对 4 并发是 **×0.96**，没有达到父 spec 的 2× 判据。本文第九节如实写这件事。

## 背景：为什么「异步外壳 + 同步内核」必须收口

父 spec 把病根写得很清楚，这里只留结论式的三条：

1. **并发上限不是数据库，是主循环**：每个请求要串行做完若干次同步查询 + 折叠 + 写库，这些时间没有被任何并发掩盖。第 10 步的检索执行池只是把**其中一次**（pgvector 的同步查询）挪出了主循环——代价是「并发上限变成 4 条线程」「排队超 2 秒就降级这一路」「取消传不进去」。
2. **取消传导不到**：客户端断开之后，线程里的查询还在跑、配额还在扣、trace 还在写。
3. **两种写法并存**：写代码的人要先判断「这个函数里该用同步还是异步 `Session`」，而这个判断错的方式是**沉默的**（漏一个 `await`，某段代码悄悄不执行）。

第 11 步按垂直切片逐条路径搬（检索 → 观测与反馈 → 控制面读 → 控制面写 → 入库与索引 → Redis），每片搬完就把同步那一半删掉。**票 #134 是最后一步：把剩下没有调用点的那一半删干净，并把「还剩什么」写下来。**

## 决策一：请求路径上只有 `AsyncSession`（同步的两个依赖彻底删除）

删掉的是 `app/db/session.py` 的 `get_db` 与 `get_transaction`。判断标准是**真实调用点**，不是「也许以后有用」：

| 被删的东西 | 怎么确认没人用 |
| --- | --- |
| `get_db` / `get_transaction`（FastAPI 依赖） | 全仓 `grep` 之后只剩三处：① 两个「控制面只用异步栈」的守卫用例（`test_console_async_reads.py` / `test_console_async_writes.py`，它们的断言是**「不在依赖树里」**）；② 若干夹具里为了挡住真库而写的 `dependency_overrides`（同步那两条已经没人解析，挡不挡都一样）；③ 各自的 docstring。**没有一个生产调用点**。 |
| 同步仓储孪生 `chunk_repository.count_by_kb`、`document_repository.create` / `update_status` / `count_by_kb` / `count_processing_for_tenant` | 逐个按「连自己模块内部都没人引用」筛出来的（其余 `*_statement` 之类的私有语句构造器被异步孪生共用，**不删**）。删完跑全量，1708 条用例一条没红。 |
| 「空事务」替身 `tests/fake_db.py::no_transaction` | 它存在的唯一理由是「同步事务依赖拿到 `object()` 会炸」，那两条依赖删了之后它没有调用点。 |
| 同步请求替身的接缝（`override_all_db` 里换 `get_db` / `get_transaction` 那两行、`async_mirror` / `share_rows_with`） | 后者只服务「一个用例里同时有两套栈」，迁移完成后再没有这种用例；前者换成异步那两条入口。 |
| 阶段计时的线程锁（`StageTimer._lock`） | 第 10 步的向量分支跑在执行池的常驻线程里，`record` 因此来自两个线程；池删除（#127）之后六段全在同一个循环上，`record` 里没有 `await`，不存在抢占。 |

**考虑过的替代方案**：

| 方案 | 为什么不选 |
| --- | --- |
| 留着 `get_db`「以防有人要写同步路由」 | 留着就是留着一份可以照抄的示范，而照抄的人不会去读 ADR。删掉之后「再写一条同步查询」需要先重建一整个依赖，那一步会被人看见。守卫用例也从「它没被依赖树用到」升级成「它不存在」——前者的漏洞是「它又被加回来但恰好没人用」。 |
| 保留同步孪生以便回滚 | 回滚的单位是**提交**，不是函数。第 11 步每个切片一个提交，回滚那一片就等于回到那片之前；留半套同步实现只会让下一个人以为它是可以用的。 |
| 把同步读者全部改成异步，一个不留 | 见决策四：有三处不是删掉就能了事的（第四处 Provider 装配已在票 #137 搬走），逐个说明。 |

**代价**：

- **测试里少了一条对等尺**：迁移期「同一个操作在同步与异步替身上发同一组 SQL」的契约测试（`tests/test_session_double_contract.py`）现在只剩异步那一半有意义。保留它是因为 `RecordingSession` 仍是异步替身的状态机（`AsyncRecordingSession` 继承它），不是因为它还在守两套栈。
- **`app/db/session.py` 这个名字会误导**：它现在只服务不在请求路径上的读者，模块文档第一段就把这件事写在最前面，并写清「别在这里加第四个读者」。

## 决策二：HTTP 客户端从「按 loop 注册表」收敛为「一个进程一个」

`app/core/http_clients.py` 不再维护 `WeakKeyDictionary[loop, client]`，只留一个槽：客户端本身 + 「它属于哪个循环」。取用时比对循环，不一致就重建、旧的丢掉（并记一条 warning）。

**为什么现在可以简化**：注册表要解决的前提是「同一个进程里同时活着好几个长活循环」——第 10 步的检索执行池有 4 条常驻线程各持一个循环，Celery 又每个任务 `asyncio.run` 一次。第 11 步把这两件事都消掉了（执行池删除；Worker 换成一个常驻循环，ADR-0023）。剩下的形状是「一个进程一个循环」，那张表就成了一张永远只有一行的表。

**随注册表一起删掉的三段复杂度**：弱引用键、「逐 loop 遍历关闭」、「往另一个活着的循环投协程再等结果」。它们全是多循环的解法。

**保住了什么**：那条硬约束没有松——跨循环复用 `AsyncClient` 会当场 `RuntimeError: Event loop is closed`（ES Provider 与 Celery 各付过一次学费）。循环比对仍在，只是从「表」变成「槽里的一个指针」。生产里这个比对恒为真，它只服务测试（一个用例一个循环）与脚本 / 异常退出留下的旧客户端。

**收尾仍是确定性的**：`aclose_http_client()`（API 的 lifespan、`WorkerLoop.shutdown`），幂等、没有就是安静 no-op；关不掉的只记 warning。任务体**不关**客户端——常驻循环下那句 `finally` 等于每个任务把共享客户端关掉，复用立刻归零（ADR-0023 记过这次险）。

**代价**：`WorkerLoop` 与 `lifespan` 的收尾语义绑在同一份实现上，跨进程不共享（这是对的：Worker 与 API 是两个进程，各自的槽在本进程内）。

## 决策三：驱动仍是 psycopg 3，asyncpg 留作翻案条件

**选择 psycopg 3（`postgresql+psycopg`）的理由**：

- 同一个驱动、同一个 SQLAlchemy dialect、同一套类型映射：JSONB / 数组 / pgvector 的行为与改造前**逐字一致**，这是「响应逐字节不变」最便宜的保证；
- 连接串的键与格式不变（`.env` 里仍是 `postgresql+psycopg://…`），部署侧零改动；
- psycopg 3 原生支持异步，不需要引入第二个驱动来承担一半流量。

**代价（如实写）**：psycopg 的异步实现比 asyncpg 慢约 20~30%——这是**别人的社区基准**，本仓库没做过 psycopg / asyncpg 的对照压测，不能当成本仓库的读数。本仓库的压测（`docs/step11-loadtest-after-134.md`）是**进程内模拟延迟**的尺子，只能量链路的形状：并发档之间怎么变、阻塞占比账本里记了什么。它既不能证明驱动是瓶颈，也不能证明驱动不是瓶颈——第九节自认有洞的「阻塞占比 = 0」只包了走异步会话的几条路径，压测又换掉了 Provider 工厂，那段真实的驱动往返根本不在账本里。所以这里不写「数据库往返不构成瓶颈」这类量化结论；驱动该不该换，交给下面的翻案条件与真正的对照压测。

**翻案条件（写清楚，免得以后有人以为「没选 asyncpg 是妥协」）**：

- 压测显示**驱动本身**成为瓶颈（`pool_timeout` 频繁触发而 `pg_stat_activity` 里连接并不缺 / 单次往返耗时随并发线性上升）→ 换 asyncpg 只改 dialect 与 URL，业务代码零改动；
- 需要 asyncpg 独有的能力（例如 `COPY` 的异步流式、LISTEN/NOTIFY 的异步迭代）；
- 换驱动**不改变**本文其余任何决定（池绑循环、一套会话、常驻循环）。

## 决策四：同步栈为什么可以「基本消失」，以及**还剩哪三处**

「同步栈消失」在一句话里是对的，在一份 ADR 里必须给边界。第 11 步删掉的是**请求路径上的**
同步栈；票 #137 把最后一位**在事件循环上**的读者——Provider 装配期的角色指针——也搬走了。
现在还剩以下三处同步读者，逐个说明为什么：

| 剩下的同步读者 | 在哪 | 为什么留着 | 翻案条件 |
| --- | --- | --- | --- |
| **运行时配置的热刷新**（`runtime_settings.ensure_runtime_overrides`） | 线程池里（`app/api/runtime_settings_middleware.py` 用 `run_in_threadpool` 调） | 它**不占事件循环**：读库发生在线程池的那一条线程上。每请求只做一次时间比较，真正读库是 TTL 级的（十几秒一次）。改成异步能省掉的只是一次线程跳转，代价是把二十来条用例的同步调用点改成 `async def` 并且要重造异步假会话——收益与改动面不成比例。 | 当刷新变成**每请求都读库**（TTL 缩到 0 或改成推送）时，它就从「边缘」变成「路径内」，那时按请求级异步依赖重写。 |
| **运维脚本**（`scripts/*.py`，10 个） | 独立进程的 `main()` | 它们用的种子 / 运维仓储**只有同步实现**（`tenant_repository.create`、`plan_repository.create`、`existing_tenant_ids` 等）。给它们造异步孪生＝为了脚本新增生产代码，而脚本是「运维敲一次、跑完就退」的单线程动作：没有并发、没有事件循环、没有可取消的请求。 | 哪天运维脚本要被服务端调用（例如做成控制台按钮背后的任务），它就不再是脚本，那时按请求路径的写法重写，并把仓储的异步孪生补齐。 |
| **启动期的档位装载**（`app/main.py::_load_profile_presets_from_db`） | lifespan 里、开始接请求之前 | 一次性读，发生在「服务还没对外」的那一段；失败也只是记 warning。改成异步的收益是 0 行复杂度、代价是给注入点换一个形状（`set_profile_preset_loader` 收协程）。 | 同上：若档位装载要变成「有写入就重载」，它会进入请求路径。 |

**已经搬走的那一处（第 11 步唯一一处在事件循环上的同步读）**：Provider 装配的角色指针。
`get_llm_provider(role)` 以前是同步工厂，它算配置指纹要靠 `_resolved_endpoint(role)` →
`model_config_service.resolve_role_config(role)` 开一个同步 `Session` 读角色指针；每次
装配 Provider 的请求都在循环上做一次同步库读（改写开启时每请求一次，重排对照路径同理）。
票 #137 把它整条搬到了异步栈：

- `resolve_role_config` / `role_endpoint` 是协程，指针与配置行都 `await`（`AsyncSession`）；
  `model_config_repository` 的同步孪生 `list_all` / `get_by_id` 随之删除；
- `get_llm_provider` 是协程，注入的 `RoleResolver` 也是协程（同步替身在 `await` 处当场坏掉，
  不许比真货宽容）；
- `.env` 回落分支逐字不变：**指针为空不是错误**（离线 / CI / 全新部署都落到这里）；
  读库失败照旧 `except Exception` 吞掉、只记 warning 并回落 `.env`；
- 缓存指纹的语义不变（角色 / 供应商 / 地址 / 模型 / key / 超时 / 思考强度），配置一改，
  下一次拿到的仍是新实例；
- `apply_framework_telemetry_switches()` 仍在**任何**客户端构造之前落地，包括「没配 key、
  走空实现」的早退路径；
- 调用点：请求路径（`rewrite` / `section_context` / `rerank_stage`）一律 `await`；Celery
  索引任务本来就在常驻循环里（ADR-0023），直接 `await`；评测脚本在自己的进程里用
  `asyncio.run` 桥接**一次性装配**（那里不是请求路径，`build_answer_set` 的注释写明了这一点）。

**这张表本身就是这份 ADR 的一部分**：下次有人问「还有没有同步写法」，答案是「有三处，
理由与翻案条件在这一节」；第 11 步曾经是四处，第四处（Provider 装配）已随票 #137 搬走。
不要在别处另起一份。

## 决策五：Worker 侧只用「一个进程一个常驻循环」

结论与论证在 **ADR-0023**（探针读数、三个方案的对比、确定性释放的顺序、win32 的 `SelectorEventLoop` 分支都在那里）。本文只记它与「端到端异步」的关系，以及为什么它必须和本步一起落地：

- **异步引擎的连接池绑在创建它的循环上**，而 Worker 的循环是「每任务一个、跑完即关」，于是「连接归谁管」第一次成了需要决定的问题；
- 选常驻循环之后，任务体把**工厂**投进去（`get_worker_loop().run(lambda: ...)`），第一次 `connect` 发生在那个循环里；
- **两个任务都接上了**：索引任务在票 #132 接线，旁证跑批（`app/tasks/side_evidence.py`）曾长期留着 `asyncio.run(_run_in_its_own_loop(...))` + `finally: await aclose_http_client()` 的旧形状，票 #137 的评审才发现并改掉。常驻循环之后，任务体**绝不能自己关共享客户端**——那会掐掉下一个任务要用的池子；关闭只发生在 `worker_process_shutdown`（见 ADR-0023）。
- **提交之后的投递也不占循环**：`apply_async` 是同步 broker 写，`after_commit` 回调在事件循环上。三处登记点（上传 `document_service`、控制台重建 `console_kb_service`、数据面重建 `routes/documents`）统一走 `index_dispatch.enqueue_document_after_commit`，由 `asyncio.to_thread` 把 publish 交给线程；同步的 `enqueue_document` 保留给运维脚本。Celery 若提供可 await 的发布通道，这一层就该删（翻案条件）。
- 收尾上移到 `worker_process_shutdown`：在循环**还活着的时候** `dispose` 引擎、关 HTTP 客户端，然后才停循环。

**翻案条件**：见 ADR-0023「翻案条件」三条（任务内高并发多文档 / 换 asyncpg / Celery 换 async 框架）。本文不重复。

## 决策六：连接预算按「一套 + 一个常驻循环」算

算式与逐项含义写在 `docs/架构.md`「链路与连接 · 四」。这里只记决定本身：

- **请求路径上只有一套池**（异步 15 = 5 + 10，`pool_pre_ping=True`、`pool_recycle=1800`）；
- **同步那一套仍存在**（上限同为 15，实际占用常数 1~2 条），但它只服务决策四里那三处；预算里按满额给，是给迁移脚本与将来多一条读者的余量，不是当前占用；
- **并发由进程数给**：API 一个进程一个池，Celery prefork 每个子进程一个池（常驻循环**不**放大池数——这是 ADR-0023 选 A 不选 B 的一半理由）；
- 监控口径跟着实现走：`queue_wait_ms` 随执行池消失；现在看「池里借不到连接」（`pool_timeout` 的前提是 `pool_size + max_overflow` 用满）与 `WorkerLoop.shutdown()` 的 `worker_loop_pool_state`。

## 不这么做会怎样（汇总）

- **两种写法并存**：下一个人写同步查询不会报错，只会在压测里表现为「某个并发档突然劣化」，而那时改的人已经走了。
- **按 loop 注册表的复杂度会一直付利息**：弱引用键、「往别人的循环投协程再等结果」这两段代码没有任何一条生产路径会走到，却要每次读 `http_clients.py` 都读一遍。
- **执行池的「排队超预算 → 降级」会继续把成功的检索变成降级**：并发越高越容易触发，而父 spec 的目标恰恰是「并发下不打折」。
- **阶段计时的锁**会让人以为「跨线程写 span 是允许的」，而那正是执行池时代的事故形状。

## 翻案条件（整体）

- **压测证明 psycopg 的异步驱动本身是瓶颈**：换 asyncpg（决策三），其余不动。
- **Provider 装配再出现新的带数据库场景**：票 #137 已经把工厂与角色解析整体变成协程，
  决策四的表里少了一行；新场景按同一形状（`await` + `AsyncSession`），不要再开一条同步
  装配路径。
- **索引任务变成一个任务内高并发多文档**：单常驻循环成为并发上限，回看 ADR-0023 的翻案条件（那时可以重新讨论「按 loop 的池」，而不是重新发明一张注册表）。
- **Celery 换成 async 框架**：`WorkerLoop` 退化成薄封装，ADR-0023 的决策二可删；本文其余不变。
- **出现「同一进程多个长活循环」的新理由**（例如进程内跑多个独立批次）：那时才需要重新讨论客户端的循环隔离——**先讨论，别先加回注册表**。

## 九、压测结论：把「没达到」写清楚

读数全文在 `docs/step11-loadtest-after-134.md`，这里只留结论：

| 判据 | 结果 |
| --- | --- |
| 64 并发吞吐 ≥ 2× | **没达到**：4 → 64 是 **×0.96**（161.3 → 154.4 req/s）；#127 同口径 ×0.92。第 11 步从头到尾都没有把吞吐随并发放大过。 |
| 单请求 P95 不劣化（±5%） | **没有定论**：#127 那份读数（−50% ~ −61%）、#134 同机复跑（−4% ~ +39%）与 #137 复跑（−17% / +3% / −18%）三份读数的参数与机器状态都不同，彼此对不上，**不足以证明或证伪** ±5%。这里只如实记录一句：**没有观察到把延迟系统性推高的改动**，不把任何一份读数包装成判据通过。 |
| 阻塞事件循环的 DB 占比 = 0 | **读数达成，但口径有洞**：压测账本只包异步会话，同步会话根本不在计量里；压测又换掉了 Provider 工厂、置空了 `RERANK_BASE_URL`，于是「唯一真在循环上读库的那一处」（`get_llm_provider` 的角色指针，见决策四第一条）从没进入过这条读数。所以 **0 不等于「循环上没有同步读库」**，只等于「走异步会话的那几条路径上没有」。票 #137 已把那一处整条搬走（`get_llm_provider` 与角色解析都是协程、指针读走 `AsyncSession`），从此这条口径不再有一个「故意不在账本里」的读者；本票没有把它包装成压测证明——守卫是结构性的（工厂与解析器的形状，见 `tests/test_llm_provider.py`；指针读只走异步会话，见 `tests/test_console_models.py`）。 |
| 噪音（`Event loop is closed`） | 0（第 10 步的收尾 + 本文决策二）。 |
| 每进程一套池且有上限 | 是（异步 15；同步那一套只服务决策四的三处）。 |

**该怎么说这一步的价值**：它换来的不是吞吐，是**形状**——并发下不再有「排队超预算就降级」、取消能传导到驱动、请求路径上只有一种会话写法、少一层（执行池 + 注册表）。父 spec 早就写了这句话；本文的义务是不把它包装成性能优化。

**票 #137 搬完后的同参数复跑**（读数写在临时目录，**不覆盖**已提交的 `docs/step11-loadtest-after-134.md` / `eval/loadtest-baseline/results-after-134.json`）：4 / 16 / 64 并发的 P95 是 30.23 / 243.61 / 480.61 ms，after-134 是 36.56 / 235.52 / 584.15 ms，相对变化 −17% / +3.4% / −18%；阻塞事件循环的同步数据库调用三档都是 0。这个脚本自己记的同机抖动约 ±15%，所以它能证明的是「没有劣化」，**不是**「变快了」；它也不覆盖 Provider 装配（压测里改写与重排都关着），那一处的守卫是结构性的（见上表）。

## 十、本步引入的契约增量（一处，需登记）

删掉检索执行池时，`RETRIEVAL_POOL_SIZE` / `RETRIEVAL_QUEUE_BUDGET_MS` 两个**运行时配置项**
一并从 `SETTING_SPECS` 删除——它们配置的对象（执行池）已经不存在了。后果是
`GET /console/settings` 的列表**少两行**。

这与父 spec「请求与响应契约一个字节不变」有冲突，必须说清取舍：

* 留着它们＝留两行「改了不生效」的面板项，那正是票 #116 花力气消灭的那类假话；
* 删掉它们＝一次**可见的、只影响控制面板列表**的收缩，检索接口的响应一个字节没变。

选后者：**配置项跟着它配置的东西一起死**。这一条是父 spec 的例外，记在这里，不藏着。

## 自检

一个没读过本项目的人，只看这份 ADR，能否说清：

1. **为什么请求路径上不能再出现同步 `Session`？** —— 因为它会上主循环，而主循环是这条链路的并发上限；两种写法并存的错法是沉默的。
2. **为什么现在可以「一个进程一个 HTTP 客户端」，而第 10 步不行？** —— 因为那时同一进程里活着好几个循环（执行池 + 每个任务一个），现在只剩一个。
3. **还有没有同步写法？** —— 有三处，在不在请求路径上是分界线，理由与翻案条件都在决策四那张表里；第 11 步曾经是四处，第四处（Provider 装配）已随票 #137 搬走。
4. **64 并发吞吐没到 2× 这件事写在哪？** —— 第九节，和「这一步换到的是什么」写在一起。

说不清就补大白话，不要补术语。
