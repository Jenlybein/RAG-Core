# 0017. 套餐定义进库，管理员可改、可预览、可追责

- 状态：已采纳（**推翻**架构文档原先「套餐硬编码」的决定）
- 日期：2026-11-10
- 相关：父 spec #72「第 7 步」、[`../架构.md`](../架构.md) ②平台管控、ADR-0018「三层授权与配置自洽校验」、ADR-0003「API Key 即应用身份」、[`../../GLOSSARY.md`](../../GLOSSARY.md)「套餐」「配额两级」

> ⚠️ **本 ADR 明确推翻一处既有决定**：[`../架构.md`](../架构.md)（②平台管控，第 188 行附近）写着「`PLAN_PRESETS` 是**硬编码**在代码里的（free / standard / pro 各有 features + limits），变更频率极低、改错代价极高，所以走 code review + 版本可控，不进数据库」。从第 7 步起这句话作废：**套餐定义进数据库，管理员在控制台可改**。架构文档本步那一节的回写单独立稿，本 ADR 是该处的唯一决策依据。

## 一句话

套餐（租户买了多少）在数据库里是一行**可编辑的数据**，不是代码里的常量。凡是面板上会出现输入框的字段，必须全部在库——一个都不许留在常量里。

## 背景

套餐原本是代码里的常量表：free / standard / pro 三组 features + limits，改一次走代码评审 + 发版。当时的理由听起来很硬——「变更频率极低、改错代价极高」。

但这条理由和另一件事放在一起就矛盾了：控制面的交付清单里，**「改套餐」本身就是一项功能**，而且要求「先算影响面、再落库、落库后即时生效、每次留审计」。也就是说：界面上一定会有套餐内容的输入框（QPS、日配额、库数、单库文档数、并发处理数、档位白名单、四个能力开关），这些输入框的后端却读常量。

于是有了那句判据：

> **界面能改、后端不读，比界面上没这个字段更糟。**

「没这个字段」只是功能缺失，运营知道去找研发；「填了不生效」是欺骗——运营以为给客户提了额度，而那次改动其实要等下一次发版才落实，客户第二天照样被限流，事故现场看起来却像限流坏了。更糟的是审计里会留下一条「管理员把 QPS 改成 200」的记录，配上实际仍在用的旧值，事后无法自证哪一边才对。

硬编码还有第二个实际代价：给某个客户临时提额度，只能改代码发版。这不是「变更频率极低」，而是「每次变更都很贵」，两件事被混成了一件。

## 决策

**套餐定义进库。** 一条套餐是一行数据：

- 档位白名单 + 四个能力开关 + 六个数值上限，全部是列（具体列名与表形状留在父 spec #72 与建表票，本文不重复）；
- 管理员在控制台改的是这一行；改完**删缓存**（不是写缓存）、即时生效，不必重启、不必发版、不必等过期；
- 面板上会出现输入框的字段必须全部在库。**一个字段留在常量里，那个字段就是「能改但不生效」的那一个。**

### 主键用整数自增，是决定而不是遗留

`plans` 的主键是整数自增，另外六张新表用的是裸字符串 id。这不是前后不一致：套餐 id 是**内部键**，调用方从来只见 `code`（脚本入参、错误信息、响应里出现的都是 `free` / `standard` / `pro`）；整数自增让 `tenants.plan_id` 与 `accounts.plan_id` 只存一个数字，比 32 字符的字符串紧凑，改 `code` 时也不牵动引用方。裸字符串 id 留给那些**本身就是对外标识**的行（租户、账号、配置、Key、会话、审计）；两种形态各自服务于「谁会被外面看见」。

### 预设文件只剩一个身份：首次启动的种子

`plan_presets` 不再是被读取的「真相」，只在**首次启动**时把三个标准套餐写进库里，之后以库为准。

种子是单向的：库里已经有同 id 的套餐时**不覆盖**。否则运维调过的数值会被下一次部署悄悄抹平——那正是「硬编码」换了个壳。

迁移口径也随之定下：升级前已存在的租户按标准套餐建档，本地演示租户按最高档，此后新建租户默认最低档。

## 为什么可以改：五道护栏兜住误改

「能改」不等于「随便改」。数据库里的定义之所以安全，是因为下面五条同时成立：

| 护栏 | 具体做法 | 挡住的是哪种事故 |
| --- | --- | --- |
| **变更预览**（`dry_run`） | 落库前先试算：这次改动会让哪几个账号**当场超限**（会超出库数 / 文档数的、会失去当前档位的）。试算只读，不写库 | 管理员把某套餐的库数从 10 降到 3，改完才发现 40 个客户当场撞上限 |
| **审计留档** | 每一次变更记「谁、什么时候、把什么改成了什么」，改前与改后各一份快照 | 事后追责与回滚都无从下手；也挡住「谁改的」只能靠猜 |
| **被引用的套餐不可删** | 还有账号挂在某套餐上时，删除被拒绝（`20019`） | 把客户挂空——账号指向一个不存在的套餐，下一次调用直接崩在这里 |
| **档位必须是已知枚举** | 白名单里出现未知档位即拒绝（`20018`） | 手打成 `qualty`，从此这个档位下的 Key 全都展开不出链路 |
| **数值上限必须 ≥ 1** | QPS、日配额、库数、单库文档数、单次检索库数、并发处理数一律不得为 0 或负数（`20018`） | 一个手滑把 QPS 填成 0，等于当场把这个套餐下的所有客户停服 |

另外一条不是护栏但同样必要：

- **改完是删缓存，不是写缓存。** 写缓存要求「每一处修改都记得同步」，删缓存则让下一次读自然拿到新值；后者漏不掉。

「被引用不可删」这条与「可改」是配套的：改是调额度，删是让客户失去定义——所以对同一份数据，改开、删关。

## 后果

### 正面

- 运营不必为改一个数字发版；「临时给客户提额度」从一次发布变成一个请求。
- 改之前能看见影响面，改之后有前后快照——这两件事合起来，才让「让运营动生产配置」这件事可以被批准。
- 套餐与密钥配置、租户数据在同一套事务与备份里，不再有两处真相。

### 代价

- 多一张表、多一次读；读要缓存（按套餐 id 短期缓存，Redis 而不是进程内字典，多 worker 才一致）。
- 多一套写入口：改套餐必须经过那个「一次接口两种模式」的入口（先试算、后落库、删缓存、写审计），不能散落成几个直接 UPDATE。
- 库里的数值可以被改成代码从没验证过的组合——这正是控制台与预览存在的理由，而不是回到硬编码的理由。

## 备选方案

| 方案 | 为何不选 |
| --- | --- |
| 继续硬编码常量（现状） | 与「控制台可改套餐」这条交付直接冲突，落地即「界面能改、后端不读」；临时提额度仍需发版 |
| 套餐放配置文件 / 环境变量 | 摆脱了发版，但没摆脱重启，也没法在界面上安全地改；预览与审计仍然无处落脚 |
| 进库但只在启动时读一次 | 「即时生效」做不到：改完得靠重启，而重启一次要停掉全平台的检索 |
| 进库且不做任何校验 | 一个手滑就能把 QPS 改成 0 或把档位写成不存在的名字，事故面比硬编码大得多——护栏是「能改」的前提，不是可选项 |
