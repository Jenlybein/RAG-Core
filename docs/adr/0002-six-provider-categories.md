# 0002. Provider 分六类，判据是「有没有自己的外部依赖」

- 状态：已采纳
- 日期：2026-11-03
- 相关：`GLOSSARY.md`「Provider（六类）」、「docs/技术栈.md」、「docs/架构.md」⑤Provider

## 背景

项目里的「外部依赖适配」一开始是按目录直觉分的：凡是能换实现的东西都建一个 Provider 目录。结果是分类不稳定——

- 一期把 Rerank 写成 `LLMRerankProvider`（内部只是包着 `LLMProvider` 打分），看着像 LLM 的一个变体，被算作「七类」之一；
- 查询改写与同义词扩展也调 LLM，被要求单独建类；
- 换一个角度看，VectorStore 与 KeywordSearch 又都是「存储」。

同一个仓库在不同文档里出现「六类」「七类」两种说法，目录数量、文档章节数、面试口径全都对不上。

## 决策

**Provider 固定为六类**：Embedding / VectorStore / KeywordSearch / LLM / Rerank / DocumentParser。

判据两条：

1. **有自有外部依赖**：这一类要不要连一个中台之外的端点或进程。Rerank 二期有了独立的 Cross-Encoder 端点，所以它成立；查询改写只是 `LLMProvider` 的一种用法，没有自己的外部依赖，**不算一类**。
2. **按最终生产形态算，不按一期形态算**。一期的 `LLMRerankProvider` 虽然靠 LLM 实现，但它在架构上占的是「重排」这个位置，二期换成专用模型时上层零改动。分类必须描述位置，不能描述当时的实现手段。

因此：**查询优化（改写 + 同义词）归属 `app/services/query/`，是服务层的一段流程，不是第七类 Provider。**

## 后果

### 正面

- 分类稳定，不会因为「某期用了什么实现手段」而漂移。
- 目录、文档章节、评测分组、面试口径全部对齐到同一个数字（六）。
- 换实现手段（LLM 重排 → Cross-Encoder 重排）不影响分类，只换实现类。

### 代价

- 判据需要解释一句才能讲清（「按最终形态算」），不如「数目录」直观。
- `query/` 放在服务层而不是 Provider 层，会让「为什么它不算 Provider」成为必答题（面试里也确实会被问）。

## 备选方案

| 方案 | 为何不选 |
| --- | --- |
| 按「能否替换」分类 → 七类（含查询优化） | 查询优化没有自有外部依赖，纳进来就打开了口子：以后每个调 LLM 的流程都能算一类 |
| 按「存储 / 模型 / 解析」三分 | 太粗，VectorStore 与 KeywordSearch 是一对一错的两条召回通道，必须分开 |
| 按一期实现手段分类（Rerank 归 LLM） | 二期换专用模型时分类要重排，历史文档全部作废 |
