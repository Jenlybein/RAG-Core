# 0001. 中台不生成答案，接口是 `retrieve` 不是 `chat`

- 状态：已采纳
- 日期：2026-11-03
- 相关：`GLOSSARY.md`「边界」「检索结果」、「docs/架构.md」②平台管控

## 背景

第一版设计的是 `POST /api/v1/chat`，职责是「检索上下文 → 调大模型 → 生成答案」。这个形状符合直觉：调用方只要一句 query 就能拿到答案，接入最省事。

但它把两个问题一并引入了：

1. **职责重叠**：租户自己的业务系统本来就有问答逻辑（提示词、人设、兜底话术、审核）。中台再生成一份，租户要么放弃自己的那套，要么把中台的答案再包一层——两种都别扭。
2. **契约扩张**：一旦中台开始拼上下文、调生成模型，就得跟着租户的需求演化出 `system_prompt`、`temperature`、`max_tokens`、多轮历史……这些是应用的关注点，不是能力中台的。

## 决策

中台对外的唯一业务动作是 **`POST /api/v1/rag/retrieve`**：给定一个 query，返回最相关的切片有序列表、每条带分数与出处，并带「这次是否降级」的标记。

- **不生成答案**，不调生成模型；
- **不返回 `context_text`**（拼好的大段上下文），拼接是租户的事；
- 生成侧能力由租户自己接，中台只保证「找准、找全、可追溯」。

## 后果

### 正面

- 边界稳定：所有后续能力（混合检索、重排、上下文恢复、文档版本、MCP）都长在「返回切片」这条契约上，没有被生成侧的需求污染。
- 可评测：召回质量可以用 `context_precision` / `context_recall` 直接度量，不需要经过一层生成再判断。
- 租户可替换：租户换生成模型、改提示词，中台一行不用动。
- 责任清晰：答错了是租户的生成逻辑问题还是中台的召回问题，可以分开归因。

### 代价

- 接入成本转移给租户：租户要自己拼上下文、调模型、处理多轮。这一点用控制台的「调试台」和 MCP 入口来缓解（调试台直接打真实 retrieve，MCP 让 Agent 自己组织回答）。
- 中台做的事情看起来「不够酷」：只有检索，没有答案。但对能力中台来说这是正确的形状。

## 备选方案

| 方案 | 为何不选 |
| --- | --- |
| `/chat` 生成答案 | 职责重叠、契约扩张；边界一破，后面每章都会往「答案」上长 |
| 同时提供 `/chat` 与 `/retrieve` | 两套契约要各自维护权限、配额、评测，且租户会倾向用 `/chat`，把中台拉成应用 |
| 返回 `context_text` 由租户直接喂模型 | 看似折中，实际让中台替租户决定了「怎么拼」——切片条数、顺序、格式仍是业务决策 |
