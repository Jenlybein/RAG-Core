# 0013. 一条检索结果代表一节，而不是一个切片

- 状态：已采纳；**两个折叠开关的归属已由第 7 步修订改为「密钥配置」，见文末「后续修订（第 7 步）」**；**响应里 `section_id` 的两种含义（单元 id / 节 id）与节 id 的新算法已由第 11 步（#143 / #156）登记，见文末「后续修订（第 11 步）」**
- 日期：2026-11-09
- 相关：ADR-0010「检索契约（含后续修订）」、ADR-0012「装饰字段（已取代）」、**ADR-0018「三层授权与配置自洽校验」**、`GLOSSARY.md`「交付单元」「父块」「结果形状组」、`app/services/result_collapse.py`

## 背景

第 3 步把切块粒度变细（h3 成边界、表格按行产出），检索的「找得准」变好了，
但引入了两个新问题：

1. **一条结果喂不饱模型。** 145 字的细片刚好覆盖一个子节的一小段，模型要回答
   问题得再发三五次请求补齐上下文。
2. **名额被同节碎片占满。** `top_k=5` 里可能有 3 条来自同一节的不同片，
   真正该出现的另一节挤不进来。

ADR-0012 的解法是给结果**附加** `parent` 与 `table_context` 字段（不改结果本身）。
实测下来这只解决了一半：字段有了，但排序与名额分配仍按「片」进行，
第 2 个问题一点没好转。

## 决策

### 1. 折叠：用小片算分，用大块交付

检索仍按小片算分（保住「找得准」），**返回前把同一父节的命中折成一条**。

| 单元种类 | 归组键 | 内容 |
| --- | --- | --- |
| 表格 | `(文档, 章节, table_part)` | 整表全文 |
| 其余 | `(文档, 章节路径前两段)` | 该节全文（分级，见下） |

**归组键用章节路径的前两段，不是 `parent_section_id`。** 这条在实现里踩过坑：`parent_section_id` 是「上一级」，对 h2 级的切片（它下面没有 h3）会指到 h1，按它归组会把整篇文档折成 1 个单元——一份有 40 个 h2 小节的文档实测就被折成 1 条结果，交付口径的分数因此虚高。`unit_path_of(heading_path)` 取前两段（文档 > 大节）才是稳定的 h2 级单元；无标题文档没有章节路径，就各自成单元，不造一个假父节。
`Hit.parent_section_id` 仍作为溯源元数据填值，但**折叠全程不读它**。

同一张表的多个行级片、同一父节的多个片，各只占一个名额。

### 2. 身份是 `section_id`，`chunk_id` 降级为代表片

一条结果代表一节，所以它的身份必须是节，不是片。新增 `section_id` 作为主标识，
`chunk_id` 保留为「让它浮上来的那一片」（组内分最高那片）。

**为什么不把多个 `chunk_id` 放进一个列表**：那会把内部索引结构漏进契约，
让调用方以为「一条结果 = 多个切片」，语义反而更糊。子片 id 另放
`source_chunk_ids`，只作溯源用，不是主键。

### 3. 内容内联返回

**不**返回节 id 让调用方或模型再去取一次。small-to-big 的全部价值就是省掉这次
往返；让模型去取等于把「两轮」变成「三轮」，比一开始就用大块更慢。

### 4. `score` = 单元内命中片的最高分

取 max，不取平均。平均会惩罚「一节里多片都命中」这种**好情况**：命中越多，
平均越低，方向是反的。

### 5. 分级：不是每次都返回整节

| 命中情况 | 给什么 | `expansion` |
| --- | --- | --- |
| 同一单元只命中 1 片 | 该片 + 前后各 1 片 | `neighbors` |
| 同一单元命中 ≥2 片 | 整节 | `parent` |
| 跨 ≥2 个单元 | 各节全文 | `parent` |
| 表格单元 | 整表 | `table` |

一刀切返回整节会把 token 花在没命中的片上：命中 1 个 150 字细片却返回 1000 字
整节，是 7 倍浪费。

### 6. over-fetch 补足条数

内部召回 `top_k × 3` 个候选，折叠后截断到 `top_k`。

**因子写成常量，不做成配置项**：15 道题的样本量下，任何可调旋钮都必然被调成
过拟合值。×3 的依据是实测每题平均 1.7 片同节命中，余量足够。

## 与 LangChain 参考实现的两处有意偏离

`ParentDocumentRetriever` / `MultiVectorRetriever` 是这套模式的参考实现。我们对齐
了它的主干（小片检索 → 按父 id 去重保序 → 批量取父内容 → 返回父内容），但有两处
**刻意不同**：

| 偏离 | 参考实现 | 我们 | 理由 |
| --- | --- | --- | --- |
| 去重后条数 | 不补足，可能只返回 1 条 | over-fetch 后截断到 `top_k` | `top_k` 是对外承诺，返回 1 条会让调用方困惑，评测的 R@k 也会失真 |
| 单元的分数 | `mget` 只返回文档，没有分 | 取组内最高分 | 我们的响应有 `score`，调用方会拿它做阈值判断，不能空着 |

两条都写进代码注释，避免后人以为是漏抄。

## 后果

- **破坏性变更**：`parent` 与 `table_context` 两个字段删除（折叠后 `content`
  已经是大的，它们是重复数据）。调用方若读这两个字段需改用 `content`。
- 响应体积变大：`top_k=5` 从 5×145 字变成最多 5×整节。要旧体积传
  `include_parent=false`，此时不折叠、逐字返回小片。

另一个开关 `expand_table_rows` 只影响**表格单元**：``false`` 时行级片不再折回整表，各自成单元（身份仍是它所属的节，不是 chunk id），给「只要精确到那一行」的调用方。它不改变节单元的折叠行为。
- 向量召回多取 3 倍候选；向量查询本身是对数级，延迟影响很小。
- **不需要重建索引**：折叠全在返回前完成。
- 评测必须同时报两个口径（`chunk 级` 与 `delivered 级`），否则「片变碎」与
  「返回单元变了」这两件事又会被混为一谈。

## 备选方案

- **继续用 ADR-0012 的附加字段**：否决。实测只解决了「喂不够」，没解决「名额被占满」。
- **按父节重新打分后再排**（邻居分数聚合）：否决。这是自造公式，没有参考实现；
  15 道题的样本量下，任何聚合权重都会被调成过拟合值。
- **在评测里复刻折叠逻辑**：否决。此前三次数字出错的根因都是「评测复刻生产逻辑
  但复刻错了」，所以折叠必须是纯函数，生产与评测共用一份实现。

## 后续修订（第 7 步，#73，2026-11-10）：折叠开关改由密钥配置提供

**本文「后果」一节里「要旧体积传 `include_parent=false`」与「另一个开关 `expand_table_rows`……」两处提到的开关，不再在请求体里**：第 7 步起它们是**密钥配置**里的结果形状偏好，随这把 Key 固定，调用方改不了；请求体只剩 `kb_ids` + `query`（见 [ADR-0010](0010-retrieval-contract.md)「第三次修订」）。决策 1–6 与「以小片算分、以大块交付」的主干一律不变——`expand_table_rows` 关掉时的行为（行级片各自成单元、身份仍是它所属的节而非 `chunk_id`）原样保留，只是这个「关」由配置给出，不由请求给出。

### 为什么改归属

- **交付粒度不是检索能力。** 折叠改变的是「一条结果覆盖一节还是一片」；候选、融合顺序、重排与 `score` 的算法一字未动。折叠开与关，找得准不准、排得对不对完全一样。把它做成按次可选，等于让人误以为「不折叠」是另一种检索质量。
- **它不该按次重新决定。** 同一集成里一半请求折成整节、一半逐片返回，调用方的解析代码必须同时兼容两种形状。形状是这套集成的属性，与「返回条数由档位固定」同理。
- **请求必须停在两个字段。** 这是本步最硬的一条约束：请求只表达「问什么、查哪些库」。为两个粒度开关开一次例外，下一个开关就会要求第二次例外。

### 后果

- 「要旧体积」的操作从「传 `false`」变成「改这把 Key 的密钥配置」，改完即时生效，不必重新签发 Key。
- 两个开关仍默认开：折叠是这套设计的主干，默认关等于没做。
- 与本文「后果」一节那两句话冲突之处以此节为准；归组键取章节路径前两段、over-fetch ×3 **仍是写死的常数**（决策 6），不随这次归属变更挪进配置。

## 后续修订（第 11 步，#143 / #156）：响应里的 `section_id` 有两种含义，别混

决策 2 说「身份是 `section_id`」，那句话在**折叠态**下指的是**单元 id**，不是库里存的节 id：

| 响应里的这一条是什么 | `section_id` 是哪个 id | 算法 |
| --- | --- | --- |
| 折叠出的节单元 / 表格单元（`include_parent=true`） | **单元 id** | `sha256(unit_path_of(heading_path))`，即「文档 > 大节」前两段的哈希——与归组键同一份前缀 |
| 无标题文档、或关掉行级片合并的 `table_row`（单元小于一节） | 它所属的**节 id** | `stable_hash(文档 id : 标题路径)`，`chunks.section_id` 那一列 |

- **为什么不能统一成一个**：`section_id` 是这条结果的身份，而身份必须与「这条结果覆盖多大一块正文」一致。折叠态覆盖的是一整节（h2），此时拿库里存的 h3 级节 id 当身份，同一个单元里的不同命中会给出不同的 id；反之单元小于节时（一片一行），拿单元 id 又会把「精确到那一行」的那条说成「整节」。
- **节 id 的算法在第 11 步改过**（#143，见 [ADR-0025](0025-index-as-build-artifact.md) 决策五）：现在带**文档 id**，所以两份文档的同名章节是两个 id；不含版本，所以重建前后同一节仍是同一个 id。折叠态那个单元 id 不含文档 id 也不含版本——它只由路径算出，**跨文档不保证唯一**，要唯一定位一条结果请连 `document_id` 一起读。
- 无标题文档真的没有章节路径时 `section_id` 是空串，响应层落成 `null`——**绝不把 `chunk_id` 填进 `section_id`**，那会让调用方以为拿到的是节。
- 实现只有一处：`app/services/result_collapse.py` 的 `_unit_section_id`（`docstring` 里写着这三种情况），本文只登记口径，不改决策 1–6。
