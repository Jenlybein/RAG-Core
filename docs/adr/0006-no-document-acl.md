# 0006. 不做文档级 ACL，隔离只到租户 + Key 的数据范围

- 状态：已采纳；**运维脚本专用的三条跨租户只读扫描已由文末「第 1 次修订」显式豁免**
- 日期：2026-11-03
- 相关：`GLOSSARY.md`「身份与权限」「租户」「数据范围」、「docs/架构.md」②平台管控

## 背景

多租户隔离方案落定后，讨论里反复出现一个诉求：「同一家公司里，HR 的文档不能让财务搜到」。自然的解法是引入 `document_acl` / `department_id` 这类文档级权限，让检索时再按「谁在看」过滤。

这个诉求合理，但它要求中台知道**「谁在看」**——而中台的调用方是第三方应用，请求里只有一把 Key 和一个 query。要支持文档级权限，就得让调用方把「终端用户的身份 / 部门 / 角色」一并传上来，并且让中台信任它。

## 决策

**本期不做部门级 / 角色级 / 文档级 ACL。** 隔离只到两层：

1. **租户级**：`tenant_id` 由 Key 解出，所有查询强制过滤（Repository 方法签名强制带 `tenant_id`，pgvector 与 ES 也强制带）。
2. **Key 数据范围**：`key_config.kb_ids` + `index_version` 决定这把 Key 能摸到哪些库、哪套索引。作用域被物理锁定——不是校验拦的，是它没有那个能力。

**中台不识别「用户」，只认 Key。** 需要更细粒度隔离的租户，做法是**按人群切知识库 + 发不同的 Key**：给 HR 团队一把只含 HR 库的 Key，给财务一把只含财务库的 Key。

## 后果

### 正面

- 隔离的真相只有一处（Key → 数据范围），不会出现「应用层 ACL 与 Key 范围打架」。
- 不需要让调用方上传终端用户身份，避免了「谁都能自报身份」这类漏洞。
- 检索链路没有额外过滤步骤，延迟与复杂度都不受影响。
- 评测口径干净：同一把 Key 跑评测，结果可复现。

### 代价

- 租户内「同一批库里按人过滤」的需求无法满足，只能用「多建库 + 多把 Key」绕。库数量会涨，管理成本转移给租户。
- 如果将来必须做，这不是加个字段的事：要引入「调用方声明用户身份 + 中台验签」的机制，属于架构级变更。
- 面试里会被问「为什么不做 ACL」——答案必须是这套取舍，而不是「没时间做」。

## 备选方案

| 方案 | 为何不选 |
| --- | --- |
| 加 `document_acl` 表，按 `department_id` 过滤 | 要求中台信任调用方传入的用户身份；且每条 SQL 都要多一次 ACL join，隔离真相分散到各处 |
| 让调用方传 `user_id`，中台按用户查权限 | 中台没有用户体系，也没有权限数据；等于替租户做一套 IAM |
| 做「库级」权限（谁能用哪个库） | 这个已经由 Key 的 `kb_ids` 实现了——再多一层只增加复杂度，不增加隔离强度 |

## 第 1 次修订（第 12 步，#180，2026-11-16）：运维脚本专用的跨租户扫描是显式豁免

本文的决策 1 是「Repository 方法签名强制带 `tenant_id`」。落地时有三条**只读扫描**刻意不带它，这里把豁免写清楚，否则下一个人会把它们「顺手修好」，而对账从此只能看见一个租户：

| 方法（`app/repositories/document_repository.py`） | 唯一调用方 | 为什么必须跨租户 |
| --- | --- | --- |
| `list_missing_content` | `scripts/backfill_document_content.py` | 「整库里还有哪些文档没有正文」是一次性回填问题，按租户切分会让别的租户里缺正文的文档永远补不上 |
| `list_with_expired_versions` | `scripts/purge_document_versions.py` | 清理要问「整库里谁的保留窗口非空」，按租户切分只会让一次清理跑成 N 次、并漏掉运维没想到的那些租户 |
| `list_for_version_reconcile` | `scripts/verify_document_versions.py` | 对账的对象是**整库存量数据**；按租户切分会让「另一个租户里的分歧」永远看不见，而那正是这条脚本存在的理由 |

**这不是「租户过滤可以省」**，而是「这一层不该有租户这个维度」：三条都只回答一次性运维问题，不服务任何一种业务查询。真正需要租户的地方一步都没让——扫描只交出「要对账 / 要清 / 要补」的文档 id，**拿这批 id 去读内容或关键词仍逐租户强制过滤**（`verify_document_versions.py` 的关键词那一维就是逐租户问的；`purge_document_chunks` 的删除键也带租户）。

**这类方法的纪律**（三条，缺一条就变成假守卫或真越权）：

1. docstring 必须写明「**仅运维脚本使用**」，并点名是哪一个脚本；
2. docstring 必须写明「**跨租户是刻意的**」并给出理由——只写「没有租户参数」而不写为什么，下一个人会认为那是缺陷；
3. docstring 必须写明「**数据面禁用**」——检索 / 列表 / 管控接口一律不得调用，也不得拿它当先例。

新增同类方法时照这三条写；CR 里看到「没有 `tenant_id` 的 Repository 方法」，第一件事是问它属于不属于这一节，而不是先补参数。
