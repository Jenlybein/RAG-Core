# 0006. 不做文档级 ACL，隔离只到租户 + Key 的数据范围

- 状态：已采纳
- 日期：2026-11-03
- 相关：`GLOSSARY.md`「身份与权限」「租户」「数据范围」、「docs/架构.md」②平台管控

## 背景

多租户隔离方案落定后，讨论里反复出现一个诉求：「同一家公司里，HR 的文档不能让财务搜到」。自然的解法是引入 `document_acl` / `department_id` 这类文档级权限，让检索时再按「谁在看」过滤。

这个诉求合理，但它要求中台知道**「谁在看」**——而中台的调用方是第三方应用，请求里只有一把 Key 和一个 query。要支持文档级权限，就得让调用方把「终端用户的身份 / 部门 / 角色」一并传上来，并且让中台信任它。

## 决策

**本期不做部门级 / 角色级 / 文档级 ACL。** 隔离只到两层：

1. **租户级**：`tenant_id` 由 Key 解出，所有查询强制过滤（Repository 方法签名强制带 `tenant_id`，pgvector 与 ES 也强制带）。
2. **Key 数据范围**：`key_config.kb_ids` + `index_version` 决定这把 Key 能摸到哪些库、哪套索引。作用域被物理锁定——不是校验拦的，是它没有那个能力。

**中台不识别「用户」，只认 Key。** 需要更细粒度隔离的租户，做法是**按人群切知识库 + 发不同的 Key**：给 HR 团队一把只含 HR 库的 Key，给财务一把只含财务库的 Key。

## 后果

### 正面

- 隔离的真相只有一处（Key → 数据范围），不会出现「应用层 ACL 与 Key 范围打架」。
- 不需要让调用方上传终端用户身份，避免了「谁都能自报身份」这类漏洞。
- 检索链路没有额外过滤步骤，延迟与复杂度都不受影响。
- 评测口径干净：同一把 Key 跑评测，结果可复现。

### 代价

- 租户内「同一批库里按人过滤」的需求无法满足，只能用「多建库 + 多把 Key」绕。库数量会涨，管理成本转移给租户。
- 如果将来必须做，这不是加个字段的事：要引入「调用方声明用户身份 + 中台验签」的机制，属于架构级变更。
- 面试里会被问「为什么不做 ACL」——答案必须是这套取舍，而不是「没时间做」。

## 备选方案

| 方案 | 为何不选 |
| --- | --- |
| 加 `document_acl` 表，按 `department_id` 过滤 | 要求中台信任调用方传入的用户身份；且每条 SQL 都要多一次 ACL join，隔离真相分散到各处 |
| 让调用方传 `user_id`，中台按用户查权限 | 中台没有用户体系，也没有权限数据；等于替租户做一套 IAM |
| 做「库级」权限（谁能用哪个库） | 这个已经由 Key 的 `kb_ids` 实现了——再多一层只增加复杂度，不增加隔离强度 |
