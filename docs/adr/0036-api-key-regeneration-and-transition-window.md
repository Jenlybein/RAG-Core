# 0036. 重新生成 Key：为什么是「同一把换凭证」，为什么旧密钥还能用 24 小时

- 状态：已采纳（第 17 步 #227 现场五）
- 日期：2026-11-27
- 相关：[ADR-0004](0004-api-key-hashed-storage.md)（Key 只存哈希：原文不可取回）、[ADR-0007](0007-business-errors-http-200.md)（业务失败走 200 + 非零 `code`）、`GLOSSARY.md`「API Key」「Key 哈希」「签发」「重新生成」「过渡密钥」

## 背景

`api_keys` 里只有 `scrypt` 哈希（[ADR-0004](0004-api-key-hashed-storage.md)），于是「Key 丢了」「Key 泄了」这两件必然会发生的运维事故，在本仓只有一条出路：**让这把 Key 换一份密钥本体**。

改造前那条出路其实是「删了再签发一把」。它有三个真实的坏处，而每一个都在运维现场先炸一次再被发现：

1. **配置会丢**。密钥配置（白名单、授权位、额度）独立于 Key（[GLOSSARY「密钥配置」](../GLOSSARY.md)），删 Key 不删配置，但新 Key 需要**重新配一遍**——而用户在「钥匙刚丢了」的当口，最不想做的事就是回去核对「上次这套是查哪几个库、额度多少」。
2. **身份会变**。`key_id` 变了，任何按 `key_id` 归档的东西（日志、审计里的 `target: key:<id>`、对账脚本）都对不上前后两条记录。
3. **失效没有过渡**。旧 Key 要么此刻还能用（删之前），要么此刻立刻不能用（删之后），中间没有一段「两边都能用」的时间给线上业务换配置。删除那一刻就是一次**立即中断**。

本文只决策三件事：**换的是什么**、**旧的还能用多久**、**过渡期怎么结束**。

## 决策一：重新生成 = 同一把 Key 换凭证，不是签发一把新的

| | 签发（issue） | 重新生成（regenerate） |
| --- | --- | --- |
| `key_id` | 新的 | **不变** |
| 名字 / 密钥配置 | 新的（要随签发一起配） | **不变**（沿用原来那套） |
| 旧 Key | 不受影响（加法） | 旧**密钥本体**失效（替换） |
| 审计 | `key.issue` | `key.regenerate` |

**为什么不是「删旧 + 签发新」**：那等于把「配置」变成用户的任务，且在丢 Key 的当口让他再配一遍白名单。**为什么审计要分两个动作名**：这两件事的后果不同（加法 vs 替换 + 旧凭证失效），混成一个动作名，事后没人能从账本里看出「这次是多发了一把，还是把在用的那把换了」。

## 决策二：旧密钥本体保留 24 小时，且**只保留最近一把**

重新生成的那一刻，正在跑的业务还拿着旧 Key。让它立刻失效就是把所有集成当场打断；让它长期有效，则「怀疑泄露」这个场景永远收不了口。

于是留一个**窗口**：旧哈希与旧末 5 位搬进 `prev_key_hash` / `prev_key_tail`，截止时刻写进 `prev_key_expires_at`。窗口内新旧都能过校验，窗口外只认新的。

**为什么只保留一把**：留一串旧址等于同时允许一串凭证有效，与「一把 Key 只有一份有效密钥」正好相反，也让「这把 Key 现在到底有几个有效凭证」无法回答。窗口内再重新生成一次，上一把旧址直接被覆盖（等于同时作废）。

**为什么窗口长度的常量在服务层、不在这张表**：表里存的是**那一把 Key 在轮换那一刻**按当时的策略算出来的截止时刻。策略以后改成 1 小时或 72 小时，不会追溯修改已在窗口里的行——审计才讲得清「它为什么在某个时刻还能用」。

## 决策三：过渡期的结束只有一个判据——`prev_key_expires_at` 已过去

「自然到期」与「用户点了『作废旧 Key』」视为**同一件事的两种结束方式**：作废就是把截止时刻改成过去（`now - 1s`）。

这样做的理由有三条：

1. 判定只有**一个不等式**（`now <= prev_key_expires_at`），鉴权与界面读的是同一个形状；多一个 `revoked_at` 状态位就是第二个条件，而两个条件里宽一秒、严一秒都是事故（宽一秒 = 作废了还能用；严一秒 = 还没到期却先拒了）。
2. 旧 Key 被拒时的文案可以**精确**：只有确认「这串确实是那把旧密钥」，才回「这把 Key 的密钥已重新生成，请使用新 Key」；否则（比如随便一串错密钥）仍回「Key 不存在」，不泄露内部状态。为此作废时**不清空**哈希与末 5 位——它们已经过不了校验（判据是时刻），但留着才能继续说出那句专用文案、并让审计讲清「这次过渡是怎么结束的」。
3. 界面上只需要「截止时刻 > 现在」一个条件，不需要区分「是作废的还是到期的」。

## 决策四：过渡密钥**不进** Key 校验缓存

`KeyVerifyCache` 的承诺是「撤销一律立即生效」（[`app/core/key_verify_cache.py`](../../app/core/key_verify_cache.py) 模块文档）。但过渡期内的旧串如果进了缓存，用户点完「作废旧 Key」之后它还能靠缓存再活一个 TTL——缓存就成了「一把 60 秒有效的钱包」。

所以：**当前密钥照常进缓存；过渡密钥每次真校验**。代价是过渡期内旧业务每请求多烧一次 scrypt（50~100ms），而这本来就是一段要被赶快的状态。

## 后果与代价

- **泄露窗口**：怀疑泄露时点了重新生成，攻击者手里的旧 Key 仍可用最多 24 小时。缓解在于界面上「作废旧 Key」随时可点（立刻关闭窗口），文案也必须说清「它仍然可用 24 小时」——不说清，用户会以为已经立刻失效。
- **一次迁移**：`api_keys` 加 4 列（`prev_key_hash` / `prev_key_tail` / `prev_key_expires_at` / `rotated_at`），纯加列、可回滚。
- **一个与旧行为不同之处**：从没轮换过的 Key 行为逐字不变（`prev_key_hash` 为 NULL 时不比对、不错文案）。
