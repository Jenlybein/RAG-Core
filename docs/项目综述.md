# RAG-Core 项目综述

RAG-Core 是一个面向业务系统的 **RAG 能力中台**。

核心边界一句话：**文档进来，切片出去**。它不生成最终答案 —— 你问它一个问题，它返回「最相关的切片 + 相似度分数 + 出处」；怎么拼 Prompt、调大模型、组织成自然语言答复，是租户自己的事。

## 定位：中台，而非应用

这个边界是刻意的架构决策，不是技术限制。最早的第三个接口叫 `POST /api/v1/chat`（收到问题 → 检索 → 调大模型 → 返回答案），后来改成 `POST /api/v1/rag/retrieve`（收到问题 → 检索 → 返回检索结果，全程不调生成模型）。原因很直接：一旦中台开始生成答案，就会被各家租户的 Prompt 风格、话术要求、免责声明拖着走，最后变成永远改不完的定制项目。**只返回切片，中台才能被不同租户复用。**

租户接入时不需要关心 embedding、向量库、切片策略、重排、Prompt 组装、模型切换这些底层细节，只需要三件事：**建知识库 → 上传 / 同步文档 → 调检索接口**。

### 三种接入面

| 接入面 | 入口 | 面向 |
| --- | --- | --- |
| HTTP API | `POST /api/v1/rag/retrieve` | 业务系统后端 |
| MCP | `POST /mcp`（JSON-RPC） | AI Agent（Claude Desktop 等） |
| 控制台 | Vue 3 调试台 | 人 |

- **HTTP API** —— 业务系统后端直接调检索。
- **MCP** —— 暴露三个工具：`rag_retrieve` / `rag_research` / `rag_list_knowledge_bases`，**入参只有 `query`**，配置全挂在 API Key 上；与 HTTP 共用同一道平台层判定内核（`auth_core`），不另起链路。
- **控制台** —— 分**用户面板**（账号操作本租户资源：建库 / 上传 / Key 配置 / 检索调试）与**管理员面板**（需 `admin` 角色，管账号 / 套餐 / 审计，普通账号直接 403）。

## 为什么值得做：别让五个团队各造一遍轮子

一家公司里至少有五个团队会有「智能问答」的需求：客服基于产品文档与工单答疑、运营查 SOP 与活动规则、销售生成客户回复、内部员工搜制度与流程、某个业务系统在页面里嵌一个知识助手。

如果每个团队各做一套 RAG，下面九件事会重复做五遍：文档解析、文本切片、向量化、索引更新、权限隔离、Prompt 调优、召回优化、模型成本控制、日志追踪与效果评测。而且大概率每套都只做到「能演示」，上不了生产、难持续优化、没法规模化复用。

把 RAG 从单点应用升级为企业可复用的 AI 基础设施，把那九件共性工作收敛成一份公共服务，租户的接入成本才能从「数周」压到「几天」。

## 它解决的四个实际问题

1. **接入成本高** —— 租户不必理解 RAG 底层，也不用自己维护向量库、Embedding 模型、检索策略和 Prompt 模板。传知识库与问题即可接入，底层细节全部由中台封装。
2. **答案不可控、不可追溯** —— 直接调大模型容易幻觉，且回答依据不透明。中台返回检索结果时会带上**引用来源、命中的切片、相似度分数和原始文档信息**，让结果可解释、可审计；租户据此自己生成答案，每段话都能指到出处。
3. **效果无法持续优化** —— 很多 RAG 项目上线后判断不了「回答准不准、召回合不合理」。中台记录 query、召回切片、反馈分数、耗时、token 消耗与模型调用日志，并支持评测集、人工反馈与离线量化，让切片策略、召回策略、重排模型与模型选择都能持续迭代。
4. **多租户与数据范围隔离** —— 隔离分两层，都在**检索阶段前置**：租户级靠 `tenant_id`（A 公司查不到 B 公司），租户内靠 API Key 上挂的数据范围（可用哪些知识库、哪个索引版本），不属于该范围的切片在召回前就被过滤掉。部门级 / 角色级 / 文档级 ACL 本期不做 —— 中台不识别「用户」，只认 Key。

## 核心功能

调试台上可实操的 5 项（用户面板，仅操作本租户）：

1. **知识库创建与上传** —— 新建知识库、上传多格式文档，后端异步解析并建索引。
2. **知识库管理** —— 查看知识库配置、文档列表与处理状态（处理中 / 成功 / 失败）。
3. **知识库检索** —— 输入问题，发起一次检索请求。
4. **检索结果展示** —— 返回最相关的切片，带出处、相似度分数与 `heading_path` 章节上下文。
5. **提交检索反馈** —— 对单次检索结果打 1–5 分，低分样本进入评估闭环。

此外还有**管理员面板**（账号 / 套餐 / 审计，需 `admin` 角色）与 **MCP 入口**。

## 五个竞争力亮点

大多数 RAG 项目停在「搭个向量库 + embedding + topK 检索」就收工。RAG-Core 把检索做成能真正交付的基础设施，每一块都在解决生产环境的真实问题。

### 一、中台定位 + 企业级权限

- **中台而非应用** —— 检索做成统一 API，多个租户共用一套能力；中台只负责找准找全切片，答案怎么组织由租户决定，各租户可独立迭代生成策略。
- **权限体系** —— API Key 是数据面的**唯一**凭证：账号在控制台配置一套信息后签发，一把 Key 携带一套密钥配置（配置**归租户所有、租户内共享**，一套配置可以发多把 Key，实际先按一对一用）；一个租户可以有多把 Key，分发给不同外部应用；Key 形如 `rk_live_` + 32 位随机十六进制，**本期明文存储**（连同备注名 `label`），生产应改为「哈希 + 密文」或「明文只展示一次」。请求头 Bearer token 解析出 Key 对应的租户与配置，调用方无法伪造他人身份。同一把 Key 同时可用于 HTTP 与 MCP 入口。
- **套餐分级** —— free / standard / pro 三档，逐档放开混合检索、LLM 查询改写等能力，能力边界从系统层面锁死。
- **数据隔离前置** —— 不属于当前租户的知识库在检索阶段就过滤掉，不进入候选上下文。

### 二、生产级检索全链路

不是「embedding + topK」那样一条线，而是完整管道，每个环节都有设计意图且可降级：

1. **查询优化** —— 同义词扩展（知识库级词表，改词表即时生效、无需重建索引）+ LLM 改写（口语化问题规范化）；两步都有超时保护，超时直接降级用原始 query。
2. **双路召回** —— pgvector 向量检索 + Elasticsearch BM25 关键词检索，语义与精确命中互补。
3. **RRF 融合** —— `score = Σ 1/(k + rank)`（k 默认 60）解决两路分数量纲不一致，只认名次不认绝对值。
4. **重排** —— 对融合后的候选求准；重排失败自动降级回融合顺序，响应里标注 `degraded: true`。

### 三、结构化文档处理引擎

检索效果上限由入库数据质量决定，所以在文档处理阶段投入专门设计：

- **多格式解析** —— `DocumentParser` 抽象层识别格式、提取结构化文本，与切块层解耦。
- **Markdown 感知切块** —— 按标题层级切逻辑段落，同节内容尽量落在同一切片，表格整块保留；每个切片带 `heading_path` 元数据。
- **异步索引** —— Celery + Redis 驱动，上传接口秒级返回，状态机 处理中 → 成功 / 失败。
- **幂等重索引** —— 调了切块参数不用重新上传，从数据库读已解析文本用新参数重切，可反复执行。

### 四、可量化的效果评估闭环

RAG 最难的是「知道它哪里出问题、改了参数有没有用」。闭环四步：

1. **打分反馈** —— 单条检索 1–5 分，低分样本直接对应缺陷查询，是排查线上异常的一手数据源。
2. **Langfuse 全链路可视化** —— 展示各阶段中间输出与耗时，快速区分问题根源（改写失效 / 召回缺失 / 重排压低）。
3. **低分样本导出** —— 导出低分 trace，补标准答案整理成评测集，把偶发问题固化成可反复跑的 case。
4. **RAGAS 离线量化** —— 在同一测试集上算 context_precision / context_recall，改策略前后可量化对比。

### 五、可插拔的工程架构

对外部依赖做 Provider 抽象，分 Embedding / VectorStore / KeywordSearch / LLM / Rerank / DocumentParser 六类，每类定义 ABC，靠工厂函数 + 环境变量切换，上层业务代码零改动。配套三层工程优化：

1. **空实现 Provider** —— 内置 `NoopRerankProvider`，不启用重排时原样返回，消除大量 `if` 分支。
2. **全局标准化错误码** —— 统一 20000–59999 区间，如 20013 方案功能限制、20014 配额超限，调用方按码区分异常。
3. **组件级降级** —— LLM 超时跳过查询优化、ES 不可用切纯向量、Langfuse 异常仅告警不阻塞，非核心故障不打断主流程。

## 第二期延伸

在原型之上叠加的四块能力：

- **检索性能优化** —— 统一评测基线 → 用 Qwen3 重排替换 LLM 重排 → 并行召回 → 全局融合 → 档位收口。
- **轻量文档图谱** —— 从结构化切片到关系图谱，图谱增强检索与上下文恢复，从 TopK 走向可信切片编排。
- **受控 Research** —— 从查询分解到切片驱动的多跳补证，明确执行边界与安全降级。
- **MCP 接入** —— 把检索内核以 `rag_retrieve` / `rag_research` / `rag_list_knowledge_bases` 三个工具暴露给 AI Agent，与 HTTP 入口共用 `auth_core` 判定内核；控制面（建库 / 传文档 / 建 Key）走面板，不暴露成工具。
