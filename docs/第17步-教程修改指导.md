# 第 17 步 · 教程修改指导

> 给「要按这次改动更新教程/文档」的人看的一份对照表：改了什么、为什么、教程哪一节要动、
> 哪些真实缺陷适合拿来讲。
>
> 配套材料：`docs/第17步-改造报告.md`（工程视角；含首轮 19 项评审修复与**之后四轮现场**，见其
> §十一–§十四）、ADR-0034（排队状态与构建收敛）、ADR-0035（容量上限与第四本账）、
> `GLOSSARY.md`（术语）。

---

## 一、一句话概括

**这一票把「索引」从「一个任务跑完一个库」改成了「一次构建拆成 N 篇、按篇投递、按真值收敛、
自己会自愈」，同时给套餐加了两个「按内容算」的旋钮（单库 token 容量、每日切块额度），
并把套餐里那道体验型的「并发处理名额」整条删掉。**

教程层面的净效果：**状态从三态变四态、账从三本变四本、规模上限从 4 个变 5 个、部署多一个
worker 但没有 beat、错误码多四个**。

之后**四轮现场**（都以用户的截图/一句话为起点）又带来四条要改教程的：
**读模型一个接口拆成三份、切片计数从一轴变两轴、文档多一根 `build_state` 轴、
刷新从「会静默停」变成「两档 + 三档理由且界面自证时刻」**
（见本文件 §二 的第 13–16 组、§五 的第 9–11 个故事）。

## 二、十六组改动（每组：改了什么 / 为什么 / 代码落点 / 教程怎么讲）

### 1. 文档状态三态 → 四态（新增 `4 排队中`）

- **改了什么**：`SUCCESS=1 / FAILED=2 / PROCESSING=3 / QUEUED=4`（**序号沿用旧值，不重排**）。
  上传、重建、回滚三个入口落 `4`；Worker 抢占才写 `3`。`3` 的唯一权威证据是**租约**
  （`index_claimed_at` 在窗口内），租约过期即视为「没人跑」。
- **为什么**：改造前 `3` 盖着三种事实——在排队、真的在跑、跑崩了没人管。用户看到同一个词，
  分不出「再等一分钟」和「永远等不到」。
- **落点**：`app/utils/status.py`、`app/repositories/document_repository.py`（`try_claim_for_indexing`）、
  迁移 `b3f7c2a91d40`（存量「3 且无租约」→ 4）。
- **教程怎么讲**：把「状态机」那一节的图重画成四态，并强调 **`3` 不是「在处理中」而是「有人持有它」**。
  排队中可以删、可以重提；只有真的在跑的那一篇不接受操作。轮询条件从「等于 3」改成「属于 {3,4}」。

### 2. 整库构建 → 按篇投递（派活 + 子任务 + 续建）

- **改了什么**：`start_build` 只建一行 `building` 并记下参与篇数快照、稿号、收敛期限；
  `dispatch_build_task` 分页读参与文档、逐条投 `build_document_task`（走 `build` 队列、
  由独立的 `worker-build` 消费）；每篇跑完记账；任何一方都能尝试收敛。
  重投/重试时**已有切片的篇直接跳过**（续建）。
- **为什么**：一个任务跑完一个库有三个代价——失败粒度是整个库、进度不可见、整段时长占一个槽位。
  5000 篇会产生 5000 条消息，留在默认队列里会把别人的上传压后面几十分钟。
- **落点**：`app/services/index_build_service.py`（`dispatch` / `record_outcome`）、
  `app/tasks/index_build.py`、`app/celery_app.py`（`task_routes`）。
- **教程怎么讲**：新增一节讲「任务拓扑」，主图从「一个任务」改成「派活 → N 篇 → 收敛」。
  要强调**构建不另写一套索引逻辑**——它复用单篇重建那条流水线，于是两者只有一套状态语义。
  **旧形状已删干净**：`build_index_version_task`（一次跑完整个库）以及它的投递缝都不在了，
  现在构建只有一种形状；运维要「按需推进某一次构建」用 `scripts/reconcile_build.py`（按 build_id
  收敛/续建）。教程里若还写着「两条入口」，那是过时的。

### 3. 收敛判据：计数器 → 真值

- **改了什么**：`converge` 读 `COUNT(DISTINCT document_id) FROM chunks WHERE (index_version, doc_version)`，
  与起跑快照比；够了且没有失败明细才 `ready`，否则 `failed`。进度计数器只画进度条，不判据。
- **为什么**：计数器可丢、可重复、可漂高。漂低让构建永远转圈；**漂高会让一篇都没真重建的空版本
  上线**（「版本正常、检索全空」）。
- **落点**：`index_build_service.decide_convergence`（纯函数，四种组合可离线钉死）、
  `_failure_reason_of`（失败原因文案的唯一一张表）。
- **教程怎么讲**：这是全篇最值得讲的一处**判据设计**——「用能对账的真值当判据，用只能当参考的
  计数当进度」。可以配一句反例：改造前的循环丢掉返回值、每篇都 `indexed += 1`。

### 4. 清扫器（自愈）

- **改了什么**：Worker 进程内的**守护线程**，每 60 秒用 Redis `SET NX EX` 抢单实例锁，抢到跑一轮。
  三件事：过期限的构建按真值收尾、期限未到但缺篇的补投、心跳过期的文档清租约重投；
  重投有次数上限，到顶标失败。
- **为什么**：改造前卡住的东西全靠人记得跑脚本。**「救不回来」也是一个必须兑现的结论**——
  没有上限就会无限重投，用户看到的是永远转圈。
- **落点**：`app/tasks/index_sweeper.py`（`SWEEP_INTERVAL_SECONDS` / `_try_lock` / `sweep_once`）、
  `app/celery_app.py` 的 `worker_process_init`（起线程）、`worker_process_shutdown`（先停线程再停循环）。
- **教程怎么讲**：新增一节「兜底」：为什么是**线程**而不是**任务**（作为任务会被自己的队列堵住，
  而那正是所有槽位被长任务占满的时刻）；为什么**不用 beat**（多一个进程 + 一条队列，
  而 spec 的 Out of Scope 明写不许，锁方案正面回答「N 核 × 周期」）。

### 5. 心跳与租约分两列

- **改了什么**：`index_claimed_at` = fencing 令牌（**永不变**，谁持有谁就是主人）；
  `index_heartbeat_at` = 生存证据（**会变**，解析后与每批嵌入前各刷一次）。
  清扫器判「死了没」看心跳，`COALESCE(心跳, 抢占时间)` 回落兼容老行。
- **为什么**：一件东西不能同时满足「令牌必须不变」和「心跳必须会变」。合成一列只有两个坏结果：
  抢走正在跑的长文档（白烧一轮嵌入），或长文档永远不被救。
- **落点**：`document_repository.renew_claim`、`indexing_service._heartbeat`。
- **教程怎么讲**：**心跳必须用独立会话**——用流水线会话提交会把「本应等 Tx2 才落库的正文」
  一起刷出去，破坏「正文、切片、版本行、状态同一笔事务」这条纪律。

### 6. 两种 token 口径

- **改了什么**：`documents.token_count` 存**正文** token（容量判据用；与切块器同一把尺子）；
  每日额度记**检索文本** token（真正发给嵌入模型的那一行，比正文多 10–20%）。
- **为什么**：混用会让「容量没满但额度超了」解释不清。
- **落点**：`indexing_service`（解析后 `token_count(parsed.content)` → 容量门禁；
  嵌入前 `Σ token_count(retrieval_text)` → 日额度）。
- **教程怎么讲**：强调**两个数字各管一件事**，而且都不等于「供应商账单上的 token」——
  那是同族但不同乘数的量。

### 7. 容量门禁两道 + 一处刻意的「不加门」

- **改了什么**：入口预检（库满了不收新的、额度用尽不收） + 解析后硬拦（`incoming` 带本篇 token）。
  重建排除自己（`excluding_document_id`）。
- **为什么**：入口预检挡在代价最低处（不白解析一次、不白排一次队）；解析后硬拦给准确判据。
- **「不加门」的地方**：**建版本与回滚不加**。它们不增加库内 token 总量，而超限库（ADR-0035
  允许它继续存在、继续检索）恰恰最需要回滚到一个容量更小的旧版本——加门会把救援路径封死。
- **教程怎么讲**：这条很适合讲「按意图而不是按字面实现 spec」。

### 8. 第四本账（切块账）

- **改了什么**：`plans.chunk_daily_tokens` + `usage_events.meter_chunk` + `usage_daily.meter_chunk`；
  Redis 租户日桶 `quota:chunk:daily:tenant:<tid>:<YYYYMMDD>`（TTL 26h）；
  **只有租户级**（索引里没有密钥身份这个主语）；记账沿用「先判后记、被拒不记账」。
- **为什么**：前三本数的是「请求侧调用了几次」，一次整库重建在它们上面留不下痕迹——用户能一边
  看到「今天没怎么用」，一边被嵌入账单追着跑。
- **教程怎么讲**：第四本与前三本**单位不同**（token vs 次数），所以界面上必须写单位。
  而且它**不进**「调用次数 / 成功率 / 耗时分位」（`endpoint='index'` 的行排除出请求统计）；
  但**保留计量**——「排除出请求统计」不是「排除整行」。

### 9. 删掉「并发处理名额」

- **改了什么**：`plans.max_processing_documents` 物理删除（迁移 `b9f4d2c70e13`），
  门禁、按租户数处理中的仓储查询、五个调用点一起删。写入口一律接受、全部排队。
- **为什么**：它是**体验型**限制（不是容量型），且被拒时的文案三条全错（不是按天用量、
  等重置解决不了、密钥配置改不了）。
- **代价（要讲）**：没有按租户的公平调度，一个大客户批量上传会拖慢别人。缓解手段只有构建专用队列，
  公平调度不在本票范围（ADR-0034 决策八）。

### 10. 错误码分码

- **改了什么**：新增 `20034`（库数）/ `20035`（单库文档数）/ `20036`（单库 token）/ `20037`（日切块额度）；
  `20014` 收窄成「日调用额度」。每个码带机器可读 `reason` + `used/limit/plan`，文案是中文人话。
- **为什么**：原来的「配额已用尽」盖着四种完全不同的事，而有两类的处置是相反的：
  「删掉旧文档就能继续」vs「只能等明天 UTC 0 点重置」。
- **教程怎么讲**：这是**有意的破坏性变更**——老客户端按旧码判「库满」会漏判。要在错误码全表里
  写成一次「语义迁移」而不是「加四个码」。

### 11. embedding 批大小可编辑

- **改了什么**：模型→单批上限表（v1/v2=25、v3/v4=10、qwen3.7=20，全局封顶 25）；
  面板可编辑，但保存后需重启 Worker（进 `RESTART_PANEL_WRITABLE_KEYS`，属「可写但有重启提示」）。
- **教程怎么讲**：讲清「面板可写」与「保存即生效」是**两件事**——这一项是前者。

### 12. 部署形状

- **改了什么**：新增 `worker-build`（`-Q build --concurrency=1`）；常规 worker 只消费 `celery`；
  **没有 beat**。
- **教程怎么讲**：连接预算一节要按**进程数**重算（`15×API + 15×常规worker + 15×构建worker + …`）；
  清扫器是线程，不额外开池。

### 13. 读模型：一个接口拆成三份（第三轮）

- **改了什么**：`/console/knowledge-bases/tree` 一次读全租户「库 + 全部文档」；现在拆成
  **列表摘要**（`GET /console/knowledge-bases`，只回四个数字 + 构建快照 + 四态各几篇）、
  **详情一页**（`GET /{kb_id}/documents`，**打开即取**、SQL 层分页、关键字/状态交服务端）、
  **构建快照**（升为摘要的一格，不再单列接口）。`GET /api/v1/documents` 照旧。
- **为什么**：卡片只要四个数字，却被 5000 行的文档数组喂着；详情没有自己的请求，只能读列表
  上一次轮询的快照——这就是用户嘴里「进详情要按 F5」的**唯一原因**（不是缓存）。
- **落点**：`console_kb_service._summary_of / list_documents_page`；
  `document_repository.list_page_by_kb / count_by_kb_filtered / count_by_kb_by_status`；
  `index_version_repository.latest_for_kb`（**building 优先于最新**）。
- **教程怎么讲**：「读模型按『回答什么问题』拆开」；顺带讲两个**只在真 SQL 上显形**的坑：
  `total` 与这一页必须用**同一组条件**（否则翻到第 3 页是空的）；`keyword` 要**转义 LIKE 元字符**
  （`%`/`_` 不转义时「搜 `%` 返回整库」，而且不报错）。

### 14. 切片计数的两轴（第三轮，真 bug）

- **改了什么**：「这篇有多少片」从只锁**当前稿**改成锁 **生效版本 × 当前稿**
  （`chunk_repository.serving_chunk_filters` 一处编译，三处调用点共用：控制面列表/详情、数据面
  `GET /documents`、设置预览）。库没有生效版本时回 0，界面说「未建索引」而不是「0 个分块」。
- **为什么**：留存版本（给回滚留着的 `archived` 版本）的切片也被数进去了——实测某文档界面
  152 片，生效版本只有 38 片，**正好 4 倍 = 4 个留存版本**，每次重建涨一份、永不回落。
  而检索链路上每条 SQL 都带版本条件：**界面与检索说着两个数**。
- **落点**：`serving_chunk_filters`；`count_in_kb`（库级合计，与逐行之和**必须相等**）；
  `tests/test_console_kb_read_model_sql.py` 里有一条把「多库召回拼写」与「单库计数拼写」
  在同一批数据上跑、要求行集合相同的用例。
- **教程怎么讲**：一个数字**覆盖多大范围**必须与它被解释的方式一致；「合计 = 逐行之和」可以当
  自检断言。可以配一句反例：检索命中的那句正文，与界面上说这篇有几片，各自自洽却互不相符。

### 15. 文档的第二根轴 `build_state`（第三轮）

- **改了什么**：文档行新增 `build_state`：`done`（已重建进这一版）/ `pending`（还没进去）/
  `failed`（这一版明确没收它）/ `null`（没有构建可参照）。**文档自己的四态一个字没动。**
- **为什么**：构建期间文档状态几乎一直是「成功」（每篇只有自己那一秒是「索引中」），状态列
  **根本表达不出**「正在重建」；而把「构建没收它」写进四态又会让失败污染状态机
  （ADR-0034 决策九：构建失败不改文档状态）。
- **落点**：`console_kb_service._build_state_of`（判据读构建行的**全量**失败明细，**不读**界面
  那份截断到 5 条的列表——否则第 6 篇以后的失败会永远显示成「待重建」）。
- **教程怎么讲**：「两根轴」：文档自己的生命周期 vs 构建与它的关系。配一句反例：把两者合并成
  一个状态，会让「构建失败」看起来像「文档坏了」。

### 16. 刷新：两档 + 三档理由（第三、四轮）

- **改了什么**：删掉 `useTreePolling`（它在「全终态」时 `refetchInterval` 返回 `false`，**彻底停**）。
  改成 `lib/refreshPolicy.ts` 的纯函数：**在途 3 秒 / 空闲 60 秒慢查**（永远返回一个数字，不再有
  「停止」这一档）+ 2 分钟→**30 秒**活动窗（刚收尾再跟几轮）+ **理由三档**
  （`running` 真有在途工作 / `recent` 刚收尾 / `idle` 慢查），横幅按理由写话。
  界面常驻 `LiveStatus`：**更新于 HH:MM:SS · 档位 · 刷新**；关弹窗即清 `kb_id` 停轮询。
- **为什么**：见 §五 的「刷新停得很安静」与「对了但说错了话」两个故事——**停了不告诉人**，
  以及**两档抽象压掉一个真实理由、文字替它编**（用户看到「两个库都写着已生效，顶上还说有构建在跑」）。
- **落点**：`frontend/src/lib/refreshPolicy.ts`（判定全在纯函数里，`useQuery` 只负责塞间隔）、
  `components/LiveStatus.vue`、`composables/useKbQueries.ts`（`createDebouncer` 等纯函数可单测）。
- **教程怎么讲**：一条可以贯穿全教程的规矩——**用户能信的不是「有没有在动」，而是「这一刻的数据
  是几点拿的、为什么还在动」**。

## 四、建议新增的八节

按「教程里缺一节就会讲不清」的顺序排：

1. **「排队中」为什么必须是独立状态**（配 1、5）
   要讲的反面例子：`3` 盖三种事实；以及「租约才是权威证据，状态字面值不是」。
   锚点：`app/utils/status.py`、`document_repository.try_claim_for_indexing`。

2. **一次构建的生命周期**（配 2、3）
   派活 → 子任务 → 记账 → 收敛 → 激活；续建；失败明细为什么不改文档状态。
   锚点：`index_build_service.dispatch / record_outcome / converge`、`tests/test_index_build_convergence.py`。
   **必须讲清的一条**：「0 篇参与」有两种，处置相反——真空库产出空版本是合法的（ADR-0025），
   而「库里有十篇、全是失败」必须**拒绝起构建**（`20038`）或判 `failed`，否则会激活一个空版本
   （线上检索一条都查不到，界面写着「构建成功」）。判据是纯函数
   `guard_against_an_empty_version`，服务、运维脚本共用；「0 篇即收尾」是**派活任务的显式选择**
   （`settle_when_nothing_to_send`），清扫器的补投路径不许用——它在最后一篇正在跑时必然看到
   0 篇，那时收尾会把健康构建判死。

3. **兜底任务的形状：线程 + 单实例锁**（配 4）
   为什么不是队列任务、为什么不用 beat、N 核×周期怎么变成一把锁。
   锚点：`app/tasks/index_sweeper.py` 的模块 docstring（它是本次写得最完整的一段「为什么」）。

4. **两种 token**（配 6）
   正文 token / 检索文本 token / 供应商账单 token，三者关系与各自用途。
   锚点：`indexing_service` 里那两处调用、`static_quota` 的文案模板。

5. **四本账与它们的单位**（配 8）
   前三本次数、第四本 token；租户级 vs Key 级；为什么排除出请求统计但保留计量。
   锚点：`console_usage._denies_index`（**两张表共用一份判据**，注释里有长解释）。

6. **容量型拒绝的分码**（配 10）
   四个码 + 两种处置（删东西 / 等重置）。给一张「用户看到什么 → 他该做什么」的对照表。
   锚点：`app/services/static_quota.py`（`CapacityQuota` 表）、`frontend/src/lib/envelope.ts` 的 `CODE_COPY`。

7. **一个接口不该同时服务三件事**（第三轮那件事的根）
   反面例子：`/console/knowledge-bases/tree` 一次读全租户的「库 + 全部文档」，而卡片只要四个数字、
   详情只要一页文档——两者被迫共用一份太重的东西，于是谁都没法有自己的刷新节奏，**详情从来没有
   过「打开即取」这个动作**（用户看到的是列表上一次轮询的快照）。
   要讲的三条：读模型按「回答什么问题」拆开；分页必须在 SQL 层（`total` 与这一页**用同一组条件**）；
   服务端筛关键字要**转义 LIKE 元字符**（`%`/`_` 不转义时「搜 `%` 返回整库」不报错，只让「没搜到 /
   全搜到」变成说不清的事）。
   锚点：`app/services/console_kb_service.py` 的 `_summary_of / list_documents_page / _build_state_of`、
   `app/repositories/chunk_repository.py` 的 `serving_chunk_filters`。

8. **刷新是可以慢的，但不能是安静的**（第三、四轮）
   反面例子：轮询在「全终态」时返回 `false` **彻底停**，界面上没有任何东西说明它停了——「已经刷新完」
   与「停在十分钟前」长得一模一样，用户唯一出路是 F5。
   要讲的三条：(a) **永远返回一个间隔**（空闲改 60 秒慢查，不是停）；(b) 界面常驻「更新于 HH:MM:SS」，
   一个会变慢的界面必须自证数据有多旧；(c) **放慢的理由要能说出来**——live 里还有「刚收尾、再跟
   几轮」这一档，横幅不能念一句写死的话（`RefreshReason = running | recent | idle`）。
   锚点：`frontend/src/lib/refreshPolicy.ts`（纯函数，判定与 `useQuery` 分离）、`components/LiveStatus.vue`。

   > 这两节合起来是一条可以贯穿全教程的规矩：**用户能信的不是「有没有在动」，而是「这一刻的数据
   > 是几点拿的、为什么还在动」。**

## 五、十四个真实缺陷故事（教程素材）

都是本次真实踩到、且**离线测试全绿也抓不到**的形态。每条都能当「为什么要有这条设计」的反例讲。
（第七个是补用例时抓到的：它不在离线套件里，而在**没人走过的那条分支**里；第八个是「按钮调对了接口才叫修好」的典型；第十、十一个都来自**用户自己截图指出来**的界面问题——同一个界面，两次都是「状态对了，范围/说法错了」。）

| 故事 | 一句话 | 适合放在哪一节 |
| --- | --- | --- |
| **空操作的状态回写** | 抢占用 SQL 改了库、却 `synchronize_session=False` + `expire_on_commit=False`，内存对象还停在旧值；收尾「赋成本来就是的值」被 ORM 静默吞掉，**一条 UPDATE 都不发** | 状态机 / ORM 陷阱 |
| **假数字的构建** | 循环丢掉 `index_existing_document` 的返回值，每篇都 `+1`；一篇都没真重建的构建靠计数对账通过并激活 → 「版本正常、检索全空」 | 收敛判据 |
| **看不见写语句的测试缝** | 离线替身明写「不模拟写语句的行变化」，在那条缝上断言状态只能得到**假绿**——而缺陷机制正是「SQL 改了库、内存对象不知道」 | 测试策略 |
| **NOT NULL 只会在真库炸** | 第四本账的行落在按「检索请求」设计的表上，`top_k` / `latency_ms` / 两个 jsonb 全是 NOT NULL；测试全绿，第一次真跑索引就炸 | 账与表设计 |
| **清扫器不提交** | 三个分支的写都没 commit，症状是「日志说有动作、库里一行没变」——与「清扫器根本没跑」一模一样 | 兜底任务 |
| **半路丢失的布尔量** | 改切块设置带 `activate=True`，改成按篇投递后它在新链路上被静默丢弃 → 「保存了但没生效」；修法是把状态记在**构建行**上而不是塞进载荷 | 重构时的「副作用清单」 |
| **没人走过的那条分支** | 构建子任务的**失败**分支从落地起没有一条用例走过，里面藏着两个必然报错的写法（`indexing_service` 里找 `index_build_service` 的常量、把实例方法当模块级函数调）。补上「驱动任务体」的用例，第一次跑就炸出来 | 测试策略 / 「没有测试的分支等于不存在」 |
| **语义猜错的按钮** | 「一键重建」第一版做成「逐篇重新投递」：文档都重切了，可「需重建」提示还在——因为提示比的是**版本参数快照**，而逐篇重建写回的是旧版本。要让设置生效只能产出新版本 | 「同名不同物」/ 先问「这个提示比的是什么」再决定按钮调哪个接口 |
| **算了一个不存在的范围** | 界面上「这篇有多少片」只锁了「当前稿」、没锁「**生效版本**」，于是把留存版本的切片全算进去：显示 152 片，生效版本只有 38 片，**正好 4 倍 = 4 个留存版本**，每次重建涨一份且永不回落。而检索链路上每条 SQL 都带版本条件——界面与检索说着两个数。修法不是补一句注释，而是让两个口径**共用同一个谓词函数** | 「口径」/ 一个数字被误信一整轮 |
| **刷新停得很安静** | 轮询规则是「还在跑就 3 秒一次，否则返回 `false`——彻底停」。省请求是对的，但它**不告诉任何人它停了**：实测构建 18.975 秒收尾、最后一次轮询 19.014 落地，之后一个请求都没有，屏幕停在「重建中 3/10」。用户能想到的唯一办法是按 F5。修法是两件：**永远返回一个间隔**（空闲改 60 秒慢查，不是停）+ 界面常驻「更新于 HH:MM:SS」——一个会变慢的界面必须自证数据有多旧 | 「可观测性」/ 「停了」与「卡住了」长得一样 |
| **写账在扣账之前** | 「这次真扣了几次」由门禁在 `record_n` 那一刻记进上下文，写账方优先读它。但顺序是反的：组合根**先**写下 `usage_events` 那一行，门禁的扣账要等它返回**之后**才执行——于是写账那一刻那份计数必然是 `(0,0,0)`，而这个「优先读真值」的分支把**一个确定的错数**写进了库：用量页「检索 / 重排 / 大模型」永远 0。修法：**全 0 不是事实，是「还没走到那一步」**，返回 `None` 让写账方回落到「按能力推断」的值（与真扣值相等） | 「缓存/真值与顺序」/ 一个被优化掉的分支会把错数伪装成真值 |
| **0 额度被报成「太频繁」** | 一份密钥配置把「大模型」这本账配成 0、同时把改写/分解/Research 三个能力位开着（配置时合法——0 是「这套不用它」）。额度门禁按 `used >= limit` 判，`0 >= 0` 永远成立，于是每次都走进「秒级超额」那支，报 `20005 操作太频繁：稍等一会儿再试`——**一个永远不会到来的下一步**（等多久都是 0）。修法两层：`limit <= 0` 单独判、报 `20013`（「这本账没开，去 Key 管理页填额度」）；界面在**勾选能力位的那一屏**就按套餐上限把额度补齐并写明后果。与「横幅念错台词」是同一个病：内部少一档，表达层替它编一句 | 「错误码要说下一步」/ 「限流」与「没买」必须分开 |
| **缓存把「校验」省了、把「判定」也一起省了** | 过渡密钥的第一版把在窗口内验过的**旧**串也写进 `KeyVerifyCache`。缓存命中就短路（`key_id_of(token) == key_id` 直接返回），于是用户点了「作废旧 Key」之后，旧串还能靠缓存再活一个 TTL——缓存把一把正在退役的凭证变成了「60 秒有效的钱包」，而那个模块的文档承诺恰恰是「撤销一律立即生效」。修法：**会过期的判定不许进缓存**，过渡密钥每请求真校验（旧业务在过渡期里每请求多 50~100ms，值得） | 「缓存与撤销」/ 缓存省掉的必须只是「算」，不能是「判」 |
| **对了但说错了话** | 刷新改成两档（live / idle）之后，顶上的横幅文案是**写死**的一句「有构建在跑或有文档在排队/索引中」。可是 live 里其实还有一档：**刚收尾、再跟几轮确认**。于是用户截图里两个库都写着「v2/v7 已生效」，横幅还在说有构建在跑——状态是对的，**解释是错的**。修法：内部理由从 2 档补到 3 档（`running / recent / idle`），文案按理由分支，活动窗从 2 分钟收到 30 秒 | 「抽象少一档，表达层就会替它编一句」/ 状态机与文案必须同源 |

> 这十四条的共同教训可以写成五句：
> **「调用过了」不是证据，「库里那几行变了」才是**；
> **「界面上没错」也不是证据，「它算的那个范围与检索用的是同一个范围」才是**；
> **「状态对了」也不够——一句写死的文案会把两档事实说成一档，用户只信那句文案**；
> **「错误码」也是一句文案：它得给出一个真的存在的下一步，否则就是让用户白等**；
> **「这里没数据」可能是一段没人跑的运维步骤——周期性的东西必须有人替你跑。**

## 六、术语变更对照（教程里搜替换）

| 旧说法 | 新说法 | 备注 |
| --- | --- | --- |
| 处理中（三态之一） | 拆成 **排队中** / **索引中** | `3` 的正名是「索引中」；`4` 是「排队中」 |
| 一键重建 / 全库重建 | **重建**（`POST /console/knowledge-bases/{id}/rebuild`） | 按**当前**切块设置产出**新版本**并自动激活。它**不是**「把每篇重新投一遍」——那种写法写回旧版本，`params` 快照不变，「需重建」提示消不掉（第一版就踩了这个坑） |
| 三本账 | **四本账** | 第四本是切块账（token，只有租户级） |
| 并发处理名额 / 处理中名额 | **（已删除）** | 不要再出现在「上限」清单里 |
| 规模上限 4 个 | **5 个** | 新增单库 token 容量 |
| 索引批次 / 建库任务 | **构建（build）**、**派活（dispatch）**、**续建（resume）** | 见 `GLOSSARY.md` |
| 配额已用尽（20014 的旧义） | 收窄为 **日调用额度** | 容量型走 20034/20035/20036 |
| 定时任务 / cron / beat | **清扫器（index sweeper）** | 它是 Worker 内的线程 + Redis 锁，不是调度器上的任务 |
| 当前版本 / 线上版本 / 索引版本 | **生效版本**（`active` 那一版） | 「索引版本」是所有版本的通称；被替下来但留着给回滚的叫**留存版本**。二者不能混：留存版本的切片不参与检索、不参与任何对外计数 |
| 处理中 / 重建状态 | **本次构建**（`build_state`：已重建 / 待重建 / 未入版） | 它与文档自己的四态**正交**：构建失败不改文档状态（ADR-0034 决策九）。构建期间文档几乎一直是「成功」，所以「正在重建」只能由这根轴说 |
| 轮询 / 自动刷新开关 | **刷新档位（live / idle）** | live = 有在途工作，3 秒；idle = 其余，60 秒慢查。**没有「停止」这一档**，也没有开关 |
| 生成 / 创建 Key | **签发（issue）** | **加法**：新增一把 Key（新 `key_id` + 新配置），旧 Key 一个字都不受影响 |
| 重置 Key / 换 Key / 获取 Key 原文 | **重新生成（regenerate）** | **替换**：同一把 Key 换密钥本体，`key_id` 与配置全不变，旧原文失效。控制台按钮叫「获取 Key」——它的实质是重新生成（原文不可取回） |
| 旧 Key / 备用 Key / 双 Key 并存 | **过渡密钥** | 重新生成后仍能通过校验的**旧密钥本体**，只在一个窗口（24 小时）内有效、**只保留最近一把**；判定只看 `prev_key_expires_at`，自然到期与提前作废是同一件事的两种结束方式 |
| 「正在自动刷新」一句话说全部 | **刷新理由（running / recent / idle）** | live 里有两档事实：真有在途工作（`running`）与刚收尾再跟几轮（`recent`，活动窗 30 秒）。横幅必须按理由写话——写死一句会让「已生效」与「有构建在跑」同时出现在屏幕上 |

`GLOSSARY.md` 的 `_Avoid_` 字段已经把这些「不要用的名字」逐条列出，写教程时直接对照它。
本次（第三、四轮）新补的五组是：**生效版本 / 留存版本 / 本次构建 / 刷新档位 / 刷新理由**
——前四组指向同一类错误：**把一个数字或一个状态说得比它实际覆盖的范围更宽**；
最后一组指向另一类：**内部少一档抽象，文案就会替它编一句**。
