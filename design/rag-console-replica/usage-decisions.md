# 用量看板 · 设计决策（评审用）

四屏设计稿 + 一屏观测页改造，配合「每把 Key 能看到自己的用量、管理员能看站点与租户」这条需求。
**本文件是设计侧的结论汇总**：里面每条都是已经拍过的口径，落地时不用再猜；代码一行没动。

- 设计稿：`usage.html`（租户总览）、`usage-key.html`（单 Key）、`admin-usage.html`（站点）、
  `admin-tenant.html`（管理员下钻到租户）、`admin-observability.html`（观测页三段式）
- 时间窗可切、图会重算（ECharts，配色从 `tokens.css` 的变量里读，跟着画布那枚三段主题开关走）；数据是自洽的假数据（同一屏里 KPI / 图 / 表能对上）

---

## 一、口径（最容易吵架的部分，先钉死）

| 项 | 结论 | 理由 |
| --- | --- | --- |
| 1 小时 | 滚动 60 分钟，**10 分钟**一桶（6 点） | 6 个柱子够看「刚才有没有尖尖」；桶再小，小租户大多为 0 |
| 1 天 | **现在这个小时 + 往前 23 小时**（滚动 24 桶） | 用户要的是「过去一天」，不是「今天 0 点到现在」 |
| 7 / 30 天 | **日历天**，最后一天是今天，标「未完整」 | 「今天为最后一天，一周往前倒 7 天」 |
| 换天时区 | **UTC**（配额窗口现在就是 UTC），页面标注「本地 08:00 换天」 | 改口径会让历史出现一天断层；先不改 |
| 「调用」 | 进了门就算一次（`20010` / `20013` / `20014` 都算） | 不给被拒请求记账，成功率就没有分母 |
| 「成功」 | `code = 0` | 业务失败一律 HTTP 200 + 非零码，不能用 HTTP 状态判 |
| 没计数时 | 显示 **「未统计」**，不画 0 线 | 0 = 查过确实没有；`RATE_LIMIT_ENABLED=false` 时是「不知道」 |
| 最后一个桶 | 矮是正常的：标「未完整」 | 避免误判成掉量 |
| 额度 vs 图 | 额度按**当日 UTC**；图是滚动 24 小时，跨两次日切 | 页面上直接写「今日 190，图上是 952，为什么」 |

## 二、数据模型

### 1. `retrieval_traces` → 改名 `usage_events`

原来这张表只装「走到响应成形」的检索，现在一个请求一行，**失败也落行**，它同时是「账」和「归属索引」。

新增 6 列：

| 列 | 用途 |
| --- | --- |
| `key_id` | Per-Key 视图的唯一依据（老行为 `NULL`，归「历史汇总」） |
| `endpoint` | retrieve / rewrite / decompose / research —— 不记它，「按接口拆」永远做不出来 |
| `code` | 业务码（0 / 20010 / 20013 / 20014 / 5xxxx）；观测页三段式靠它 |
| `meter_r` / `meter_rr` / `meter_llm` | 这一次请求在检索 / 重排 / 大模型三本账各计几次（decompose 的检索是 N 次，research 的 LLM 是 M 次） |

索引：`(tenant_id, created_at)`、`(key_id, created_at)`。

**写入点要挪**：现在写在 service 末尾（成功路径），必须挪到门禁抛错之前，否则 `20013` / `20014` 永远抓不到。

### 2. `usage_daily`（新表，按天汇总）

`day + tenant_id + key_id + endpoint + code` 为维度，存 `requests` / `ok_requests` / 三本账合计 /
**8 档延迟直方图计数**。保留 **13 个月**；明细 `usage_events` 保留 **90 天**，过期由定时任务删。

> P95 不能相加：日汇总里必须存直方图桶（8 档，误差约 13%），否则 7 / 30 天这两档画不出延迟。
> 把「每天的 P95 再平均一次」是错的，但肉眼看不出来，所以这里写死不要那么做。

### 3. 阈值进「运行时配置」，不新建表

两条键：`USAGE_ALERT_QUOTA_PCT`（默认 80）、`USAGE_ALERT_SUCCESS_DROP_PP`（默认 3）。
管理员页的「需要看一眼」按这两条判定，右上角是「阈值可改 →」直链。

## 三、观测页：三段式（全部 / 只看成功 / 只看失败）

一张表三种看法，各自回答不同问题：

- **全部** = 容量与故障总量（容量规划、对外 SLA）
- **只看成功** = 检索质量（降级率、空结果率、延迟分位只在这一档算得对）
- **只看失败** = 治理（额度用尽该调额度，越权该查配置，鉴权失败该查 Key）

被挡下的请求既不会降级、也不会空结果，所以**“降级率”在「全部」与「失败」里显示「—」，不是 0**。

## 四、额度条：怎么表达「还剩多少」

**问题**：原来那一版只有 `190 / 5,000`——两个数字并排，读者得自己减一次才知道还剩多少。
用量页要被回答的是「我还能跑多少」，减法不该由用户做。

**结论**：一行一本账，两行结构；**剩余是主数字**。

```
● 检索                                        剩余 4,810 / 5,000
  ▓▓░░░░░░░░░░░░░░░░░░░░░░░░       已用 190
```

四条编码规则：

| 通道 | 表达 | 理由 |
| --- | --- | --- |
| 数字 | 「剩余」给 17px/600，`/ 上限` 给 12px 灰 | 答案优先，上限是参考 |
| 条形长度 | 已用 / 上限 | 与上面的数字同一个事实，只是能一眼看出「快满了」 |
| 条形颜色 | 按**严重度**升级：accent → star（≥80%）→ danger（100%） | 条形回答「危不危险」，不回答「是哪本账」 |
| 名称前的方点 | 账本身份色（与趋势图图例同源） | 同一个方点在趋势图里出现过，读者能对上 |

不做的：不加百分比（剩余/上限已经是答案）、不给正常状态挂「正常」二字（三行里两行是正常，那是噪声）、
不加解释句（口径在 `usage-decisions.md`，页面不复述）。

**未统计**（`RATE_LIMIT_ENABLED=false`，`used=null`）：三本账同时变成未知，所以它是**整卡状态**而非单行状态——
剩余位显示「未统计」、条形换成虚线空槽、上限照常显示。绝不画成 0%：0 是「查过确实是 0」，与「不知道」必须分得开。
**第五种：未开通**（`limit = 0`）。free 档的 `rerank_daily` / `llm_daily` 就是 0——这一档根本不包含这本账。
写「未开通」、不画条、不显示「/ 0」：把 0 当上限画出来，等于告诉用户「你有 0 份额度，已经用完了」，
而事实是「你买的这一档没有这一项」。判定顺序也因此是：先看 `limit <= 0`，再看 `used` 是否为空。
画法见 `usage-untracked.html`：剩余位写「未统计」（正文字号，不占数字位）、条形换成**虚线空槽**（有空槽说明这里本该有一条，虚线说明量未知）、上限照常显示；卡片副标题写「限流关闭」，把原因留在标题行而不是加一段解释句。三本账一起变——开关是平台级的，不可能只有一本没记账。

## 五、能画 / 不能画（现状盘点结论）

| 指标 | 结论 |
| --- | --- |
| 租户今日调用次数 | 现在就有（唯一有的：租户级 + 当日 + Redis 日桶） |
| Key 级次数、重排 / LLM 次数 | 需要新增聚合（Redis 里有 key 级桶，但没有读接口也没有表） |
| 成功率 | 现在完全没有（失败不落行，没有分母） |
| P50 / P95（全局） | 现在就有；按租户 / 按 Key 要新增聚合 |
| 降级率、空结果率 | 现在就有 |
| Top 知识库 | 需要新增聚合（`kb_ids` JSONB 已有数据） |
| Token 数、成本估算 | 现在完全没有（全仓零记录），本期不做 |
| Top 查询词 | **不做**：需要问句原文，违反 ADR-0021；要看就去观测栈 |
| 「最后一次调用」 | `api_keys.last_used_at` **从未被写入**，这一列现在是空的；要么由 `usage_events` 反查，要么删掉这一列 |
